Critical Security Issues ​

1. JWT "None" Algorithm Acceptance ​

Severity: Critical

Description: The API currently accepts JWT tokens with the none algorithm, which allows attackers to forge tokens without a valid signature.

Impact: Attackers can bypass authentication by creating tokens like:

text
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFkbWluIiwiaWF0IjoxNTE2MjM5MDIyfQ.

Recommendation:

typescript
// In your JWT validation module, explicitly reject "none" algorithm
{
  secretOrKeyProvider: (request, rawJwtToken, done) => {
    // Reject "none" algorithm
    const decoded = jwt.decode(rawJwtToken, { complete: true });
    if (decoded?.header?.alg === 'none') {
      return done(new Error('JWT "none" algorithm is not allowed'));
    }
    done(null, process.env.JWT_SECRET);
  }
}

Status: ⚠️ Open

2. Missing Security Headers ​

Severity: High

Description: The API response does not include standard security headers.

Missing Headers:

  • X-Content-Type-Options: nosniff
  • X-Frame-Options: DENY
  • X-XSS-Protection: 1; mode=block
  • Strict-Transport-Security: max-age=31536000; includeSubDomains
  • Content-Security-Policy

Recommendation:

typescript
// In main.ts or app.module.ts
app.use((req, res, next) => {
  res.setHeader('X-Content-Type-Options', 'nosniff');
  res.setHeader('X-Frame-Options', 'DENY');
  res.setHeader('X-XSS-Protection', '1; mode=block');
  res.setHeader('Strict-Transport-Security', 'max-age=31536000; includeSubDomains');
  res.setHeader('Content-Security-Policy', "default-src 'self'");
  next();
});

Status: ⚠️ Open

High Priority Issues ​

3. IDOR (Insecure Direct Object Reference) ​

Severity: High

Affected Endpoints:

  • GET /ota/bookings/:id
  • GET /api/v1/wallet/{walletId}
  • GET /admin/ota/fare-preferences/:id

Description: Some endpoints may allow users to access resources belonging to other users by enumerating IDs.

Recommendation:

typescript
// Always verify ownership before returning resources
@Get('bookings/:id')
async getBooking(@Param('id') id: string, @Request() req) {
  const booking = await this.bookingService.findOne(id);

  // Verify ownership
  if (booking.userId !== req.user.id && !req.user.roles.includes('ADMIN')) {
    throw new ForbiddenException('Access denied');
  }

  return booking;
}

Status: ⚠️ Needs Review

4. SQL Injection Potential ​

Severity: High

Affected Areas:

  • Search origin/destination parameters
  • Booking origin/destination fields

Description: While Prisma ORM provides protection, some string concatenation may still exist in custom queries.

Recommendation:

  • Always use parameterized queries
  • Validate input against whitelist of valid station codes
  • Use Prisma's built-in parameter binding

Status: ✅ Mostly Protected (ORM-based)

5. Rate Limiting Gaps ​

Severity: Medium

Current Status:

  • ✅ /auth/login - 5 requests per 15 minutes
  • ✅ /auth/otp/request - Using OtpThrottleGuard
  • ✅ /auth/otp/verify - 5 requests per 5 minutes
  • ✅ /ota/book/calculate - 30 requests per minute
  • ⚠️ /ota/search - No rate limiting configured

  // ...

6. DoS (Denial of Service) Vectors ​

Severity: Medium

Issues:

  • Large payloads accepted (10MB+)
  • No request timeout configured
  • Potential for resource exhaustion via concurrent requests

Recommendation:

typescript
// In main.ts
app.use(express.json({ limit: '1mb' })); // Limit payload size
app.use(express.urlencoded({ limit: '1mb', extended: true }));

// Configure timeout
const server = await app.listen(3000);
server.timeout = 30000; // 30 second timeout
server.keepAliveTimeout = 65000;

Status: ⚠️ Needs Implementation

7. Timing Attack Vulnerabilities ​

Severity: Medium

Issues:

  • User enumeration possible via timing differences in OTP verification
  • Wallet balance prediction via response timing analysis

Recommendation:

typescript
// Use constant-time comparison for sensitive values
import { timingSafeEqual } from 'crypto';

function constantTimeCompare(a: string, b: string): boolean {
  const bufA = Buffer.from(a);
  const bufB = Buffer.from(b);

  if (bufA.length !== bufB.length) {
    return false;
  }

  return timingSafeEqual(bufA, bufB);
}

// Add artificial delay to normalize response times
async function verifyWithTimingNormalization(otp: string, expected: string) {
  const startTime = Date.now();
  const result = await constantTimeCompare(otp, expected);
  const elapsed = Date.now() - startTime;

  // Normalize to 200ms
  if (elapsed < 200) {
    await new Promise(resolve => setTimeout(resolve, 200 - elapsed));
  }

  return result;
}

Status: ⚠️ Open

Mass Assignment Protection ​

Current Status: ✅ Good ​

The application uses class-validator DTOs which provide good protection against mass assignment attacks.

Example:

typescript
export class CreateBookingDto {
  @IsString()
  @IsNotEmpty()
  bookingType: BookingType;

  @IsString()
  @IsNotEmpty()
  fareId: string;

  // Only allowed fields are defined
  // Extra fields in request body are automatically ignored
}

Recommendation: Continue using DTOs with explicit field definitions. Avoid using @Body() without DTO classes.

Identifier Change Security ​

The system uses a simplified 2-step verification flow for changing email or phone:

ControlImplementation
VerificationSame OTP sent to both old and new identifiers
Session bindingOTP stored in session metadata (not separate table)
Attempt limit3 failed attempts max before session expires
Session expiry15 minutes from initiation
OTP expiry5 minutes
Token rotationAll refresh tokens revoked after successful change
Cross-notificationAlert sent to other identifier (e.g., phone if email changed)
Anti-enumerationGeneric error messages, random response delays

Security Model:

  • User must have access to at least one of the identifiers (old or new) to receive the OTP
  • Attacker would need both: valid session token + access to one identifier
  • Equivalent security to double OTP with better UX

Content verification on every upload ​

The multipart Content-Type is chosen by the client, so an allowlist checked against it proves only that the client claimed an allowed type. StorageService.uploadFile reads the leading bytes before the label is persisted and before the object is handed to R2 under that type.

Declared typeChecked against
application/pdf%PDF-
image/pngthe 8-byte PNG signature
image/jpeg, image/jpgFF D8 FF
image/webpRIFF + WEBP at offset 8
application/mswordthe OLE2 compound-file header
application/zip, application/x-zip-compressed, .xlsx, .docxPK\x03\x04
text/csv, image/svg+xmlnothing — no signature exists

Three properties worth knowing:

  • Container signatures bound the container, not the member. PK\x03\x04 proves "a real ZIP", so a ZIP declared as xlsx passes. Separating them means parsing the archive directory, which an upload gate should not do. The same applies to OLE2, shared by .doc/.xls/.ppt.
  • text/csv and image/svg+xml cannot be verified and are accepted without a content check. They are instead refused inline by the routes that serve stored bytes: the shortfall-attachment redeem route, the shortfall-proof redeem route, the presigned /url link, and the storage download routes, which send attachment regardless of type. ⚠️ A file stored with visibility: PUBLIC is reached by none of those. File.publicUrl is R2_PUBLIC_URL + the object key, and the bucket host then serves the object under the type it was written with, outside the headers this API sets. R2_PUBLIC_URL was read on the three deployed hosts and is unset on prod and a stray comment string on staging and preprod, so none of them hands out a usable link today — but nothing in the code prevents one.
  • A declared type with no signature case is rejected, so adding a MIME to ALLOWED_MIME_TYPES cannot silently restore trust-the-client behaviour. The one exception is spelling: image/jpg resolves to image/jpeg before the lookup, because it is a type production's allowlist admits and the bytes are checked identically either way.

One signature table backs the upload gate, the mitra document check and the B2B PDF check, so the three cannot drift apart.

⚠️ This constrains new uploads only. Rows stored before it carry whatever was declared, and there is no backfill. Serve-time re-derivation is what handles them, and it is applied on the routes where the answer decides whether a browser renders the bytes — not on every download route.

File Download Security ​

Downloads are governed by validateFileAccess (storage.service.ts). See Storage — Download a File by ID for the full model.

Security ControlStatus
Owner-or-admin check on PRIVATE files✅ file.userId === userId or admin
Organization scoping on ORGANIZATION files✅ same organizationId
/url presigned link is access-checked (not any JWT)✅ same owner-or-admin check
Presigned URL time-limit✅ expiresIn, default 3600s
Presigned URL forces its own type and disposition✅ renderable types only; everything else downloads as application/octet-stream
Shareable token is capability-scoped✅ expiresIn (default 24h) + maxDownloads (default 1)
Download token drawn from a CSPRNG✅ randomBytes, 24 hex characters
Token is bound to the rail that minted it✅ purpose; each redeem route accepts only its own
Public route serves PUBLIC-visibility only✅ never serves PRIVATE docs

Notes:

  • A minted download token grants no-auth access to a single file until it expires or hits maxDownloads — treat tokens like bearer secrets; do not log or share them beyond the intended recipient.
  • Revoke a leaked token with DELETE /api/v1/storage/tokens/{tokenId}. Links minted by a dedicated rail are revoked on that rail's own route instead — for the shortfall attachment, DELETE /api/v1/admin/custom-booking/{id}/shortfall-attachment/link; for a settlement's transfer proof, DELETE /api/v1/admin/shortfall-settlements/{id}/proof/link.
  • A route that mints a token and returns it must carry @AuditRedactResponse(...) naming every response field the credential appears in. A global interceptor copies an admin's non-GET response into AuditLog.newValue — the exemptions are the audit-log routes themselves and internal Nest contexts — and it redacts nothing unless the URL matches an audit-config entry carrying a sensitiveFields list — which the minting URLs do not. Without the marker the minted capability is stored verbatim and keeps working for as long as the row is readable. Which fields to name follows the response shape: the two shortfall rails return a ready-made link and are marked ('token', 'url'), because the URL contains the token; the generic POST /api/v1/storage/{fileId}/token returns token and expiresAt with no URL and is marked ('token').
  • A presigned /url link previously carried no disposition and replayed the content type the object was uploaded with, so a renderable type rendered on the storage host, outside every header this API sends. An image/svg+xml therefore executed its script there. The link now states both, and anything outside PNG / JPEG / WebP / PDF is forced to download.

⚠️ Known and accepted: validateFileAccess returns any file to any ADMIN. Combined with GET /api/v1/storage — which applies no filter for an admin and accepts an entityType query — this means an admin can list and download any stored file regardless of which permission codes their role carries. Per-route permissions on the feature modules therefore do not govern file content on the generic storage rail. Feature rails that mint their own links are gated on their own permission, which is why they do not route through POST /storage/{fileId}/token; that narrows what this work adds, it does not close the existing rail.

CORS Configuration ​

Current Status: ⚠️ Needs Review

typescript
// Recommended configuration
const corsOptions = {
  origin: function (origin, callback) {
    const allowedOrigins = process.env.ALLOWED_ORIGINS?.split(',') || ['https://hhr.com'];
    if (!origin || allowedOrigins.indexOf(origin) !== -1) {
      callback(null, true);
    } else {
      callback(new Error('Not allowed by CORS'));
    }
  },
