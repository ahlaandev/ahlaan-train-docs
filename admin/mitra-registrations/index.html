Mitra Registrations Management Guide ​

Admin review and approval of Mitra (partner) self-serve registrations. Approval always issues a per-tier registration number and grants the tier's pricing access. Whether it also creates an Organization depends on the applicant, not on you — see Three kinds of registration.

Three kinds of registration (mode) ​

Each registration carries a server-derived mode (also on the customer response). It is set from the applicant's account, not typed by anyone, and it decides the shape of the approval:

modeWhat approve does
NEW_ORG (companyName present, non-member)Creates an Organization + org SAR wallet; the account is promoted to B2B; the tier flags live on the new org. nib/npwp/companyPhone are on the row.
ORG_LESS (no companyName)No Organization, no org wallet. The account stays B2C and the tier + promo flags are written onto the user.
MEMBER (targetOrganizationId set)Grants the applicant's existing organization mitra access — flips its tier + promo flags in place. No new org, no wallet, no role change. The member-submitted org fields were dropped at registration and are not shown.

A MEMBER-eligible applicant may instead register as ORG_LESS. A B2B account with an org that sends registerAsIndividual: true is resolved to ORG_LESS, not MEMBER. Approving it then detaches them from their organization — role → B2C, org link cleared — an intentional, admin-in-the-loop org unlink (see the ORG_LESS approval branch below).

A MEMBER row exposes targetOrganizationId and (on get/list) a targetOrganization object with the org's current pricingTier / promoAccessEnabled, so you can see exactly what the approval will change. Approving a MEMBER promotes every member of that org whose personal pricing is inherited from the org — that bulk grant is the intent, not a leak.

An individual partner with no Organization is not a bug. They are priced identically — a B2C user carrying pricingTier: GOLD gets the full special pricing set, because the per-user override outranks the organization axis in the pricing engine. There is nothing to fix and nothing to create by hand.

To find them on the users list, filter by ?pricingTier=GOLD, not by ?specialCustomPricingEnabled=true — that flag is org-only and does not describe these partners. See the Users guide.

Base URL ​

https://<host>/api/v1

Authentication ​

All endpoints require a JWT with the ADMIN role.

http
Authorization: Bearer <admin-jwt>

Permission-gated (Access Roles). The ADMIN role on its own is no longer enough. Each route also requires a fine-grained permission from the admin's Access Role. Reading (list, detail) needs mitra-registrations:read. Marking under review, approving, and rejecting all need mitra-registrations:review. A role holding mitra-registrations:* gets every route, and Super Admin (*) is unaffected. An admin whose Access Role has neither code gets 403, even though the JWT is valid. See Access Roles.

Approve currently shares mitra-registrations:review with the triage verbs, so granting review also grants the ability to approve. That matters because approving assigns the registration number, can create an Organization and its SAR wallet, and flips the pricing-tier flags. Grant mitra-registrations:review only to staff you intend to let provision partners.

Status Workflow ​

PENDING ─┬─> UNDER_REVIEW ─┬─> APPROVED  (terminal)
         │                 └─> REJECTED ─> PENDING (resubmit)
         ├─> APPROVED
         └─> REJECTED

APPROVED is terminal. Illegal transitions are rejected with 400.

reviewer — who approved or denied, at a glance. Every row carries a reviewer object ({ id, name, email }) resolved from reviewedBy (the deciding admin's user id). The admin shape is the full internal record — not the customer shape. List, get-one, review, approve and reject all return every field the customer endpoints deliberately withhold: auditLog, metadata (the IP + user-agent captured at submit), reviewedBy, the resolved reviewer, adminNotes, submissionCount, openRegistrationKey, userId, and the document slots as flat spkDocumentId / ktpDocumentId / paymentProofDocumentId / nibDocumentId / npwpDocumentId scalars — plus the deprecatedpartnershipDocumentId (still returned for existing records, no longer required for approval). The spkNumber (05.100/ADI/07/2026) is server-minted at the applicant's email verification, never typed by anyone — see Mitra Registration.

The four fee* fields are null here because MG.001 predates the frozen fee snapshot — that is the real stored value for it, not a placeholder. A registration submitted today carries feePriceSAR (the normal price at submit), feeChargedSAR (what that applicant owes), feePromoLabel, and feeConfigId (which price row applied, null when the built-in default fired). The admin list carries the same fields. feeConfigId is admin-only — the customer shape exposes the other three and not this one. feeChargedSAR is the figure to check a payment proof against, never today's price from Mitra Registration Fee.

auditTrail — the resolved decision history (detail only). The get-one response adds auditTrail, a resolved mirror of the raw auditLog: every transition with its actor's identity resolved to { id, name, email }. Actor resolution prefers the write-time snapshot now stamped on each admin transition (byName / byEmail on the auditLog entry) and falls back to a live user lookup — so the trail keeps a readable name even after an admin account is deleted or renamed. actor is null only when an entry is neither snapshotted nor resolvable (the system sentinel, or a legacy id-only entry whose user is gone). Old entries written before this feature stay id-only in auditLog and resolve live, best-effort. The whole timeline resolves in a single batched lookup — no per-entry query.

This is an early GOLD NEW_ORG record: its nib/npwp/companyPhone are null because it was onboarded before those became required for NEW_ORG, and its registrationInvoiceId is null because it was approved before the registration-receipt invoice shipped. Download a document ​

Each document slot is a stored file. Take the id from any slot — spkDocumentId, ktpDocumentId, paymentProofDocumentId, nibDocumentId, npwpDocumentId, or the deprecated partnershipDocumentId (or read it off the nested *Document objects) — and download it:

GET /api/v1/storage/{id}/download — returns the file. These slots are PRIVATE; as an admin you can fetch any of them.

For a time-limited link (email / preview) or a shareable no-login token, see Storage — Download a File by ID: GET /api/v1/storage/{id}/url (presigned) and the POST /api/v1/storage/{id}/token flow.

Mark under review ​

Endpoint: POST /admin/mitra-registrations/:id/review

Moves a PENDING registration to UNDER_REVIEW — an optional "I am looking at this" step; you can also approve or reject straight from PENDING.

Request Body: none (send {} or an empty body).

Response: 201 Created — the registration at status: "UNDER_REVIEW".

An illegal transition (e.g. a registration already APPROVED) is rejected:

json
{ "message": "Cannot transition mitra registration from 'APPROVED' to 'UNDER_REVIEW'", "error": "Bad Request", "statusCode": 400 }

Approve ​

Endpoint: POST /admin/mitra-registrations/:id/approve

Request Body:

json
{ "adminNotes": "Documents verified against source.", "depositConfirmed": true }
FieldRequiredNotes
adminNotesNoFree-text, recorded on the audit log.
depositConfirmedGOLD and RESELLERMust be true to approve a GOLD or RESELLER registration — the admin confirms the deposit was received off-system. Check the proof against that registration's own feeChargedSAR, not against a fixed figure: a partner who registered during a promo owes the promo amount. Ignored for SILVER, whose money is a fee rather than a deposit. Recorded on the audit-log entry.

What happens (atomic transaction):

  1. Assigns the next per-tier registration number (MS. / MG. / MR.). Both kinds of partner draw from the same per-tier counter.

  2. Then it branches on the registration's mode:

    NEW_ORG (companyName present):

    • Creates an Organization + SAR Wallet. The org email is the applicant's account email.
    • Sets the tier's pricing fields on the org (pricingTier is the source of truth; specialCustomPricingEnabled is written as its deprecated mirror):
      • GOLD ⇒ pricingTier = GOLD, specialCustomPricingEnabled = true, promoAccessEnabled = true
      • SILVER ⇒ pricingTier = SILVER, promoAccessEnabled = true
      • RESELLER ⇒ pricingTier = RESELLER, promoAccessEnabled = true. specialCustomPricingEnabled stays false: a reseller is priced as silver, and what the tier adds is commission, not special pricing
    • Promotes the applicant account to a B2B member of the new org (and clears any per-user overrides, so the org flags govern).
    • Sets the account's b2bApplicationStatus = APPROVED (b2b-applications parity — a NEW_ORG created an organization, so its b2b application is now approved). MEMBER and ORG_LESS leave b2bApplicationStatus untouched.

    MEMBER (targetOrganizationId set):

    • Creates no organization or wallet, and does not change the applicant's role or org.
    • Flips the existing organization's tier + promo flags in place (same per-tier mapping as above). This grants mitra pricing to every member of that org whose personal pricing is inherited from it.
    • Clears the applicant's per-user overrides so the org flags govern.
    • 409 if the applicant no longer belongs to the target organization.

    ORG_LESS (companyName is null):

    • Creates no Organization and no organization wallet.
    • Writes the tier onto the user: promoAccessEnabled = true plus pricingTier = GOLD, SILVER or RESELLER. The account stays B2C.
    • The registration keeps organizationId: null.
    • Intentional individual detach (registerAsIndividual). If this ORG_LESS registration came from a B2B org member who opted in with registerAsIndividual: true, approval additionally sets the user's role to B2C and clears their organizationId — the org detach. A genuine B2C org-less applicant has their role/org left untouched.

  3. Mints the registration receipt — a formal Invoice (status PAID, no Payment row) for the payment that already moved off-system, in the same transaction so it commits atomically with the approval. The amount is the registration's frozen feeChargedSAR — set when the applicant submitted, never re-read from the live fee configuration, so a price change or an expired promo between submit and approval cannot alter what the receipt claims. Priced in SAR, one line item, with the promo label appended to the description when one applied. Idempotent — a retried approval reuses the existing invoice (mitraRegistrationId is unique). Its id surfaces as registrationInvoiceId on the get-one / list responses and on the applicant's application/status; fetch the document via GET /admin/invoice/:id (or the customer GET /invoice/:id).

    Accounting note. The GOLD and RESELLER amounts are refundable security deposits (a liability), not revenue like SILVER's fee. Since a promo may apply to either, the deposit owed back to a given partner is their own feeChargedSAR — it is not one system-wide number. Both use one invoice shape for FE-PDF simplicity; if finance later needs the distinction, an invoice-category field is a follow-up, not part of this receipt.

  4. Sends the mitra-registration-approved email (the organization-code row is omitted for an individual partner).

Pre-conditions (else 400): all required documents must be present — SPK for all, KTP for INDIVIDUAL, payment proof whatever the tier. A missing document returns the enriched validation envelope (captured live):

json
{ "statusCode": 400, "error": "Bad Request", "message": "Cannot approve: missing required document(s): KTP", "code": "UNCODED", "category": "VALIDATION", "retryable": false }

The partnership document is deprecated and not checked. Approving a GOLD or RESELLER registration also requires depositConfirmed: true — including an individual partner: the deposit is keyed on the tier, not on whether the applicant has a company.

The SPK always arrives with the registration — it is attached to the submit request itself and a submission without it is rejected, so no row ever reaches your queue missing its signed MoU. The other three documents are optional at submit time (an applicant has no payment proof before they have the bank details) and are added later by the signed-in applicant. This gate is what still enforces the full set at approval; it has not changed.

Conflicts (409): the linked account is an admin; a MEMBER applicant no longer belongs to the target organization; a NEW_ORG/ORG_LESS applicant became a B2B member or joined an organization since submitting (approval would clobber it); or the account already has an approved mitra registration (one approved registration per account, ever — the guard that stops an approved individual partner, still B2C, from being approved a second time and burning another registration number). Note a B2B member registering for their own org is MEMBER mode and is allowed — that is no longer a conflict.

Response: 201 Created — the approved registration with its registrationNumber. Note the registrationInvoiceId on this approve response can still read null even though the receipt invoice was minted in the same transaction — re-fetch with get-one (or read the applicant's application/status) to see the id populated (captured live).

Worked example — approving a GOLD MEMBER ​

Approving the MEMBER row above. First without depositConfirmed — the Gold deposit gate rejects it:

bash
curl -X POST "$BASE/admin/mitra-registrations/019f6427-1b8f-740d-9486-48c0a91f408f/approve" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"adminNotes":"member gold"}'
json
{ "message": "Confirm the 50000 SAR GOLD deposit (received off-system) before approval", "error": "Bad Request", "statusCode": 400 }

Now with depositConfirmed: true → 201, registrationNumber: "MG.002" (the next global Gold sequence — not tied to the org), mode: "MEMBER", organizationId: null (no org created). The audit-log approve entry carries depositConfirmed: true.

The effect on the target organization (PT Ruwaidi) — approval flipped its promoAccessEnabled in place, and cleared the applicant's per-user overrides so the org flags govern:

promoAccessEnabledpricingTierapplicant roleapplicant overrides
before approvefalseGOLDB2BpromoAccessEnabled: null, pricingTier: null
after approvetrueGOLDB2B (unchanged)reset to null (org governs)

No new organization, wallet, or role change — the member's existing org simply gained mitra access, and every member of it who inherits pricing from the org is promoted with it.

Reject ​

Endpoint: POST /admin/mitra-registrations/:id/reject

Request Body:

json
{
  "rejectionReason": "SPK document is illegible. Please re-upload a clear scan.",
  "adminNotes": "Second rejection for this applicant."
}

Response: 201 Created — the rejected registration. A rejection email is sent to the applicant.

Notes ​

  • Tier is a stored label mapped to access flags on approval (Option A). The pricing engine is driven by those flags — on the organization for an organization partner, on the user for an individual partner. The stored tier drives numbering and the onboarding record. Manually toggling the flags later can drift from the recorded tier — the flags stay the source of truth for pricing.
  • The Gold and Reseller security deposit proof is captured as the payment proof, and the admin confirms receipt via depositConfirmed at approve time. The deposit stays manual / off-system — it is not credited to any wallet, and there is no deposit ledger or reconciliation table for it.
  • Personal wallets are created at registration, not at approval. Every mitra applicant gets a personal SAR wallet when they submit, so an individual partner (who never receives an organization wallet) still has a working wallet. The applicant cannot read it on the mitra host until they are approved (403), which is deliberate — nothing is ever credited to an applicant, and the deposit is settled off-system. The row exists so that an approved org-less partner is not the one B2C user in the system without a wallet.
  • An applicant can log in while you review them. From submission until approval or rejection they hold a session on the mitra host confined to their own application (profile, application status, re-submit + upload, and their own documents). They cannot book, and they cannot see a wallet or an invoice. A rejected applicant keeps that session so they can read rejectionReason and re-apply. See Mitra Registration.
  • Their documents cannot be deleted by them. The applicant owns their uploads (so they can view them), but DELETE /storage/:id is refused for mitra documents — they are review evidence. Only an admin can remove one.
  • Invoices carry the partner identity either way. The MS./MG. number and partner name are snapshotted onto every invoice — resolved from the owning organization when there is one, and from the user's own approved registration when there is not.
