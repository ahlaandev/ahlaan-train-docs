Refund Management (Admin) Guide ​

This guide is the API reference hub for the admin refund surface (/api/v1/admin/refunds). It covers how administrators list, inspect, and report on refunds, the two refund methods (direct-to-bank and wallet), and the end-to-end flow for an admin-initiated direct-to-bank refund — the operative refund path today.

For the deep operational walkthrough of the bank disbursement (eligibility rules, dual-control, proof storage), see the companion Direct-to-Bank Refund (Admin Disbursement) Guide.

Access: all endpoints below require a JWT with the ADMIN role and are rate-limited. Controller: @Controller({ path: 'admin/refunds', version: '1' }) → every route is served under /api/v1/.

Permission-gated (Access Roles). Each route also requires a fine permission: read/report/calculate routes need refunds:read, the manual and direct-to-bank create routes (POST /manual, POST /bank) need refunds:create, override / retry / proof-upload / bank-approve need refunds:approve, and bank-reject needs refunds:reject. See Access Roles.

Refund methods ​

The system models two refund methods (RefundMethod enum):

MethodStatusHow it settles
BANK_TRANSFERActive (default for admin refunds)Admin initiates a bank refund, transfers the money out-of-band, and uploads transfer proof. The upload finalizes the refund → COMPLETED.
WALLETDisabledCredits the customer's in-app wallet. Used by the legacy auto-on-cancel, ticketing-failure, and POST /admin/refunds/manual paths.

Why wallet refunds are disabled ​

The wallet feature is currently switched off operationally — wallet top-up is gated by a kill switch (WALLET_TOPUP_ENABLED) and wallets are not part of the active product surface (see the note in Financial Reports). Because no customer wallets are in active use, the wallet-credit refund paths — including POST /admin/refunds/manual, which credits the wallet (creditRefundToWallet) — are effectively inactive.

In practice: issue refunds via the direct-to-bank flow below. The wallet method and POST /admin/refunds/manual remain in the codebase for the historical/auto paths but should not be used while wallets are disabled. Existing WALLET refund records (created before the feature was switched off) are still readable via the list and detail endpoints.

Refund lifecycle ​

RefundStatus enum:

PENDING ───▶ PROCESSING ───▶ COMPLETED
   │                              ▲
   └──────────────────────────────┘  (single-control: PENDING ─▶ COMPLETED)
   └──────────────────────▶ FAILED   (reject / processing error)
  • PENDING — refund record created, money not yet moved.
  • PROCESSING — bank refund awaiting a checker (dual-control mode only).
  • COMPLETED — money disbursed (proof uploaded in single-control, or approved in dual-control; wallet credited for wallet refunds).
  • FAILED — rejected or processing error. Eligible for POST /:id/retry.

See the bank status machine for the single- vs dual-control transitions.

List refunds ​

GET /api/v1/admin/refunds

Query params (all optional):

ParamTypeValues
pagenumberPage (default 1)
limitnumberPage size (default 10)
statusenumPENDING, PROCESSING, COMPLETED, FAILED
bookingTypeenumREGULAR, GROUP
userIdstringFilter by user
bookingIdstringFilter by booking
organizationIdstringFilter by organization (B2B)
sourceenumBOOKING, STANDARD, BLOCKSEAT, CUSTOM_BOOKING — filter by booking kind (see below)

Filtering by booking source (BlockSeat vs OTA vs both) ​

source narrows the list by the kind of booking the refund belongs to. Every refund attaches to an OTA Booking (Booking.bookingVariant), so:

sourceReturns
(omitted) or BOOKINGBoth — all OTA refunds (STANDARD + BLOCKSEAT)
STANDARDOTA standard bookings only (excludes BlockSeat) — the "OTA" service bucket
BLOCKSEATBlockSeat (wholesale) bookings only
CUSTOM_BOOKINGAlways empty — custom bookings have no refund records (they refund via the booking's own price reducer, not the refund surface)

Uses the same shared BookingSourceFilter as the invoice / payment-report / audit-log list filters.

Request

bash
# Both (default — no source param)
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?limit=2&status=COMPLETED" \
  -H "Authorization: Bearer <ADMIN_JWT>"

# BlockSeat refunds only
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?source=BLOCKSEAT" \
  -H "Authorization: Bearer <ADMIN_JWT>"

# OTA (standard) refunds only
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?source=STANDARD" \
  -H "Authorization: Bearer <ADMIN_JWT>"

# Custom bookings — always empty (no refund records)
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?source=CUSTOM_BOOKING" \
  -H "Authorization: Bearer <ADMIN_JWT>"

Direct-to-bank refund flow ​

This is the operative admin refund path. A booking must be cancelled first; then the admin refunds the money to the customer's bank and uploads proof.

1. Cancel the booking
   STANDARD : POST /admin/ota/bookings/:id/cancel
   BLOCKSEAT: POST /admin/blockseat-bookings/bookings/:id/cancel

2. (Optional) Prefill the customer's saved bank details
   GET  /admin/refunds/bank-details/:bookingId

3. Initiate the bank refund  →  refund created in PENDING
   POST /admin/refunds/bank

4. Transfer the money out-of-band, then upload proof
   POST /admin/refunds/:id/bank-proof   →  COMPLETED  (single-control)

   (Dual-control only: upload → PROCESSING, then
    POST /admin/refunds/:id/bank-approve → COMPLETED)

Bank refunds are gated by eligibility rules (default: BlockSeat bookings only). See Eligibility rules and the operational guide.

Calculate refund amount ​

POST /api/v1/admin/refunds/calculate — read-only, creates nothing. Returns the deterministic refund amount the admin confirms (anchored to what the customer paid — Rule A) plus a full audit breakdown (charged facts, policy, eligibility, payout). The UI renders the amount read-only; admins do not key it in.

For FE — only bookingId is needed. The payout currency and amount are derived automatically from the settled payment at the payment-time exchange rate. A customer who paid Rp 4,702,500 receives exactly Rp 4,702,500 back on a full refund — no rate conversion, no admin input.

Body: bookingId (✅), cancelledAt (optional ISO; defaults to the booking’s actual cancellation event, not the request time). overrideAmountSAR is an admin-only edge-case field (force a SAR amount when policy yields 0); FE does not need to expose it in the normal refund flow. Full request/response in Refund bank disbursement → Calculate the refund.

bash
curl -s -X POST "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/calculate" \
  -H "Authorization: Bearer <ADMIN_JWT>" \
  -H "Content-Type: application/json" \
  -d '{ "bookingId": "019ef302-34f2-731c-a702-8e728f22908c" }'

Initiate direct-to-bank refund ​

POST /api/v1/admin/refunds/bank — creates a BANK_TRANSFER refund in PENDING (no money moved yet).

Body (AdminBankRefundDto):

FieldTypeRequiredNotes
bookingIdstring✅Cancelled booking to refund
reasonstring✅Admin reason (audited)
destinationBankCodestring✅e.g. BRI
destinationBankNamestring✅e.g. BRI
destinationAccountNumberstring✅Customer account number
destinationAccountNamestring✅Account holder name
saveBankDetailsToCustomerboolean—Persist these bank details back to the customer profile

No amount or currency input. The payout currency and amount are derived automatically from the settled payment at the payment-time exchange rate (Rule A) — the FE never supplies them. Pre-fill the figures from POST /admin/refunds/calculate. See Refund bank disbursement → Non-SAR payout.

Edge case — overrideAmountSAR: when the policy yields 0 (booking is non-refundable per the GROUP tier), add "overrideAmountSAR": <number> to force a specific SAR amount. The IDR/USD payout is still back-calculated from the payment-time rate — the client never supplies the foreign amount. Without this field the server returns 400 Refund amount must be greater than zero.

bash
curl -s -X POST "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/bank" \
  -H "Authorization: Bearer <ADMIN_JWT>" \
  -H "Content-Type: application/json" \
  -d '{
    "bookingId": "019ef302-34f2-731c-a702-8e728f22908c",
    "reason": "Customer cancellation - full refund approved",
    "destinationBankCode": "BRI",
    "destinationBankName": "BRI",
    "destinationAccountNumber": "1234567890",
    "destinationAccountName": "Ahmad Fauzi",
    "saveBankDetailsToCustomer": true
  }'

Returns the new refund in PENDING with refundMethod: "BANK_TRANSFER" and the destination* fields populated (same shape as Refund detail).

Upload transfer proof ​

POST /api/v1/admin/refunds/:id/bank-proof — multipart form, field file (PDF/JPG/PNG/WebP, ≤5 MB). In single-control mode the upload finalizes the refund → COMPLETED.

Body (multipart/form-data):

FieldTypeNotes
filefileTransfer proof (PDF/JPG/PNG/WebP, ≤5 MB)
bankTransferReferencestringOptional bank reference number
transferredAtstring (ISO)Optional transfer timestamp, e.g. 2026-06-23T10:00:00Z
payoutAmountnumberOptional — actual amount transferred in the payout currency (overrides the initiate-time suggestion)
payoutRateToSARnumberOptional — actual FX rate used (SAR per 1 unit of payout currency). Reconciled against refundAmountSAR; a divergence is stored + flagged (or blocked if REFUND_PAYOUT_RECONCILE_ENFORCE=true)
bash
curl -s -X POST "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/019ef307-fedc-730e-b0a8-992b97cd2c46/bank-proof" \
  -H "Authorization: Bearer <ADMIN_JWT>" \
  -F "file=@transfer-proof.pdf" \
  -F "bankTransferReference=TRX-998877" \
  -F "transferredAt=2026-06-23T05:50:49Z"

Returns the refund as COMPLETED with bankProofUploaded: true and bankTransferredAt set.

The finalizing step uses an atomic compare-and-swap — two concurrent finalizations cannot both settle (the loser gets 409 Conflict).

Reject a bank refund ​

POST /api/v1/admin/refunds/:id/bank-reject → FAILED. Body (BankRefundRejectDto): { "reason": "..." } (required).

Override refund amount ​

PATCH /api/v1/admin/refunds/:id/override

Override an existing refund's amount (e.g. a goodwill adjustment). Cannot override a COMPLETED refund.

Body (AdminOverrideRefundDto):

FieldTypeRequired
refundAmountSARnumber✅
reasonstring✅
bash
curl -s -X PATCH "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/<REFUND_ID>/override" \
  -H "Authorization: Bearer <ADMIN_JWT>" \
  -H "Content-Type: application/json" \
  -d '{ "refundAmountSAR": 500, "reason": "Goodwill adjustment" }'

The refund is marked policyType: "ADMIN_OVERRIDE" and adminOverride: true.

Retry a FAILED refund ​

POST /api/v1/admin/refunds/:id/retry — reprocess a refund in FAILED status (400 if it is not FAILED). Increments retryCount.

bash
curl -s -X POST "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/<REFUND_ID>/retry" \
  -H "Authorization: Bearer <ADMIN_JWT>"

Manual wallet refund — disabled ​

POST /api/v1/admin/refunds/manual creates a refund that credits the customer wallet (AdminManualRefundDto: bookingId, reason, optional overrideAmount). Because the wallet feature is disabled (see Refund methods), do not use this endpoint — it would create a WALLET refund that cannot be delivered to an active wallet. Use the direct-to-bank flow instead.

Eligibility rules ​

Direct-to-bank refunds are gated by admin-configurable eligibility rules under a sibling controller: /api/v1/admin/refund-bank-eligibility/rules (GET list, GET /:id, POST create, PUT /:id update, DELETE /:id deactivate).

Request

bash
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refund-bank-eligibility/rules" \
  -H "Authorization: Bearer <ADMIN_JWT>"

Response 200 OK (real — note the auto-seeded default allowing BlockSeat only):

Rule body (CreateRefundBankEligibilityRuleDto): name, action (ALLOW/DENY), priority, isActive (required); optional description, originId, destinationId, tripClass (BUSINESS/ECONOMY), tripType (ONE_WAY/ROUND_TRIP), bookingType (REGULAR/GROUP), bookingVariant (STANDARD/BLOCKSEAT), minPassengers, maxPassengers.

Notes ​

  • Refunds apply only to cancelled bookings; cancel first, then refund.
  • The customer is not auto-notified — admins contact the customer directly (matches the existing refund/booking communication policy).
  • Proof files are stored privately in R2; admins fetch a short-lived signed URL via GET /admin/refunds/:id/bank-proof.
  • Every state transition (initiate / upload / approve / reject / override) is written to the audit log.
