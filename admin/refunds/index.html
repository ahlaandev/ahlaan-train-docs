Refund Management (Admin) Guide ​

This guide is the API reference hub for the admin refund surface (/api/v1/admin/refunds). It covers how administrators list, inspect, and report on refunds, the two refund methods (direct-to-bank and wallet), and the end-to-end flow for an admin-initiated direct-to-bank refund — the operative refund path today.

For the deep operational walkthrough of the bank disbursement (eligibility rules, dual-control, proof storage), see the companion Direct-to-Bank Refund (Admin Disbursement) Guide.

Access: all endpoints below require a JWT with the ADMIN role and are rate-limited. Controller: @Controller({ path: 'admin/refunds', version: '1' }) → every route is served under /api/v1/.

Permission-gated (Access Roles). Each route also requires a fine permission: read/report/calculate routes need refunds:read, the manual and direct-to-bank create routes (POST /manual, POST /bank) need refunds:create, override / retry / proof-upload / bank-approve need refunds:approve, and bank-reject needs refunds:reject. See Access Roles.

⚠️ The refunds resource carries a fifth code that no route on this page uses: refunds:shortfall-settlement. It gates POST /api/v1/admin/shortfall-settlements, on its own page. It is called out here because a reader building a Refunds role from the four codes above will not otherwise discover it, and because refunds:* does confer it — so a wildcard grant made for bank refunds also hands over the shortfall write. Grant the four codes individually if that is not intended.

Refund methods ​

The system models two refund methods (RefundMethod enum):

MethodStatusHow it settles
BANK_TRANSFERActive (default for admin refunds)Admin initiates a bank refund, transfers the money out-of-band, and uploads transfer proof. The upload finalizes the refund → COMPLETED.
WALLETDisabled, and enforced in codeCredits the customer's in-app wallet. Every path that would do so — the auto-on-cancel and ticketing-failure refunds, POST /admin/refunds/manual, PATCH /:id/override and POST /:id/retry — is gated by WALLET_AUTO_REFUND_ENABLED, which is unset (off) everywhere.

Why wallet refunds are disabled ​

The wallet feature is currently switched off operationally — wallet top-up is gated by a kill switch (WALLET_TOPUP_ENABLED) and wallets are not part of the active product surface (see the note in Financial Reports). Because no customer wallets are in active use, the wallet-credit refund paths — including POST /admin/refunds/manual, which credits the wallet (creditRefundToWallet) — are effectively inactive.

Until 2026-09 that was policy only — the code still credited wallets on every cancellation. It is now enforced by WALLET_AUTO_REFUND_ENABLED:

  • The automatic paths record instead of paying. A cancellation or a ticketing failure creates the Refund row as PENDING with the amount owed and no wallet credit. It appears in the list and detail endpoints below — GET /admin/refunds?awaitingDisbursement=true is the queue of exactly these rows — and in Refund reports as summary.awaitingDisbursementCount / awaitingDisbursementAmount. The report's money figures count COMPLETED refunds only, so a recorded-but-unpaid debt is never counted as refunded money.
  • The three admin wallet-credit endpoints return 403.POST /admin/refunds/manual, PATCH /admin/refunds/:id/override (when the override would credit) and POST /admin/refunds/:id/retry. Nothing is written when they refuse.
  • One exemption. A booking the customer actually paid from their own wallet is still credited automatically — the money is going back where it came from. This needs a COMPLETED DEBIT wallet transaction for the booking, not just paymentMethod = 'WALLET', because funds may have been held and never charged.

In practice: a cancellation now leaves money owed and recorded, and an admin disburses it through the direct-to-bank flow below. Nothing pushes those PENDING rows at anyone — no customer surface and no notification — so the queue is found by asking for it: ?awaitingDisbursement=true on the list, or the awaitingDisbursement* pair on the report. Existing WALLET refund records (created before the feature was switched off) are still readable via the list and detail endpoints.

Refund lifecycle ​

RefundStatus enum:

PENDING ───▶ PROCESSING ───▶ COMPLETED
   │                              ▲
   └──────────────────────────────┘  (single-control: PENDING ─▶ COMPLETED)
   └──────────────────────▶ FAILED   (reject / processing error)
   └──────────────────────▶ SUPERSEDED_BY_BANK_REFUND  (wallet rows only)
  • PENDING — refund record created, money not yet moved.
  • PROCESSING — bank refund awaiting a checker (dual-control mode only).
  • COMPLETED — money disbursed (proof uploaded in single-control, or approved in dual-control; wallet credited for wallet refunds).
  • FAILED — rejected or processing error. Eligible for POST /:id/retry.
  • SUPERSEDED_BY_BANK_REFUND — an undisbursed wallet row whose debt a later direct-to-bank refund on the same booking has taken over. Terminal, and set only by POST /admin/refunds/bank. It is a separate status rather than FAILED so the retry endpoint, which credits a wallet, can never be offered it. Such a row stops counting toward the over-refund total, but still counts toward refundSequence and still carries the booking's cancellation time.

See the bank status machine for the single- vs dual-control transitions.

The awaiting-disbursement queue ​

?awaitingDisbursement=true is the work list created by the wallet-credit gate: a cancellation recorded what is owed and paid nothing, and an admin must send it through the direct-to-bank flow.

bash
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?awaitingDisbursement=true" \
  -H "Authorization: Bearer <ADMIN_JWT>"

Response 200 OK — live staging capture, 2026-09-03. Each row carries the same fields as the list item above; the page is empty here because staging held no undisbursed wallet row at capture time.

json
{
  "refunds": [],
  "total": 0,
  "page": 1,
  "limit": 20,
  "totalPages": 0
}

All three fields are required together, because each alone matches a row that is not this one: PENDING alone also matches a direct-to-bank refund awaiting its proof, and a null wallet transaction does not identify a wallet row at all, since a direct-to-bank refund has no reason to carry one either. On the same staging data that returned the empty page above, ?status=PENDING returned two rows — both direct-to-bank refunds awaiting proof.

Sending it as true together with a status is a 400, not a silent override — the flag already pins the status, so any status next to it is redundant or asks for a different set. awaitingDisbursement=false filters nothing and carries no such conflict, so a client that always sends the parameter is never refused.

Response 400 on ?awaitingDisbursement=true&status=PENDING (live staging capture, 2026-09-03 — status=COMPLETED returns the same body):

Partner identity on the row ​

Each row carries partnerRegistrationNumber, partnerName and partnerTier (SILVER / GOLD / RESELLER), resolved live from the mitra registration: the owning organization's own registration first, then the refund user's own approved numbered one. Three nulls is the normal answer for a refund that belongs to no mitra — render -.

⚠️ These three are present on this list only. The refund mapper is shared with the other refund responses, and only this list eager-loads the registrations, so elsewhere the keys are absent rather than null: branch on presence, not on a null check.

The partner filters follow the same precedence the column does. ⚠️ One case parts them: a user holding more than one approved, numbered registration matches on any of them, while the column shows the one resolved newest-reviewed-first — so the row can name a different number than the one searched for. Matching the column exactly would tie the filter to the resolver's ordering, which is the trade taken.

Scope: this list is OTA refunds. A refund always links a Booking, and source=CUSTOM_BOOKING returns an empty page without querying, because custom bookings have no Refund rows. The custom-booking side of the Refunds screen is shortfall settlements, which carries the same three fields and the same two filters — but on its detail and create responses as well, where this module leaves the keys absent.

Live capture, staging, 2026-09-03 — GET /api/v1/admin/refunds?partnerRegistrationNumber=MG.002&limit=1 as a super admin, trimmed to the identity fields and enough of the refund to place them:

json
{

  "bookingCode": "WF3ZHMF",
  "status": "PENDING",
  "refundAmountSAR": 50,

That call reported 18 rows, and reading the full page back showed MG.002 as the only registration number on it. A search by name (?partnerName=imam) reported the same 18, which is the filter and the column agreeing on this partner.

A refund belonging to no mitra reports three nulls rather than omitting the keys. RFD-202606-0008, from an unfiltered GET /api/v1/admin/refunds?limit=5 on the same day, is one:

json
{ "partnerRegistrationNumber": null, "partnerName": null, "partnerTier": null }

Where rate limiting is enabled (ENABLE_RATE_LIMITING) the route allows 30 requests per minute per caller, because each page also mints up to 100 signed download links. That flag is false on both staging and preprod (checked in each host's .env on 2026-08-22), so neither environment enforces it. limit above 100 is refused with a 400, not trimmed — a report that asked for 500 rows and quietly received 100 would look complete. Page wider windows with page; the response carries totalPages.

Filtering by date ​

Two windows, because they are different days:

WindowColumnFilled on
created*createdAtevery refund
transferred*bankTransferredAtonly a BANK_TRANSFER refund whose money has actually been sent

A wallet refund never has a bankTransferredAt, and neither does a bank refund still awaiting disbursement — so a transferred* window is the money-left-the- account report, and a created* window is the everything-that-happened report.

The two are independent and combine with AND, so "created yesterday, paid today" is expressible:

bash
# Refunds paid out on the Riyadh day 2026-08-21
GET /api/v1/admin/refunds?transferredOn=2026-08-21

# Created in an arbitrary UTC range
GET /api/v1/admin/refunds?createdFrom=2026-08-01&createdTo=2026-08-21

# Both windows at once
GET /api/v1/admin/refunds?createdOn=2026-08-20&transferredOn=2026-08-21

Clocks. A From/To pair resolves in UTC, and a bare YYYY-MM-DD upper bound is extended to that day's 23:59:59.999Z so a single-day window covers the whole day — the same contract the invoice list serves. An On shorthand instead cuts the day in the application timezone (PRICING_TIMEZONE, default Asia/Riyadh), so transferredOn=2026-08-21 spans 2026-08-20T21:00:00Z up to (not including) 2026-08-21T21:00:00Z. The two spellings of "the 21st" therefore differ by three hours at each edge. Send the offset form on both ends of a pair (2026-08-21T00:00:00+03:00) to ask for a Riyadh day that way.

Sending an On together with its own From/To is a 400 — one of them would otherwise be silently ignored. Mixing createdOn with transferredFrom is fine: the rule is per pair, not across pairs.

Measured on preprod 2026-08-22 against the same 87-row table, super-admin token:

Requesttotal
?limit=100 (no window)87
?transferredOn=2026-06-242
?transferredFrom=2026-06-23T21:00:00Z&transferredTo=2026-06-24T20:59:59.999Z2 — the same two rows, which is what makes transferredOn a Riyadh day rather than a UTC one
?transferredFrom=2026-06-24&transferredTo=2026-06-242 — the bare upper bound reached 10:40Z, so it was extended past midnight as documented
?createdOn=2026-06-24&transferredOn=2026-06-242

Of the 87 rows, 6 carried a bankTransferredAt and 81 did not (78 wallet refunds plus 3 bank refunds not yet sent). That ratio is the reason there are two windows rather than one: a lone transferred* pair would have hidden 81 rows from every date search.

Give the upper bound a time component when the lower bound has one. Same behaviour as the invoice list.

⚠️ A blank value is a 400, not "no filter". ?createdOn= fails validation rather than being read as absent, so a form that always sends every field must omit the empty ones.

Transfer proof on the row ​

Each row carries bankProofUploaded, bankProofFileId, and bankProofDownloadUrl — a signed URL valid for 24 hours, minted for the whole page in one batch, so assembling a day of receipts is one call instead of one GET /:id/bank-proof per row. The detail route still mints its own short-lived URL on demand.

bankProofDownloadUrl is null when the row has no proof, when the link could not be minted, and on any host where the direct-to-bank rail is disabled — the list still returns its rows there, because it serves wallet refunds too.

Measured on preprod 2026-08-22: the list URL carries X-Amz-Expires=86400 (24 hours) and GET /admin/refunds/:id/bank-proof carries X-Amz-Expires=300 (5 minutes). Both fetched the object directly when fresh, and the list URL returned 200 on a second request, so it is a plain presigned URL with no download counter — it is not spent by the first click. The 5-minute TTL is enforced, not decorative: the same detail URL re-fetched about ten minutes later returned 403 from R2.

bankProofFileId and bankProofDownloadUrl appear on the admin list only. GET /api/v1/admin/refunds/:id omits both keys rather than returning null, because a null there would read as "this proof has no link" when the truth is that the detail read never looked; use GET /admin/refunds/:id/bank-proof for a single row. The customer-facing refund reads carry neither key — they keep the bankProofUploaded boolean, since a transfer receipt is an internal reconciliation artefact.

Filtering by booking source (BlockSeat vs OTA vs both) ​

source narrows the list by the kind of booking the refund belongs to. Every refund attaches to an OTA Booking (Booking.bookingVariant), so:

sourceReturns
(omitted) or BOOKINGBoth — all OTA refunds (STANDARD + BLOCKSEAT)
STANDARDOTA standard bookings only (excludes BlockSeat) — the "OTA" service bucket
BLOCKSEATBlockSeat (wholesale) bookings only
CUSTOM_BOOKINGAlways empty — custom bookings never produce Refund rows. When a ticket source under-delivers, the booking goes to TICKET_UPLOADED_PARTIAL and the money owed for the un-ticketed passengers is settled via Shortfall Settlements, moving the booking to SHORTFALL_REFUNDED. See Custom Booking (Admin).

Uses the same shared BookingSourceFilter as the invoice / payment-report / audit-log list filters.

Request

bash
# Both (default — no source param)
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?limit=2&status=COMPLETED" \
  -H "Authorization: Bearer <ADMIN_JWT>"

# BlockSeat refunds only
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?source=BLOCKSEAT" \
  -H "Authorization: Bearer <ADMIN_JWT>"

# OTA (standard) refunds only
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds?source=STANDARD" \
  -H "Authorization: Bearer <ADMIN_JWT>"

# Custom bookings — always empty (no refund records)
curl -s "https://preprod.mitra.ahlaan.co.id/api/v1/admin/refunds?source=CUSTOM_BOOKING&limit=1" \
  -H "Authorization: Bearer <ADMIN_JWT>"

Real response for source=CUSTOM_BOOKING (preprod, admin token, re-captured 2026-08-07 after shortfall settlements shipped) — confirms the always-empty contract. The limit=1 in the response is the one sent on the request above; omit it and the echoed limit is the endpoint's own default:

json
{ "refunds": [], "total": 0, "page": 1, "limit": 1, "totalPages": 0 }

Re-verified after a real shortfall settlement existed on that environment, which is the case that matters: the settlement recorded against booking UW4V4KK on 2026-08-07 did not appear here. (That settlement was a test record and was removed on 2026-08-22; the check it supported stands — a settlement is not a Refund, whether or not this particular one still exists.)

This contract is unchanged by custom-booking shortfall handling: a shortfall settlement is not a Refund, so this filter stays empty by design rather than by omission. Do not build a "custom booking refunds" screen on this endpoint — use Shortfall Settlements instead.

Refund detail ​

GET /api/v1/admin/refunds/:id

Returns the full refund record. Direct-to-bank refunds carry the destination* / bank* fields; wallet refunds carry walletTransactionId and (for OTA-sourced refunds) the metadata.ota penalty/pricing breakdown.

Request

bash

  -H "Authorization: Bearer <ADMIN_JWT>"

Response 200 OK — direct-to-bank refund (same shape as the list item above).

Refund reports ​

GET /api/v1/admin/refunds/reports

Aggregated refund volume, status, and policy breakdown for the period.

Every money figure counts COMPLETED refunds only. The report answers how much money left the account, and a PENDING row is money still owed. That rule covers summary.totalRefunds, totalAmount, avgAmount, chartData and byPolicyType. byStatus is the exception — it is the one breakdown covering every status, so that is where an unpaid row is read.

Two summary fields carry the recorded-but-unpaid debt: awaitingDisbursementCount and awaitingDisbursementAmount. They apply the same three-field rule as GET /admin/refunds?awaitingDisbursement=true, over the rows this report is computed on — so they are that queue narrowed to the report's period and filters, not the whole queue.

failureRate is failedCount / (completedCount + failedCount) — resolved rows only, so recording an unpaid refund does not move it.

The status filter narrows the rows before any counting, and the money rule still applies to what is left: ?status=PENDING reports zero paid, with the rows themselves visible in byStatus and in the awaitingDisbursement* pair.

Request

bash
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/reports?preset=CUSTOM&from=2026-06-01&to=2026-06-24" \
  -H "Authorization: Bearer <ADMIN_JWT>"

Response 200 OK — live staging capture, 2026-09-03, super-admin token.

json
{

  "periodTo": "2026-06-24",

The counting rule is legible inside that one response: byStatus covers five rows, and totalRefunds counts the three COMPLETED ones. Summing byStatus gives what the old all-status rule reported for the same period — 5 rows and 6463.4 SAR, against 4667.4 actually paid.

awaitingDisbursementCount is 0 here because the two PENDING rows in this period are direct-to-bank refunds awaiting proof, not the gated wallet debt — which is the distinction the three-field rule exists to make.

Reports are SAR-only. Every amount above is the canonical refundAmountSAR. A non-SAR direct-to-bank payout (payoutCurrency USD/IDR) still contributes its SAR figure here — the foreign payoutAmount is not broken out or rolled up by currency. To review actual disbursement currencies, use the refund list (payoutCurrency / payoutAmount per row) or a refund's detail.

Direct-to-bank refund flow ​

This is the operative admin refund path. A booking must be cancelled first; then the admin refunds the money to the customer's bank and uploads proof.

1. Cancel the booking
   STANDARD : POST /admin/ota/bookings/:id/cancel
   BLOCKSEAT: POST /admin/blockseat-bookings/bookings/:id/cancel

2. (Optional) Prefill the customer's saved bank details
   GET  /admin/refunds/bank-details/:bookingId

3. Initiate the bank refund  →  refund created in PENDING
   POST /admin/refunds/bank

4. Transfer the money out-of-band, then upload proof
   POST /admin/refunds/:id/bank-proof   →  COMPLETED  (single-control)

   (Dual-control only: upload → PROCESSING, then
    POST /admin/refunds/:id/bank-approve → COMPLETED)

Bank refunds are gated by eligibility rules (default: BlockSeat bookings only). See Eligibility rules and the operational guide.

Calculate refund amount ​

POST /api/v1/admin/refunds/calculate — read-only, creates nothing. Returns the deterministic refund amount the admin confirms (anchored to what the customer paid — Rule A) plus a full audit breakdown (charged facts, policy, eligibility, payout). The UI renders the amount read-only; admins do not key it in.

For FE — only bookingId is needed. The payout currency and amount are derived automatically from the settled payment at the payment-time exchange rate. A customer who paid Rp 4,702,500 receives exactly Rp 4,702,500 back on a full refund — no rate conversion, no admin input.

Body: bookingId (✅), cancelledAt (optional ISO; defaults to the booking’s actual cancellation event, not the request time). overrideAmountSAR is an admin-only edge-case field (force a SAR amount when policy yields 0); FE does not need to expose it in the normal refund flow. Full request/response in Refund bank disbursement → Calculate the refund.

bash
curl -s -X POST "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/calculate" \
  -H "Authorization: Bearer <ADMIN_JWT>" \
  -H "Content-Type: application/json" \
  -d '{ "bookingId": "019ef302-34f2-731c-a702-8e728f22908c" }'

POST /api/v1/admin/refunds/bank — creates a BANK_TRANSFER refund in PENDING (no money moved yet).

Body (AdminBankRefundDto):

FieldTypeRequiredNotes
bookingIdstring✅Cancelled booking to refund

Upload transfer proof ​

POST /api/v1/admin/refunds/:id/bank-proof — multipart form, field file (PDF/JPG/PNG/WebP, ≤5 MB). In single-control mode the upload finalizes the refund → COMPLETED.

Body (multipart/form-data):

FieldTypeNotes
filefileTransfer proof (PDF/JPG/PNG/WebP, ≤5 MB)
bankTransferReferencestringOptional bank reference number
transferredAtstring (ISO)Optional transfer timestamp, e.g. 2026-06-23T10:00:00Z
payoutAmountnumberOptional — actual amount transferred in the payout currency (overrides the initiate-time suggestion)
payoutRatenumberOptional — actual FX rate used, written the way the exchange-rate screen shows that currency (IDR ~4100 as IDR per SAR, USD ~3.75 as SAR per USD, SAR exactly 1). The direction is fixed by the payout currency and is not selectable. Rejected with 400 outside the accepted window (USD 2–8, IDR 200–20000 by default) — that check always blocks, whatever REFUND_PAYOUT_RECONCILE_ENFORCE is. Reconciled against refundAmountSAR; a divergence is stored + flagged (or blocked if that flag is true)
payoutRateToSARnumberOptional, legacy spelling — supported, not scheduled for removal. The same rate as SAR per 1 unit of payout currency. Inverted onto the canonical direction before the window is applied. Send this or payoutRate, never both. Prefer payoutRate in new code
bash
curl -s -X POST "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/019ef307-fedc-730e-b0a8-992b97cd2c46/bank-proof" \
  -H "Authorization: Bearer <ADMIN_JWT>" \
  -F "file=@transfer-proof.pdf" \
  -F "bankTransferReference=TRX-998877" \
  -F "transferredAt=2026-06-23T05:50:49Z"

Returns the refund as COMPLETED with bankProofUploaded: true and bankTransferredAt set.

The finalizing step uses an atomic compare-and-swap — two concurrent finalizations cannot both settle (the loser gets 409 Conflict).

Reject a bank refund ​

POST /api/v1/admin/refunds/:id/bank-reject → FAILED. Body (BankRefundRejectDto): { "reason": "..." } (required).

Override refund amount ​

PATCH /api/v1/admin/refunds/:id/override

Override an existing refund's amount (e.g. a goodwill adjustment). Cannot override a COMPLETED refund, nor one in SUPERSEDED_BY_BANK_REFUND — that row's debt is carried by the bank refund that replaced it, so act on the bank refund instead.

⚠️ 403 while wallet credit is off. An override that would credit a wallet — an amount above zero on a row that has no wallet transaction yet, or a FAILED one — is refused unless WALLET_AUTO_REFUND_ENABLED is set. Nothing is written when it refuses. An override that would not reach a wallet is unaffected.

Body (AdminOverrideRefundDto):

FieldTypeRequired
refundAmountSARnumber✅
reasonstring✅
bash
curl -s -X PATCH "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/<REFUND_ID>/override" \
  -H "Authorization: Bearer <ADMIN_JWT>" \
  -H "Content-Type: application/json" \
  -d '{ "refundAmountSAR": 500, "reason": "Goodwill adjustment" }'

Retry a FAILED refund ​

POST /api/v1/admin/refunds/:id/retry — reprocess a refund in FAILED status (400 if it is not FAILED). Increments retryCount.

⚠️ 403 while wallet credit is off. Retrying means crediting a wallet, so this endpoint is refused outright unless WALLET_AUTO_REFUND_ENABLED is set. Nothing is written when it refuses. A refund that failed while the flag is off is disbursed through the direct-to-bank flow instead.

bash
curl -s -X POST "https://staging.tiket.ahlaan.co.id/api/v1/admin/refunds/<REFUND_ID>/retry" \
  -H "Authorization: Bearer <ADMIN_JWT>"

A refund that never produced a record ​

The retry endpoint above needs a Refund row in FAILED status. A refund can be lost earlier than that, before any row exists, and those cases are not reachable from that endpoint at all.

After a booking is cancelled, a background job asks the carrier for its refund offer. Until the carrier publishes one the job throws and is retried; it is allowed three attempts on a backoff starting at ten seconds, so it gives up after roughly half a minute. A carrier slower than that leaves the booking cancelled with no Refund row and nothing to retry.

That give-up is now recorded on the booking. Read it with:

bash
curl -s "https://staging.tiket.ahlaan.co.id/api/v1/admin/ota/bookings/<BOOKING_ID>/status-history" \
  -H "Authorization: Bearer <ADMIN_JWT>"

Response 200 OK — newest first. Captured on staging 2026-09-01 from a cancellation whose refund job exhausted its attempts:

json
[
  {
    "id": "01a05b6f-8d1b-71d4-b22d-5909e6cef34c",
    "bookingId": "01a05b6d-ede2-752a-9dea-e68b317845eb",
    "fromStatus": "CANCELLED",
    "toStatus": "CANCELLED",
    "reason": "Refund job failed after all attempts - requires manual processing",
    "metadata": {
      "error": "Bad Request",
      "jobId": "refund-01a05b6d-ede2-752a-9dea-e68b317845eb-PARTNER_CANCEL",
      "attemptsMade": 3,
      "triggerSource": "PARTNER_CANCEL",
      "requiresManualRefund": true
    },
    "createdBy": null,
    "createdAt": "2026-09-01T05:27:12.411Z"
  }
]

fromStatus equals toStatus because the booking was already CANCELLED — the entry records the refund outcome, not a transition. createdBy is null: no human made this happen.

Two entries can appear, and the difference decides what you do:

reasonWhat happened
Refund queue failed - requires manual processingThe job was never queued. The cancellation itself succeeded; nothing ever asked the carrier.
Refund job failed after all attempts - requires manual processingThe job ran, asked the carrier, and gave up. metadata.error carries the last error and metadata.attemptsMade how many tries it had.

Both carry metadata.requiresManualRefund: true, so one search finds either.

⚠️ Cancelling again does not retry it. The failed job is kept for 30 days under an identifier built from the booking and the refund trigger. While that record exists, asking for the same refund again returns the old failed job rather than running a new one — and reports that it queued one.

Observed on staging 2026-09-01: re-triggering the cancellation logged Refund job queued for booking ... - trigger: PARTNER_CANCEL, while the stored job's attempt counter stayed at 3 and its finish time did not move. Nothing ran. Do not read that log line as proof a refund was re-attempted. Settle these by hand through the direct-to-bank flow.

Manual wallet refund — disabled ​

POST /api/v1/admin/refunds/manual creates a refund that credits the customer wallet (AdminManualRefundDto: bookingId, reason, optional overrideAmount). Because the wallet feature is disabled (see Refund methods), do not use this endpoint — it would create a WALLET refund that cannot be delivered to an active wallet. Use the direct-to-bank flow instead.

Since WALLET_AUTO_REFUND_ENABLED shipped off it is refused rather than left to discipline. Response 403 (real, staging 2026-09-02):

json
{
  "message": "Crediting a refund to a wallet is disabled in this environment. Disburse it through the direct-to-bank refund instead.",
  "error": "Forbidden",
  "statusCode": 403
}

PATCH /:id/override and POST /:id/retry return the same body when they would credit a wallet.

Check every environment before relying on the rail there.

Notes ​

  • Refunds apply only to cancelled bookings; cancel first, then refund.
  • The customer is not auto-notified — admins contact the customer directly (matches the existing refund/booking communication policy).
  • Proof files are stored privately in R2; admins fetch a short-lived signed URL via GET /admin/refunds/:id/bank-proof.
  • Every state transition (initiate / upload / approve / reject / override) is written to the audit log.
