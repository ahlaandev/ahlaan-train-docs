Direct-to-Bank Refund (Admin Disbursement) Guide ​

This guide explains how administrators issue a refund directly to a customer's bank account instead of crediting the wallet, and how the admin-configurable eligibility rules gate who qualifies.

Status: Ships OFF. The endpoints reject with 403 unless BANK_REFUND_ENABLED=true in the target environment. All other refunds (auto-on-cancel, ticketing-failure, and POST /admin/refunds/manual) continue to credit the wallet — this feature changes nothing about them.

Quick Overview ​

AspectDetail
Who initiatesAdmin only — never a customer, never the auto-cancel path
Where money goesThe customer's bank account (admin records the destination)
TriggerA separate, explicit admin disbursement on a CANCELLED booking
ControlMaker-checker dual control (configurable), proof of transfer, full audit trail
EligibilityConfigurable rules — passenger window, route, trip, booking type
CurrencySAR (matches the booking priceSAR base)

Refunds are never customer-requested. They are created by cancellation (auto → wallet) or by an admin. This feature adds an admin-only path that routes a refund to a bank account instead of the wallet.

Operator Workflow ​

1. Admin cancels the booking with skipRefund=true
   POST /admin/ota/bookings/:id/cancel   { "skipRefund": true }
   → booking CANCELLED, NO automatic wallet refund

2. Admin initiates the bank refund (maker)
   POST /api/v1/admin/refunds/bank
   → creates a BANK_TRANSFER refund in PENDING (no money moved yet)

3. Admin uploads proof of the bank transfer
   POST /api/v1/admin/refunds/:id/bank-proof   (multipart, field "file")
   → refund moves to PROCESSING (awaiting approval)

4. A second admin approves (checker)
   POST /api/v1/admin/refunds/:id/bank-approve
   → refund COMPLETED

If BANK_REFUND_REQUIRE_DUAL_CONTROL=false, step 3 finalizes the refund (COMPLETED) and step 4 is skipped.

Avoiding a double refund: if the booking was cancelled WITHOUT skipRefund=true, the wallet refund already fired. The over-refund guard then blocks the bank refund once the booking base price is fully refunded. To refund to bank instead of an already-credited wallet you must reverse the wallet credit first (out of scope for this feature).

Endpoints ​

All under admin/refunds, JWT + ADMIN role, rate-limited.

MethodPathPurpose
POST/admin/refunds/bankInitiate a bank refund (maker)
POST/admin/refunds/:id/bank-proofUpload transfer proof (multipart file, ≤5 MB, PDF/JPG/PNG/WebP)
POST/admin/refunds/:id/bank-approveApprove (checker) → COMPLETED
POST/admin/refunds/:id/bank-rejectReject → FAILED
GET/admin/refunds/:id/bank-proofShort-lived signed URL to download the proof

Initiate body (POST /admin/refunds/bank) ​

json
{
  "bookingId": "0190...",
  "overrideAmount": 1000,
  "reason": "Customer requested refund to bank",
  "destinationBankCode": "MANDIRI",
  "destinationBankName": "Bank Mandiri",
  "destinationAccountNumber": "1234567890",
  "destinationAccountName": "John Doe"
}

overrideAmount is optional; when omitted the standard refund policy computes the amount. Responses mask the destination account number except the last 4 digits.

Status machine ​

PENDING ──upload proof──▶ PROCESSING ──approve──▶ COMPLETED
   │                          │
   └──────────reject──────────┴────────────────▶ FAILED

Approval uses an atomic compare-and-swap on PROCESSING, so two concurrent approvals cannot both settle (the loser gets 409 Conflict).

Eligibility Rules ​

A booking may receive a bank refund only when an active ALLOW rule matches. Rules are admin-configured and fail-closed: no matching ALLOW rule ⇒ denied.

MethodPathPurpose
POST/admin/refund-bank-eligibility/rulesCreate a rule
GET/admin/refund-bank-eligibility/rulesList rules (filter by route / active)
GET/admin/refund-bank-eligibility/rules/:idGet a rule
PUT/admin/refund-bank-eligibility/rules/:idUpdate a rule
DELETE/admin/refund-bank-eligibility/rules/:idDeactivate (soft delete)

Rule fields:

  • Scope (all optional, null = wildcard): originId, destinationId, tripClass, tripType, bookingType. Note: originId/destinationId hold the route location code (e.g. DMX, max 7 chars) — the Location.code, not a Location UUID (contrast Tariff / Custom Route Price).
  • Passenger window (either bound optional): minPassengers, maxPassengers (both inclusive).
  • action: ALLOW or DENY.
  • priority: higher wins on a specificity tie.

Resolution ​

1. Keep ACTIVE rules whose scope matches the booking AND whose
   passenger window contains the booking's passenger count.
2. Rank: most-specific first (more constraining fields),
   then highest priority.
3. The winning rule's action decides ALLOW vs DENY.
4. No match ⇒ DENIED (fail-closed).

Examples ​

Allow bank refund only for large groups (≥ 11 passengers):

json
{
  "name": "Bank refund for groups >= 11 pax",
  "bookingType": "GROUP",
  "minPassengers": 11,
  "action": "ALLOW",
  "priority": 0,
  "isActive": true
}

Allow only small parties (≤ 10 passengers):

json
{
  "name": "Bank refund for <= 10 pax",
  "maxPassengers": 10,
  "action": "ALLOW",
  "priority": 0,
  "isActive": true
}

Allow everything but carve out a denied route (DENY wins by specificity):

json
[
  { "name": "Allow all", "action": "ALLOW", "priority": 0, "isActive": true },
  { "name": "Deny DMX→MKX", "originId": "DMX", "destinationId": "MKX",
    "action": "DENY", "priority": 0, "isActive": true }
]

Configuration ​

Env varDefaultEffect
BANK_REFUND_ENABLEDfalseMaster switch; endpoints 403 when off
BANK_REFUND_REQUIRE_DUAL_CONTROLtrueRequire a separate approver ≠ initiator

Notes ​

  • The customer is not auto-notified; admins contact the customer directly (matches existing refund/booking communication policy).
  • Proof files are stored privately in R2; admins fetch a short-lived signed URL.
  • Every state transition (initiate / upload / approve / reject) is written to the audit log.
