Direct-to-Bank Refund (Admin Disbursement) Guide ​

This guide explains how administrators issue a refund directly to a customer's bank account instead of crediting the wallet, and how the admin-configurable eligibility rules gate who qualifies.

Status: Enabled. This feature is ON (BANK_REFUND_ENABLED=true) and runs in single-control mode (BANK_REFUND_REQUIRE_DUAL_CONTROL=false): one admin initiates the refund and uploads proof, and that upload finalizes it — there is no separate approver step. All other refunds (auto-on-cancel, ticketing-failure, and POST /admin/refunds/manual) continue to credit the wallet — this feature changes nothing about them.

Quick Overview ​

AspectDetail
Who initiatesAdmin only — never a customer, never the auto-cancel path
Where money goesThe customer's bank account (admin records the destination)
TriggerA separate, explicit admin disbursement on a CANCELLED booking
ControlSingle-control: one admin initiates and uploads proof to finalize. Proof of transfer + full audit trail. (Maker-checker dual control is available behind BANK_REFUND_REQUIRE_DUAL_CONTROL=true.)
EligibilityConfigurable rules — passenger window, route, trip, booking type
AmountDeterministic — pre-calculated by POST /admin/refunds/calculate and confirmed, never keyed in by hand. See Calculate the refund.
CurrencyThe currency the customer paid in (derived from the settled payment). refundAmountSAR is the canonical SAR anchor; the foreign payout equals what the customer paid × the refund fraction at the payment-time rate.

Refunds are never customer-requested. They are created by cancellation (auto → wallet) or by an admin. This feature adds an admin-only path that routes a refund to a bank account instead of the wallet.

Operator Workflow ​

Step 1 — Cancel with skipRefund: true

STANDARD : POST /admin/ota/bookings/:id/cancel
BLOCKSEAT: POST /admin/blockseat-bookings/bookings/:id/cancel

Request body (both variants):

json
{ "reason": "Refund to bank", "skipRefund": true }

Response 200 — booking moves to CANCELLED, refundStatus: "QUEUED" (the queued refund job is a no-op because skipRefund suppressed the auto wallet credit):

json
{
  "id": "019eeeb6-00a1-744c-8c7f-60d21feacd87",
  "bookingCode": "WF3ZHMF",
  "status": "CANCELLED",
  "refundStatus": "QUEUED",
  "cancelledAt": "2026-06-22T09:30:00.000Z"
}

Step 2 — Calculate, then initiate the bank refund

First call POST /api/v1/admin/refunds/calculate (read-only) to obtain the deterministic amount + breakdown the admin confirms — see Calculate the refund. Then POST /api/v1/admin/refunds/bank creates a BANK_TRANSFER refund record in PENDING (no money moved yet). The body carries no amount or currency — the server recomputes both from what the customer paid, so the figure can never diverge from the calculate preview:

json
{
  "bookingId": "019eeeb6-00a1-744c-8c7f-60d21feacd87",
  "reason": "Customer requested refund to bank account",
  "destinationBankCode": "BCA",
  "destinationBankName": "Bank Central Asia",
  "destinationAccountNumber": "1234567890",
  "destinationAccountName": "Ahmad Wholesale",
  "saveBankDetailsToCustomer": true
}

Response 201 (BlockSeat 11 pax × SAR 95 net = SAR 1045, paid Rp 4,702,500 at rate 4500 — full GROUP refund returns exactly what was paid):

json
{
  "id": "019ef100-0000-7000-8000-000000000001",
  "refundCode": "RFD-202606-0004",
  "status": "PENDING",
  "refundAmountSAR": 1045,
  "policyType": "GROUP_FULL",
  "refundMethod": "BANK_TRANSFER",
  "destinationBankCode": "BCA",
  "destinationBankName": "Bank Central Asia",
  "destinationAccountNumber": "******7890",
  "destinationAccountName": "Ahmad Wholesale",
  "payoutCurrency": "IDR",
  "payoutAmount": 4702500,
  "payoutRateToSAR": 0.00022222,
  "payoutReconciled": true,
  "createdAt": "2026-06-22T09:31:00.000Z"
}

Account number is masked (last 4 digits only) in all responses. Admins see the full number only on GET /admin/refunds/bank-details/:bookingId (prefill endpoint).

The payout currency is not an input. Under Rule A the refund is disbursed in the currency the customer paid in (derived from the settled payment). refundAmountSAR is the canonical owed SAR. The foreign payoutAmount equals the customer's paid amount × the refund fraction, and payoutRateToSAR is back-calculated to the payment-time rate (so payoutAmount × payoutRateToSAR ≈ refundAmountSAR). A full refund returns the exact amount paid. See Non-SAR payout.

Step 3 — Upload proof → COMPLETED

POST /api/v1/admin/refunds/:id/bank-proof — multipart form, field file (PDF/JPG/PNG/WebP, ≤5 MB). Optional form fields bankTransferReference, transferredAt, and — for a non-SAR payout — the actual payoutAmount + payoutRateToSAR you transferred (these override the initiate-time suggestion). In single-control mode the upload immediately finalizes the refund:

Response 201 (single-control):

json
{
  "id": "019ef100-0000-7000-8000-000000000001",
  "refundCode": "RFD-202606-0004",
  "status": "COMPLETED",
  "bankProofUploaded": true,
  "bankApprovedBy": "019c9105-311a-732f-a1c5-da44758a7e5b",
  "bankTransferredAt": "2026-06-22T09:32:05.000Z",
  "payoutCurrency": "IDR",
  "payoutAmount": 4702500,
  "payoutRateToSAR": 0.00022222,
  "payoutReconciled": true
}

Dual control (optional, not the current mode). When BANK_REFUND_REQUIRE_DUAL_CONTROL=true, the proof upload in step 3 only moves the refund to PROCESSING, and a second admin must approve it (POST /api/v1/admin/refunds/:id/bank-approve) to reach COMPLETED. The current environment runs single-control, so this approver step does not apply.

BlockSeat bookings — use the BlockSeat cancel route. BlockSeat is the seeded-default-eligible variant (see Eligibility Rules), so most bank refunds are BlockSeat. BlockSeat bookings are variant-isolated: the POST /admin/ota/bookings/:id/cancel route 404s on a BlockSeat id (it resolves bookingVariant = STANDARD only). Cancel a BlockSeat booking via POST /admin/blockseat-bookings/bookings/:id/cancel with the same AdminCancelBookingDto body (reason required, skipRefund: true). The customer-facing POST /api/v1/blockseat-bookings/:id/cancel takes no body and always auto-refunds to wallet — it cannot skipRefund, so a bank refund must be initiated by an admin through the admin cancel route above. Steps 2–4 (initiate / proof / approve) are variant-agnostic — they key on bookingId / refund id and work for BlockSeat unchanged.

Avoiding a double refund: if the booking was cancelled WITHOUT skipRefund=true, the wallet refund already fired. The over-refund guard then blocks the bank refund once the amount paid is fully refunded. To refund to bank instead of an already-credited wallet you must reverse the wallet credit first (out of scope for this feature).

Calculate the refund (deterministic amount) ​

POST /admin/refunds/calculate — read-only, creates nothing. Returns the exact amount the admin will confirm, anchored to what the customer actually paid (Rule A), plus a full audit breakdown. The admin confirms this figure; the UI must render it read-only, never as a free-text field.

For FE: just send bookingId. Everything else — payout currency, payout amount, exchange rate — is computed server-side from the settled payment and returned in the response. No amount or currency input is needed or accepted.

Request (normal case — only bookingId required):

json
{
  "bookingId": "019eeeb6-00a1-744c-8c7f-60d21feacd87"
}

cancelledAt (optional) overrides the timestamp the policy is evaluated against. When omitted it defaults to the booking’s actual cancellation event (the CANCELLED status-history time, else a prior refund’s snapshot, else now) — not the request time — so the time-cliffed GROUP tiers stay deterministic regardless of admin processing latency.

Edge case — overrideAmountSAR: when the policy yields 0 (e.g. GROUP cancelled within 20 days — GROUP_NO_REFUND) the response returns refundable: false. An admin can force a specific SAR amount by supplying overrideAmountSAR (integer or decimal, in SAR). The non-SAR payout is still derived at the payment-time rate — the admin never inputs the IDR/USD amount. The response sets isOverride: true and policyType: "ADMIN_OVERRIDE". This is a backend-only safety valve; the FE should surface it only in an advanced override flow after confirming the non-refundable status with the admin.

Response 201:

json
{
  "bookingId": "019eeeb6-00a1-744c-8c7f-60d21feacd87",
  "bookingCode": "WF3ZHMF",
  "bookingVariant": "BLOCKSEAT",
  "bookingType": "GROUP",
  "serviceClass": "Y",
  "charged": {
    "currency": "IDR",
    "amountPaid": 4702500,
    "amountSAR": 1045,
    "paidAt": "2026-06-20T08:00:00.000Z",
    "exchangeRate": { "rateToSAR": 0.00022222, "exchangeRateId": "019ea684-34d4-712d-a32e-3d463b584de3" }
  },
  "policy": { "policyType": "GROUP_FULL", "refundPercentage": 100, "hoursBeforeDeparture": 720 },
  "eligibility": { "allowed": true, "appliedRuleId": "01992000-0000-7000-8000-000000000001", "reason": "Allowed by rule \"Default BlockSeat bank refund\"" },
  "refund": {
    "refundAmountSAR": 1045,
    "payoutCurrency": "IDR",
    "payoutAmount": 4702500,
    "payoutRateToSAR": 0.00022222,
    "payoutReconciled": true,
    "isOverride": false
  },
  "alreadyRefunded": { "refundAmountSAR": 0 },
  "refundable": true,
  "warnings": []
}

How to read the response:

  • charged.currency / charged.amountPaid — what the customer actually paid (currency + amount). The refund is disbursed in this same currency.
  • refund.payoutCurrency — derived automatically (= charged.currency). Never an input.
  • refund.payoutAmount — derived automatically:
    • Full refund → exactly charged.amountPaid (zero rounding drift).
    • Partial (e.g. 80%) → charged.amountPaid × 0.8.
    • Override → charged.amountPaid × (overrideAmountSAR / charged.amountSAR).
    • Uses the payment-time exchange rate, not the current live rate — so the figure is locked to what the customer was charged.
  • refund.refundAmountSAR — canonical SAR amount (for accounting/audit).
  • refundable: false — policy yields 0 (e.g. GROUP within 20 days) or prior refunds already cover the full paid amount.
  • warnings — non-fatal notes (no settled payment, multiple payments quoted against latest, cancellation time unknown, booking not yet CANCELLED).

charged.exchangeRate.rateToSAR is a payment-time fact — amountSAR / amountPaid, the rate the customer actually paid at. It is independent of the refund leg, so even a non-refundable preview (refund payoutRateToSAR: 0) reports the real charged rate. 1 for SAR-paid bookings.

Initiate body (POST /admin/refunds/bank) ​

For FE: do not send an amount or currency — the server recomputes both from the settled payment (same Rule A as the calculate preview). The body needs only the booking id, reason, and destination bank account.

json
{
  "bookingId": "019eeeb6-00a1-744c-8c7f-60d21feacd87",
  "reason": "Customer requested refund to bank account",
  "destinationBankCode": "BCA",
  "destinationBankName": "Bank Central Asia",
  "destinationAccountNumber": "1234567890",
  "destinationAccountName": "Ahmad Wholesale",
  "saveBankDetailsToCustomer": true
}

The server recomputes the refund amount and payout from the settled payment — the client never supplies a figure. The booking must have a settled (PAID) payment, else 400. Responses mask the destination account number to the last 4 digits. saveBankDetailsToCustomer is optional (default false) — see Customer bank details.

Edge case — overrideAmountSAR: if the policy yields 0 (e.g. GROUP_NO_REFUND) and the admin decides to force a refund anyway, supply overrideAmountSAR: <SAR amount>. This is always in SAR — the IDR/USD payout is still derived at the payment-time rate, never supplied by the client. Without it, the server returns 400 Refund amount must be greater than zero.

Customer bank details (prefill & save-back) ​

To save admins re-typing the same account every time, the destination bank details can be prefilled from — and optionally saved back onto — the customer. Both surfaces are admin-only (JWT + ADMIN, rate-limited) and variant-agnostic: they serve STANDARD and BlockSeat bookings (both are Booking rows). CustomBooking is a separate table and is not supported here (its id resolves to null on prefill and 404s on initiate) — see Phase 2.

Storage reuses the customer's wallet bank-details row (the same row used by wallet withdrawals). Resolution applies B2B precedence: a B2B customer with an organization uses the organization wallet; everyone else uses their personal wallet. There is no migration and no new env var.

Prefill — GET /admin/refunds/bank-details/:bookingId ​

Resolves the booking → customer → wallet → stored bank details.

  • Returns null (HTTP 200) when the booking has no customer, or the customer has no wallet / no stored bank-details:

    json
    null

  • Returns the stored details with the full account number (admin-only surface, so the admin can copy it straight into the initiate form) when details exist:

    json
    {
  "bankCode": "BCA",
  "bankName": "Bank Central Asia",
  "accountNumber": "1234567890",
  "accountName": "Ahmad Wholesale",
  "isVerified": true,
  "updatedAt": "2026-06-22T09:26:23.909Z"
}

Read-only — it never creates a wallet.

Save-back — saveBankDetailsToCustomer on initiate ​

When saveBankDetailsToCustomer: true on POST /admin/refunds/bank, the destination* fields are also written to the customer's wallet bank-details row, inside the same database transaction as the refund:

  • Auto-provisions the wallet if the customer has none (B2B → organization wallet) — a missing wallet never blocks the save.
  • Overwrites any existing stored row (it is the customer's single per-wallet bank account, shared with wallet withdrawals). Opt-in and default-false, so nothing changes unless an admin chooses to save.
  • Marked verified (admin-entered, admin-trusted) and clears any prior rejection state (rejectedBy, rejectedAt, rejectionReason all set to null).
  • Atomic: because the save runs inside the refund transaction, a save failure rolls the whole refund back (no disbursement is recorded with a failed save). Auto-provisioning removes the dominant failure cause (missing wallet), so real-world aborts are near-zero.

Wallet state after save-back — the customer's organization wallet bank-details row:

json
{
  "bankCode": "BCA",
  "bankName": "Bank Central Asia",
  "accountNumber": "1234567890",
  "accountName": "Ahmad Wholesale",
  "isVerified": true,
  "verifiedBy": "019c9105-311a-732f-a1c5-da44758a7e5b",
  "verifiedAt": "2026-06-22T09:31:00.000Z",
  "rejectedBy": null,
  "rejectedAt": null,
  "rejectionReason": null
}

B2B precedence. For a B2B customer with an organization, details are saved to and read from the organization wallet — not the user's personal wallet. For B2C customers, the personal wallet is used.

Default false ⇒ zero behaviour change until an admin opts in per refund.

When BANK_REFUND_ENABLED is unset/false, every bank-refund endpoint rejects before any money logic — a fully-valid body still returns 403:

json
{
  "statusCode": 403,
  "error": "Forbidden",
  "message": "Direct-to-bank refund is disabled in this environment"
}

Status machine ​

Single-control (current mode) — the proof upload finalizes:

PENDING ──upload proof──▶ COMPLETED
   └────────reject───────▶ FAILED

Dual-control (BANK_REFUND_REQUIRE_DUAL_CONTROL=true) — a separate approver:

PENDING ──upload proof──▶ PROCESSING ──approve──▶ COMPLETED
   │                          │
   └──────────reject──────────┴────────────────▶ FAILED

The finalizing step (proof upload in single-control, approve in dual-control) uses an atomic compare-and-swap, so two concurrent finalizations cannot both settle (the loser gets 409 Conflict).

Eligibility Rules ​

A booking may receive a bank refund only when an active ALLOW rule matches. Rules are admin-configured and fail-closed: no matching ALLOW rule ⇒ denied.

Default rule (auto-seeded). On the first deploy that finds the rule table completely empty, a migration seeds one rule scoped to bookingVariant: BLOCKSEAT, action: ALLOW — so the feature works out of the box once BANK_REFUND_ENABLED=true (without a default, fail-closed would deny every booking until an admin created a rule). It allows a direct-to-bank refund for BlockSeat (wholesale) bookings only; STANDARD bookings match no ALLOW rule and stay denied. Passenger count is not constrained — the ≥ 11 floor is already enforced upstream when a BlockSeat booking is created. The seed runs only when the table is empty, so it never overrides a configured rule set and is safe to edit or delete afterward — deleting it does not bring it back. Money still never moves while BANK_REFUND_ENABLED=false.

Rule fields:

  • Scope (all optional, null = wildcard): originId, destinationId, tripClass, tripType, bookingType, bookingVariant. Note: originId/destinationId hold the route location code (e.g. DMX, max 7 chars) — the Location.code, not a Location UUID (contrast Tariff / Custom Route Price). bookingVariant is STANDARD or BLOCKSEAT — scope a rule to BLOCKSEAT to target wholesale bookings only.
  • Passenger window (either bound optional): minPassengers, maxPassengers (both inclusive).
  • action: ALLOW or DENY.
  • priority: higher wins on a specificity tie.

Resolution ​

1. Keep ACTIVE rules whose scope matches the booking AND whose
   passenger window contains the booking's passenger count.
2. Rank: most-specific first (more constraining fields),
   then highest priority.
3. The winning rule's action decides ALLOW vs DENY.
4. No match ⇒ DENIED (fail-closed).

]

Non-SAR payout (multi-currency) ​

A direct-to-bank refund is disbursed in the currency the customer paid in (e.g. IDR for an Indonesian Xendit payment) while keeping SAR as the canonical accounting amount. The currency is derived from the settled payment, not chosen by the admin — that is what makes the figure deterministic.

  • refundAmountSAR is the single source of truth. Refund policy, the over-refund guard, and every report stay in SAR. The payout fields describe only the physical transfer.
  • payoutCurrency — the settled payment's currency. SAR is the identity (payoutAmount = refundAmountSAR, payoutRateToSAR = 1).
  • payoutAmount — Rule A: the customer's paid amount × the refund fraction (refundAmountSAR / amountPaidSAR). A full refund returns the exact amount paid; a partial refund proportions it. This embeds the payment-time rate, so there is no re-conversion at a later (drifted) rate.
  • payoutRateToSAR — SAR per 1 unit of payoutCurrency, back-calculated from refundAmountSAR / payoutAmount so the pair reconciles exactly. It equals the payment-time rate. The payment's ExchangeRate snapshot id (Invoice.exchangeRateId, fallback Booking.exchangeRateId) is retained for audit.
  • payoutReconciled — whether (payoutAmount, payoutRateToSAR) back-converts to refundAmountSAR within tolerance (±1 SAR). For a high-magnitude / low-rate currency (large IDR), the tolerance widens by the rate's storage granularity (payoutRateToSAR is stored at 8 decimals, so up to payoutAmount × 1e-8 SAR) — this absorbs pure rounding and never masks a real divergence.

Worked example (the requirement scenario). A BlockSeat booking of 11 pax at SAR 95 net = SAR 1045, paid in IDR at the payment-time rate 4500 = Rp 4,702,500 (stored as Payment.amount). A full GROUP refund returns payoutAmount = 4,702,500 IDR exactly — what the customer paid — with refundAmountSAR = 1045 and payoutRateToSAR = 1/4500 ≈ 0.00022222. Three admins now produce one number, defensible against the stored payment.

Correcting at proof upload. At proof upload the admin may still pass the actual payoutAmount + payoutRateToSAR transferred (bank spread, fees, rounding to a round figure), which overrides the computed pair. It is reconciled against the owed SAR:

  • Default (warn + store): a divergence beyond tolerance is stored (payoutReconciled: false) and logged — the refund still completes. Manual transfers legitimately diverge, so divergence is surfaced for finance review, not blocked. Filter unreconciled payouts on the admin refund list.
  • Enforce mode: set REFUND_PAYOUT_RECONCILE_ENFORCE=true to block a divergent payout with 400 (no proof stored, no state change).

This covers manual direct-to-bank payouts only — automated Xendit reversal is a separate path.

Configuration ​

Env varValueEffect
BANK_REFUND_ENABLEDtrueFeature ON. (Endpoints 403 only if an environment sets this to false.)
BANK_REFUND_REQUIRE_DUAL_CONTROLfalseSingle-control: the proof upload finalizes the refund — no separate approver. Set true to require a maker-checker approval step.
REFUND_PAYOUT_RECONCILE_ENFORCEfalseWarn + store a non-SAR payout that doesn't reconcile to refundAmountSAR (default). Set true to hard-block it with 400.

Notes ​

  • The customer is not auto-notified; admins contact the customer directly (matches existing refund/booking communication policy).
  • Proof files are stored privately in R2; admins fetch a short-lived signed URL.
  • Every state transition (initiate / upload / approve / reject) is written to the audit log.
