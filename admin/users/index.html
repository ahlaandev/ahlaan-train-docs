Users Management ​

Admin endpoints for listing and inspecting platform users. All routes require an admin JWT (role = ADMIN) and are served under /api/v1.

Admin-initiated password resets are documented separately under Password Reset.

Each user response embeds a compact organization object that includes specialCustomPricingEnabled — letting admins tell, at a glance, whether a user belongs to a special custom-ota/custom-booking B2B pricing organization or a regular one. Toggle it per organization via the Special Custom B2B Pricing enroll endpoint.

Each user also carries promo-access fields:

  • promoAccessEnabled — the per-user override (tri-state): true = force promo access, false = exclude, null = inherit the organization's flag.
  • effectivePromoAccess — the resolved boolean the promo gate actually enforces (override coalesced with organization.promoAccessEnabled). true marks the user as a promo customer (may log in and book on the promo frontend).

A promo customer does not need an organization — set the override to true. See the Promo Customer Onboarding guide for the full workflow, and the per-user endpoint Set promo-access override below.

1. List Users ​

Endpoint: GET /admin/users

Returns a paginated list of users, each with a nested organization summary (null for users not attached to an organization).

Query Parameters:

ParameterTypeRequiredDescription
rolestringNoFilter by user role (ADMIN, SUPPORT, B2B, B2C)
organizationIdstringNoFilter to a single organization
isActivebooleanNoFilter by active flag
promoAccessEnabledbooleanNoFilter by effective promo access (true = promo customers — override on, or inheriting a promo org; false = everyone else, including users with a null override whose organization is non-promo, absent, or who are not B2B members). Composes with the other filters (AND)
specialCustomPricingEnabledbooleanNoFilter by effective special custom B2B pricing. true = active B2B members of an org whose organization.specialCustomPricingEnabled is on; false = everyone else. B2C users are excluded even when an organizationId is still attached (org rules do not apply to B2C). Composes with the other filters (AND)
searchstringNoCase-insensitive partial match on the user email, name, or phone. Blank/whitespace is ignored. Composes with the filters above (AND)
pagenumberNoPage number (default: 1)
limitnumberNoItems per page (default: 20)

Example:

bash
curl -X GET "/api/v1/admin/users?role=B2B&page=1&limit=20" \
  -H "Authorization: Bearer <admin-jwt>"

3. Attach a User to an Organization (organizationId) ​

Both POST /admin/users (create) and PATCH /admin/users/:id (update) accept an optional organizationId to attach the user (typically a B2C customer) to an existing organization. The organization must already exist — an unknown id is rejected with 400 Organization <id> not found.

Example (create):

bash
curl -X POST "/api/v1/admin/users" \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "customer@example.com",
    "name": "Promo Customer",
    "role": "B2C",
    "organizationId": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f"
  }'

Example (assign an existing user):

bash
curl -X PATCH "/api/v1/admin/users/0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e61" \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{ "organizationId": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f" }'

This is how admins onboard promo customers: create the organization, enable its flag via the promo-access endpoint, then create users with that organizationId (or assign existing users via PATCH). B2B/B2C users are passwordless — promo customers then log in on the promo host via OTP or Google/Apple. See the Promo Customer Onboarding guide for the full step-by-step flow (new vs existing customer, verification, downgrade).

Errors:

StatusMessage
400Organization <id> not found (unknown organizationId)
404User not found (PATCH only)

Org change resets the promo override. Attaching, switching, or detaching an organization (including organizationId: null to detach, and B2B application approval) resets promoAccessEnabled to null so the user re-inherits the new context — unless the same request also sends an explicit promoAccessEnabled, which wins. See Promo Customer Onboarding.

4. Set a User's Promo-Access Override ​

Endpoint: PATCH /admin/users/:id/promo-access

Sets the tri-state per-user promo override, orthogonal to organization membership. Throttled to 30 requests/minute; audit-logged as USER_PROMO_ACCESS_SET.

http
PATCH /api/v1/admin/users/:id/promo-access
Authorization: Bearer <admin-jwt>
Content-Type: application/json

{ "enabled": true }
enabledEffect
trueForce promo access ON (even with no organization / a non-promo org)
falseExclude this user even inside a promo-enabled organization
nullClear the override — the user inherits organization.promoAccessEnabled

Response: 200 OK

json
{ "id": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e61", "promoAccessEnabled": true }

Errors:

StatusMessage
404User not found

You can also set promoAccessEnabled inline when creating (POST /admin/users) or updating (PATCH /admin/users/:id) a user.
