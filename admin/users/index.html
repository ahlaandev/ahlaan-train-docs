Users Management ​

Admin endpoints for listing and inspecting platform users. All routes require an admin JWT (role = ADMIN) and are served under /api/v1.

Permission-gated (Access Roles). Each route now also requires a fine permission: read routes users:read (stats users:stats), POST users:create, PATCH users:update, DELETE users:delete. Those codes govern customer rows; the same routes also accept the admin-users: code for the staff side and the handler decides which rows you reach — see Staff administration has its own permissions. Deactivating a staff account (ADMIN/SUPPORT) is Super-Admin-only and is NOT delegated by users:delete; the last active Super Admin can never be deactivated. POST /admin/users optionally takes roleIds to assign Access Roles in one step (needs roles:assign). See Access Roles.

Writes against a staff row are restricted beyond the permission. Holding users:create or users:update governs customer rows; against an ADMIN/SUPPORT row the writes that decide who can sign in as that account are refused separately. The full matrix is in Staff rows are not ordinary rows below — read it before wiring an admin-user screen, because these writes return 403 to a caller whose permission check passed.

Admin-initiated password resets are documented separately under Password Reset.

Each user response embeds a compact organization object that includes pricingTier (SILVER/GOLD/RESELLER) — the source of truth for whether the user belongs to a special custom-ota/custom-booking B2B pricing (GOLD) organization or a regular one. RESELLER is priced exactly as SILVER and additionally earns commission. The object also carries specialCustomPricingEnabled, a deprecated mirror of pricingTier === "GOLD" kept in lockstep; new admin UI should read pricingTier. Set the tier per organization via the Pricing Tier endpoint (the Special Custom B2B Pricing enroll endpoint still works and writes the mirror in lockstep).

Real response (GET /api/v1/admin/users?search=imam.faro@gmail.com on preprod.mitra.ahlaan.co.id, gold mitra, trimmed):

json

The user's own pricingTier/promoAccessEnabled are null (inherit); the org's pricingTier: "GOLD" is what makes this a gold caller. The two list filters are not interchangeable — on this preprod dataset ?pricingTier=GOLD returns 8 users (effective tier, org or user override) while the deprecated ?specialCustomPricingEnabled=true returns 10 (org-flag only).

Each user also carries promo-access fields:

A promoAccessEnabled: false exclusion is a hard ban, and it holds. It outranks a mitra registration, so the excluded account cannot let itself back in by submitting the self-service registration form. And it is not sidestepped by switching hosts: a token that account mints on the main site is confined when replayed against the mitra host — it reaches its own profile and nothing else. (On the main site the account remains an ordinary customer; the exclusion is scoped to the mitra portal.)

  • promoAccessEnabled — the per-user override (tri-state): true = force promo access, false = exclude, null = inherit the organization's flag.
  • effectivePromoAccess — the resolved boolean the promo gate actually enforces (override coalesced with organization.promoAccessEnabled). true lets the user log in on the mitra frontend, but as of PR #456 it is no longer sufficient to book: a promo-eligible user with no approved, numbered mitra registration resolves promoAccessLevel: REGISTRATION_REQUIRED and is hard-locked to the register form. Booking requires PARTNER — promo eligibility plus a numbered registration.
  • pricingTier — the per-user pricing-tier override (SILVER / GOLD / RESELLER / null = inherit the org's pricingTier). A concrete value wins over the org, so a B2C user can be GOLD (special pricing) or a member forced to SILVER despite a GOLD org. This column is also where an organization-less reseller's tier lives, since there is no organization to carry it. Only honoured once promo access resolves. See Set a user's pricing tier below.
  • effectivePricingTier — the resolved configured tier (HOLDER / SILVER / GOLD / RESELLER) the pricing engine would charge, computed the same way the engine computes it: per-user pricingTier override → org pricingTier → SILVER floor. This is the field to read for "what tier is this customer" — the raw pricingTier is null for the majority who inherit. It already reflects an org-less GOLD individual partner (whose own pricingTier is set but organization is null) and a member whose override diverges from the org. By design it does not fold in promo eligibility — that stays the separate effectivePromoAccess fact, so you can see "configured GOLD" and "promo eligible? no" as two independent columns.
  • promoAccessLevel — the 4-state mitra-host access level, the same ladder the runtime enforces: PARTNER (promo-eligible and a numbered mitra) | APPLICANT (an open, unapproved registration on file) | REGISTRATION_REQUIRED (promo-eligible but no number and no application — a "gap" account) | DENIED. Kept alongside effectivePromoAccess: the boolean is not a clean subset — an inactive-but-promo-enabled user reads effectivePromoAccess: true while promoAccessLevel: DENIED.
  • impersonationEligible — boolean, the admin "act as customer" mark. true exactly when this user is a non-ADMIN/SUPPORT PARTNER — the same predicate POST /admin/impersonation/start enforces, so a green mark never disagrees with what start accepts. An inactive user or a non-PARTNER reads false.
  • partner — the mitra partner identity { registrationNumber, name }, or null when no numbered registration resolves. MEMBER-complete: it resolves a member whose number sits on the org's targetOrganizationId link, not only a NEW_ORG registration.

Host-gated (Option A). As of this release the entire promo/mitra panel above — pricingTier, effectivePricingTier, promoAccessEnabled, effectivePromoAccess, promoAccessLevel, impersonationEligible, partner, and the nested organization's promo flags — is returned only on the mitra host (mitra.ahlaan.co.id and subdomains). On every other host these keys are stripped from the admin user responses. (This reverses the earlier admin-exempt behaviour: admin views were previously the one place these fields showed on any host.)

A promo customer does not need an organization — set the override to true. See the Promo Customer Onboarding guide for the full workflow, and the per-user endpoint Set promo-access override below.

These two columns are no longer set only by hand. Approving a mitra registration whose applicant left the organization form blank writes promoAccessEnabled = true and pricingTier = SILVER|GOLD|RESELLER onto the user, and leaves them B2C with no organization. A B2C user carrying pricingTier: GOLD and no organization is a Mitra Gold individual partner, not a misconfiguration. Find them with ?pricingTier=GOLD — not with ?specialCustomPricingEnabled=true, which is an org-only flag and excludes them.

Filtering by effective pricing tier ​

?pricingTier= resolves a user the same way the pricing engine does, in order:

  1. Promo gate first. A user who is not promo-eligible is a HOLDER and matches no filter value — regardless of what their pricingTier column says. (A GOLD override with promoAccessEnabled: false is a HOLDER: the access gate runs before tier resolution.)
  2. Per-user override wins. pricingTier = GOLD on the user beats the org — this is how a B2C user with no organization can be GOLD (a Mitra Gold individual partner).
  3. Otherwise a B2B member inherits the organization's tier.
  4. Otherwise the user floors at SILVER — a promo customer with no override and no organization is a SILVER.

HOLDER is not an accepted value: it is not a tier a user holds, it is what a promo-ineligible caller gets. To list those, use ?promoAccessEnabled=false.

Use this, not specialCustomPricingEnabled, to find Gold partners.specialCustomPricingEnabled keys off B2B org membership, so an individual Mitra Gold partner is excluded from ?specialCustomPricingEnabled=true and included in ?specialCustomPricingEnabled=false — the opposite of the truth. ?pricingTier=GOLD returns every Gold user: org members and individual partners alike.

bash
# Every Gold partner — organization members AND org-less individual partners
curl "$BASE/admin/users?pricingTier=GOLD" -H "Authorization: Bearer $ADMIN_JWT"

3. Attach a User to an Organization (organizationId) ​

Both POST /admin/users (create) and PATCH /admin/users/:id (update) accept an optional organizationId to attach the user (typically a B2C customer) to an existing organization. The organization must already exist — an unknown id is rejected with 400 Organization <id> not found.

Example (create):

bash
curl -X POST "/api/v1/admin/users" \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "customer@example.com",
    "name": "Promo Customer",
    "role": "B2C",
    "organizationId": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f"
  }'

Example (assign an existing user):

bash
curl -X PATCH "/api/v1/admin/users/0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e61" \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{ "organizationId": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f" }'

This is how admins onboard promo customers: create the organization, enable its flag via the promo-access endpoint, then create users with that organizationId (or assign existing users via PATCH). B2B/B2C users are passwordless — promo customers then log in on the promo host via OTP or Google/Apple. See the Promo Customer Onboarding guide for the full step-by-step flow (new vs existing customer, verification, downgrade).

Role transitions are constrained (PATCH) ​

For privilege-escalation safety, PATCH /admin/users/:id restricts which role changes it will apply. Staff accounts are provisioned only through the explicit create path (POST /admin/users), never by mutating an existing customer row.

SUPPORT is no longer a writable role. POST /admin/users and PATCH /admin/users/:id accept ADMIN, B2B and B2C; a body carrying role: "SUPPORT" is rejected with 400. The value stays in the schema enum, so existing rows and the ?role= list filter keep working, but nothing can create or move a row into it. It has no sign-in path — the password rail is closed to it, the admin reset OTP filters role: ADMIN, and the customer OTP and OAuth rails refuse staff rows — and PermissionsGuard serves only ADMIN callers, so a SUPPORT row could hold no permission either. There are none on any database.

B2B403400ok (no-op)allowed
B2C403400allowedok (no-op)

The SUPPORT column is 400, not 403: the role is no longer an accepted value for the role field, so validation rejects the body before any transition rule is consulted. That includes the SUPPORT → SUPPORT no-op.

  • No promotion into staff — any transition whose target is ADMIN or SUPPORT (from a customer OR from the other staff role) is rejected with 403. This includes SUPPORT → ADMIN.
  • No staff demotion either — a staff row cannot leave the staff set through this endpoint. That covers ADMIN and SUPPORT alike, and it matters because every staff-row restriction below tests the row's current role: one demotion would otherwise strip all of them at once.
  • No-op re-writes pass — re-sending the user's current role (e.g. while editing other fields) is not blocked.
  • Lateral customer moves (B2B ↔ B2C) are unaffected.

Staff administration has its own permissions ​

/admin/users serves customer rows (B2C, B2B) and staff rows through the same routes, so the permission model splits them by resource, not by route:

CodeGrants
admin-users:viewsee staff rows in the list, and GET one by id
admin-users:createPOST /admin/users with a staff role
admin-users:updatePATCH a staff row
admin-users:statsstaff counts on GET /admin/users/stats

users:* does not confer any of them — the <resource>:* rule matches on the resource string, so a customer-support role stops reaching admin accounts. * does confer them, so a Super Admin is unaffected. *:read reaches none of them: that wildcard fires only for the literal action read, and the staff view action is deliberately named view.

What each side sees:

RouteWith users: onlyWith admin-users: only
GET /admin/usersstaff rows excluded; ?role=ADMIN returns an empty page rather than a 403staff rows only
GET /admin/users/:ida staff row is 404, not 403 — the response does not confirm the account existsa customer row is 404
POST /admin/usersrole: ADMIN → 403a customer role → 403
PATCH /admin/users/:ida staff row → 403a customer row → 403
GET /admin/users/statscounts exclude staff, mirrors includedstaff counts only
DELETE /admin/users/:idunchanged: users:delete, plus the Super-Admin gate on a staff rowunchanged

DELETE sits outside the split on purpose. Deactivating a staff account is Super-Admin-only and is not delegated by either family, which is stricter than anything the partition would impose.

PATCH :id/promo-access and :id/pricing-tier get no admin-users counterpart: promo access and pricing tier describe how a customer is billed and are refused on a staff row for every caller — except null, which clears an existing override rather than granting one.

Nobody was granted admin-users:* when this shipped. Roles holding users:* kept their customer surface and lost their reach into staff rows; Super Admin is unaffected through *. Granting it is an ordinary role edit.

Staff rows are not ordinary rows ​

A staff row (role in ADMIN / SUPPORT) is a login into this admin surface, so writing to one is a privilege question rather than a profile edit. users:create and users:update govern customer rows; against a staff row the fields that decide who can sign in as that account carry their own gate, and a caller whose permission check passed still gets a 403.

Why those particular fields:

  • password is written straight onto the row, and the password login rail exempts ADMIN from the email-confirmation gate. Setting one is therefore a sign-in as that admin, with no mailbox access needed.

  • email and phone are what an account is identified by, and the admin password reset is public: it looks an account up by email or phone, prefers the email whenever the row carries both, and filters role: ADMIN. Repointing an identifier at your own mailbox therefore puts you one public reset away from a session as that admin.

    The customer OTP rail used to be a second route to the same place — it matched a row by identifier alone and minted a token carrying that row's role. It now refuses a staff row outright, as do the Google and Apple sign-in rails. Staff accounts sign in through the admin doors: the password rail, and the admin password-reset OTP.

The email/phone door stays open to a Super Admin on purpose. It is how an admin who has lost access to their mailbox — or their number — is reached back; the OTP rail sends to whichever identifier the row carries, so closing both would push that recovery into direct database access. password gets no such door because the owner can already set their own through the OTP rail.

isActive is guarded on PATCH as well as on DELETE. They write the same column, so a gate on only the DELETE route would be one a delegate could walk around — isActive is an ordinary field on the update body. Deactivation through either route still refuses to remove the last active Super Admin. Reactivation is Super-Admin-only for the same reason: PATCH is the only way back, so a delegate holding it could revive an account a Super Admin had deliberately disabled.

The two billing overrides are refused for everyone, Super Admins included — except null. Promo access and pricing tier describe how a customer is billed and have no meaning on a staff row, so unlike the identifiers there is no repair case a carve-out would serve. Clearing to null is not such a carve-out: it is the absence of an override, so it moves the row toward the state this rule wants. Refusing it would strand any staff row that already carries a value, with no API path back — and such rows are not only historical: mitra approval writes both columns onto an applicant's row and its guard refuses only ADMIN.

POST /auth/admin/force-change-identifier also now requires users:update. It previously ran on the bare ADMIN role — no Access Role was consulted — so every admin account reached it whatever their permissions. It is additionally rate-limited (10/min, keyed on the request IP like every other throttle here — so callers behind one NAT share the budget). An admin UI that offered this action to all admins should now hide it from callers lacking users:update.

You can also set promoAccessEnabled inline when creating (POST /admin/users) or updating (PATCH /admin/users/:id) a user.

5. Set a User's Pricing Tier ​

Endpoint: PATCH /admin/users/:id/pricing-tier

Force a per-user pricing tier, independent of the organization. This is how a B2C user is put on GOLD (special pricing) — the override bypasses the org axis that otherwise nulls out for B2C.

PATCH /api/v1/admin/users/:id/pricing-tier

Body:

tierEffect
"SILVER"Force the user onto SILVER (non-special) even inside a GOLD org
"GOLD"Force the user onto GOLD (special pricing) — works for B2C users
"RESELLER"Silver pricing plus a per-passenger commission on the user's custom bookings
nullClear the override — the user inherits organization.pricingTier

HOLDER is not accepted (holder is the off-promo / not-eligible runtime state, never an assignable tier).

⚠️ A user moved to RESELLER here earns from their next booking, not from their past ones. Commission keys off the tier recorded on the booking when it was made, and there is no backfill.

Auto-grant: setting a tier also sets promoAccessEnabled = true (a tier is inert without promo access, since the access gate runs first). An admin can still revoke access afterwards via Set promo-access override, which wins at runtime. Clearing with null leaves promo access untouched.

Response:

json
{ "id": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e61", "pricingTier": "GOLD", "promoAccessEnabled": true }

Errors:

StatusMessage
403Promo access and pricing tier apply to customer accounts only. Clearing the value (null) is allowed. (staff target — see Staff rows are not ordinary rows)
404User not found

Like the promo-access override, pricingTier is reset to null automatically whenever the user's organization membership changes (attach / switch / detach).
