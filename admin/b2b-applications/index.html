B2B Applications Management Guide ​

This guide explains how administrators can review, approve, and reject B2B partner applications.

Quick Overview ​

FeatureDescription
PurposeManage B2B partner application workflow
Admin AccessADMIN role plus Access Role permissions: reads (list, detail) need b2b-applications:read, and mark-under-review, approve, and reject need b2b-applications:review. See Access Roles
User AccessPublic endpoints available for applicants
ScopeB2B application submission, review, and approval

Base URL ​

All B2B application endpoints use:

/api/v1

Authentication ​

All B2B application endpoints require:

  • JWT Token in Authorization header
  • ADMIN role in user account
  • An Access Role permission for the route being called (admin endpoints only)
http
Authorization: Bearer <your-admin-jwt-token>

Permission-gated (Access Roles). The ADMIN role on its own is no longer enough for the admin endpoints. Each route also requires a fine-grained permission from the admin's Access Role. Reading (list, detail) needs b2b-applications:read. Marking under review, approving, and rejecting all need b2b-applications:review. A role holding b2b-applications:* gets every route, and Super Admin (*) is unaffected. An admin whose Access Role has neither code gets 403, even though the JWT is valid. The public applicant endpoints are unaffected. See Access Roles.

Approve currently shares b2b-applications:review with the triage verbs, so granting review also grants the ability to approve. That matters because approving creates the organization and its wallet and promotes the applicant's user role. Grant b2b-applications:review only to staff you intend to let provision B2B accounts.

Application Workflow ​

┌─────────────────────────────────────────────────────────────────────────────┐
│                       B2B APPLICATION WORKFLOW                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  1. User submits B2B application                                             │
│     ├─ POST /api/v1/auth/b2b/register (new user)                                │
│     └─ POST /api/v1/auth/b2b/upgrade (existing B2C user)                        │
│     Status: PENDING                                                          │
│                        ↓                                                     │
│  2. User uploads NIB document (required before approval)                    │
│     POST /api/v1/auth/b2b/register/:id/upload-nib                               │
│                        ↓                                                     │
│  3. Admin reviews application                                                │
│     POST /admin/b2b-applications/:id/review                                 │
│     Status: UNDER_REVIEW                                                    │
│                        ↓                                                     │
│  4. Admin decision:                                                          │
│     ├─ APPROVE → Creates organization, wallet, updates role to B2B          │
│     │            (B2C upgrades: transfers wallet balance to org wallet)     │
│     └─ REJECT → Application closed with reason                              │
│                 User can edit and resubmit via PATCH /api/v1/auth/b2b/application│
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘

Public Endpoints (User-Facing) ​

These endpoints are used by applicants to submit and manage their B2B applications.

2. Upgrade B2C Account to B2B ​

Endpoint: POST /api/v1/auth/b2b/upgrade

Existing B2C users can upgrade to B2B. Same approval workflow as new registrations. On approval, personal wallet balance is transferred to organization wallet.

Authentication: Required (JWT token)

Request Body: Same as Submit B2B Application

Response: 201 Created

3. Upload NIB Document ​

Endpoint: POST /api/v1/auth/b2b/register/:id/upload-nib

Upload the NIB document (PDF only, max 10MB) for a B2B application. Uses the application ID from the registration response.

Authentication: Status-conditional. Public for PENDING / REJECTED. For APPROVED applications a JWT is required and the caller must be the application owner or an admin; owner-less auto-approved applications are admin-only. Uploading is blocked while UNDER_REVIEW.

Request: multipart/form-data

FieldTypeRequiredDescription
fileFileYesPDF file (max 10MB, valid PDF structure required)

Example:

bash
curl -X POST \
  https://api.example.com/api/v1/auth/b2b/register/0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f/upload-nib \
  -F "file=@nib-document.pdf"

Response: 200 OK

json
{
  "id": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e60",
  "filename": "nib-document.pdf",
  "mimeType": "application/pdf",
  "size": 245862,
  "uploadedAt": "2026-01-31T09:55:00Z",
  "message": "NIB document uploaded successfully"
}

Errors:

StatusMessage
400File is required
400Only PDF files are allowed
400File size must not exceed 10MB
400Invalid PDF file
403Not authorized to upload documents for this application (APPROVED, non-owner/non-admin)
404Application not found

3b. Upload NPWP Document (optional) ​

Endpoint: POST /api/v1/auth/b2b/register/:id/upload-npwp

Upload an optional NPWP document (PDF only, max 10MB). The NPWP never gates approval and can be added at any time, including after approval. Same status-conditional authorization as the NIB upload (public for PENDING / REJECTED; owner-or-admin for APPROVED, owner-less approved apps admin-only).

Request: multipart/form-data with a file field.

Response: 200 OK

json
{
  "id": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f",
  "npwpDocument": {
    "id": "0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e61",
    "filename": "npwp-document.pdf",
    "mimeType": "application/pdf",
    "size": 198450,
    "uploadedAt": "2026-01-31T09:56:00Z"
  },
  "message": "NPWP document uploaded successfully",
  "uploadedAt": "2026-01-31T09:56:00Z"
}

nibDocument and npwpDocument are independent File slots; uploading one never touches the other.

For a time-limited link or a shareable no-login token instead of the raw download, see Storage — Download a File by ID: GET /api/v1/storage/{id}/url (presigned) and POST /api/v1/storage/{id}/token.

Approval Workflow ​

Step 1: Review Application ​

bash
# Get application details
GET /admin/b2b-applications/:id

# Mark as under review
POST /admin/b2b-applications/:id/review

Step 2: Verify Documents ​

Check the following:

  • NIB document is uploaded and valid
  • Business license is valid and not expired
  • Tax ID (NPWP) matches company records
  • Address is complete and verifiable
  • Contact information is valid

Important

Applications without an NIB document cannot be approved. The system will reject the approval request.

Step 3: Approve Application ​

bash
POST /admin/b2b-applications/:id/approve
{
  "adminNotes": "All documents verified. NIB is valid."
}

What happens on approval:

  1. Organization is created with company name and auto-generated code
  2. Wallet is automatically created for the organization (SAR currency, 0 initial balance)
  3. User role is changed from B2C to B2B
  4. User is linked to the organization
  5. For B2C upgrades: Personal wallet balance is transferred to organization wallet
  6. Application status is set to APPROVED
  7. User receives approval notification (Email + WhatsApp + In-App)

Rejection & Resubmission Workflow ​

Step 1: Reject with Clear Reason ​

bash
POST /admin/b2b-applications/:id/reject
{
  "rejectionReason": "NIB document is not clear. Please upload a clearer version.",
  "adminNotes": "Internal notes not visible to user"
}
FieldRequiredVisible to UserDescription
rejectionReasonYesYesReason shown to applicant
adminNotesNoNoInternal notes for audit trail

What happens on rejection:

  1. Application status is set to REJECTED
  2. User receives rejection notification (Email + WhatsApp + In-App)
  3. User can edit and resubmit the application

Step 2: User Resubmits Application ​

After rejection, users can update their application via:

bash
PATCH /api/v1/auth/b2b/application
{
  "companyAddress": "Updated address",
  "nib": "Updated NIB"
}

Users can also upload a new NIB document if needed:

bash
POST /api/v1/auth/b2b/register/:id/upload-nib

Step 3: Review Resubmitted Application ​

The application returns to PENDING status with incremented submissionCount. Review as normal.

Organization Code ​

Organization codes are auto-generated from the company name when an application is approved. The system:

  1. Extracts the first letters of each word in the company name
  2. Converts to uppercase
  3. Appends a 2-digit random number for uniqueness
  4. Ensures uniqueness by regenerating if code exists

Examples:

  • "PT Teknologi Maju Bersama" → PTMB42
  • "Hajar Travel Umrah & Haji" → HTUH17
  • "Makkah Travel Agency" → MTA89
