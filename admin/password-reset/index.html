Admin Password Reset ​

This guide covers the self-service password-reset flow for admin accounts that have lost access to their credentials. The endpoints are intentionally public (no JWT or ADMIN role required) — the admin requesting the reset cannot authenticate yet — but they are heavily rate-limited.

Quick Overview ​

ItemDescription
PurposeSelf-service password recovery for ADMIN accounts
AuthenticationNone — these endpoints are publicly reachable
AuthorizationImplicit: the request target must match an existing ADMIN user that is isActive: true
Delivery channelEmail (preferred) or WhatsApp, depending on what the admin account has on file
OTP TTL5 minutes
Side effects on resetAll existing refresh tokens for the user are revoked; a fresh access + refresh token pair is returned in the response

Base URL ​

/api/v1

Flow ​

1. POST /admin/users/password-reset/forgot   → OTP sent to email or phone
2. Admin reads the OTP from email / WhatsApp
3. POST /admin/users/password-reset/reset    → password updated, sessions revoked, new tokens returned

1. Request OTP ​

Endpoint: POST /admin/users/password-reset/forgot

Sends a 6-digit OTP to the admin's email or phone. If the account has both, email is prioritized.

Rate limit: 3 requests per hour per IP. Exceeding this returns 429 Too Many Requests.

Request Body:

json
{
  "target": "admin@example.com"
}
FieldTypeDescription
targetstringEmail address or phone number of the admin account. Max 254 chars.

Response (200):

json
{
  "message": "OTP sent successfully",
  "sentTo": "email",
  "target": "admin@example.com"
}

sentTo is "email" or "phone". target reflects the channel the OTP was actually delivered to — when the admin has both, this echoes the email even if the request used the phone number.

Errors:

StatusReason
404 Not FoundNo active admin account matches target
400 Bad RequestThe matched admin has neither email nor phone configured
429 Too Many RequestsThrottle exceeded (3/hour)

2. Reset password ​

Endpoint: POST /admin/users/password-reset/reset

Verifies the OTP and sets a new password. On success, all existing refresh tokens for the user are revoked and a fresh token pair is issued so the caller can log straight in.

Rate limit: 5 requests per 15 minutes per IP.

Request Body:

json
{
  "target": "admin@example.com",
  "code": "123456",
  "newPassword": "newPassword123"
}
FieldTypeDescription
targetstringSame value used in step 1. Max 254 chars.
codestring6-digit OTP from email / WhatsApp.
newPasswordstringNew password. Min 6, max 128 chars.

Response (200):

json
{
  "success": true,
  "message": "Password reset successfully",
  "accessToken": "<jwt>",
  "refreshToken": "<refresh-token>",
  "user": {
    "id": "0193…",
    "email": "admin@example.com",
    "name": "Admin Name",
    "role": "ADMIN",
    "isEmailConfirmed": true,
    "isPhoneConfirmed": false
  }
}

Errors:

StatusReason
404 Not FoundNo active admin account matches target
401 UnauthorizedOTP is invalid or expired
429 Too Many RequestsThrottle exceeded (5/15min)

Security notes ​

  • Public by design. Both endpoints sit outside AuthGuard('jwt') and RolesGuard — an admin who has lost their credentials cannot pass either guard. Throttling is the primary abuse control.
  • OTP enumeration is bounded. OTPs expire after 5 minutes, and the per-IP throttle on reset (5 / 15 min) keeps brute-force probability negligible against a 6-digit space.
  • Account enumeration. The forgot endpoint returns 404 when no admin matches target. This trades a small enumeration signal for clearer operator feedback; the throttle limits how fast that signal can be probed.
  • Session revocation on reset. Successful reset revokes every refresh token for the user, kicking out any stolen sessions. The new tokens in the response are scoped to the caller only.
