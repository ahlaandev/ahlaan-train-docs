Exchange Rate Management Guide ​

This guide explains how administrators manage IDR to SAR exchange rates for the HHR platform.

Quick Overview ​

FeatureDescription
PurposeManage IDR↔SAR rates and the SAR↔USD rate (the USD peg is now admin-editable)
AccessAdmin only
ScopeWallet top-up, OTA pricing, custom-OTA / custom-booking pricing, invoice conversion, and other SAR conversion flows

USD note. USD was previously a hardcoded peg of 3.75 SAR per USD. It is now driven by an admin-managed SAR↔USD rate (see USD Rate below). Until an admin sets a divergent rate, the seeded default (3.75 buy/sell) reproduces the old peg exactly. USD is display/quote-only — it is never a charged or settlement currency.

Base URL ​

All exchange rate endpoints use:

http
/api/v1

Authentication ​

All exchange rate endpoints require:

  • JWT token in the Authorization header
  • ADMIN role
http
Authorization: Bearer <your-admin-jwt-token>

Rate Modes ​

The system supports three operating modes:

ModeDescription
SCHEDULEDUses the configured weekday toggles plus the configured switch times to decide when Mandiri vs manual rates are effective.
FORCE_AUTOMATICAlways uses the latest scraped BANK_MANDIRI rate, ignoring weekday toggles and switch times.
FORCE_MANUALAlways uses the latest manually entered rate, ignoring weekday toggles and switch times.

Scheduled Mode ​

In SCHEDULED mode, the system now uses only the current day's toggle plus the configured switch times.

Day toggle rules ​

  • If today's toggle is false, the system uses manual rates for the entire day.
  • If today's toggle is true, the system uses the configured time window:
    • before autoSwitchTimeWib: manual
    • from autoSwitchTimeWib until before manualSwitchTimeWib: BANK_MANDIRI
    • from manualSwitchTimeWib onward: manual

Default weekday toggles ​

The default configuration is:

json
{
  "MON": true,
  "TUE": true,
  "WED": true,
  "THU": true,
  "FRI": true,
  "SAT": false,
  "SUN": false
}

This means scheduled switching is enabled by default on Monday through Friday, and disabled on Saturday and Sunday.

Important note ​

Holiday-based switching has been removed. The system no longer has holiday endpoints or holiday-aware rate selection. Only the current day's toggle is used.

How Exchange Rates Work ​

Rate flow ​

text
1. The system scrapes Mandiri rates on the configured sync interval.
2. Rates are stored in the exchange-rate table.
3. Manual rates can be entered by an admin at any time.
4. The active source is resolved from:
   - mode
   - weekday toggle for the current day
   - auto/manual switch times
5. If the preferred source has no record, the system falls back to the other source.

Rate types ​

TypeDescriptionUsage
Buy RateBank's rate to buy foreign currencyStored for audit/history
Sell RateBank's rate to sell foreign currencyUsed for wallet top-ups and current conversion

Rate sources ​

SourceDescription
BANK_MANDIRIRate scraped from Mandiri
MANUALRate entered by admin

USD Rate ​

USD↔SAR uses a dedicated admin-managed rate stored as an ExchangeRate row with toCurrency = USD and fromCurrency = SAR. Both buyRate and sellRate are expressed as SAR per 1 USD (e.g. 3.75).

  • SAR → USD divides by sellRate (the larger side of the spread).
  • USD → SAR multiplies by buyRate (the smaller side).
  • With buyRate == sellRate the maths collapses to a single peg.

Setting a new rate updates pricing immediately across all instances (in-process cache refreshed locally and via Redis pub/sub). It is forward-only: custom bookings created before the change keep the USD figure they were priced at.

The public rate is available at GET /api/v1/exchange-rate/current?currency=USD (optional auth — public read).

Per-org USD tiering on the promo host ​

On the promo host, the USD rate on GET /api/v1/exchange-rate/current?currency=USD is tiered by the authenticated, promo-eligible caller (mirrors the special-B2B SAR reducer, and matches what the promo custom-ota / custom-booking flow charges). The tier gate is the caller's promo eligibility + specialness — NOT whether they have an organization:

The caller's resolved pricingTier (HOLDER / SILVER / GOLD) selects the rate:

Caller (on the promo host)pricingTiersellRate (SAR per USD) returned
Promo-eligible + resolves to GOLD (special org, or a per-user GOLD override — incl. a B2C user)GOLDspecialUsdSarRate (default 3.75)
Promo-eligible + NOT special — any B2C, org-less, or non-special orgSILVERdefaultUsdSarRate (default 3.72)
Guest (unauthenticated) OR authenticated-but-not-promo-eligibleHOLDERglobal holder rate (unchanged)
Off the promo host (any)HOLDERglobal holder rate (unchanged)

SILVER is not gated on having an organization. A promo-eligible B2C or org-less customer resolves to SILVER (defaultUsdSarRate) — the only requirement is promo eligibility (promoAccessEnabled, resolved per-user) and not resolving to GOLD. Guests stay on the holder peg. GOLD is driven by the org pricingTier (specialCustomPricingEnabled is a deprecated mirror) OR a per-user pricingTier = GOLD override, so a B2C user can be GOLD.

Only the SAR→USD sellRate/rate and the recomputed midRate change; buyRate (USD→SAR) is untouched. The two rates are admin-configurable via PATCH /api/v1/admin/special-custom-b2b-pricing/config (specialUsdSarRate / defaultUsdSarRate) — see the Special Custom B2B Pricing doc.

?currency=IDR is a transitional alias of ?currency=SAR on the /current endpoint (the SAR row is the IDR↔SAR pair; there is no dedicated IDR row, so ?currency=IDR previously returned null). The alias applies to /current only — /history and /{id} still query the literal currency. The IDR query param is deprecated and will be removed in a future release; use SAR.

Both USD admin endpoints below are admin-only: they require a JWT token and the ADMIN role, exactly like every other endpoint on this controller (see Authentication). The POST endpoint is additionally rate-limited to 10 requests/minute.

Public Current Rate (GET /exchange-rate/current) ​

Unlike the admin endpoints above, GET /api/v1/exchange-rate/current is a public read (no ADMIN role required). It uses OptionalAuthGuard, so it accepts an optional bearer token and adapts its response to the caller:

  • Standard callers — a guest, a not-promo-eligible user, or any request on a non-promo host — receive the plain active SAR rate. (For USD on the promo host any promo-eligible non-special caller — including a B2C or org-less customer — receives defaultUsdSarRate (silver), not the holder — see Per-caller USD tiering on the promo host; only a guest / not-promo-eligible / off-promo caller gets the plain holder USD rate.)
  • Special-pricing (GOLD) callers — a caller whose resolved pricingTier is GOLD (org Organization.pricingTier = GOLD, or a per-user User.pricingTier = GOLD override — including a B2C user; specialCustomPricingEnabled is a deprecated mirror of that tier), and whose request arrives on the mitra host (mitra.ahlaan.co.id or a subdomain; configurable via PROMO_BASE_DOMAIN) — receive the reducer-adjusted SAR rate. The exchangeRateReducer (from Special Custom B2B Pricing) is subtracted from sellRate, and the mirrored rate is reduced to match; midRate is recomputed as (buyRate + reducedSellRate) / 2; buyRate is left unchanged.

This exchangeRateReducer adjustment is SAR only — the reducer never touches USD. USD is instead tiered per promo-eligible caller via specialUsdSarRate (gold) / defaultUsdSarRate (silver) on the promo host (see Per-caller USD tiering on the promo host above); off the promo host (or for a guest / not-promo-eligible caller) ?currency=USD returns the plain holder rate, unchanged. The reduced SAR rate mirrors the IDR sell rate that custom-OTA / custom-booking actually charge a special-pricing org on the promo host, so the FE can show a consistent number.

Automatic Sync ​

The system automatically syncs Mandiri rates from the configured scrape source.

SettingValue
Default scrape frequencyEvery 30 minutes
Default evaluation frequencyEvery 1 minute
SourceMandiri exchange-rate page
Distributed lockRedis
FallbackFalls back to the alternate source if the preferred source has no record

Fallback behavior ​

If the preferred source for the current schedule window has no available record, the system falls back to the opposite source:

ScenarioPreferred SourceFallback Source
No Mandiri rate availableBANK_MANDIRIMANUAL
No manual rate availableMANUALBANK_MANDIRI

If neither source has a record, the system keeps the current active rate unchanged.

Rate deduplication ​

Before creating a new BANK_MANDIRI rate, the system compares it with the latest existing BANK_MANDIRI record. If both buy and sell rates are unchanged, no new record is created.

Transactional activation ​

When the effective source is BANK_MANDIRI, activation is done transactionally so only one active SAR rate exists at a time.
