Custom Booking Management (Admin) ​

This guide covers the admin lifecycle endpoints for custom bookings: status transitions, capital-source assignment, ticket upload, and the side effects (invoice auto-generation, customer confirmation email, customer-initiated payment-instruction delivery, payment-webhook transitions, admin payment-success WhatsApp notification, manifest-download auto-transition, passenger-upload auto-transition + auto-confirm + admin WhatsApp notification, hourly auto-complete cron).

For manifest file upload/download (separate concern), see Custom Booking Manifests (Admin).

Pricing & seat cap (booking creation). POST /api/v1/custom-booking prices via the custom-OTA unit-pax probe: the supplier is searched with a fixed 1/1/1 body (so groups within 3 days still price) and the per-passenger fares are scaled to the real adultCount / childCount / infantCount. The cabin seat limit is enforced — a request whose seated count (adultCount + childCount; infants are lap) exceeds the remaining availableSeats is rejected with HTTP 400 code INSUFFICIENT_SEATS. Get Custom Booking Detail ​

http
GET /api/v1/admin/custom-booking/:id

Retrieve a single custom booking with full relations (user, organization, ticketChannel, invoice, exchangeRate, manifest files). Returns 404 if not found. Throttled at 60 req / 60s.

manualTransfer review block. When the linked invoice's payment uses the MANUAL_TRANSFER gateway, the response embeds a manualTransfer field with the proof review payload (proof status, retry budget, sender metadata, rejection history, expected bank account, and a 24-hour signed signedDownloadUrl for the uploaded proof file). For all other cases (non-manual-transfer, no proof yet) the field is null or omitted. The block is identical to the one returned from GET /api/v1/admin/invoice/:id — see the Manual Transfer admin guide for the full schema and approve/reject workflow.

Admin-only capital-price fields. The admin detail response also exposes frozen cost-basis fields that are stripped from customer responses (GET /custom-booking/:id):

FieldLocationPurpose
capitalPriceTotalSARtop levelFrozen total cost basis: (outboundCap + returnCap) × (adults + children × 0.5), infants excluded. Defaults to 0 and is only populated once a capital source is set — either by confirming with a ticketChannelId (legacy flow) or by calling PATCH .../source. Auto-confirmed bookings (see §7) carry 0 until an admin sets the source.
pricingSnapshot.outbound.capitalPriceSARper-legPer-adult capital price snapshotted from TicketChannelRoutePrice.capitalPrice when the capital source is set (legacy CONFIRMED-with-channel transition or PATCH .../source). null when no active row matches (ticketChannelId, origin, destination, tripClass, tripType).
pricingSnapshot.outbound.ticketChannelIdper-legID of the ticket channel that sourced the capital price for this leg.
pricingSnapshot.return.*per-legSame two fields on the return leg (ROUND_TRIP only).
pricingSnapshot.capitalPriceHistorytop levelAppend-only log of capital-basis changes: source set/change via PATCH .../source and manual corrections via PATCH .../capital-price.

These fields never appear on the customer-facing detail endpoint — FE code that targets the customer flow must not depend on them. Bookings with no capital source carry capitalPriceTotalSAR: 0 and no per-leg capital fields; the snapshot is written when the capital source is set — either by transitioning to CONFIRMED with a ticketChannelId (legacy flow) or by calling PATCH .../source. The capital source is decoupled from confirmation: a booking can be CONFIRMED (including by auto-confirm) without a channel and stay at capitalPriceTotalSAR: 0 until an admin sets the source. If no TicketChannelRoutePrice row matches when the source is set, the call still succeeds with capitalPriceTotalSAR: 0 and per-leg capitalPriceSAR: null — the admin can correct it via PATCH .../capital-price. Historical bookings created before the 2026-04-22 migration also carry 0 (additive backfill with DEFAULT 0).

Status State Machine ​

The booking status field is a VARCHAR(256) whose values are managed by the CustomBookingStatus enum and a strict transition map. Transitions are enforced server-side — invalid transitions return 400 Bad Request.

                │ PENDING │

  └───────────┘

Payment settlement (Xendit webhook, manual-transfer proof approval, or the
admin "mark invoice paid" override) advances the booking from
WAITING_FOR_PAYMENT / WAITING_PAYMENT_REVIEW **directly to
WAITING_FOR_TICKET** — the PAID state is no longer persisted for new
bookings. PAID remains in the enum and VALID_TRANSITIONS only so rows that
predate this change (and that still rely on the manifest-download
auto-transition, see §8) can close out. The earlier "admin downloads the
manifest to leave PAID" step is no longer required for new bookings.

Admin ticket upload transitions WAITING_FOR_TICKET directly to COMPLETED
and asynchronously emails the ticket to the customer. The older
TICKET_RECEIVED state is a legacy value that remains in the enum only so
rows already in that state can still be closed out via the customer
confirm-received endpoint or the hourly auto-complete cron.

PENDING → UPLOADED_MANIFEST is auto-triggered when a customer (or guest)
submits the passenger list via `PATCH /custom-booking/:id/passengers`.
Manifest **file** upload no longer moves the status. Admins may set it
directly. On the winning transition the server also enqueues a WhatsApp
notification to the admin phone configured under
`CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE` (see
[System Configuration](/admin/system-config/)).

UPLOADED_MANIFEST → CONFIRMED is **auto-triggered by default**: the same
passenger-upload that lands `UPLOADED_MANIFEST` immediately confirms the
booking — generating the invoice and emailing the customer a confirmation
(the payment instruction follows only when the customer picks a method via
`generate-payment`) — without an admin review step. This is gated by the
`CUSTOM_BOOKING_AUTO_CONFIRM_ON_MANIFEST` system config key (default ON;
set to `false` to restore the manual admin-confirm gate). Auto-confirm is
best-effort: a failure leaves the booking at `UPLOADED_MANIFEST` for an
admin to confirm manually via `PATCH .../status`. See
[§7](#_7-side-effect-passenger-upload-auto-confirm-admin-whatsapp-notification).

Customers may also trigger CONFIRMED → CANCELLED via
PATCH /custom-booking/:id/status (see the customer guide). All other
customer-initiated transitions are rejected with 403.

CANCELLED is reachable from every non-terminal state (admin/system).

* EXPIRED is set by the Xendit payment webhook when the payment window
  elapses; reachable from WAITING_FOR_PAYMENT and WAITING_PAYMENT_REVIEW. The
  gateway webhook is the sole trigger — there is no cron fallback, so the
  PaymentStatusUpdateProcessor MUST carry the booking from waiting-for-payment
  to EXPIRED when the gateway reports the invoice expired.

  Manual-transfer (SAR/USD) payments have **no gateway webhook**, so a lapsed
  manual-transfer window does **not** auto-transition the booking to EXPIRED —
  the booking stays in waiting-for-payment and expiry is enforced passively at
  proof-**upload** time: once `expiresAt` passes, a new upload or re-upload is
  rejected with `409` (`Payment has expired; please start a new payment.`). A
  proof submitted before the window closed stays approvable — admin approval
  has no `expiresAt` guard, so a real transfer that arrived in time still
  settles even if review runs late. The manual-transfer window is a fixed,
  configurable span (default 30 minutes,
  `CUSTOM_BOOKING_MANUAL_TRANSFER_EXPIRY_MINUTES`), mirroring the Xendit window
  (`CUSTOM_BOOKING_XENDIT_PAYMENT_EXPIRY_MINUTES`).

Terminal states (no further transitions allowed):
  COMPLETED, CANCELLED, EXPIRED, NOT_AVAILABLE

http

Authorization: Bearer <admin-token>

Request Body ​

FieldTypeRequiredNotes
statusenumYesOne of CustomBookingStatus. Must be a valid transition from the current status.

Side Effect — Invoice auto-generation ​

When the transition target is CONFIRMED and the booking has no invoiceId, the server calls InvoiceService.generateFromCustomBooking inline. The invoice uses SAR-only pricing derived from the booking's pricePerAdultSAR, pricePerChildSAR, and pricingSnapshot.return (if ROUND_TRIP).

If invoice generation fails, the status update still succeeds and the response body includes a _warnings array:

json
{
  "id": "booking-123",
  "status": "CONFIRMED",
  ...,
  "_warnings": [
    "Invoice auto-generation failed: <error message>. Please generate manually."
  ]
}

In that case, generate the invoice manually via the Invoice Management endpoints.

Side Effect — Customer confirmation email ​

On the UPLOADED_MANIFEST → CONFIRMED transition (whether triggered by auto-confirm or by an admin), the server enqueues a confirmation email to the customer (best-effort — a failed/missing email does not roll back the already-committed CONFIRMED transition).

No payment instruction is sent on confirmation. The Xendit link (or SAR/USD bank-transfer details) is delivered only after the customer picks a payment method — see the next section. This lets the customer choose between Xendit and manual transfer before we tell them how/where to pay.

Side Effect — Customer payment instruction (on generate-payment) ​

When the customer (or an admin on their behalf) calls POST /invoice/:id/generate-payment for a custom-booking invoice, the endpoint enqueues a payment-instruction notification on the custom-booking-payment-notification queue. A worker then delivers the instruction matching the chosen gateway:

  1. XENDIT → the hosted Xendit payment link.
  2. MANUAL_TRANSFER (SAR/USD) → the destination bank account (bank name, account number, account holder, optional notes) plus the exact amount to transfer.

Delivery prefers WhatsApp to the booking's contactPerson phone and falls back to email when there is no phone on record or the WhatsApp enqueue fails (the fallback reuses the custom-booking-paid email type). The job is keyed by invoiceId + gateway + currency, so switching method re-sends while an identical re-request deduplicates.

This is best-effort — a gateway/queue error does not fail the generate-payment response (the payment row already exists and the FE shows the same details). Other gateways and non-custom-booking invoices do not trigger a notification.

Side Effect — Payment webhook transitions ​

When a Xendit payment webhook is processed for an invoice linked to a custom booking, the booking is auto-transitioned inside the same Prisma transaction:

Webhook eventBooking transition
Payment paidWAITING_FOR_PAYMENT / WAITING_PAYMENT_REVIEW → WAITING_FOR_TICKET (skip-PAID)
Payment expiredWAITING_FOR_PAYMENT → EXPIRED

The paid transition is a status-guarded updateMany scoped to the waiting-for-payment states, so a re-delivered webhook (or a booking already advanced) is a benign no-op. If the booking is not in one of those states (or the transition is otherwise invalid), the webhook silently logs a warning and skips the booking update — the invoice/payment record itself is still updated.

On the paid transition the server also notifies the admin by WhatsApp — see §10.

Errors ​

  • 400 Bad Request — Invalid status value, invalid transition, or attempt to transition from a terminal state.
  • 400 Bad Request — Ticket channel '<name>' is not active (only when a ticketChannelId is supplied).
  • 404 Not Found — Booking or ticket channel not found.

2. Update Capital Price (admin margin correction) ​

Correct the capital-price basis that was snapshotted at the PENDING → CONFIRMED transition from TicketChannelRoutePrice. Use this when the channel-negotiated cost changes after confirmation (tariff revision, channel-specific variant, data-entry fix), or when no TicketChannelRoutePrice row matched at confirm time and the basis needs to be entered manually. Does not alter the customer-facing selling price or the booking status — margin reporting only.

Status guard: The booking must be exactly CONFIRMED. Calls against any other status (PENDING, UPLOADED_MANIFEST, COMPLETED, CANCELLED, etc.) return 400 Bad Request. Editing capital before CONFIRMED has no meaning because the basis isn't sourced until the channel is selected; editing after the booking has moved past CONFIRMED is intentionally blocked — corrections must happen during the CONFIRMED window.

http
PATCH /admin/custom-booking/:id/capital-price
Authorization: Bearer <admin-token>
Content-Type: application/json

Request Body ​

FieldTypeRequiredNotes
outboundCapitalPricePerAdultSARnumber ≥ 0, ≤ 2 decimalsYesPer-adult cost basis for the outbound leg. 0 is legal (comped seat).
returnCapitalPricePerAdultSARnumber ≥ 0, ≤ 2 decimalsConditionalRequired for ROUND_TRIP, must be omitted for ONE_WAY.
reasonstring, ≤ 500 charsNoFree-text reason recorded in the audit log and capitalPriceHistory.

Behavior ​

  1. Recomputes capitalPriceTotalSAR using the booking's stored passenger counts: (outboundCap + returnCap) × (adultCount + childCount × 0.5). Infants are excluded. Children are billed at 50% of adult cost, matching the selling-price formula.
  2. Overwrites pricingSnapshot.outbound.capitalPriceSAR (and pricingSnapshot.return.capitalPriceSAR for ROUND_TRIP). Other snapshot fields (pricePerAdultSAR, priceSource, etc.) are left untouched.
  3. Appends a new entry to pricingSnapshot.capitalPriceHistory recording the previous values, the next values, the acting admin, and the optional reason.
  4. Writes an AuditLog row with action = "CUSTOM_BOOKING_CAPITAL_PRICE_UPDATE", entity = "CustomBooking", entityId = :id, and the full diff under newValue.
  5. Atomicity: steps 2–4 run inside a single prisma.$transaction. If the audit write fails, the booking update is rolled back — a booking will never be mutated without a matching audit row.

cURL — ONE_WAY ​

bash

Errors ​

Rate Limit ​

Notes for frontend ​

  • Status guard — the endpoint requires booking.status === CONFIRMED exactly. Calls against any other status (PENDING, UPLOADED_MANIFEST, COMPLETED, CANCELLED, etc.) return 400 Bad Request.   • capitalPriceHistory is append-only and grows with every call. Render it as a reverse-chronological list when displaying margin history.

3. Set Capital Source (admin) ​

Set (or change) the capital source — the ticket channel the seats are procured from — independently of confirming the booking or uploading the ticket. This is the canonical (and only reliable) endpoint for setting or changing a booking's ticketChannelId. Confirm first (or let auto-confirm run), then attach the source whenever the procurement channel is decided; call again with a different channel to change it. Do not use PATCH .../status with ticketChannelId for this (legacy, snapshots only on the CONFIRMED transition and cannot change an existing channel).

Snapshots the capital-price basis from the channel's TicketChannelRoutePrice (per leg; adults + children × 0.5, infants excluded), appends a pricingSnapshot.capitalPriceHistory entry, and writes an audit log. Does not change the booking status.

Re-settable on any non-terminal booking. Allowed from UPLOADED_MANIFEST onward; calling again with a different channel re-snapshots the basis and appends another history entry. Blocked only for terminal bookings (COMPLETED, CANCELLED, EXPIRED, NOT_AVAILABLE). Unlike PATCH .../capital-price (which requires the booking to be exactly CONFIRMED), this endpoint has no CONFIRMED-only guard.

http
PATCH /admin/custom-booking/:id/source
Authorization: Bearer <admin-token>
Content-Type: application/json

Request Body ​

FieldTypeRequiredNotes
ticketChannelIdstringYesThe ticket channel to use as the capital source. Must reference an active TicketChannel. Max 36 chars.

cURL ​

bash
curl -X PATCH /api/v1/admin/custom-booking/booking-123/source \
  -H "Authorization: Bearer <admin-token>" \
  -H "Content-Type: application/json" \
  -d '{ "ticketChannelId": "0190abc1-..." }'

Response (200) ​

Returns the updated booking. capitalPriceTotalSAR and the per-leg pricingSnapshot.*.capitalPriceSAR / ticketChannelId reflect the new source, and a new capitalPriceHistory entry is appended:

  "id": "booking-123",
  "status": "CONFIRMED",
  "ticketChannelId": "0190abc1-...",

        "source": "TICKET_CHANNEL",
        "ticketChannelId": "0190abc1-...",
        "previous": { "ticketChannelId": null, "totalCapitalPriceSAR": 0 },
        "next": {
          "outboundCapitalPricePerAdultSAR": 300,

If no TicketChannelRoutePrice row matches the booking's route/class, the call still succeeds with capitalPriceTotalSAR: 0 and per-leg capitalPriceSAR: null — correct it afterwards via PATCH .../capital-price.

Behavior notes ​

  • The booking + audit-log write commit in a single Prisma transaction — the audit row is compliance evidence and cannot drift from the change.
  • Selling price, invoice, and status are untouched — margin/reporting only.

Errors ​

  • 400 Bad Request — Booking is in a terminal state, or the channel is not active.
  • 404 Not Found — Booking or ticket channel not found.

Rate Limit ​

30 requests / 60s.

4. Upload Ticket ​

Upload the issued ticket PDF for a booking. Atomically transitions the booking from WAITING_FOR_TICKET → COMPLETED and asynchronously queues the ticket email to the customer. Email dispatch is best-effort and is not retried by the queue worker (the email provider guarantees delivery). If the customer reports a missing email, use the Resend Ticket Email endpoint below.

http
POST /admin/custom-booking/:id/ticket
Authorization: Bearer <admin-token>
Content-Type: multipart/form-data

Form Field ​

FieldTypeRequiredNotes
filefileYesThe ticket file (PDF/image). Stored in R2 with entityType: custom_booking_ticket, visibility: PRIVATE.

Pre-conditions ​

  • Booking must exist.
  • Booking status must be WAITING_FOR_TICKET. Any other status returns 400 Bad Request.

cURL ​

bash
curl -X POST /api/v1/admin/custom-booking/booking-123/ticket \
  -H "Authorization: Bearer <admin-token>" \
  -F "file=@HHR-ticket.pdf"

Response (201) ​

json
{
  "id": "file-uuid-1",
  "filename": "HHR-ticket.pdf",
  "mimeType": "application/pdf",
  "size": 102400,
  "visibility": "PRIVATE",
  "entityType": "custom_booking_ticket",
  "entityId": "booking-123",
  "uploadedAt": "2026-04-13T10:00:00.000Z"
}

Side Effect — Ticket email to customer ​

After the file is stored and the status is updated, an email is queued on the emails BullMQ queue (consumed by the cron worker container) with:

  • emailType: custom-booking-ticket
  • to: contactPerson.email
  • subject: Tiket Pemesanan Anda Telah Tersedia - <bookingCode>
  • attachmentUrls: [<R2 presigned download URL>]
  • attempts: 1 — the queue does not retry this job on failure.

Email failures are logged but do not fail the upload — the file is saved and the status is already COMPLETED. If the booking has no contactPerson.email, the email is skipped with a warning; trigger a manual send via the resend endpoint after updating the contact details.

See the shared buildTicketConfirmedEmail template at src/modules/email/templates/booking-email.template.ts for the exact body — custom bookings reuse the OTA ticket-confirmed layout, rendering the total amount in the booking's invoice currency.

Errors ​

  • 400 Bad Request — File is required (no file form field).
  • 400 Bad Request — Booking is not in WAITING_FOR_TICKET.
  • 404 Not Found — Booking does not exist.
  • 409 Conflict — Another admin uploaded concurrently and won the atomic transition race; the losing upload is rolled back and the orphan R2 file is cleaned up.

5. Resend Ticket Email ​

Re-queue the ticket email for a booking using its most recently uploaded ticket file. The booking status is not modified, so this endpoint is safe to call on COMPLETED bookings as well as on legacy TICKET_RECEIVED rows.

http
POST /admin/custom-booking/:id/resend-ticket-email
Authorization: Bearer <admin-token>

Pre-conditions ​

  • Booking must exist.
  • Booking status must be TICKET_RECEIVED (legacy) or COMPLETED. Cancelled, expired, or not-available bookings are rejected with 400 so stale tickets cannot be resent after a refund or cancellation.
  • Booking must have at least one uploaded ticket file on record (i.e. POST .../ticket has been called at least once previously).
  • Booking must have a contactPerson.email on record.

cURL ​

bash
curl -X POST /api/v1/admin/custom-booking/booking-123/resend-ticket-email \
  -H "Authorization: Bearer <admin-token>"

Response (201) ​

json
{
  "enqueued": true,
  "fileId": "file-uuid-1"
}

Behavior ​

The service looks up the newest custom_booking_ticket file for the booking (entityType = custom_booking_ticket, status = UPLOADED, orderBy createdAt desc), regenerates its R2 presigned download URL, and enqueues a fresh custom-booking-ticket email job with a unique jobId (suffixed with the current timestamp) so the queue's deduplication does not drop repeated resends.

Errors ​

  • 400 Bad Request — Booking is not in TICKET_RECEIVED or COMPLETED, or has no contactPerson.email on record.
  • 404 Not Found — Booking does not exist, or no ticket file has been uploaded yet (upload via POST .../ticket first).

Rate Limit ​

10 requests per 60 seconds per admin.

6. Update a Passenger's Flight PNR / Airline (admin correction) ​

Correct one passenger's airline reservation details — airlineFlightPNR and/or airline. These fields live per-passenger inside the booking's passengers JSON, so the correction targets a single passenger identified by passengerIdNumber (their document ID). Use this when a customer mistyped a PNR or named the wrong carrier for a passenger.

PATCH /admin/custom-booking/:id/flight-info

Request Body ​

FieldTypeRequiredNotes
passengerIdNumberstring (≤50)yesDocument ID (idNumber) of the passenger to correct. Must match exactly one passenger in the manifest. Trimmed server-side.
airlineFlightPNRstring (≤20)at least one of the twoAirline carrier PNR (the operating airline's record locator, not the HHR booking code). Uppercased + trimmed server-side. Omit to leave unchanged.
airlinestring (≤100)at least one of the twoOperating airline / carrier name. Trimmed server-side. Omit to leave unchanged.
reasonstring (≤500)noFree-text reason, recorded in the audit log.
json
{
  "passengerIdNumber": "A12345678",
  "airlineFlightPNR": "XYZ789",
  "airline": "flynas",
  "reason": "Customer corrected PNR over the phone"
}

Behavior ​

  • At least one of airlineFlightPNR / airline must be supplied — a payload that sets neither (or only nulls) is rejected with 400. An empty/blank string for a supplied field is also rejected.
  • Only the supplied field(s) on the matched passenger are updated; an omitted (or null) field, and every other passenger field, is left unchanged.
  • The update and an audit-log entry (CUSTOM_BOOKING_FLIGHT_INFO_UPDATE, with passengerIdNumber + per-field previous / next values) are written in a single transaction.
  • No status guard — corrections are allowed at any status (the audit log is the control). Does not alter pricing, status, or any other passenger field.

cURL ​

curl -X PATCH /api/v1/admin/custom-booking/booking-123/flight-info \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{ "passengerIdNumber": "A12345678", "airlineFlightPNR": "XYZ789", "airline": "flynas", "reason": "typo fix" }'

Response (200) ​

Returns the full admin booking detail (same shape as GET /admin/custom-booking/:id); the corrected airlineFlightPNR / airline appear on the matched passenger inside passengers.

Errors ​

  • 400 Bad Request — Neither airlineFlightPNR nor airline supplied, or a supplied value is empty/blank or exceeds its max length, or passengerIdNumber is missing.
  • 404 Not Found — Booking does not exist, or no passenger matches passengerIdNumber.
  • 409 Conflict — More than one passenger shares the given passengerIdNumber, so the target is ambiguous.

Rate Limit ​

30 requests per 60 seconds per admin.

7. Side Effect — Passenger Upload, Auto-Confirm & Admin WhatsApp Notification ​

When a customer, guest, or admin successfully submits the passenger list via PATCH /custom-booking/:id/passengers and the booking is currently in PENDING, the server atomically transitions it to UPLOADED_MANIFEST.

The transition uses an updateMany guarded by status: PENDING so concurrent passenger updates are race-safe — only the winning request performs the transition (count === 1); losers are a silent no-op (count === 0).

On the winning transition (and only the winning transition) the server enqueues a WhatsApp job to notify the admin phone configured under the CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE system config key (see System Configuration).

Message format (plain text, English) — ONE_WAY:

Booking Code: {bookingCode}
Date: {DD/MM/YYYY}
Time: -
From: {origin display name}
To: {destination display name}
Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

Message format — ROUND_TRIP (one block per leg; the return leg runs the opposite direction, destination → origin, dated by returnDate):

Booking Code: {bookingCode}
Trip: Round Trip

Outbound
Date: {departure DD/MM/YYYY}
Time: -
From: {origin display name}
To: {destination display name}

Return
Date: {return DD/MM/YYYY}
Time: -
From: {destination display name}
To: {origin display name}

Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

Pax counts are booking-wide — the schema has no per-leg counts, so both legs cover the same passenger list.

Origin and destination use a small built-in display-name map for the supported HHR stations (DMX, MKX, JED, JXD, KCX) and fall back to the booking's stored originName / destinationName when the code is not in the map.

Manifest attachment (Excel or CSV) ​

When the submitted passenger list is complete (passenger count matches adultCount + childCount + infantCount), the WhatsApp message also carries a generated manifest file as an attachment, with the text message as its caption. The file is uploaded to R2 under tmp/wa-manifest/{bookingId}/{uuid}.{xlsx|csv} and only the object key travels through the queue — see R2 Lifecycle Rule: Temp Manifest Attachments.

The format is selected by the CUSTOM_BOOKING_ADMIN_MANIFEST_FORMAT environment variable:

  • Unset or any value other than csv → Excel (.xlsx, default).
  • csv → importer-friendly semicolon-delimited CSV (per-passenger rows only, no trip summary).

Excel layout. A summary table leads with a Trip column — a ONE_WAY booking renders a single Outbound row; a ROUND_TRIP booking adds a Return row (stations swapped, dated by returnDate, same booking-wide pax counts):

TripDateTimeFromToPax NumberAdultKid (2 - 12)Baby (< 2 years)
Outbound18/06/2026-Madinah Al-Munawwarah, Madinah (DMX)Makkah Al-Mukarramah, Makkah (MKX)101000
Return30/06/2026-Makkah Al-Mukarramah, Makkah (MKX)Madinah Al-Munawwarah, Madinah (DMX)101000

Below the summary, a passenger detail section lists one row per passenger: No, Passport Name, Type, Sex, Date Of Birth, Nationality, Passport Number, Expiry Date, Airline, PNR. One manifest covers both legs — airline/PNR are per-passenger and trip-wide.

Fail-soft. Manifest generation or the R2 upload failing downgrades the notification to text-only (logged as warn); it never blocks the passenger update or the message itself.

Fail-soft. The notification path cannot fail the passenger update. Each of the following cases logs a warn and silently skips the job:

  • CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE not configured or empty.
  • Configured phone fails international-format validation (e.g. leading 0, non-digit characters, wrong length).
  • The queue producer throws while enqueuing.

The WhatsApp job type is custom-booking-admin with a stable jobId of custom-booking-admin-{bookingId} so duplicate dispatches for the same booking are deduped by the queue.

Auto-Confirm on Manifest Upload (default ON) ​

Immediately after the admin WhatsApp notification, the same winning transition auto-confirms the booking — UPLOADED_MANIFEST → CONFIRMED — without an admin review step. This is the new default behaviour.

It is gated by the CUSTOM_BOOKING_AUTO_CONFIRM_ON_MANIFEST system config key (see System Configuration):

  • Unset or any value other than "false" → auto-confirm ON (default).
  • "false" → auto-confirm OFF; the booking parks at UPLOADED_MANIFEST and an admin confirms manually via PATCH .../status (the legacy gate).

The auto-confirm runs the exact same CONFIRMED code path as a manual admin confirm — so it triggers the invoice auto-generation and the customer confirmation email side effects (the payment instruction is delivered later, when the customer picks a method — see customer payment instruction). Note that auto-confirm does not set a capital source (ticketChannelId is omitted), so the booking lands at capitalPriceTotalSAR: 0 — an admin attaches the source afterwards via PATCH .../source.

Fail-soft. Auto-confirm cannot fail the passenger upload. If anything in the CONFIRMED transition throws, the server logs a warn and leaves the booking at UPLOADED_MANIFEST for an admin to confirm manually — the passenger-upload response still returns 200.

8. Side Effect — Manifest Download Auto-Transition (legacy fallback) ​

Legacy fallback only. New bookings advance to WAITING_FOR_TICKET automatically when payment settles (skip-PAID — see the status diagram and §10), so they never rest in PAID for this side effect to act on. This auto-transition now matters only for pre-change rows still sitting in PAID.

When an admin downloads a manifest file (see Custom Booking Manifests) for a booking currently in PAID, the booking is automatically transitioned to WAITING_FOR_TICKET. This happens inside the manifest download handler — there is no separate endpoint to call.

The transition is silently skipped if the booking is in any other status (already past this stage, still pending payment, etc.) — which is now the common case, since new bookings are already in WAITING_FOR_TICKET.

If the manifest is delivered to the channel out-of-band (e.g. forwarded from a previous download, or for a legacy row still in PAID), an admin can move the booking to WAITING_FOR_TICKET manually via PATCH /admin/custom-booking/:id/status with { "status": "WAITING_FOR_TICKET" }. The transition follows the same VALID_TRANSITIONS rules as any other status change — no ticket channel or additional payload is required.

9. Hourly Auto-Complete Cron (legacy-only) ​

A scheduled job (@Cron(EVERY_HOUR)) runs every hour to finalize any legacy booking still in TICKET_RECEIVED after the trip date has passed. The new ticket-upload flow already transitions bookings to COMPLETED synchronously, so this cron only affects rows that were already in TICKET_RECEIVED before the flow changed (or rows that an admin manually set back to TICKET_RECEIVED).

  • Selector: status = TICKET_RECEIVED AND departureDate < now - 24h.
  • Action: Set status = COMPLETED and stamp autoCompletedAt = now.
  • Guard: updateMany is filtered by both id and status so concurrent customer confirmations cannot be overwritten (race-safe; a zero-count update is treated as a benign race).

The autoCompletedAt field on CustomBooking is null for bookings completed by admin ticket upload or by manual customer confirmation, and a timestamp when the cron completed the booking. Operators can use this to distinguish the completion source in reports.

10. Side Effect — Admin Payment-Success WhatsApp Notification ​

When a Xendit payment webhook settles the invoice linked to a custom booking and the booking advances WAITING_FOR_PAYMENT (or WAITING_PAYMENT_REVIEW) → WAITING_FOR_TICKET (skip-PAID), the server enqueues a WhatsApp job to the admin phone configured under CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE (see System Configuration) — the same phone used for the manifest-upload alert.

Scope — Xendit webhook only. The notification fires only for the gateway-webhook settlement path with the Xendit gateway. It does not fire for manual-transfer proof approvals or the admin "mark invoice paid" override, which also advance the booking to WAITING_FOR_TICKET — those are admin-initiated, so the admin already knows. The dispatch is gated on the settlement trigger (WEBHOOK) and the payment gateway (XENDIT).

Idempotent. The settlement flip is a status-guarded updateMany scoped to the waiting-for-payment states; a re-delivered webhook finds the booking already advanced out of those states (count === 0) and the notification is skipped. The admin is notified exactly once per booking, on the delivery that actually performs the transition.

Message format (plain text, English):

✅ Payment Received

Booking Code: {bookingCode}
Date: {DD Mon YYYY}
Time: -
From: {origin display name}
To: {destination display name}
Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

Amount Paid: {invoice total in the booking currency, e.g. Rp 6.250.000}
Paid At: {DD Mon YYYY, HH:mm in Asia/Riyadh}
Payment: Xendit

The summary block (booking code, route, pax) mirrors the manifest-upload caption — same station display-name map and fallback to stored originName / destinationName. Amount Paid renders the invoice totalAmount in the booking's own currency only (no SAR cross-display), via the shared formatCurrency helper used by the payment-confirmation email. Time is intentionally blank until the outbound flight time is finalized (kept in sync with the manifest caption).

Fail-soft. The notification path can never fail the settlement (the payment is already durably recorded). Each of these cases logs a warn and silently skips the job:

  • CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE not configured or empty.
  • Configured phone fails international-format validation.
  • The queue producer throws while enqueuing.

The WhatsApp job type is custom-booking-admin-payment with a stable jobId of custom-booking-paid-{bookingId} so duplicate dispatches for the same booking are deduped by the queue.
