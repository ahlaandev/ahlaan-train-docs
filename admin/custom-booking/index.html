Custom Booking Management (Admin) ​

This guide covers the admin lifecycle endpoints for custom bookings: status transitions, ticket upload, and the side effects (invoice auto-generation, payment-webhook transitions, manifest-download auto-transition, hourly auto-complete cron).

For manifest file upload/download (separate concern), see Custom Booking Manifests (Admin).

Quick Overview ​

FeatureEndpoint
Update statusPATCH /api/v1/admin/custom-booking/:id/status
Upload ticketPOST /api/v1/admin/custom-booking/:id/ticket
AccessAdmin role (ADMIN) required

Authentication ​

http
Authorization: Bearer <admin-jwt-token>

All admin custom-booking endpoints require ADMIN role.

Status State Machine ​

The booking status field is a VARCHAR(256) whose values are managed by the CustomBookingStatus enum and a strict transition map. Transitions are enforced server-side — invalid transitions return 400 Bad Request.

                ┌─────────┐
                │ PENDING │
                └────┬────┘
                     │
        ┌────────────┼─────────────┐
        ▼            ▼             ▼
  ┌──────────┐ ┌───────────┐ ┌───────────┐
  │ CONFIRMED│ │ CANCELLED │ │ EXPIRED*  │
  └────┬─────┘ └───────────┘ └───────────┘
       │
       ├──────────────────────────► NOT_AVAILABLE
       │
       ▼
  ┌──────────────────┐
  │UPLOADED_MANIFEST │
  └────┬─────────────┘
       ▼
  ┌────────────────────┐
  │WAITING_FOR_PAYMENT │
  └────┬──────────┬────┘
       │          │
       ▼          ▼
   ┌──────┐  ┌─────────┐
   │ PAID │  │ EXPIRED │
   └──┬───┘  └─────────┘
      ▼
  ┌──────────────────────┐
  │DOWNLOADED_MANIFEST   │
  └──────┬───────────────┘
         ▼
  ┌──────────────────┐
  │WAITING_FOR_TICKET│
  └────┬─────────────┘
       ▼
  ┌──────────────────┐
  │ TICKET_RECEIVED  │
  └────┬─────────────┘
       ▼
  ┌───────────┐
  │ COMPLETED │  (terminal)
  └───────────┘

CANCELLED is reachable from every non-terminal state.

* EXPIRED only reachable directly from PENDING and WAITING_FOR_PAYMENT.

Terminal states (no further transitions allowed):
  COMPLETED, CANCELLED, EXPIRED, NOT_AVAILABLE

1. Update Booking Status ​

http
PATCH /admin/custom-booking/:id/status
Authorization: Bearer <admin-token>
Content-Type: application/json

Request Body ​

FieldTypeRequiredNotes
statusenumYesOne of CustomBookingStatus. Must be a valid transition from the current status.
ticketProviderIdstringConditionalRequired when transitioning to CONFIRMED. Must reference an active TicketProvider.

cURL — Confirm with provider ​

bash
curl -X PATCH /api/v1/admin/custom-booking/booking-123/status \
  -H "Authorization: Bearer <admin-token>" \
  -H "Content-Type: application/json" \
  -d '{ "status": "CONFIRMED", "ticketProviderId": "0190abc1-..." }'

Response (200) ​

json
{
  "id": "booking-123",
  "bookingCode": "ABC1234",
  "status": "CONFIRMED",
  "ticketProviderId": "0190abc1-...",
  "ticketProvider": { "id": "0190abc1-...", "name": "HHR", "isActive": true },
  "invoiceId": "inv-456",
  "invoice": { "id": "inv-456", "invoiceNumber": "INV-...", "status": "ISSUED" }
}

Side Effect — Invoice auto-generation ​

When the transition target is CONFIRMED and the booking has no invoiceId, the server calls InvoiceService.generateFromCustomBooking inline. The invoice uses SAR-only pricing derived from the booking's pricePerAdultSAR, pricePerChildSAR, and pricingSnapshot.return (if ROUND_TRIP).

If invoice generation fails, the status update still succeeds and the response body includes a _warnings array:

json
{
  "id": "booking-123",
  "status": "CONFIRMED",
  ...,
  "_warnings": [
    "Invoice auto-generation failed: <error message>. Please generate manually."
  ]
}

In that case, generate the invoice manually via the Invoice Management endpoints.

Side Effect — Payment webhook transitions ​

When a Xendit payment webhook is processed for an invoice linked to a custom booking, the booking is auto-transitioned inside the same Prisma transaction:

Webhook eventBooking transition
Payment paidWAITING_FOR_PAYMENT → PAID
Payment expiredWAITING_FOR_PAYMENT → EXPIRED

If the booking is not in WAITING_FOR_PAYMENT (or the transition is otherwise invalid), the webhook silently logs a warning and skips the booking update — the invoice/payment record itself is still updated.

Errors ​

  • 400 Bad Request — Invalid status value, invalid transition, or attempt to transition from a terminal state.
  • 400 Bad Request — ticketProviderId is required when transitioning to CONFIRMED.
  • 400 Bad Request — Ticket provider '<name>' is not active.
  • 404 Not Found — Booking or ticket provider not found.

2. Upload Ticket ​

Upload the issued ticket PDF for a booking. Automatically transitions the booking from WAITING_FOR_TICKET → TICKET_RECEIVED and emails the customer.

http
POST /admin/custom-booking/:id/ticket
Authorization: Bearer <admin-token>
Content-Type: multipart/form-data

Form Field ​

FieldTypeRequiredNotes
filefileYesThe ticket file (PDF/image). Stored in R2 with entityType: custom_booking_ticket, visibility: PRIVATE.

Pre-conditions ​

  • Booking must exist.
  • Booking status must be WAITING_FOR_TICKET. Any other status returns 400 Bad Request.

cURL ​

bash
curl -X POST /api/v1/admin/custom-booking/booking-123/ticket \
  -H "Authorization: Bearer <admin-token>" \
  -F "file=@HHR-ticket.pdf"

Response (201) ​

json
{
  "id": "file-uuid-1",
  "filename": "HHR-ticket.pdf",
  "mimeType": "application/pdf",
  "size": 102400,
  "visibility": "PRIVATE",
  "entityType": "custom_booking_ticket",
  "entityId": "booking-123",
  "uploadedAt": "2026-04-13T10:00:00.000Z"
}

Side Effect — Ticket email to customer ​

After the file is stored and the status is updated, an email is queued via the EmailJobData queue with:

  • emailType: custom-booking-ticket
  • to: contactPerson.email
  • subject: Tiket Pemesanan Anda Telah Tersedia - <bookingCode>
  • attachmentUrls: [<R2 presigned download URL>]

Email failures are logged but do not fail the upload — the file is saved and the status is already TICKET_RECEIVED. If the booking has no contactPerson.email, the email is skipped with a warning.

See the email template at src/modules/email/templates/custom-booking-ticket.template.ts for the exact body.

Errors ​

  • 400 Bad Request — File is required (no file form field).
  • 400 Bad Request — Booking is not in WAITING_FOR_TICKET.
  • 404 Not Found — Booking does not exist.

3. Side Effect — Manifest Download Auto-Transition ​

When an admin downloads a manifest file (see Custom Booking Manifests) for a booking currently in PAID, the booking is automatically transitioned to DOWNLOADED_MANIFEST. This happens inside the manifest download handler — there is no separate endpoint to call.

The transition is silently skipped if the booking is in any other status (already downloaded, still pending payment, etc.).

4. Hourly Auto-Complete Cron ​

A scheduled job (@Cron(EVERY_HOUR)) runs every hour and finalizes any booking that has been delivered but not customer-confirmed:

  • Selector: status = TICKET_RECEIVED AND departureDate < now - 24h.
  • Action: Set status = COMPLETED and stamp autoCompletedAt = now.
  • Guard: updateMany is filtered by both id and status so concurrent customer confirmations cannot be overwritten (race-safe; a zero-count update is treated as a benign race).

The autoCompletedAt field on CustomBooking is null when the customer manually confirmed, and a timestamp when the cron completed the booking. Operators can use this to distinguish manual vs auto completions in reports.
