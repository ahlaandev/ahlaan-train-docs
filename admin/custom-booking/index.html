Custom Booking Management (Admin) ​

This guide covers the admin lifecycle endpoints for custom bookings: status transitions, capital-source assignment, ticket upload, and the side effects (invoice auto-generation, customer confirmation email, customer-initiated payment-instruction delivery, payment-webhook transitions, admin payment-success WhatsApp notification, manifest-download auto-transition, passenger-upload auto-transition + auto-confirm + admin WhatsApp notification, hourly auto-complete cron).

For manifest file upload/download (separate concern), see Custom Booking Manifests (Admin).

Permission-gated (Access Roles). Beyond the ADMIN role, these routes require a fine-grained permission. Reads (list, detail) need custom-bookings:read. Status and flight-info edits need custom-bookings:update. The three capital routes — capital-price, source and recompute-capital — need custom-bookings:write-capital, a separate code: holding custom-bookings:update does not confer them. Ticket upload needs custom-bookings:upload-ticket, and resend-ticket-email needs custom-bookings:resend-ticket. Seeing any money on any of these responses needs custom-bookings:read-pricing — see the migration note below. See Access Roles.

⚠️ Migrating — money fields now need custom-bookings:read-pricing ​

What changed. Permissions used to control only which endpoints a role may call. Once a role could call an endpoint it saw every field that endpoint returned, so any role holding custom-bookings:read — and any role holding the *:read wildcard — received our full cost basis.

A new code, custom-bookings:read-pricing, now gates the money fields on every admin route that returns a booking body. Without it these keys are omitted entirely — absent, never null:

KeyWhere it appears
pricePerAdultSAR, pricePerChildSAR, pricePerInfantSARdetail + write routes
totalPriceSARlist, detail, write routes
totalPriceIDR, totalPriceUSDdetail + write routes
capitalPriceTotalSARlist, detail, capital/flight write routes
pricingSnapshot (incl. capitalPriceHistory)detail + capital/flight write routes
invoice (the whole nested block)detail + capital/flight write routes
manualTransfer (incl. uniqueAmount and our destination bank account)detail only
exchangeRate (the EFFECTIVE, reducer-applied rate)detail only

What still returns without the code. invoiceId and exchangeRateId — pointers, not figures, so the FE can still link out to the invoice, which enforces its own permission. priceSource and isSpecialB2B stay too, as do the booking summary, the passengers, the manifest and the ticket. The list meta (pagination) is untouched.

Why the action segment is read-pricing and not read. The *:read wildcard matches only a literal read action, so read-pricing falls outside it. That is the point — a role built as "read-only, harmless" stops carrying our cost basis. custom-bookings:* and * still confer it, like any other code.

Nothing changed for existing roles on release day. Every role holding custom-bookings:read was granted custom-bookings:read-pricing in the database before the deploy, so the gate begins to bite only when a role is deliberately edited.

write-capital does not imply read-pricing. They are independent codes, so a role that may correct the capital figure still gets a money-free response unless it also holds read-pricing.

The operational point of the split is a role like "may upload tickets, must not see any money": grant custom-bookings:read + custom-bookings:upload-ticket and withhold read-pricing.

⚠️ Migrating — capital writes moved to their own permission ​

What changed. custom-bookings:update used to cover five routes. It now covers two — PATCH .../status and PATCH .../flight-info. The three capital routes moved to the new custom-bookings:write-capital:

CallPermission now
PATCH .../capital-pricecustom-bookings:write-capital
PATCH .../sourcecustom-bookings:write-capital
POST .../recompute-capitalcustom-bookings:write-capital

Wildcard holders (custom-bookings:*, *) are unaffected — they inherit the new code as they do every other one. Nobody else holds it until it is granted in the role builder, so on arrival these three routes answer 403 for every non-wildcard role.

⛔ The ticket-upload screen breaks for upload-only roles. Admin ticket upload is two calls: PATCH .../source and then POST .../ticket. The first one now needs custom-bookings:write-capital, so a role holding only custom-bookings:upload-ticket gets 403 and never reaches the upload. Until the admin UI grows a separate capital-source control and stops chaining the calls, ticket upload works only for wildcard holders — or for roles granted custom-bookings:write-capital as a bridge.

PATCH .../status no longer accepts ticketChannelId. The field is gone from the request. It is not rejected, it is silently dropped, so a client still sending it gets 200 back and no capital source is set. Set the source with PATCH .../source instead.

POST /api/v1/custom-booking prices via the custom-OTA unit-pax probe: the supplier is searched with a fixed 1/1/1 body (so groups within 3 days still price) and the per-passenger fares are scaled to the real adultCount / childCount / infantCount. Beyond the capital fields, pricingSnapshot also carries the special-B2B pricing audit fields (isSpecialB2B copy, baseSellRate, effectiveSellRate, exchangeRateReducerIDR, economyReducerSource, economyPriceCapped / economyPriceCapDetail) — see Special Custom B2B Pricing for their semantics. The top-level isSpecialB2B boolean, by contrast, is returned on both admin and customer detail responses.

exchangeRate.sellRate on this admin detail is the EFFECTIVE rate. The booking's exchangeRateId FK points at the base ExchangeRate row, but a GOLD booking was priced at baseSellRate − exchangeRateReducerIDR, so the exchangeRate block renders sellRate == pricingSnapshot.effectiveSellRate (e.g. 4770 where the base row holds 4920). The other columns — buyRate, source, fetchedAt, id — pass through untouched, so buyRate remains the base figure. Legacy bookings whose snapshot predates effectiveSellRate, and every non-GOLD booking, show the base rate. The customer-facing detail exposes only exchangeRateId (no rate value); the customer sees the effective rate on their invoice. See Which rate is displayed where.

These fields never appear on the customer-facing detail endpoint — FE code that targets the customer flow must not depend on them. Bookings with no capital source carry capitalPriceTotalSAR: 0 and no per-leg capital fields; the snapshot is written when the capital source is set by PATCH .../source (or re-derived by POST .../recompute-capital), or when a figure is typed into PATCH .../capital-price. The capital source is fully decoupled from confirmation: no status transition writes capital, so a booking stays at capitalPriceTotalSAR: 0 until one of those three routes is called. If no TicketChannelRoutePrice row matches when the source is set, the call is refused with 400 and nothing is written — the remedy is to add the route price, or to enter the figure by hand via PATCH .../capital-price. Historical bookings created before the 2026-04-22 migration also carry 0 (additive backfill with DEFAULT 0).

A manual correction is possible for the whole life of a priced booking: PATCH .../capital-price is accepted at every status except CANCELLED, EXPIRED and NOT_AVAILABLE. That matters because the ticket channel normally invoices us after the customer has paid, so the true cost is often only known at WAITING_FOR_TICKET or once the booking has closed. At any status other than CONFIRMED a hand-entered figure is pinned (pricingSnapshot.manualOverride: true) so a later PATCH .../source or POST .../recompute-capital cannot silently replace it with a route-price lookup — those endpoints answer 409 until one of them is sent force: true. No status transition can overwrite it either, because none of them writes capital at all. An edit made at CONFIRMED is deliberately not pinned, which keeps the pre-existing behaviour of that window unchanged.

Payment settlement (Xendit webhook, manual-transfer proof approval, or the
admin "mark invoice paid" override) advances the booking from
WAITING_FOR_PAYMENT / WAITING_PAYMENT_REVIEW **directly to
WAITING_FOR_TICKET** — the PAID state is no longer persisted for new
bookings. PAID remains in the enum and VALID_TRANSITIONS only so rows that
predate this change (and that still rely on the manifest-download
auto-transition, see §8) can close out. The earlier "admin downloads the
manifest to leave PAID" step is no longer required for new bookings.

Admin ticket upload transitions WAITING_FOR_TICKET directly to COMPLETED
and asynchronously emails the ticket to the customer. The older
TICKET_RECEIVED state is a legacy value that remains in the enum only so
rows already in that state can still be closed out via the customer
confirm-received endpoint or the hourly auto-complete cron.

PENDING → UPLOADED_MANIFEST is auto-triggered when a customer (or guest)
submits the passenger list via `PATCH /custom-booking/:id/passengers`.
Manifest **file** upload no longer moves the status. Admins may set it
directly. On the winning transition the server also enqueues a WhatsApp
notification to the admin phone configured under
`CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE` (see
[System Configuration](/admin/system-config/)).

UPLOADED_MANIFEST → CONFIRMED is **auto-triggered by default**: the same
passenger-upload that lands `UPLOADED_MANIFEST` immediately confirms the
booking — generating the invoice and emailing the customer a confirmation
(the payment instruction follows only when the customer picks a method via
`generate-payment`) — without an admin review step. This is gated by the

* EXPIRED is set by the Xendit payment webhook when the payment window
  elapses; reachable from WAITING_FOR_PAYMENT and WAITING_PAYMENT_REVIEW. The
  gateway webhook is the sole trigger — there is no cron fallback, so the
  PaymentStatusUpdateProcessor MUST carry the booking from waiting-for-payment
  to EXPIRED when the gateway reports the invoice expired.

  Manual-transfer (SAR/USD) payments have **no gateway webhook**, so a lapsed
  manual-transfer window does **not** auto-transition the booking to EXPIRED —
  the booking stays in waiting-for-payment and expiry is enforced passively at
  proof-**upload** time: once `expiresAt` passes, a new upload or re-upload is
  rejected with `409` (`Payment has expired; please start a new payment.`). A
  proof submitted before the window closed stays approvable — admin approval
  has no `expiresAt` guard, so a real transfer that arrived in time still
  settles even if review runs late. The manual-transfer window is a fixed,
  configurable span (default 30 minutes,
  `CUSTOM_BOOKING_MANUAL_TRANSFER_EXPIRY_MINUTES`), mirroring the Xendit window
  (`CUSTOM_BOOKING_XENDIT_PAYMENT_EXPIRY_MINUTES`).

Side Effect — Invoice auto-generation ​

When the transition target is CONFIRMED and the booking has no invoiceId, the server calls InvoiceService.generateFromCustomBooking inline. The invoice uses SAR-only pricing derived from the booking's pricePerAdultSAR, pricePerChildSAR, pricePerInfantSAR, and pricingSnapshot.return (if ROUND_TRIP).

A successful confirm therefore lands on WAITING_FOR_PAYMENT, not CONFIRMED. Invoice creation and the CONFIRMED → WAITING_FOR_PAYMENT move happen in one transaction — the invoice row is created and the booking is updated with both the new status and the invoiceId together, so a booking is never left holding an invoice it does not point at. You asked for CONFIRMED and the stored status is already one step further; that is the designed path, not a race. CONFIRMED only persists when invoice generation fails (see the _warnings case below).

Those per-pax fares become the invoice line items directly: one line per pax type per leg, carrying the real passenger count as quantity and the per-passenger fare as the unit price, labelled by route direction (Economy Adult SUB - MED outbound, Economy Adult MED - SUB return). A round trip emits up to 6 lines, a one-way up to 3; zero-count pax types and free infants emit none. Full contract: Invoice → Custom-booking line items.

The invoice also snapshots the buying mitra partner identity (partnerRegistrationNumber / partnerName), which is later forwarded onto the live Xendit invoice — see the payment-instruction side effect below.

If invoice generation fails, the status update still succeeds and the response body includes a _warnings array:

json
{
  "id": "booking-123",
  "status": "CONFIRMED",
  ...,
  "_warnings": [
    "Invoice auto-generation failed: <error message>. Please generate manually."
  ]
}

In that case, generate the invoice manually via the Invoice Management endpoints.

Side Effect — Customer confirmation email ​

On the UPLOADED_MANIFEST → CONFIRMED transition (whether triggered by auto-confirm or by an admin), the server enqueues a confirmation email to the customer (best-effort — a failed/missing email does not roll back the already-committed CONFIRMED transition).

No payment instruction is sent on confirmation. The Xendit link (or SAR/USD bank-transfer details) is delivered only after the customer picks a payment method — see the next section. This lets the customer choose between Xendit and manual transfer before we tell them how/where to pay.

Side Effect — Customer payment instruction (on generate-payment) ​

When the customer (or an admin on their behalf) calls POST /invoice/:id/generate-payment for a custom-booking invoice, the endpoint enqueues a payment-instruction notification on the custom-booking-payment-notification queue. A worker then delivers the instruction matching the chosen gateway:

  1. XENDIT → the hosted Xendit payment link.
  2. MANUAL_TRANSFER (SAR/USD) → the destination bank account (bank name, account number, account holder, optional notes) plus the exact amount to transfer.

For a mitra booking the Xendit invoice additionally carries the partner identity snapshotted on the invoice: the description becomes {invoiceNumber} · {partnerRegistrationNumber} {partnerName} and the Xendit invoice-level metadata carries invoice_number, partner_number, partner_name, custom_booking_id and booking_code for webhook reconciliation. Non-mitra bookings keep the legacy Payment for {invoiceNumber} description and emit no partner keys. See Payment Gateway → Xendit invoice payload.

Delivery prefers WhatsApp to the booking's contactPerson phone and falls back to email when there is no phone on record or the WhatsApp enqueue fails (the fallback reuses the custom-booking-paid email type). The job is keyed by invoiceId + gateway + currency, so switching method re-sends while an identical re-request deduplicates.

This is best-effort — a gateway/queue error does not fail the generate-payment response (the payment row already exists and the FE shows the same details). Other gateways and non-custom-booking invoices do not trigger a notification.

Side Effect — Payment webhook transitions ​

When a Xendit payment webhook is processed for an invoice linked to a custom booking, the booking is auto-transitioned inside the same Prisma transaction:

If the booking is not in one of those states (or the transition is otherwise invalid), the webhook silently logs a warning and skips the booking update — the invoice/payment record itself is still updated.

2. Update Capital Price (admin margin correction) ​

Correct the capital-price basis — what we pay the ticket channel for the seats. Use this when the channel-negotiated cost changes (tariff revision, channel-specific variant, data-entry fix), or when no TicketChannelRoutePrice row matched when the source was set and the basis needs to be entered by hand. Does not alter the customer-facing selling price or the booking status — margin reporting only.

Status guard: allowed at every status except CANCELLED, EXPIRED and NOT_AVAILABLE, which return 400 Bad Request naming the current status. No seats were procured on those three, so there is no supplier cost that belongs on the row — and PATCH .../source and POST .../recompute-capital refuse exactly the same three, so there is no back door by any route.

All three capital-write endpoints now share this one rule. They used to disagree, and nothing principled sat behind the disagreement: an admin could correct a closed booking's capital by hand and re-derive it from the route table, but could not attach the channel that produced it.

The window reaches COMPLETED because the ticket channel normally bills us after the customer has paid — the real cost is frequently not known until the booking is closed.

PENDING and UPLOADED_MANIFEST used to be excluded, and are not any more. The exclusion existed for a concrete reason: the UPLOADED_MANIFEST → CONFIRMED transition used to recompute the capital from TicketChannelRoutePrice, so a figure typed at either status was silently overwritten — and worse, its history entry still read pinned: true, so the audit trail claimed the value was protected while the value itself was gone. That trap is closed at the source: the confirm transition no longer touches capital under any circumstances. The exclusion would refuse an edit for a reason that no longer holds.

⚠️ New order-of-operations trap. Because a pin can now be set before a channel is ever attached, typing a figure at PENDING and then attaching the channel gets you a 409 on what is the ordinary next step of a fresh booking. The pin is behaving exactly as designed. The recommended order is: attach the channel with PATCH .../source first, then correct the figure here — this endpoint is available at every recordable status, so there is no window where that order is impossible.

Pinning. An edit made at any status other than CONFIRMED sets pricingSnapshot.manualOverride: true. While that flag is set, PATCH .../source and POST .../recompute-capital refuse with 409 rather than replace the hand-entered figure with a route-price lookup — which could otherwise drop it to 0 when no route row matches. Sending force: true on either endpoint replaces the value and releases the pin in one action; there is no separate unpin.

An edit made at CONFIRMED is not pinned. That window already worked before this change and a following PATCH .../source still replaces the value silently, so no request that succeeds today starts returning 409. To protect a figure typed at CONFIRMED, re-enter it once the booking reaches WAITING_FOR_PAYMENT.

Status transitions are irrelevant to the pin: none of them writes capital, so there is nothing for the pin to defend against. (capitalChannelMismatch on older bookings was recorded by the confirm transition that used to attach a channel alongside a pinned figure; nothing writes it now.)

⚠️ Releasing a pin needs a route price to exist. force: true on either table-derived route re-derives the basis from TicketChannelRoutePrice, and that lookup now answers 400 when no row matches. PATCH .../capital-price cannot release the pin either: below CONFIRMED it re-sets the flag, and at CONFIRMED an existing true survives untouched. So on an environment where route prices have not been seeded for the channel, a figure typed by mistake stays pinned until they are. Seed the route prices first.

Behavior ​

  1. Recomputes capitalPriceTotalSAR using the booking's stored passenger counts: (outboundCap + returnCap) × (adultCount + childCount × 0.5). Infants are excluded. Children are billed at 50% of adult cost, matching the selling-price formula.
  2. Overwrites pricingSnapshot.outbound.capitalPriceSAR (and pricingSnapshot.return.capitalPriceSAR for ROUND_TRIP). Other snapshot fields (pricePerAdultSAR, priceSource, etc.) are left untouched.
  3. Appends a new entry to pricingSnapshot.capitalPriceHistory recording the previous values, the next values, the acting admin, and the optional reason. Manual entries also carry source: "MANUAL", editedAtStatus (the booking status at the moment of the edit) and pinned.
  4. Sets pricingSnapshot.manualOverride: true when the edit happens at any status other than CONFIRMED — including PENDING and UPLOADED_MANIFEST, which this endpoint now accepts. At CONFIRMED the key is not written at all — absence is what "not pinned" looks like. Also clears pricingSnapshot.capitalResolutionGap and pricingSnapshot.capitalChannelMismatch if either is present: a human has just entered the correct figure, so both markers are stale.
  5. Writes an AuditLog row with action = "CUSTOM_BOOKING_CAPITAL_PRICE_UPDATE", entity = "CustomBooking", entityId = :id, and the history entry under newValue (oldValue is null — CustomBooking is not in the audit-entity registry, so no pre-mutation snapshot is taken).
  6. Atomicity: steps 2–5 run inside a single prisma.$transaction. If the audit write fails, the booking update is rolled back — a booking will never be mutated without a matching audit row.

Two audit rows are written per call, not one. Alongside the transactional row above, the global audit interceptor writes its own row with action = "UPDATE_CUSTOM-BOOKING" and entity = "custom-booking" — and its entityId is the last URL segment (capital-price, source, recompute-capital), not the booking id, because CustomBooking is not in the audit-entity registry and resolution falls back to the URL path. The booking id is recoverable only from metadata.url. To pull the capital trail for one booking, filter on entity=CustomBooking — a query keyed on the interceptor rows cannot be narrowed to a booking at all. The interceptor also records failed attempts (UPDATE_CUSTOM-BOOKING_FAILED / CREATE_CUSTOM-BOOKING_FAILED with metadata.error), whereas a refused call writes no transactional row — every guard throws before the transaction opens. See Audit Logs.

Notes for frontend ​

  • Status guard — the endpoint accepts every status except CANCELLED, EXPIRED and NOT_AVAILABLE, which return 400 Bad Request naming the current status. Gate the edit control on that deny-list, not on an allow-list: the old seven-status allow-list is gone and PENDING / UPLOADED_MANIFEST are now accepted.

  • An edit at any status other than CONFIRMED pins the value. After such an edit, PATCH .../source and POST .../recompute-capital return 409 on this booking. Handle that 409 with a confirmation dialog that re-sends the same request with force: true, and warn that the hand-entered figure will be replaced.

  • The 409 body is not the OTA error envelope. Every 400 on these routes is normalised into { statusCode, error, message, code, category, retryable }, but the 409 is a plain Nest conflict:

    json
    {
  "message": "This booking has a manually-entered capital price. Changing the source would replace it with the ticket-channel route price. Send force: true to replace it anyway - the previous value, including the per-leg per-adult prices, is preserved in pricingSnapshot.capitalPriceHistory.",

  "statusCode": 409
}

    json
    {"statusCode":400,"error":"Bad Request","message":"Capital price cannot be edited while the booking is CANCELLED. No seats were procured, so there is no supplier cost to record.","code":"UNCODED","category":"VALIDATION","retryable":false}

    A DTO validation failure carries code: "INPUT_VALIDATION", message as an array, and a context.fields breakdown:

    json
    {"statusCode":400,"error":"Bad Request","message":["force must be a boolean value"],"code":"INPUT_VALIDATION","category":"VALIDATION","retryable":false,"context":{"fields":[{"path":"force","constraint":"isBoolean","message":"force must be a boolean value"}]}}

    Render message defensively — it is a string in one case and an array in the other.

  • force is a strict boolean. Implicit type conversion is disabled globally, so the string "true" is rejected with the INPUT_VALIDATION 400 above rather than being coerced. Send a JSON boolean. Equally, an unknown field is stripped silently rather than rejected, so a typo'd flag name reads as "not sent" and the call is refused with the 409 while the caller believes it forced.

  • The endpoint is admin-only; there is no customer equivalent. Capital fields are never exposed on customer detail/list endpoints.

  • capitalPriceHistory is append-only and grows with every call. Render it as a reverse-chronological list when displaying margin history. editedAtStatus tells you where in the lifecycle a correction was made, which is usually the interesting part when a margin figure moves after a booking has closed.

3. Set Capital Source (admin) ​

Set (or change) the capital source — the ticket channel the seats are procured from — independently of confirming the booking or uploading the ticket. This is the canonical (and only reliable) endpoint for setting or changing a booking's ticketChannelId. Confirm first (or let auto-confirm run), then attach the source whenever the procurement channel is decided; call again with a different channel to change it. PATCH .../status cannot do this — it no longer accepts a ticketChannelId and never writes capital.

Snapshots the capital-price basis from the channel's TicketChannelRoutePrice (per leg; adults + children × 0.5, infants excluded), appends a pricingSnapshot.capitalPriceHistory entry, and writes an audit log. Does not change the booking status.

Re-settable at every status except the cancelled family.CANCELLED, EXPIRED and NOT_AVAILABLE are refused with 400 — no seats were procured, so there is no supplier cost to record. Every other status is accepted, including PENDING, UPLOADED_MANIFEST and COMPLETED. Calling again with a different channel re-snapshots the basis and appends another history entry.

COMPLETED used to be refused and is not any more. The guard looked like it protected procurement state on a closed booking, but it did not: POST .../recompute-capital performs the same mutation on a COMPLETED booking and is the more permissive of the two (it accepts an inactive channel where this route refuses one), so the stricter endpoint was the blocked one. It also broke a concrete admin task — re-uploading a corrected ticket on a closed booking, which the upload flow performs as PATCH .../source followed by the file upload, and which therefore failed at the first call even though uploadTicket itself accepts COMPLETED.

Setting a source on a PENDING or UPLOADED_MANIFEST booking is allowed but rarely useful — the UPLOADED_MANIFEST → CONFIRMED transition recomputes the capital from TicketChannelRoutePrice whenever a ticketChannelId is supplied, so the basis is re-derived anyway (unless the figure is pinned, in which case that transition now leaves it alone). The normal flow is to confirm (or let auto-confirm run) and attach the source afterwards.

All three capital endpoints now share this one status rule — the two that used to disagree with it, PATCH .../capital-price and this one, were both moved onto it.

⛔ A capital basis that cannot be derived is refused, not silently written as 0. If no active TicketChannelRoutePrice row matches a leg's (channel, origin, destination, tripClass, tripType), this call returns 400 and writes nothing — the booking is never left showing one channel while its capital came from another. Previously it returned 200 with capitalPriceTotalSAR = 0, which was the typical outcome of attaching a channel, not an edge case.

There is no per-request override. A genuinely free or comped procurement is recorded as a TicketChannelRoutePrice row with capitalPrice: 0 — the zero belongs to the route and channel, where it is dated, attributable, and correct for every later booking, rather than to one request where it survives only inside a JSON history blob. See the error list below for the five distinct causes and what each one means.

A seat comped for this booking only is still covered: attach the channel against the real route price, then correct the figure with PATCH .../capital-price, which accepts every recordable status.

Refuses to overwrite a hand-entered capital price. If the booking carries pricingSnapshot.manualOverride: true — set by PATCH .../capital-price at any status other than CONFIRMED — this call returns 409 Conflict instead of replacing the figure with a route-price lookup. Send force: true to replace it anyway; that also releases the pin, and the replaced value (total and both per-leg per-adult figures) is preserved in the capitalPriceHistory entry that the forced write appends.

⚠️ A pinned booking's ticket cannot be uploaded from the admin screen. The upload dialog calls this endpoint before it sends the file, and the admin client sends no force, so a booking whose capital was typed by hand answers 409 and the file never leaves the browser. This is not new — it has been true since the pin shipped — but it is easier to hit now that a pin can be set at PENDING. The remedy is to call this endpoint with force: true through the API first, then retry the upload from the screen.

Guard order is booking-level first. The unrecordable-status 400 fires before the 409, the 409 fires before the channel is looked up — so a pinned booking sent an unknown ticketChannelId answers 409, not 404 — and the capital 400 fires last of all, after the channel has been validated. Fix the pin first, then the channel, then the route price.

4. Recompute Capital (bypass terminal guard, admin) ​

Recompute capitalPriceTotalSAR by re-running the ticket-channel route-price resolver, including on a COMPLETED booking — deliberately bypassing the terminal-status guard that PATCH .../source and PATCH .../status enforce. Use this to fix a frozen capital basis on a closed booking after the underlying TicketChannelRoutePrice data was corrected — the canonical case being a route that had no matching row and resolved to 0 (the DMX→MKX / PAD29AN incident). Once the route price is added, this endpoint re-resolves the same basis the confirm/source flow uses (150 × 10 = 1500) with no new pricing logic.

The bypass covers COMPLETED, and only COMPLETED. PATCH .../status still rejects terminal bookings outright. PATCH .../source no longer does — it now shares this route's status rule — so this endpoint is no longer the single way to correct a closed booking's basis: .../source re-derives it too, and .../capital-price sets it by hand. What remains distinctive here is the mandatory reason, and the fact that this route defaults to the booking's own channel rather than requiring one. The reason stays mandatory because a documented invariant is being overridden, and every call lands in the audit log and pricingSnapshot.capitalPriceHistory.

CANCELLED, EXPIRED and NOT_AVAILABLE are refused with 400. No seats were procured on those bookings, so there is no supplier cost that belongs on the row — by this route or by PATCH .../capital-price, which refuses the same three. The two endpoints deliberately agree here: writing a cost onto a booking that earned no revenue silently distorts every margin view built over these rows. A real cancellation penalty charged by the channel is a genuine cost with no home today; recording it needs an agreed accounting treatment first, and is not blocked here by oversight.

Guard order. The status check is the first guard after the booking lookup, so a cancelled booking answers 400 ahead of the missing-source 400, the manual-override 409 and the channel 404 alike. force releases the manual pin only — it does not release this guard.

capitalPriceTotalSAR is admin-internal accounting only — it never feeds the customer selling price, status, tickets, invoices, or refunds, so recomputing it on a COMPLETED booking cannot alter the customer contract.

Behavior ​

  1. Refuses with 400 when the booking is CANCELLED, EXPIRED or NOT_AVAILABLE. This is the first guard after the booking lookup, so it answers ahead of every check below, and force does not release it.
  2. Resolves the channel from ticketChannelId (body) or the booking's assigned channel; 400 if neither is present.
  3.   4. Re-runs computeCapitalSnapshot — the same resolver used by PATCH .../source (per leg; adults + children × 0.5, infants excluded).
  5.   6. Writes an AuditLog row with action = "CUSTOM_BOOKING_CAPITAL_RECOMPUTE", entity = "CustomBooking", entityId = :id, history entry under newValue. The interceptor writes a second, separate row (CREATE_CUSTOM-BOOKING, entityId = "recompute-capital") — see the audit note in §2.
  7. Atomicity: steps 5–6 run in a single prisma.$transaction — the booking is never mutated without a matching audit row.
  8. A recomputed total of 0 is a legitimate result only when the route-price row itself carries capitalPrice: 0 — a genuinely free or comped procurement, recorded on the route and channel where it is dated and attributable. A missing or deactivated row is no longer returned as 0: it is refused with 400 naming the lookup tuple and the endpoint that fixes it. A silent 0 was a wrong cost basis returned with a 200, and it was the typical outcome of attaching a channel, not an edge case.

  • No status guard — corrections are allowed at any status (the audit log is the control). Does not alter pricing, status, or any other passenger field.

cURL ​

curl -X PATCH /api/v1/admin/custom-booking/booking-123/flight-info \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{ "passengerIdNumber": "A12345678", "airlineFlightPNR": "XYZ789", "airline": "flynas", "reason": "typo fix" }'

Response (200) ​

Returns the full admin booking detail (same shape as GET /admin/custom-booking/:id); the corrected airlineFlightPNR / airline appear on the matched passenger inside passengers.

Errors ​

  • 400 Bad Request — Neither airlineFlightPNR nor airline supplied, or a supplied value is empty/blank or exceeds its max length, or passengerIdNumber is missing.
  • 404 Not Found — Booking does not exist, or no passenger matches passengerIdNumber.
  • 409 Conflict — More than one passenger shares the given passengerIdNumber, so the target is ambiguous.

Rate Limit ​

30 requests per 60 seconds per admin.

8. Side Effect — Passenger Upload, Auto-Confirm & Admin WhatsApp Notification ​

When a customer, guest, or admin successfully submits the passenger list via PATCH /custom-booking/:id/passengers and the booking is currently in PENDING, the server atomically transitions it to UPLOADED_MANIFEST.

The transition uses an updateMany guarded by status: PENDING so concurrent passenger updates are race-safe — only the winning request performs the transition (count === 1); losers are a silent no-op (count === 0).

On the winning transition (and only the winning transition) the server enqueues a WhatsApp job to notify the admin phone configured under the CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE system config key (see System Configuration).

Message format (plain text, English) — ONE_WAY:

Booking Code: {bookingCode}
Date: {DD/MM/YYYY}
Time: -
From: {origin display name}
To: {destination display name}
Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

Message format — ROUND_TRIP (one block per leg; the return leg runs the opposite direction, destination → origin, dated by returnDate):

Booking Code: {bookingCode}
Trip: Round Trip

Outbound
Date: {departure DD/MM/YYYY}
Time: -
From: {origin display name}
To: {destination display name}

Return
Date: {return DD/MM/YYYY}
Time: -
From: {destination display name}
To: {origin display name}

Pax Number: {adult + child + infant}
Adult: {adultCount}

Pax counts are booking-wide — the schema has no per-leg counts, so both legs cover the same passenger list.

Origin and destination use a small built-in display-name map for the supported HHR stations (DMX, MKX, JED, JXD, KCX) and fall back to the booking's stored originName / destinationName when the code is not in the map.

Manifest attachment (Excel or CSV) ​

When the submitted passenger list is complete (passenger count matches adultCount + childCount + infantCount), the WhatsApp message also carries a generated manifest file as an attachment, with the text message as its caption. The file is uploaded to R2 under tmp/wa-manifest/{bookingId}/{uuid}.{xlsx|csv} and only the object key travels through the queue — see R2 Lifecycle Rule: Temp Manifest Attachments.

The format is selected by the CUSTOM_BOOKING_ADMIN_MANIFEST_FORMAT environment variable:

  • Unset or any value other than csv → Excel (.xlsx, default).
  • csv → importer-friendly semicolon-delimited CSV (per-passenger rows only, no trip summary).

Excel layout. A summary table leads with a Trip column — a ONE_WAY booking renders a single Outbound row; a ROUND_TRIP booking adds a Return row (stations swapped, dated by returnDate, same booking-wide pax counts):

Fail-soft. Manifest generation or the R2 upload failing downgrades the notification to text-only (logged as warn); it never blocks the passenger update or the message itself.

Fail-soft. The notification path cannot fail the passenger update. Each of the following cases logs a warn and silently skips the job:

  • CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE not configured or empty.
  • Configured phone fails international-format validation (e.g. leading 0, non-digit characters, wrong length).
  • The queue producer throws while enqueuing.

The WhatsApp job type is custom-booking-admin with a stable jobId of custom-booking-admin-{bookingId} so duplicate dispatches for the same booking are deduped by the queue.

Auto-Confirm on Manifest Upload (default ON) ​

Immediately after the admin WhatsApp notification, the same winning transition auto-confirms the booking — UPLOADED_MANIFEST → CONFIRMED — without an admin review step. This is the new default behaviour.

It is gated by the CUSTOM_BOOKING_AUTO_CONFIRM_ON_MANIFEST system config key (see System Configuration):

  • Unset or any value other than "false" → auto-confirm ON (default).
  • "false" → auto-confirm OFF; the booking parks at UPLOADED_MANIFEST and an admin confirms manually via PATCH .../status (the legacy gate).

The auto-confirm runs the exact same CONFIRMED code path as a manual admin confirm — so it triggers the invoice auto-generation and the customer confirmation email side effects (the payment instruction is delivered later, when the customer picks a method — see customer payment instruction). Note that auto-confirm does not set a capital source — no confirm path does — so the booking lands at capitalPriceTotalSAR: 0 — an admin attaches the source afterwards via PATCH .../source.

Fail-soft. Auto-confirm cannot fail the passenger upload. If anything in the CONFIRMED transition throws, the server logs a warn and leaves the booking at UPLOADED_MANIFEST for an admin to confirm manually — the passenger-upload response still returns 200.

9. Side Effect — Manifest Download Auto-Transition (legacy fallback) ​

Legacy fallback only. New bookings advance to WAITING_FOR_TICKET automatically when payment settles (skip-PAID — see the status diagram and §10), so they never rest in PAID for this side effect to act on. This auto-transition now matters only for pre-change rows still sitting in PAID.

When an admin downloads a manifest file (see Custom Booking Manifests) for a booking currently in PAID, the booking is automatically transitioned to WAITING_FOR_TICKET. This happens inside the manifest download handler — there is no separate endpoint to call.

The transition is silently skipped if the booking is in any other status (already past this stage, still pending payment, etc.) — which is now the common case, since new bookings are already in WAITING_FOR_TICKET.

If the manifest is delivered to the channel out-of-band (e.g. forwarded from a previous download, or for a legacy row still in PAID), an admin can move the booking to WAITING_FOR_TICKET manually via PATCH /admin/custom-booking/:id/status with { "status": "WAITING_FOR_TICKET" }. The transition follows the same VALID_TRANSITIONS rules as any other status change — no ticket channel or additional payload is required.

10. Hourly Auto-Complete Cron (legacy-only) ​

A scheduled job (@Cron(EVERY_HOUR)) runs every hour to finalize any legacy booking still in TICKET_RECEIVED after the trip date has passed. The new ticket-upload flow already transitions bookings to COMPLETED synchronously, so this cron only affects rows that were already in TICKET_RECEIVED before the flow changed (or rows that an admin manually set back to TICKET_RECEIVED).

  • Selector: status = TICKET_RECEIVED AND departureDate < now - 24h.
  • Action: Set status = COMPLETED and stamp autoCompletedAt = now.
  • Guard: updateMany is filtered by both id and status so concurrent customer confirmations cannot be overwritten (race-safe; a zero-count update is treated as a benign race).

The autoCompletedAt field on CustomBooking is null for bookings completed by admin ticket upload or by manual customer confirmation, and a timestamp when the cron completed the booking. Operators can use this to distinguish the completion source in reports.

11. Side Effect — Admin Payment-Success WhatsApp Notification ​

When a Xendit payment webhook settles the invoice linked to a custom booking and the booking advances WAITING_FOR_PAYMENT (or WAITING_PAYMENT_REVIEW) → WAITING_FOR_TICKET (skip-PAID), the server enqueues a WhatsApp job to the admin phone configured under CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE (see System Configuration) — the same phone used for the manifest-upload alert.

Scope — Xendit webhook only. The notification fires only for the gateway-webhook settlement path with the Xendit gateway. It does not fire for manual-transfer proof approvals or the admin "mark invoice paid" override, which also advance the booking to WAITING_FOR_TICKET — those are admin-initiated, so the admin already knows. The dispatch is gated on the settlement trigger (WEBHOOK) and the payment gateway (XENDIT).

Idempotent. The settlement flip is a status-guarded updateMany scoped to the waiting-for-payment states; a re-delivered webhook finds the booking already advanced out of those states (count === 0) and the notification is skipped. The admin is notified exactly once per booking, on the delivery that actually performs the transition.

Message format (plain text, English):

✅ Payment Received

Booking Code: {bookingCode}
Date: {DD Mon YYYY}
Time: -
From: {origin display name}
To: {destination display name}
Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

Amount Paid: {invoice total in the booking currency, e.g. Rp 6.250.000}
Paid At: {DD Mon YYYY, HH:mm in Asia/Riyadh}

The summary block (booking code, route, pax) mirrors the manifest-upload caption — same station display-name map and fallback to stored originName / destinationName. Amount Paid renders the invoice totalAmount in the booking's own currency only (no SAR cross-display), via the shared formatCurrency helper used by the payment-confirmation email. Time is intentionally blank until the outbound flight time is finalized (kept in sync with the manifest caption).

Fail-soft. The notification path can never fail the settlement (the payment is already durably recorded). Each of these cases logs a warn and silently skips the job:

  • CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE not configured or empty.
  • Configured phone fails international-format validation.
  • The queue producer throws while enqueuing.

The WhatsApp job type is custom-booking-admin-payment with a stable jobId of custom-booking-paid-{bookingId} so duplicate dispatches for the same booking are deduped by the queue.
