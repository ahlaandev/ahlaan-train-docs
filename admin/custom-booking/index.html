Custom Booking Management (Admin) ​

This guide covers the admin lifecycle endpoints for custom bookings: status transitions, capital-source assignment, ticket upload, and the side effects (invoice auto-generation, customer confirmation email, customer-initiated payment-instruction delivery, payment-webhook transitions, admin payment-success WhatsApp notification, manifest-download auto-transition, passenger-upload auto-transition + auto-confirm + admin WhatsApp notification, hourly auto-complete cron).

For manifest file upload/download (separate concern), see Custom Booking Manifests (Admin).

Permission-gated (Access Roles). Beyond the ADMIN role, these routes require a fine-grained permission. Reads (list, detail) need custom-bookings:read. Status and flight-info edits need custom-bookings:update. The three capital routes — capital-price, source and recompute-capital — need custom-bookings:write-capital, a separate code: holding custom-bookings:update does not confer them. Ticket upload needs custom-bookings:upload-ticket, and resend-ticket-email needs custom-bookings:resend-ticket. Releasing an uploaded ticket to the customer — or sending it back — needs custom-bookings:verify-ticket, a separate code that custom-bookings:upload-ticket does not confer, so the admin who obtains the file and the admin who signs it off can be two people. Seeing money on any of these responses needs one of two field codes: custom-bookings:read-pricing for the selling prices and custom-bookings:read-capital-markup for the capital price and the markup — see the migration notes below. See Access Roles.

⚠️ Migrating — money fields now need a field-visibility code ​

⛔ Read the note below this one before acting on the table here. This note describes the original rollout, when a single code carried every money field. capitalPriceTotalSAR, pricingSnapshot and exchangeRate have since moved to custom-bookings:read-capital-markup; every other row is still accurate.

What changed. Permissions used to control only which endpoints a role may call. Once a role could call an endpoint it saw every field that endpoint returned, so any role holding custom-bookings:read — and any role holding the *:read wildcard — received our full cost basis.

A new code, custom-bookings:read-pricing, now gates the money fields on every admin route that returns a booking body. Without it these keys are omitted entirely — absent, never null:

KeyWhere it appears
pricePerAdultSAR, pricePerChildSAR, pricePerInfantSARdetail + write routes
totalPriceSARlist, detail, write routes
totalPriceIDR, totalPriceUSDdetail + write routes
capitalPriceTotalSARlist, detail, capital/flight write routes
pricingSnapshot (incl. capitalPriceHistory)detail + capital/flight write routes
invoice (the whole nested block)detail + capital/flight write routes
manualTransfer (incl. uniqueAmount and our destination bank account)detail only
exchangeRate (the EFFECTIVE, reducer-applied rate)detail only
shortfallRefundLegs, shortfallRefundPerPaxSAR, shortfallRefundTotalSAR (the per-leg refund estimate)detail only
shortfallSettlement (a projection of the settlement row, embedded in the booking)detail only

What still returns without the code. invoiceId and exchangeRateId — pointers, not figures, so the FE can still link out to the invoice, which enforces its own permission. priceSource and isSpecialB2B stay too, as do the booking summary, the passengers, the manifest and the ticket. The list meta (pagination) is untouched. So do the four shortfall keys that are not money — expectedTicketCount, unticketedPaxCount, shortfallReason and shortfallAttachment: they are counts, an explanation and a file, and the ticket staff who record a short delivery hold upload-ticket and read, not read-pricing. They must be able to read back what they themselves wrote.

⚠️ An admin holding refunds:read but not custom-bookings:read-pricing still sees settlement amounts on GET /admin/shortfall-settlements while the booking detail hides the same figures from them. That asymmetry is intended: the settlement routes gate on their own codes and are not stripped.

⚠️ It runs the other way too. The booking detail's shortfallSettlement projection carries shortfallAmountSAR and the settlement leg, so an admin holding custom-bookings:read and custom-bookings:read-pricing reads a settled refund amount without ever holding refunds:read. Withhold read-pricing from a role that must not see refund figures — refunds:read alone is not the boundary for this response.

Why the action segment is read-pricing and not read. The *:read wildcard matches only a literal read action, so read-pricing falls outside it. That is the point — a role built as "read-only, harmless" stops carrying our cost basis. custom-bookings:* and * still confer it, like any other code.

Nothing changed for existing roles on release day. Every role holding custom-bookings:read was granted custom-bookings:read-pricing in the database before the deploy, so the gate begins to bite only when a role is deliberately edited.

write-capital implies no read code. They are independent, so a role that may correct the capital figure still gets a money-free response unless it also holds the matching read code.

The operational point of the split is a role like "may upload tickets, must not see any money": grant custom-bookings:read + custom-bookings:upload-ticket and withhold read-pricing.

⛔ That pair is enough for the API, and not enough for today's admin screen. POST .../ticket reads no ticket channel and writes no capital, so a booking whose ticketChannel is still null uploads fine on upload-ticket alone. The current admin screen chains PATCH .../source in front of the upload and makes the channel field mandatory, so an operator driving that screen also needs custom-bookings:write-capital: read + write-capital + upload-ticket. The coupling lives in the UI, not in the contract. Either way the role sees no money, because write-capital does not imply read-pricing. See §5 Upload Ticket.

⚠️ Migrating — the money gate is now TWO codes, not one ​

What changed. custom-bookings:read-pricing used to be all-or-nothing: it carried the selling prices AND the capital price AND the markup basis in a single grant. There was no way to build a role that quotes a customer their price from the booking screen without also handing it what we pay the ticket channel.

A second code, custom-bookings:read-capital-markup, now takes the cost half. The two are independent in both directions — neither confers the other.

KeyCode that shows it
pricePerAdultSAR, pricePerChildSAR, pricePerInfantSARread-pricing
totalPriceSAR, totalPriceIDR, totalPriceUSDread-pricing
invoice (the whole nested block)read-pricing
manualTransferread-pricing
shortfallRefundLegs, shortfallRefundPerPaxSAR, shortfallRefundTotalSARread-pricing
shortfallSettlementread-pricing
capitalPriceTotalSARread-capital-markup
pricingSnapshot (incl. capitalPriceHistory)read-capital-markup
exchangeRate (the EFFECTIVE, reducer-applied rate)read-capital-markup

Everything the previous note says about what is NOT money — invoiceId, exchangeRateId, priceSource, isSpecialB2B and the four shortfall counts/reason/attachment keys — is unchanged. So is the *:read behaviour: neither action segment is a literal read, so that wildcard confers neither code, while custom-bookings:* and * confer both.

⛔ Rollout requirement, not something already done. Every role holding custom-bookings:read-pricing MUST be granted custom-bookings:read-capital-markup in the database before the new build is deployed, on each database separately. Skip it and every finance role silently loses capitalPriceTotalSAR, pricingSnapshot and exchangeRate until it is run. The UPDATE statement ships in the pull request that introduced this note. Once it has run, no role has lost a field it had the day before, and revoking the new code becomes a deliberate per-role edit.

⛔ invoice.metadata.exchangeRate goes with the cost code, not with invoice. The effective SAR→IDR sell rate is persisted twice: once as the top-level exchangeRate block, and again inside the invoice metadata, written there on every custom-booking invoice at generation. invoice is on the selling side, so a read-pricing caller keeps the block — but that one key is removed from it, because leaving it in place would hand over at full precision the same figure the cost code exists to withhold. Nothing else inside invoice is filtered.

The sell-only column keeps the whole invoice block — totalAmount, metadata.bookingCode, metadata.customBookingId and the rest — and loses exactly one key inside it. custom-bookings:* and * both returned the same payload as the "both" column.

What a sell-only role gives up beyond cost. pricingSnapshot is dropped whole rather than filtered key-by-key, and it also carries the per-leg charged prices and the per-leg legSubtotalSAR / legTaxSAR split. A screen that reads a per-leg breakdown out of the snapshot renders empty for a sell-only role; the six top-level selling figures are what such a role quotes from. That is an accepted limit of a blob-level split, not an oversight. The Berita Acara sheet is the other place this bites — see What a printer needs to hold.

What the split does NOT buy. Three routes back to the same figures are unchanged, and a role holding them recovers the cost basis regardless:

  • totalPriceSAR and totalPriceIDR both stay on read-pricing, so their ratio still approximates the effective rate. Hiding exchangeRate from a sell-only role is defence in depth, not a boundary.
  • custom-route-price and ticket-channel-route-price carry capitalPrice as ordinary data of their own resources. Field gating does not reach them.
  • invoices:read-supplier-cost reaches the cost basis from the invoice side, on its own code and its own decision.

⚠️ And it buys nothing in the other direction. A role holding read-capital-markup WITHOUT read-pricing has the selling-price keys removed, but pricingSnapshot gives them back. It carries the per-leg charged pricePerAdultSAR / pricePerChildSAR / pricePerInfantSAR verbatim, so those need no derivation at all; the three totals then follow, because the per-leg legSubtotalSAR + legTaxSAR sum to what totalPriceSAR stores and effectiveSellRate / usdSarRate give the IDR and USD figures. Withholding read-pricing from a role that holds the cost code hides the fields, not the figures. The boundary this split actually buys runs the other way — sell without cost.

Measured on the same YBHWDWR capture, from the cost-only role's payload alone: pricingSnapshot.outbound.pricePerAdultSAR is 160, the withheld pricePerAdultSAR exactly; legSubtotalSAR 800 + legTaxSAR 0 is the withheld totalPriceSAR of 800; and 800 × effectiveSellRate 4770 is the withheld totalPriceIDR of 3816000. The same payload also carries baseSellRate 4920 beside effectiveSellRate 4770, so exchangeRateReducerIDR 150 is readable without subtracting anything.

write-capital confers neither read code. A role that may correct the capital figure still reads a money-free response back unless it separately holds the matching read code — the same rule as before, now applied to a narrower code.

⚠️ Migrating — capital writes moved to their own permission ​

What changed. custom-bookings:update used to cover five routes. It now covers two — PATCH .../status and PATCH .../flight-info. The three capital routes moved to the new custom-bookings:write-capital:

CallPermission now
PATCH .../capital-pricecustom-bookings:write-capital
PATCH .../sourcecustom-bookings:write-capital
POST .../recompute-capitalcustom-bookings:write-capital

Wildcard holders (custom-bookings:*, *) are unaffected — they inherit the new code as they do every other one. Nobody else holds it until it is granted in the role builder, so on arrival these three routes answer 403 for every non-wildcard role.

⛔ The ticket-upload screen breaks for upload-only roles — the route does not. POST .../ticket needs custom-bookings:upload-ticket and nothing else. The admin screen makes it two calls, PATCH .../source and then POST .../ticket, and the first one now needs custom-bookings:write-capital, so a role holding only custom-bookings:upload-ticket gets 403 on the source call and never reaches the upload. Until the admin UI grows a separate capital-source control and stops chaining the calls, grant those roles custom-bookings:write-capital as a bridge.

PATCH .../status no longer accepts ticketChannelId. The field is gone from the request. It is not rejected, it is silently dropped, so a client still sending it gets 200 back and no capital source is set. Set the source with PATCH .../source instead.

Pricing & seat cap (booking creation). POST /api/v1/custom-booking prices via the custom-OTA unit-pax probe: the supplier is searched with a fixed 1/1/1 body (so groups within 3 days still price) and the per-passenger fares are scaled to the real adultCount / childCount / infantCount. A tier-dependent minimum group size is enforced on the seated count (adultCount + childCount; infants are lap): a GOLD customer gets a lower floor (default 5, CUSTOM_BOOKING_MIN_PASSENGERS_GOLD); every other tier (SILVER / HOLDER) uses the base floor (default 10, CUSTOM_BOOKING_MIN_PASSENGERS). Below the applicable floor returns HTTP 400. The cabin seat limit is enforced — a request whose seated count (adultCount + childCount; infants are lap) exceeds the remaining availableSeats is rejected with HTTP 400 code INSUFFICIENT_SEATS. See the Custom OTA guide for the full mechanism.

The shortfall block ​

Everything the customer-facing "Berita Acara Realisasi" prints that the rest of the response did not already carry. The document itself is generated by the admin screen; these are the figures it reads.

KeyValue

shortfallReasonthe free text recorded at upload, or null
shortfallAttachment{ id, filename, mimeType, size, uploadedAt, downloadUrl }, or null. downloadUrl is the admin route below, not a signed link
shortfallRefundLegsone entry per leg — { leg, originName, destinationName, departureDateTime, perPaxSAR, refundSAR }. One for ONE_WAY, two for ROUND_TRIP with the return entry's route reversed
shortfallRefundPerPaxSARthe legs' perPaxSAR summed

shortfallSettlementa projection of the newest settlement row, or null. Singular, despite the underlying relation being a list. This key is reachable on custom-bookings:read-pricing without refunds:read; the settlement routes serve the full record behind that code

⚠️ The three refund figures are an ESTIMATE, not an accounting figure. Every missing seat is priced at the adult fare, because ticketedPaxCount is one integer and never says which passenger types went un-ticketed — so a booking mixing adults and children is over-refunded here. The document prints "Nilai final akan menyesuaikan hasil konfirmasi dari pihak Finance" beneath the total for exactly this reason, and shortfallAmountSAR on the settlement row — typed by finance — remains the only figure any money moves against.

They are also SAR. The document's IDR column is a client-side conversion at exchangeRate.sellRate, which this response already emits as the effective tier-matched rate.

null rules, which matter more than the happy path:

  • ticketedPaxCount is null on every booking that predates the column and on every booking still waiting for its ticket. When it is, unticketedPaxCount and all three refund figures are null too. Never read that as zero.
  • A fully-delivered booking has no shortfall, so the legs and both money figures are null while the counts still return.
  • A ROUND_TRIP whose pricingSnapshot carries no usable return block yields null for the whole array and for both money figures — never a one-entry array at the outbound price, which would understate the refund on a document the customer keeps.

The four money keys (shortfallRefundLegs, shortfallRefundPerPaxSAR, shortfallRefundTotalSAR, shortfallSettlement) need custom-bookings:read-pricing. The counts, the reason and the attachment do not.

Printing the "Berita Acara Realisasi" in the FE ​

The document is rendered client-side. The API cannot produce it: no PDF or template renderer is in package.json, so there is nothing to build a server-side route on. This response instead carries the figures it prints, so one GET feeds the whole sheet — a second request is needed only to embed the attachment file, which is a binary stream and cannot come back inside JSON.

What a printer needs to hold ​

Three codes, on top of the ADMIN role the controller already requires:

  • custom-bookings:read admits the caller. GET /admin/custom-booking/:id and GET /admin/custom-booking/:id/shortfall-attachment both declare it, so without it there is no partial sheet — both routes answer 403.
  • custom-bookings:read-pricing carries most of what the sheet prints: the Invoice No / Mitra ID / Travel Agency Name header (inside invoice), the per-pax prices and refund totals (inside shortfallRefundLegs and its two sums) and the settled figure (shortfallSettlement). Without it the detail still answers 200, but those keys are deleted from the built body.
  • custom-bookings:read-capital-markup carries one more line, and it is easy to miss: exchangeRate. The sheet's SAR Exchange Rate row and its computed Total Refund (IDR) both read exchangeRate.sellRate, which sits on the cost code because it is the effective rate and discloses the tier reducer. A printer role holding only read-pricing renders every SAR figure and leaves those two cells empty.

⚠️ So a role that prints this document needs three codes, not two:custom-bookings:read + custom-bookings:read-pricing + custom-bookings:read-capital-markup. Granting the third is what makes the IDR column render; withholding it is a deliberate choice to print a SAR-only sheet.

Surviving the strip, and enough to render the sheet's structure without its figures: the three counts, shortfallReason, shortfallAttachment, bookingCode, organization.name, and the route names and dates at the top level. That is deliberate rather than incidental — the ticket staff who record a short delivery must be able to read back what they wrote, and they are not the staff who print the document. See the migration note at the top of this page for the full key list and for why the *:read wildcard misses read-pricing: a role built on that wildcard reaches this endpoint and renders a sheet with no prices on it.

Four things in that capture are worth reading twice, because each is a rule this page states in prose:

  • expectedTicketCount is 6, not 7. Seven passengers were booked; the infant takes no seat and is issued no ticket.

  • The estimate over-refunds. Both un-ticketed passengers were priced at the adult fare (160 SAR per leg) even though this booking carries children at 112. Finance settled at 448, not the estimated 640 — the difference is exactly the two children across two legs. This is the case the "Nilai final akan menyesuaikan…" footnote exists for.

  • sellRate is "4770", a string, and it is the EFFECTIVE rate. This is a GOLD booking whose snapshot carries baseSellRate: 4920 and exchangeRateReducerIDR: 150. Beside it, perPaxSAR, refundSAR, shortfallRefundTotalSAR and shortfallSettlement.shortfallAmountSAR are all plain JSON numbers.

  • settlementRateToSAR is 0.00024 — SAR per rupiah. It is DERIVED on read from settlementRate + settlementRateDirection; on this row those are 0.00024 and FOREIGN_TO_SAR, because the row predates the direction column. A row written after it carries settlementRate: 4166.67 with SAR_TO_FOREIGN instead. Its derived settlementRateToSAR is then 1/4166.67 = 0.0002399998…, not exactly 0.00024. Do not compare the derived reading for equality against a value you sent.

    ⚠️ It is not the reciprocal of the 4770 on the rate line above, and nothing requires it to be. 4770 is the booking's own sell rate; this is the rate the settlement money actually moved at, typed by finance. 1/0.00024 is 4166.67. Do not derive either from the other.

What the FE has to compute or fall back to ​
  • The IDR total. Nothing in the response carries it. Multiply shortfallRefundTotalSAR by exchangeRate.sellRate — that is the direction: sellRate is rupiah per riyal, so the capture above prints 640 × 4770 = 3 052 800. exchangeRate is absent when stripped and when the booking carries no exchangeRateId — in which case the rate line and the IDR total both drop out while the SAR table above them still renders.
  • sellRate is a string. The mapper re-wraps it as a Prisma Decimal so it keeps the Decimal-serialised JSON shape its sibling buyRate has. The shortfall block's own money — perPaxSAR, refundSAR, shortfallRefundTotalSAR, shortfallSettlement.shortfallAmountSAR — is plain JSON numbers. Parse the one, do not parse the others.
  • A leg's departureDateTime can be null, because the stored flight blob is validated only as a short string and nothing has ever established that it holds a date. Fall back to the booking's own column for that leg — departureDate for OUTBOUND, returnDate for RETURN. Both are real dates; neither carries a time.
  • A leg's originName / destinationName can be null — they are nullable columns and this endpoint passes them through raw. The top-level origin and destination are location codes and are never null, so they are the fallback; reverse them for the RETURN row.
  • Print the settled figure when there is one. shortfallSettlement is finance's record of what actually went back, and its shortfallAmountSAR can differ from the estimate above it — for the reason given under the estimate warning. When it is present, print it as the total and drop the "Nilai final akan menyesuaikan…" footnote, which exists precisely because the estimate is provisional. settlementCurrency and settlementAmount describe the transfer itself — when the currency is IDR, settlementAmount is a real rupiah figure and beats converting anything.
  • ⛔ settlementRateToSAR is not sellRate. It reads "one unit of settlementCurrency is this many SAR", so for IDR it is a number near 0.0002 — the reciprocal of the rate the document prints. Multiplying a SAR figure by it produces nonsense.
  • ⛔ settlementRate is not settlementRateToSAR, and its meaning changes per row. Read it only through settlementRateDirection: FOREIGN_TO_SAR means multiply, SAR_TO_FOREIGN means divide. Direction is a property of the ROW, not of the currency — rows written before that column existed are FOREIGN_TO_SAR whatever their currency, and nothing was backfilled. If you only want a SAR-per-unit number, use settlementRateToSAR and ignore the pair entirely.

For when the block comes back empty — a booking with no recorded count, a full delivery, a ROUND_TRIP with no usable return pricing — see the null rules above; each of them blanks the table rather than zeroing it.

These fields never appear on the customer-facing detail endpoint — FE code that targets the customer flow must not depend on them. A manual correction is possible for the whole life of a priced booking: PATCH .../capital-price is accepted at every status except CANCELLED, EXPIRED and NOT_AVAILABLE. That matters because the ticket channel normally invoices us after the customer has paid, so the true cost is often only known at WAITING_FOR_TICKET or once the booking has closed. At any status other than CONFIRMED a hand-entered figure is pinned (pricingSnapshot.manualOverride: true) so a later PATCH .../source or POST .../recompute-capital cannot silently replace it with a route-price lookup — those endpoints answer 409 until one of them is sent force: true. No status transition can overwrite it either, because none of them writes capital at all. An edit made at CONFIRMED is deliberately not pinned, which keeps the pre-existing behaviour of that window unchanged.

  • fundsVerifiedAt / fundsVerifiedByAdminId record the dual-approval step and are distinct from reviewedAt / reviewerId, which stay the final approve-or-reject decision. Both are null on a proof nobody has verified and on rows created before the columns existed.
  • uniqueAmount is the total the customer was instructed to transfer (base amount + 2-digit amountSuffix for matching). Compare against the bank statement before approving.
  • signedDownloadUrl is a 24-hour R2 presigned URL for the uploaded proof image/PDF; it is regenerated on every detail fetch.
  • bankAccount is the expected recipient account snapshot at the time the proof was submitted (not a live lookup), so approvals remain valid even if the active bank-account config changes later.
  • For bookings whose invoice gateway is not MANUAL_TRANSFER, or where no proof has been uploaded yet, manualTransfer is null.

See the Manual Transfer admin guide for the approve/reject endpoints and the full state machine.

Payment settlement (Xendit webhook, manual-transfer proof approval, or the
admin "mark invoice paid" override) advances the booking from

bookings. PAID remains in the enum and VALID_TRANSITIONS only so rows that
predate this change (and that still rely on the manifest-download
auto-transition, see §8) can close out. The earlier "admin downloads the
manifest to leave PAID" step is no longer required for new bookings.

Admin ticket upload NO LONGER closes a booking. The WAITING_FOR_TICKET →
COMPLETED edge is deleted: an upload records `ticketedPaxCount` and derives
TICKET_UPLOADED_FULL or TICKET_UPLOADED_PARTIAL from it, and a manager closes
the booking separately via PATCH .../status. The upload emails NOBODY and shows
the customer nothing — a second admin holding `custom-bookings:verify-ticket`
releases the ticket, and that release is what opens the customer download and
sends the ticket email. No status change sends it. An upload
against an already-COMPLETED booking records the
new file and count and leaves the status COMPLETED — a closed booking is never
re-opened. TICKET_UPLOADED_FULL, TICKET_UPLOADED_PARTIAL and SHORTFALL_REFUNDED
are all non-terminal and are plain VARCHAR values, so adding them needed no
migration. The older TICKET_RECEIVED state is legacy: nothing transitions into
it any more, and rows already there close out via the customer confirm-received
endpoint or the hourly auto-complete cron.

PENDING → UPLOADED_MANIFEST is auto-triggered when a customer (or guest)
submits the passenger list via `PATCH /custom-booking/:id/passengers`.
Manifest **file** upload no longer moves the status. Admins may set it
directly. On the winning transition the server also enqueues a WhatsApp
notification to the admin phone configured under
`CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE` (see
[System Configuration](/admin/system-config/)).

UPLOADED_MANIFEST → CONFIRMED is **auto-triggered by default**: the same
passenger-upload that lands `UPLOADED_MANIFEST` immediately confirms the
booking — generating the invoice and emailing the customer a confirmation
(the payment instruction follows only when the customer picks a method via
`generate-payment`) — without an admin review step. This is gated by the
`CUSTOM_BOOKING_AUTO_CONFIRM_ON_MANIFEST` system config key (default ON;
set to `false` to restore the manual admin-confirm gate). Auto-confirm is
best-effort: a failure leaves the booking at `UPLOADED_MANIFEST` for an
admin to confirm manually via `PATCH .../status`. See
[§8](#_8-side-effect-passenger-upload-auto-confirm-admin-whatsapp-notification).

Customers may also trigger CONFIRMED → CANCELLED via
PATCH /custom-booking/:id/status (see the customer guide). All other
customer-initiated transitions are rejected with 403.

CANCELLED is reachable from every non-terminal state (admin/system).

* EXPIRED is set by the Xendit payment webhook when the payment window
  elapses; reachable from WAITING_FOR_PAYMENT and WAITING_PAYMENT_REVIEW. The
  gateway webhook is the sole trigger — there is no cron fallback, so the
  PaymentStatusUpdateProcessor MUST carry the booking from waiting-for-payment
  to EXPIRED when the gateway reports the invoice expired.

  Manual-transfer (SAR/USD) payments have **no gateway webhook**, so a lapsed
  manual-transfer window does **not** auto-transition the booking to EXPIRED —
  the booking stays in waiting-for-payment and expiry is enforced passively at
  proof-**upload** time: once `expiresAt` passes, a new upload or re-upload is
  rejected with `409` (`Payment has expired; please start a new payment.`). A
  proof submitted before the window closed stays approvable — admin approval
  has no `expiresAt` guard, so a real transfer that arrived in time still
  settles even if review runs late. The manual-transfer window is a fixed,
  configurable span (default 30 minutes,
  `CUSTOM_BOOKING_MANUAL_TRANSFER_EXPIRY_MINUTES`), mirroring the Xendit window
  (`CUSTOM_BOOKING_XENDIT_PAYMENT_EXPIRY_MINUTES`).

Terminal states (no further transitions allowed):
  COMPLETED, CANCELLED, EXPIRED, NOT_AVAILABLE

The four statuses between payment and closure are where the flow is most often misread, because three different people are involved and no one of them can carry a booking from end to end. This section is the whole delivery phase in one place.

The three ways out of TICKET_UPLOADED_PARTIAL ​

  1. The missing tickets arrive. The uploader re-uploads at the full count and the booking becomes TICKET_UPLOADED_FULL. Finance is never involved — this is the ordinary happy ending to a late delivery, and no money moves. Verified end to end on preprod: a 9-of-10 booking re-uploaded at 10 landed on TICKET_UPLOADED_FULL with unticketedPaxCount: 0, and closed normally.
  2. The missing tickets never arrive. Finance transfers the money back at the bank by hand, outside this system, then records that transfer at POST /api/v1/admin/shortfall-settlements. The booking becomes SHORTFALL_REFUNDED. See Shortfall Settlements.
  3. The booking is abandoned → CANCELLED, which is terminal and never reaches COMPLETED.

The customer's "Berita Acara Realisasi" is printed off the shortfall itself — while the booking sits on TICKET_UPLOADED_PARTIAL, and again after path 2, where the settled figure replaces the estimate. Path 1 leaves nothing to print: a re-upload at the full count takes unticketedPaxCount to 0 and the refund figures blank out with it. What the booking detail carries for the document, and the two permission codes the printing admin needs, are in Printing the "Berita Acara Realisasi".

⛔ Paths 1 and 2 are mutually exclusive, and the choice is one-way. Once a settlement exists, the booking's ticketedPaxCount can no longer be changed — in either direction, on any status, including after the manager has closed the booking. A later upload at a raised count is refused with a 400 naming the date the settlement was recorded — and deliberately not the amount, since that route needs no money permission. So whoever decides "the tickets are not coming" is making a decision that cannot be undone through the API. See §5.

The RELEASE is what emails the customer, and what makes the file reachable. An upload does neither, a re-upload sends nothing, and neither does the close. Both delivery routes answer from a fixed set of statuses rather than "everything after" one. The three called-off states (CANCELLED, EXPIRED, NOT_AVAILABLE) are refused by both, so a stale ticket cannot be pulled after a cancellation. COMPLETED is terminal too but delivers from both, so this is not the terminal set:

Because the release is once per booking, that later upload is downloadable the moment it lands — it is delivered, just not announced. Side Effect — Invoice auto-generation ​

When the transition target is CONFIRMED and the booking has no invoiceId, the server calls InvoiceService.generateFromCustomBooking inline. The invoice uses SAR-only pricing derived from the booking's pricePerAdultSAR, pricePerChildSAR, pricePerInfantSAR, and pricingSnapshot.return (if ROUND_TRIP).

A successful confirm therefore lands on WAITING_FOR_PAYMENT, not CONFIRMED. Invoice creation and the CONFIRMED → WAITING_FOR_PAYMENT move happen in one transaction — the invoice row is created and the booking is updated with both the new status and the invoiceId together, so a booking is never left holding an invoice it does not point at. You asked for CONFIRMED and the stored status is already one step further; that is the designed path, not a race. CONFIRMED only persists when invoice generation fails (see the _warnings case below).

Those per-pax fares become the invoice line items directly: one line per pax type per leg, carrying the real passenger count as quantity and the per-passenger fare as the unit price, labelled by route direction (Economy Adult SUB - MED outbound, Economy Adult MED - SUB return). A round trip emits up to 6 lines, a one-way up to 3; zero-count pax types and free infants emit none. Full contract: Invoice → Custom-booking line items.

The invoice also snapshots the buying mitra partner identity (partnerRegistrationNumber / partnerName), which is later forwarded onto the live Xendit invoice — see the payment-instruction side effect below.

If invoice generation fails, the status update still succeeds and the response body includes a _warnings array:

json
{
  "id": "booking-123",
  "status": "CONFIRMED",
  ...,
  "_warnings": [
    "Invoice auto-generation failed: <error message>. Please generate manually."
  ]
}

In that case, generate the invoice manually via the Invoice Management endpoints.

Side Effect — Customer confirmation email ​

On the UPLOADED_MANIFEST → CONFIRMED transition (whether triggered by auto-confirm or by an admin), the server enqueues a confirmation email to the customer (best-effort — a failed/missing email does not roll back the already-committed CONFIRMED transition).

No payment instruction is sent on confirmation. The Xendit link (or SAR/USD bank-transfer details) is delivered only after the customer picks a payment method — see the next section. This lets the customer choose between Xendit and manual transfer before we tell them how/where to pay.

Side Effect — Customer payment instruction (on generate-payment) ​

When the customer (or an admin on their behalf) calls POST /invoice/:id/generate-payment for a custom-booking invoice, the endpoint enqueues a payment-instruction notification on the custom-booking-payment-notification queue. A worker then delivers the instruction matching the chosen gateway:

  1. XENDIT → the hosted Xendit payment link.
  2. MANUAL_TRANSFER (SAR/USD) → the destination bank account (bank name, account number, account holder, optional notes) plus the exact amount to transfer.

For a mitra booking the Xendit invoice additionally carries the partner identity snapshotted on the invoice: the description becomes {invoiceNumber} · {partnerRegistrationNumber} {partnerName} and the Xendit invoice-level metadata carries invoice_number, partner_number, partner_name, custom_booking_id and booking_code for webhook reconciliation. Non-mitra bookings keep the legacy Payment for {invoiceNumber} description and emit no partner keys. See Payment Gateway → Xendit invoice payload.

Delivery prefers WhatsApp to the booking's contactPerson phone and falls back to email when there is no phone on record or the WhatsApp enqueue fails (the fallback reuses the custom-booking-paid email type). The job is keyed by invoiceId + gateway + currency, so switching method re-sends while an identical re-request deduplicates.

This is best-effort — a gateway/queue error does not fail the generate-payment response (the payment row already exists and the FE shows the same details). Other gateways and non-custom-booking invoices do not trigger a notification.

Side Effect — Payment webhook transitions ​

When a Xendit payment webhook is processed for an invoice linked to a custom booking, the booking is auto-transitioned inside the same Prisma transaction:

  • 403 Forbidden — raised inside the handler on status: "COMPLETED" when the role lacks custom-bookings:complete. Distinguishable from the guard's 403 by the body: Closing a booking requires the custom-bookings:complete permission. Uploading the ticket and verifying it are deliberately separate actions.
  • 400 Bad Request — "TICKET_UPLOADED_FULL" cannot be set manually — it is derived from a ticket upload's passenger count. Upload the ticket via POST /admin/custom-booking/<id>/ticket instead. (same for TICKET_UPLOADED_PARTIAL; <id> is the booking's own id), and "SHORTFALL_REFUNDED" cannot be set manually — it is written when the shortfall settlement is recorded.
  • 400 Bad Request — Invalid status value, invalid transition, or attempt to transition from a terminal state.
  • 400 Bad Request — Ticket channel '<name>' is not active (only when a ticketChannelId is supplied).
  • 404 Not Found — Booking or ticket channel not found.
  • 409 Conflict — Cannot change status: booking moved from "TICKET_UPLOADED_FULL" while this request was in flight. Re-read the booking and retry. The write is pinned to the status the transition was validated against, so a booking that moved in between is refused rather than overwritten. The interleaving this exists for: a manager closes a booking while an admin uploads a corrected, lower count. The upload lands first and moves the booking to TICKET_UPLOADED_PARTIAL; an unpinned close would then overwrite that with COMPLETED, closing a booking that owes a refund — and since COMPLETED has no outgoing transition, the refund could never afterwards be recorded.

2. Update Capital Price (admin margin correction) ​

Correct the capital-price basis — what we pay the ticket channel for the seats. Use this when the channel-negotiated cost changes (tariff revision, channel-specific variant, data-entry fix), or when no TicketChannelRoutePrice row matched when the source was set and the basis needs to be entered by hand. Does not alter the customer-facing selling price or the booking status — margin reporting only.

Status guard: allowed at every status except CANCELLED, EXPIRED and NOT_AVAILABLE, which return 400 Bad Request naming the current status. No seats were procured on those three, so there is no supplier cost that belongs on the row — and PATCH .../source and POST .../recompute-capital refuse exactly the same three, so there is no back door by any route.

All three capital-write endpoints now share this one rule. They used to disagree, and nothing principled sat behind the disagreement: an admin could correct a closed booking's capital by hand and re-derive it from the route table, but could not attach the channel that produced it.

The window reaches COMPLETED because the ticket channel normally bills us after the customer has paid — the real cost is frequently not known until the booking is closed.

PENDING and UPLOADED_MANIFEST used to be excluded, and are not any more. The exclusion existed for a concrete reason: the UPLOADED_MANIFEST → CONFIRMED transition used to recompute the capital from TicketChannelRoutePrice, so a figure typed at either status was silently overwritten — and worse, its history entry still read pinned: true, so the audit trail claimed the value was protected while the value itself was gone. That trap is closed at the source: the confirm transition no longer touches capital under any circumstances. The exclusion would refuse an edit for a reason that no longer holds.

⚠️ New order-of-operations trap. Because a pin can now be set before a channel is ever attached, typing a figure at PENDING and then attaching the channel gets you a 409 on what is the ordinary next step of a fresh booking. The pin is behaving exactly as designed. The recommended order is: attach the channel with PATCH .../source first, then correct the figure here — this endpoint is available at every recordable status, so there is no window where that order is impossible.

Pinning. An edit made at any status other than CONFIRMED sets pricingSnapshot.manualOverride: true. While that flag is set, PATCH .../source and POST .../recompute-capital refuse with 409 rather than replace the hand-entered figure with a route-price lookup — which could otherwise drop it to 0 when no route row matches. Sending force: true on either endpoint replaces the value and releases the pin in one action; there is no separate unpin.

An edit made at CONFIRMED is not pinned. That window already worked before this change and a following PATCH .../source still replaces the value silently, so no request that succeeds today starts returning 409. To protect a figure typed at CONFIRMED, re-enter it once the booking reaches WAITING_FOR_PAYMENT.

Status transitions are irrelevant to the pin: none of them writes capital, so there is nothing for the pin to defend against. (capitalChannelMismatch on older bookings was recorded by the confirm transition that used to attach a channel alongside a pinned figure; nothing writes it now.)

⚠️ Releasing a pin needs a route price to exist. force: true on either table-derived route re-derives the basis from TicketChannelRoutePrice, and that lookup now answers 400 when no row matches. PATCH .../capital-price cannot release the pin either: below CONFIRMED it re-sets the flag, and at CONFIRMED an existing true survives untouched. So on an environment where route prices have not been seeded for the channel, a figure typed by mistake stays pinned until they are. Seed the route prices first.

    Infantsstill excluded entirely — that config carries no infant field, so there is no configured infant ratio to honour

    Editing that percentage changes what future capital writes record as cost. Raising the percentage raises recorded cost and therefore lowers reported margin.

    Bookings already written are never touched. A capital figure is frozen on the booking row, and changing the config does not go back and rewrite history — an old booking keeps the total it was given until somebody calls one of the three capital routes on it again.     ⚠️ This deliberately couples cost to a selling-price setting.   2. Overwrites pricingSnapshot.outbound.capitalPriceSAR (and pricingSnapshot.return.capitalPriceSAR for ROUND_TRIP). Other snapshot fields (pricePerAdultSAR, priceSource, etc.) are left untouched.

  3. Appends a new entry to pricingSnapshot.capitalPriceHistory recording the previous values, the next values, the acting admin, and the optional reason. Manual entries also carry source: "MANUAL", editedAtStatus (the booking status at the moment of the edit) and pinned.

  4. Sets pricingSnapshot.manualOverride: true when the edit happens at any status other than CONFIRMED — including PENDING and UPLOADED_MANIFEST, which this endpoint now accepts. At CONFIRMED the key is not written at all — absence is what "not pinned" looks like. Also clears pricingSnapshot.capitalResolutionGap and pricingSnapshot.capitalChannelMismatch if either is present: a human has just entered the correct figure, so both markers are stale.

  5. Writes an AuditLog row with action = "CUSTOM_BOOKING_CAPITAL_PRICE_UPDATE", entity = "CustomBooking", entityId = :id, and the history entry under newValue (oldValue is null — CustomBooking is not in the audit-entity registry, so no pre-mutation snapshot is taken).

  6. Atomicity: steps 2–5 run inside a single prisma.$transaction. If the audit write fails, the booking update is rolled back — a booking will never be mutated without a matching audit row.

Two audit rows are written per call, not one. Alongside the transactional row above, the global audit interceptor writes its own row with action = "UPDATE_CUSTOM-BOOKING" and entity = "custom-booking" — and its entityId is the last URL segment (capital-price, source, recompute-capital), not the booking id, because CustomBooking is not in the audit-entity registry and resolution falls back to the URL path. The booking id is recoverable only from metadata.url. To pull the capital trail for one booking, filter on entity=CustomBooking — a query keyed on the interceptor rows cannot be narrowed to a booking at all. The interceptor also records failed attempts (UPDATE_CUSTOM-BOOKING_FAILED / CREATE_CUSTOM-BOOKING_FAILED with metadata.error), whereas a refused call writes no transactional row — every guard throws before the transaction opens. See Audit Logs.

Notes for frontend ​

  • Status guard — the endpoint accepts every status except CANCELLED, EXPIRED and NOT_AVAILABLE, which return 400 Bad Request naming the current status. Gate the edit control on that deny-list, not on an allow-list: the old seven-status allow-list is gone and PENDING / UPLOADED_MANIFEST are now accepted.

  • An edit at any status other than CONFIRMED pins the value. After such an edit, PATCH .../source and POST .../recompute-capital return 409 on this booking. Handle that 409 with a confirmation dialog that re-sends the same request with force: true, and warn that the hand-entered figure will be replaced.

  • The 409 body is not the OTA error envelope. Every 400 on these routes is normalised into { statusCode, error, message, code, category, retryable }, but the 409 is a plain Nest conflict:

    json
    {
  "message": "This booking has a manually-entered capital price. Changing the source would replace it with the ticket-channel route price. Send force: true to replace it anyway - the previous value, including the per-leg per-adult prices, is preserved in pricingSnapshot.capitalPriceHistory.",

  "statusCode": 409

    — no code, no category, no retryable. Branch on the HTTP status, not on body.code, or the check silently never matches.

  • The 400s come in two envelope flavours, and code distinguishes them. A guard thrown by the service carries code: "UNCODED" and message as a string:

    json
    {"statusCode":400,"error":"Bad Request","message":"Capital price cannot be edited while the booking is CANCELLED. No seats were procured, so there is no supplier cost to record.","code":"UNCODED","category":"VALIDATION","retryable":false}

    json
    {"statusCode":400,"error":"Bad Request","message":["force must be a boolean value"],"code":"INPUT_VALIDATION","category":"VALIDATION","retryable":false,"context":{"fields":[{"path":"force","constraint":"isBoolean","message":"force must be a boolean value"}]}}

  • The endpoint is admin-only; there is no customer equivalent. Capital fields are never exposed on customer detail/list endpoints.

3. Set Capital Source (admin) ​

Set (or change) the capital source — the ticket channel the seats are procured from — independently of confirming the booking or uploading the ticket. This is the canonical (and only reliable) endpoint for setting or changing a booking's ticketChannelId. Confirm first (or let auto-confirm run), then attach the source whenever the procurement channel is decided; call again with a different channel to change it. PATCH .../status cannot do this — it no longer accepts a ticketChannelId and never writes capital.

Snapshots the capital-price basis from the channel's TicketChannelRoutePrice (per leg; adults + children × childRatio, infants excluded), appends a pricingSnapshot.capitalPriceHistory entry, and writes an audit log. Does not change the booking status.

Re-settable at every status except the cancelled family.CANCELLED, EXPIRED and NOT_AVAILABLE are refused with 400 — no seats were procured, so there is no supplier cost to record. Every other status is accepted, including PENDING, UPLOADED_MANIFEST and COMPLETED. Calling again with a different channel re-snapshots the basis and appends another history entry.

COMPLETED used to be refused and is not any more. The guard looked like it protected procurement state on a closed booking, but it did not: POST .../recompute-capital performs the same mutation on a COMPLETED booking and is the more permissive of the two (it accepts an inactive channel where this route refuses one), so the stricter endpoint was the blocked one. It also broke a concrete admin task — re-uploading a corrected ticket on a closed booking, which the admin screen performs as PATCH .../source followed by the file upload, and which therefore failed at the first call even though the upload route itself accepts COMPLETED and never asks about the channel.

Setting a source on a PENDING or UPLOADED_MANIFEST booking is allowed, and what it writes sticks — no status transition re-derives it. Confirming a booking writes the status and nothing else, so a source attached before confirmation survives it unchanged, and a booking confirmed without one stays at capitalPriceTotalSAR: 0 until one of the three capital routes is called. Attach the source before or after confirmation as suits the workflow; only PATCH .../source, PATCH .../capital-price and POST .../recompute-capital ever write the basis.

All three capital endpoints now share this one status rule — the two that used to disagree with it, PATCH .../capital-price and this one, were both moved onto it.

⛔ A capital basis that cannot be derived is refused, not silently written as 0. If no active TicketChannelRoutePrice row matches a leg's (channel, origin, destination, tripClass, tripType), this call returns 400 and writes nothing — the booking is never left showing one channel while its capital came from another. Previously it returned 200 with capitalPriceTotalSAR = 0, which was the typical outcome of attaching a channel, not an edge case.

There is no per-request override. A genuinely free or comped procurement is recorded as a TicketChannelRoutePrice row with capitalPrice: 0 — the zero belongs to the route and channel, where it is dated, attributable, and correct for every later booking, rather than to one request where it survives only inside a JSON history blob. See the error list below for the five distinct causes and what each one means.

A seat comped for this booking only is still covered: attach the channel against the real route price, then correct the figure with PATCH .../capital-price, which accepts every recordable status.

Refuses to overwrite a hand-entered capital price. If the booking carries pricingSnapshot.manualOverride: true — set by PATCH .../capital-price at any status other than CONFIRMED — this call returns 409 Conflict instead of replacing the figure with a route-price lookup. Send force: true to replace it anyway; that also releases the pin, and the replaced value (total and both per-leg per-adult figures) is preserved in the capitalPriceHistory entry that the forced write appends.

⚠️ A pinned booking's ticket cannot be uploaded from the admin screen. The upload dialog calls this endpoint before it sends the file, and the admin client sends no force, so a booking whose capital was typed by hand answers 409 and the file never leaves the browser. This is not new — it has been true since the pin shipped — but it is easier to hit now that a pin can be set at PENDING. The remedy is to call this endpoint with force: true through the API first, then retry the upload from the screen.

Guard order is booking-level first. The unrecordable-status 400 fires before the 409, the 409 fires before the channel is looked up — so a pinned booking sent an unknown ticketChannelId answers 409, not 404 — and the capital 400 fires last of all, after the channel has been validated. Fix the pin first, then the channel, then the route price.

  • Selling price, invoice, and status are untouched — margin/reporting only.

4. Recompute Capital (bypass terminal guard, admin) ​

Recompute capitalPriceTotalSAR by re-running the ticket-channel route-price resolver, including on a COMPLETED booking — deliberately bypassing the terminal-status guard that PATCH .../source and PATCH .../status enforce. Use this to fix a frozen capital basis on a closed booking after the underlying TicketChannelRoutePrice data was corrected — the canonical case being a route that had no matching row and resolved to 0 (the DMX→MKX / PAD29AN incident). Once the route price is added, this endpoint re-resolves the same basis the confirm/source flow uses (150 × 10 = 1500) with no new pricing logic.

The bypass covers COMPLETED, and only COMPLETED. PATCH .../status still rejects terminal bookings outright. PATCH .../source no longer does — it now shares this route's status rule — so this endpoint is no longer the single way to correct a closed booking's basis: .../source re-derives it too, and .../capital-price sets it by hand. What remains distinctive here is the mandatory reason, and the fact that this route defaults to the booking's own channel rather than requiring one. The reason stays mandatory because a documented invariant is being overridden, and every call lands in the audit log and pricingSnapshot.capitalPriceHistory.

CANCELLED, EXPIRED and NOT_AVAILABLE are refused with 400. No seats were procured on those bookings, so there is no supplier cost that belongs on the row — by this route or by PATCH .../capital-price, which refuses the same three. The two endpoints deliberately agree here: writing a cost onto a booking that earned no revenue silently distorts every margin view built over these rows. A real cancellation penalty charged by the channel is a genuine cost with no home today; recording it needs an agreed accounting treatment first, and is not blocked here by oversight.

Guard order. The status check is the first guard after the booking lookup, so a cancelled booking answers 400 ahead of the missing-source 400, the manual-override 409 and the channel 404 alike. force releases the manual pin only — it does not release this guard.

capitalPriceTotalSAR is admin-internal accounting only — it never feeds the customer selling price, status, tickets, invoices, or refunds, so recomputing it on a COMPLETED booking cannot alter the customer contract.

Behavior ​

  1. Refuses with 400 when the booking is CANCELLED, EXPIRED or NOT_AVAILABLE. This is the first guard after the booking lookup, so it answers ahead of every check below, and force does not release it.
  2. Resolves the channel from ticketChannelId (body) or the booking's assigned channel; 400 if neither is present.
  3. Refuses with 409 when the booking carries a hand-entered capital price (pricingSnapshot.manualOverride: true) and force is not sent — the route-price lookup would otherwise replace a negotiated figure, possibly with 0. This check sits after the missing-source 400 and before the channel lookup, the same guard order PATCH .../source uses, so both endpoints answer the same status code for the same request.
  4. Re-runs computeCapitalSnapshot — the same resolver used by PATCH .../source (per leg; adults + children × childRatio, infants excluded).
  5. Writes capitalPriceTotalSAR, reconnects the channel, and appends a pricingSnapshot.capitalPriceHistory entry with source: "RECOMPUTE", the reason, and bypassedStatus (the status at recompute time). A forced call also sets forcedOverManualOverride: true on that entry and persists manualOverride: false.
  6. Writes an AuditLog row with action = "CUSTOM_BOOKING_CAPITAL_RECOMPUTE", entity = "CustomBooking", entityId = :id, history entry under newValue. The interceptor writes a second, separate row (CREATE_CUSTOM-BOOKING, entityId = "recompute-capital") — see the audit note in §2.
  7. Atomicity: steps 5–6 run in a single prisma.$transaction — the booking is never mutated without a matching audit row.
  8. A recomputed total of 0 is a legitimate result only when the route-price row itself carries capitalPrice: 0 — a genuinely free or comped procurement, recorded on the route and channel where it is dated and attributable. A missing or deactivated row is no longer returned as 0: it is refused with 400 naming the lookup tuple and the endpoint that fixes it. A silent 0 was a wrong cost basis returned with a 200, and it was the typical outcome of attaching a channel, not an edge case.
  9. Does not change status, selling price, or tickets.

5. Upload Ticket ​

Upload the issued ticket file for a booking and record how many passengers it covers. This endpoint does not close the booking and emails nobody — the customer sees nothing at all until a second admin releases the ticket (§5a). It writes ticketedPaxCount and derives the new status from it: TICKET_UPLOADED_FULL when the count equals the seated total, or TICKET_UPLOADED_PARTIAL when it is lower, where the customer is owed money back. The customer-facing "Berita Acara Realisasi" is generated by the admin screen from the booking detail, so nothing is uploaded here for it: record why the source under-delivered with the optional shortfallReason and shortfallAttachment. The customer is told nothing by this call — the release is what mails them, and until it lands their booking still reports WAITING_FOR_TICKET and carries no ticket. A manager then closes the booking via §1, which needs custom-bookings:complete, is an internal verification step that emails nobody, and is now refused while the ticket is still held. Re-uploads are allowed and simply append a newer ticket version; they send no email, and on an already-COMPLETED booking they record the file and count and leave the status alone.

http
POST /admin/custom-booking/:id/ticket
Authorization: Bearer <admin-token>
Content-Type: multipart/form-data

Permissions ​

Beyond the ADMIN role this route needs custom-bookings:upload-ticket. custom-bookings:update does not confer it. The wildcards that satisfy it are custom-bookings:* and *; *:read does not, because that wildcard only matches actions literally named read.

This route does not require a capital source. It reads no ticketChannelId, resolves no route price and writes no capital. A booking whose ticketChannel is null uploads and derives its new status exactly like any other. Nothing here answers 403, 400 or 409 because a channel is missing, unset or pinned.

⛔ custom-bookings:upload-ticket alone is nevertheless not enough to upload from the admin screen, because the screen performs two calls — PATCH .../source to attach the ticket channel, then POST .../ticket with the file — and the first one needs the separate custom-bookings:write-capital code. A role holding only upload-ticket gets 403 on the source call and never reaches this endpoint, so the failure surfaces as "ticket upload is broken" even though the upload permission is correct.

A ticketing-operator role driving that screen therefore needs three codes:custom-bookings:read + custom-bookings:write-capital + custom-bookings:upload-ticket. Withhold both custom-bookings:read-pricing and custom-bookings:read-capital-markup if that operator must not see money — write-capital confers neither, so the role still gets money-free responses. See §3 for the source call's own errors and Access Roles.

The third code is a UI dependency, not an API one. A screen that lets the channel be attached separately — by whoever owns cost, whenever the channel is actually known — needs no backend change and drops the operator back to two codes. It also removes two failures that today look like upload failures and are not, both raised by the source call: a pinned booking (pricingSnapshot.manualOverride: true) answers 409, and a route with no active TicketChannelRoutePrice row answers 400, which force: true does not bypass. Neither can be raised by this endpoint.

Pre-conditions ​

  • Booking must exist.
  • Booking status must be one of WAITING_FOR_TICKET, PAID, TICKET_UPLOADED_FULL, TICKET_UPLOADED_PARTIAL, SHORTFALL_REFUNDED or COMPLETED. Any other status returns 400 naming that set.
  • The booking must have at least one passenger who needs a ticket. An infants-only booking has none — infants take no seat and are issued no ticket — so every possible count is refused with 400.
  • WAITING_FOR_TICKET and PAID behave identically — PAID is a real second entry point, not a legacy courtesy.
  • The resulting status is derived from the count, not from the starting status, with two exceptions: COMPLETED and SHORTFALL_REFUNDED both keep the status they already hold. A settled booking must not be dragged back into TICKET_UPLOADED_PARTIAL by a re-upload — its shortfall has already been paid, and re-opening it invites paying the same shortfall twice.
  • A COMPLETED booking's count may be restated or raised, never lowered — and if it has no recorded count at all (true of every booking that predates this field), only a full count is accepted. Establishing a shortfall against a booking that is already closed would leave it owing a refund with no transition on which to record one.
  • A SHORTFALL_REFUNDED booking accepts a same-count re-upload (replacing a bad file) and refuses any change to the count in either direction. Raising it would hand the customer the tickets as well as the refund; lowering it would claim a larger shortfall than the one that was settled.

Side Effect — No ticket email, and the audit log ​

An upload emails nobody. It records the file and the count, and stops. The customer is not told, cannot download, and sees no sign a file exists: their booking still reports WAITING_FOR_TICKET and carries no ticket block. A second admin releases it (§5a), and THAT sends the one automatic email.

The hold is once per booking. On a booking that has already been released, this upload is downloadable the moment it lands — no second approval — and is still silent, exactly as a re-upload has always been. Use §6 to tell the customer a replacement arrived.

An upload also clears any rejection recorded against the previous file, in the same compare-and-set that stores the new one, so a stale reason is never shown beside a fresh upload.

Every upload writes an audit-log entry — a ticketedPaxCount is a money-relevant assertion by a named admin — with action: CUSTOM_BOOKING_TICKET_UPLOAD, entity: CustomBooking, and a newValue carrying ticketedPaxCount, expectedTicketCount, unticketedPaxCount, statusBefore, statusAfter, ticketFileId, shortfallAttachmentFileId and shortfallReason. The audit is written after the status write and is best-effort: a failure is logged and does not fail the upload.

⚠️ A partial booking delivers the tickets that did arrive, but it cannot be closed. TICKET_UPLOADED_PARTIAL has no edge to COMPLETED; the only ways out are back to TICKET_UPLOADED_FULL when the missing tickets arrive, SHORTFALL_REFUNDED once the shortfall is settled via the Shortfall Settlements route, or CANCELLED.

The two obligations are separate and do not queue behind each other. The tickets that exist are available immediately — the customer can download them from this status once the ticket has been released (§5a), which is also what emails them. The email makes no claim about how many passengers it covers, which is what makes it safe to send from here; §6 also works from this status, once released. The money for the passengers who were not ticketed is settled on its own timetable: the transfer is made at the bank by hand and recorded afterwards, so in practice the record follows the money by however long that takes. That ordering is a finance process rather than something this endpoint imposes — do not read the booking's status as evidence about when the money moved. Holding the tickets for that window would delay the passengers who were ticketed on account of the ones who were not, and the debt is the company's either way.

Settle the shortfall, then close. Keep the gap short: the booking stays open throughout, and no further email fires at any point — not on the settlement, not on the re-upload that completes the delivery, and not on the close.

5a. Release or Reject a Ticket ​

The second pair of eyes between an uploaded ticket and the customer receiving it. Both routes need custom-bookings:verify-ticket, which custom-bookings:upload-ticket deliberately does not confer — that separation is the whole point, so the admin who obtains the file and the admin who signs it off can be two different people.

The same admin may do both if they hold both codes: the routes compare no ids and nothing deadlocks when one person holds everything. What the split buys is the ability to require two people, not a guarantee of it.

Finding the work ​

http
GET /admin/custom-booking?pendingTicketVerification=true

Resolves to status IN (every status a release can act on — the same five the download serves) AND ticketReleasedAt IS NULL ANDticketReviewRejectedAt IS NULL AND ticketedPaxCount IS NOT NULL.

  • The status list matches the release route deliberately. Anything POST :id/ticket/verify would accept has to be visible here, or a held booking ends up on no screen in the system. Two statuses are in the list for exactly that reason and are easy to miss:
    • SHORTFALL_REFUNDED — settling a shortfall moves a booking off TICKET_UPLOADED_PARTIAL without releasing its ticket, leaving it refunded, ticketless and unannounced.
    • COMPLETED — uploading onto an already-closed booking is supported and keeps the status, so such a ticket is held with the close guard long since passed. A booking closed under the * escape lands here too.
  • ticketedPaxCount IS NOT NULL is what keeps that wider list from filling the queue with noise. Every upload records a count, so it means "a file arrived through this flow"; legacy rows that reached a delivering status with no file have neither a count nor a release stamp and would otherwise sit in the queue forever with nothing to review.
  • Rejected bookings are excluded because a rejection moves no status. Without that term, every file you have already refused comes back tomorrow mixed in with the ones nobody has looked at.
  • Combined with status it intersects rather than overriding, so pairing it with a status outside those five returns nothing.

Read the file before approving it. GET /api/v1/custom-booking/{id}/ticket serves an admin caller even while the ticket is held — that exemption exists so a reviewer is never asked to sign off a file they cannot open.

⛔ This sends nothing and moves nothing. No email to anybody, no status change, and the customer is not told — from their side the booking still looks like one waiting for its ticket, which is what it is. reason is required (max 2000 characters, trimmed) and is the entire content of a rejection.

⛔ fileId is required, and it is the file you opened — tickets[0].id from the booking detail. If the uploader replaced it while you were reading, this answers 409 and records nothing.

That check is the only thing that can catch a stale review. The risky window is the time the reviewer spends reading the PDF, and it has already closed by the time the request is sent — so nothing the server reads on its own can detect it: the replacing upload has landed, and every value the handler reads is already the new one. Without the id, a rejection written about the old file is stamped on the new one, which silently takes the fresh file off the review queue (rejected rows are excluded) where nobody looks at it again.

The uploader has no queue of their own and gets no notification: they find out by opening the booking, where the reason appears on the detail and on the admin list row. Write it for them. They correct it through the ordinary §5 upload, which clears both rejection fields as it stores the new file.

Re-rejecting an already-rejected booking is allowed and replaces the reason. Writes action: CUSTOM_BOOKING_TICKET_REJECT.

A held booking is stored as TICKET_UPLOADED_FULL, which is a deliverable status, so a gate reading the stored column lets it past the status check and refuses it later with a different code than a booking that has nothing uploaded — and one request then tells the customer which of the two they hold. ticketedPaxCount is the one that is easy to forget and the loudest of them: it moves from null to the ticketed figure the moment an admin uploads, so leaving it visible announces the upload as plainly as an unmasked status would — and on a short delivery it prints "8 ticketed" beside a status saying the tickets have not arrived.

⛔ Two different tests, not one. The FILE is withheld on the release stamp alone. They coincide everywhere except SHORTFALL_REFUNDED, where an unreleased booking reports its real status and count — that is the customer's record that money came back, and the count is part of it — while hasTicket stays false and the download still 404s. Do not infer either gate from the other.

⚠️ Scope limit — the hold is a delivery gate, not a secrecy boundary. It covers the fields listed above on the custom-booking customer surfaces. Three known channels still expose that an upload happened, and all three are left alone deliberately:

  1. The invoice payload. GET /api/v1/invoice/{id} and /invoice/number/{number} embed customBooking: { id, bookingCode, status } straight from the column, and both are reachable by the booking's own customer and by a verified guest. So a customer reading their invoice sees TICKET_UPLOADED_FULL while their booking says WAITING_FOR_TICKET. Masking it would mean teaching a mapper shared with every admin invoice route which caller it is serving.
  2. sortBy=status on the customer booking list. The ORDER is computed from the stored column while the rows render the masked one, so a held booking sorts among the TICKET_UPLOADED_* positions rather than where its displayed status would put it. Removing the option would break any client already sending it.
  3. updatedAt on the customer detail and list. An upload writes ticketedPaxCount, which moves updatedAt, so a customer polling their booking sees the timestamp advance while status stays WAITING_FOR_TICKET and ticketedPaxCount stays null. Weak on its own — many writes move that column — but it is a signal, and masking it would mean lying about when the row last changed.

They say one thing: the hold stops delivery, it does not keep the upload secret. Do not build anything — a permission, an audit story, a promise to a customer — on the assumption that a customer cannot discover that a file exists.

⚠️ Two consequences worth knowing before you debug a support ticket:

  • The admin surfaces always report the stored status, so admin and customer screens legitimately disagree for the duration of a hold. Nothing branches on the masked value — every transition, guard and settlement reads the stored one.
  • On the customer booking list the status query filter matches the status that list reports, not the stored column — so ?status=WAITING_FOR_TICKET includes held bookings and ?status=TICKET_UPLOADED_FULL excludes them. Filtering and rendering agree there; the admin list filters the stored column, as it reports it.

6. Resend Ticket Email ​

Re-queue the ticket email for a booking using its most recently uploaded ticket file. The booking status is not modified, so this endpoint is safe to call from the moment any ticket is uploaded — partial sets included — right through to COMPLETED bookings and legacy TICKET_RECEIVED rows.

⛔ Requires the ticket to have been released. A held booking answers 400: the customer has been told nothing and their download is closed, so this would mail them a link that answers 404. §5a sends the first email.

⛔ This is the only way to re-notify a customer. The release mails them once and nothing else ever does: not an upload, not the upload that completes a short delivery, not the shortfall settlement, not the close. It is also the only recovery for a failed send, because the ticket email is queued with no automatic retry. Nothing in the system prompts you to press it.

http
POST /admin/custom-booking/:id/resend-ticket-email
Authorization: Bearer <admin-token>

Pre-conditions ​

  • Booking must exist.
  • Booking status must be one of TICKET_UPLOADED_FULL, TICKET_UPLOADED_PARTIAL, SHORTFALL_REFUNDED, TICKET_RECEIVED (legacy) or COMPLETED — every status the customer download serves. A resend is legitimate before the manager closes the booking; an admin fielding "I never got it" should not have to close it first.
  • TICKET_UPLOADED_PARTIAL is accepted. It used to be refused because the email was worded for a complete delivery and would have told the customer in writing that everyone was ticketed. On a short delivery it now names no passenger count and does not claim the passenger data is complete, so there is nothing left for it to overstate. The branch is decided by the counts, not the status, so a booking that keeps a short ticketedPaxCount after SHORTFALL_REFUNDED still gets the shortened wording.
  • ⛔ The email is not a substitute for telling the customer what happened to the passengers who were not ticketed. It says the ticket is ready and nothing about the refund. Treat that conversation as a required step of the shortfall process, not something the system covers for you.
  • ⚠️ Telling the customer the REST of their tickets arrived is a manual step. They were emailed once, when the first tickets were uploaded, and hold a file covering fewer passengers than they booked. The upload that resolves the shortfall is silent and so is the close, so pressing this route is what tells them — and nothing reminds you to.
  • This set and the upload's allowed set overlap without either containing the other: PAID is uploadable but not resendable (a booking there may hold no ticket file at all), and TICKET_RECEIVED is resendable but not uploadable (legacy data no upload path produces any more). Cancelled / expired / not-available bookings are rejected with 400 so a stale ticket cannot be resent after the booking was called off. SHORTFALL_REFUNDED is not in that group and resends normally — a settled shortfall leaves the booking live for the passengers who were ticketed.
  • Booking must have at least one uploaded ticket file on record (i.e. POST .../ticket has been called at least once previously).
  • Booking must have a contactPerson.email on record.

bash
curl -X POST /api/v1/admin/custom-booking/booking-123/resend-ticket-email \
  -H "Authorization: Bearer <admin-token>"

Response (201) ​

json
{
  "enqueued": true,
  "fileId": "file-uuid-1"
}

Behavior ​

The service looks up the newest custom_booking_ticket file for the booking (entityType = custom_booking_ticket, status = UPLOADED, orderBy createdAt desc), regenerates its R2 presigned download URL, and enqueues a fresh custom-booking-ticket email job with a unique jobId (suffixed with the current timestamp) so the queue's deduplication does not drop repeated resends.

Errors ​

  • 403 Forbidden — fires ahead of every message below, because the permission guard runs before the handler. Caller is not an ADMIN, or the role lacks custom-bookings:resend-ticket. This is its own code: holding custom-bookings:upload-ticket does not confer the resend. Body: {"message":"Forbidden resource","error":"Forbidden","statusCode":403}.
  • 400 Bad Request — Cannot resend ticket email when booking status is "PAID". Expected one of: TICKET_UPLOADED_FULL, TICKET_UPLOADED_PARTIAL, SHORTFALL_REFUNDED, TICKET_RECEIVED, COMPLETED. — the message names the booking's own status, and the allowed list is printed from the same status set the download's 400 prints, so the two lists now match — or the booking has no contactPerson.email on record (Cannot send ticket email for booking <id>: no customer email on contact person or account).
  • 404 Not Found — Booking does not exist, or no ticket file has been uploaded yet (upload via POST .../ticket first).

Rate Limit ​

10 requests per 60 seconds per admin.

8. Side Effect — Passenger Upload, Auto-Confirm & Admin WhatsApp Notification ​

When a customer, guest, or admin successfully submits the passenger list via PATCH /custom-booking/:id/passengers and the booking is currently in PENDING, the server atomically transitions it to UPLOADED_MANIFEST.

The transition uses an updateMany guarded by status: PENDING so concurrent passenger updates are race-safe — only the winning request performs the transition (count === 1); losers are a silent no-op (count === 0).

On the winning transition (and only the winning transition) the server enqueues a WhatsApp job to notify the admin phone configured under the CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE system config key (see System Configuration).

Message format (plain text, English) — ONE_WAY:

Booking Code: {bookingCode}
Date: {DD/MM/YYYY}
Time: -
From: {origin display name}
To: {destination display name}
Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

Message format — ROUND_TRIP (one block per leg; the return leg runs the opposite direction, destination → origin, dated by returnDate):

Booking Code: {bookingCode}
Trip: Round Trip

Outbound
Date: {departure DD/MM/YYYY}
Time: -
From: {origin display name}
To: {destination display name}

Return
Date: {return DD/MM/YYYY}
Time: -
From: {destination display name}
To: {origin display name}

Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

Pax counts are booking-wide — the schema has no per-leg counts, so both legs cover the same passenger list.

Origin and destination use a small built-in display-name map for the supported HHR stations (DMX, MKX, JED, JXD, KCX) and fall back to the booking's stored originName / destinationName when the code is not in the map.

Manifest attachment (Excel or CSV) ​

When the submitted passenger list is complete (passenger count matches adultCount + childCount + infantCount), the WhatsApp message also carries a generated manifest file as an attachment, with the text message as its caption. The file is uploaded to R2 under tmp/wa-manifest/{bookingId}/{uuid}.{xlsx|csv} and only the object key travels through the queue — see R2 Lifecycle Rule: Temp Manifest Attachments.

The format is selected by the CUSTOM_BOOKING_ADMIN_MANIFEST_FORMAT environment variable:

  • Unset or any value other than csv → Excel (.xlsx, default).
  • csv → importer-friendly semicolon-delimited CSV (per-passenger rows only, no trip summary).

Excel layout. A summary table leads with a Trip column — a ONE_WAY booking renders a single Outbound row; a ROUND_TRIP booking adds a Return row (stations swapped, dated by returnDate, same booking-wide pax counts):

TripDateTimeFromToPax NumberAdultKid (2 - 12)Baby (< 2 years)
Outbound18/06/2026-Madinah Al-Munawwarah, Madinah (DMX)Makkah Al-Mukarramah, Makkah (MKX)101000
Return30/06/2026-Makkah Al-Mukarramah, Makkah (MKX)Madinah Al-Munawwarah, Madinah (DMX)101000

Below the summary, a passenger detail section lists one row per passenger: No, Passport Name, Type, Sex, Date Of Birth, Nationality, Passport Number, Expiry Date, Airline, PNR. One manifest covers both legs — airline/PNR are per-passenger and trip-wide.

Fail-soft. Manifest generation or the R2 upload failing downgrades the notification to text-only (logged as warn); it never blocks the passenger update or the message itself.

Fail-soft. The notification path cannot fail the passenger update. Each of the following cases logs a warn and silently skips the job:

  • CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE not configured or empty.
  • Configured phone fails international-format validation (e.g. leading 0, non-digit characters, wrong length).
  • The queue producer throws while enqueuing.

The WhatsApp job type is custom-booking-admin with a stable jobId of custom-booking-admin-{bookingId} so duplicate dispatches for the same booking are deduped by the queue.

Auto-Confirm on Manifest Upload (default ON) ​

Immediately after the admin WhatsApp notification, the same winning transition auto-confirms the booking — UPLOADED_MANIFEST → CONFIRMED — without an admin review step. This is the new default behaviour.

It is gated by the CUSTOM_BOOKING_AUTO_CONFIRM_ON_MANIFEST system config key (see System Configuration):

  • Unset or any value other than "false" → auto-confirm ON (default).
  • "false" → auto-confirm OFF; the booking parks at UPLOADED_MANIFEST and an admin confirms manually via PATCH .../status (the legacy gate).

The auto-confirm runs the exact same CONFIRMED code path as a manual admin confirm — so it triggers the invoice auto-generation and the customer confirmation email side effects (the payment instruction is delivered later, when the customer picks a method — see customer payment instruction). Note that auto-confirm does not set a capital source — no confirm path does — so the booking lands at capitalPriceTotalSAR: 0 — an admin attaches the source afterwards via PATCH .../source.

Fail-soft. Auto-confirm cannot fail the passenger upload. If anything in the CONFIRMED transition throws, the server logs a warn and leaves the booking at UPLOADED_MANIFEST for an admin to confirm manually — the passenger-upload response still returns 200.

9. Side Effect — Manifest Download Auto-Transition (legacy fallback) ​

Legacy fallback only. New bookings advance to WAITING_FOR_TICKET automatically when payment settles (skip-PAID — see the status diagram and §10), so they never rest in PAID for this side effect to act on. This auto-transition now matters only for pre-change rows still sitting in PAID.

When an admin downloads a manifest file (see Custom Booking Manifests) for a booking currently in PAID, the booking is automatically transitioned to WAITING_FOR_TICKET. This happens inside the manifest download handler — there is no separate endpoint to call.

The transition is silently skipped if the booking is in any other status (already past this stage, still pending payment, etc.) — which is now the common case, since new bookings are already in WAITING_FOR_TICKET.

If the manifest is delivered to the channel out-of-band (e.g. forwarded from a previous download, or for a legacy row still in PAID), an admin can move the booking to WAITING_FOR_TICKET manually via PATCH /admin/custom-booking/:id/status with { "status": "WAITING_FOR_TICKET" }. The transition follows the same VALID_TRANSITIONS rules as any other status change — no ticket channel or additional payload is required.

10. Hourly Auto-Complete Cron (legacy-only) ​

A scheduled job (@Cron(EVERY_HOUR)) runs every hour to finalize any legacy booking still in TICKET_RECEIVED after the trip date has passed. Nothing transitions into TICKET_RECEIVED any more — new bookings land on TICKET_UPLOADED_FULL / TICKET_UPLOADED_PARTIAL from the upload and are closed by a manager — so this cron only affects rows that were already in TICKET_RECEIVED before the flow changed. It writes COMPLETED without sending anything — and so does every other writer of that status, including the admin close on §1. No status change sends the ticket email; it fires on the release (§5a), so this cron cannot wake a long-closed booking by touching it. This cron also bypasses the release guard on the admin close, and safely: it acts only on TICKET_RECEIVED, which nothing routes into any more.

  • Selector: status = TICKET_RECEIVED AND departureDate < now - 24h.
  • Action: Set status = COMPLETED and stamp autoCompletedAt = now.
  • Guard: updateMany is filtered by both id and status so concurrent customer confirmations cannot be overwritten (race-safe; a zero-count update is treated as a benign race).

The autoCompletedAt field on CustomBooking is null for bookings closed by an admin via PATCH .../status or by manual customer confirmation, and a timestamp when the cron completed the booking. Operators can use this to distinguish the completion source in reports.

11. Side Effect — Admin Payment-Success WhatsApp Notification ​

When a Xendit payment webhook settles the invoice linked to a custom booking and the booking advances WAITING_FOR_PAYMENT (or WAITING_PAYMENT_REVIEW) → WAITING_FOR_TICKET (skip-PAID), the server enqueues a WhatsApp job to the admin phone configured under CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE (see System Configuration) — the same phone used for the manifest-upload alert.

Scope — Xendit webhook only. The notification fires only for the gateway-webhook settlement path with the Xendit gateway. It does not fire for manual-transfer proof approvals or the admin "mark invoice paid" override, which also advance the booking to WAITING_FOR_TICKET — those are admin-initiated, so the admin already knows. The dispatch is gated on the settlement trigger (WEBHOOK) and the payment gateway (XENDIT).

Idempotent. The settlement flip is a status-guarded updateMany scoped to the waiting-for-payment states; a re-delivered webhook finds the booking already advanced out of those states (count === 0) and the notification is skipped. The admin is notified exactly once per booking, on the delivery that actually performs the transition.

Message format (plain text, English):

✅ Payment Received

Booking Code: {bookingCode}
Date: {DD Mon YYYY}
Time: -
From: {origin display name}
To: {destination display name}
Pax Number: {adult + child + infant}
Adult: {adultCount}
Kid (2 - 12): {childCount}
Baby (< 2): {infantCount}

The summary block (booking code, route, pax) mirrors the manifest-upload caption — same station display-name map and fallback to stored originName / destinationName. Amount Paid renders the invoice totalAmount in the booking's own currency only (no SAR cross-display), via the shared formatCurrency helper used by the payment-confirmation email. Time is intentionally blank until the outbound flight time is finalized (kept in sync with the manifest caption).

Fail-soft. The notification path can never fail the settlement (the payment is already durably recorded). Each of these cases logs a warn and silently skips the job:

  • CUSTOM_BOOKING_ADMIN_NOTIFICATION_PHONE not configured or empty.
  • Configured phone fails international-format validation.
  • The queue producer throws while enqueuing.

The WhatsApp job type is custom-booking-admin-payment with a stable jobId of custom-booking-paid-{bookingId} so duplicate dispatches for the same booking are deduped by the queue.
