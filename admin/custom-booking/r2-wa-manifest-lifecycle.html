R2 Lifecycle Rule: Temp Manifest Attachments ​

Context ​

The admin WhatsApp notification for custom bookings attaches a generated Excel manifest. To avoid storing large base64 blobs in BullMQ/Redis, the service uploads the Excel buffer to Cloudflare R2 under a temporary prefix and passes only the object key through the queue. The WhatsApp worker downloads the object, forwards it to GoWA, and best-effort deletes it on success.

The lifecycle rule described below is the authoritative cleanup path for the unhappy case — jobs that fail, phones skipped as local-format, or any other path where the post-send delete never runs. Without this rule, orphaned objects accumulate indefinitely.

  • Prefix written by the app: tmp/wa-manifest/{bookingId}/{uuid}.{xlsx|csv} (extension follows the CUSTOM_BOOKING_ADMIN_MANIFEST_FORMAT env var)
  • Code references:
    • Upload: src/modules/custom-booking/custom-booking.service.ts (inside notifyAdminViaWhatsApp)
    • Download + best-effort delete: src/modules/queue/processors/whatsapp.processor.ts

Setting up the rule (Cloudflare Dashboard) ​

Apply this per bucket per environment (dev, staging, production).

  1. Log in to the Cloudflare dashboard and open the account that owns the R2 bucket the application is using.

  2. Navigate to R2 → select the bucket.

  3. Open the Settings tab.

  4. Scroll to Object lifecycle rules → click Add rule.

  5. Fill in the form:

    FieldValue
    Rule nameexpire-tmp-wa-manifest
    Prefixtmp/wa-manifest/
    ActionDelete uploaded objects
    Age1 day (or 2 days if you want extra buffer)

    Optional (recommended for hygiene, no functional impact here): enable Abort incomplete multipart uploads at 1 day. Our manifest uploads are small and single-part, so this will normally be a no-op, but it protects the bucket from unrelated junk accumulating under the same prefix.

  6. Click Save.

The rule is live immediately. R2 evaluates lifecycle rules roughly once per day, so expect objects to linger up to ~24 hours past the age threshold before deletion — acceptable for this use case.

Important details ​

  • Trailing slash matters. The prefix must be tmp/wa-manifest/ (with slash). tmp/wa-manifest (no slash) would match unintended sibling keys; /tmp/wa-manifest/ (leading slash) would match nothing, because the app never writes a leading slash.
  • Minimum age is 1 day. R2 does not support sub-day expiration via lifecycle rules. This is why the post-send delete exists in the worker — it handles the common case within seconds, and this rule handles the exceptions.
  • Other rules are preserved. Adding a rule through the dashboard does not replace existing rules on the bucket. (This is different from the S3 API's PutBucketLifecycleConfiguration, which replaces the whole ruleset.)

Verification ​

After saving:

  1. Upload a probe object manually (via the dashboard or any S3 client) at tmp/wa-manifest/__probe/probe.txt.
  2. Note the upload timestamp.
  3. Return within 24–48 hours and confirm the object is gone.

Alternatively, trigger a real admin notification and confirm that:

  • The object appears under tmp/wa-manifest/{bookingId}/ briefly.
  • It disappears after the worker sends (immediate, via the best-effort delete).
  • For a deliberately failing case (e.g. phone misconfigured so the worker never sends), the object disappears within ~24–48 hours via the lifecycle rule.

Rollback ​

To remove the rule, return to R2 → bucket → Settings → Object lifecycle rules and delete the entry named expire-tmp-wa-manifest. No data loss — existing objects remain in place; the rule only governs future expirations.
