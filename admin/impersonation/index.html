Admin "Act as Customer" (Impersonation) Guide ​

Let an admin drive the customer custom-booking flow (search → calculate → create → manage) as a specific customer, from the mitra host. The admin mints a short-lived impersonation token pair bound to the customer, injects it into the customer frontend, and every action — plus the token generation itself — is recorded in the admin audit trail. Bookings land in the customer's own list, tagged with the responsible admin (handledByAdmin, admin-only).

Supersedes the old MITRA-3 direct admin-create endpoint: creation now happens through the real customer flow, so ownership, pricing, and eligibility all resolve exactly as they would for the customer.

Quick Overview ​

ActionEndpointAuth
Start acting as customerPOST /admin/impersonationAdmin, mitra host only
List active sessionsGET /admin/impersonationAdmin
Stop (revoke both tokens)DELETE /admin/impersonation/:idAdmin
Refresh impersonation tokensPOST /auth/impersonation/refreshImpersonation refresh token

Permission-gated (Access Roles). Beyond the ADMIN role, the admin routes require a fine-grained permission. Start needs impersonation:start, listing active sessions needs impersonation:read, and stop needs impersonation:stop. The impersonation-token refresh route is not admin-gated. See Access Roles.

Base URL ​

https://<mitra-host>/api/v1

The mitra host matters: generation is rejected off it, and the acting requests must run on it so promo/mitra pricing resolves correctly for the customer.

Authentication ​

Admin control-plane endpoints require a JWT with the ADMIN role:

http
Authorization: Bearer <admin-jwt>

The refresh endpoint instead takes the (possibly expired) impersonation access token in the header + the impersonation refresh token in the body.

How it works ​

Token model ​

POST /admin/impersonation returns an access token and an opaque refresh token. The admin injects both into the customer frontend.

The access token is a JWT (HS256, same secret as normal auth) whose principal is the customer so ownership and pricing resolve as the customer, while carrying the acting admin's identity separately:

jsonc
{
  "sub":   "<customerUserId>",  // principal = the customer
  "email": "<customerEmail>",
  "role":  "B2B",               // the customer's own real role — B2B or B2C, never ADMIN
  "scope": "impersonation",     // discriminator
  "act":   "<adminUserId>",     // the responsible admin (RFC 8693 "act")
  "sid":   "<impersonationSessionId>",
  "jti":   "<rotates on refresh>"
}

Access-token TTL follows JWT_ACCESS_EXPIRES_IN; the session (and refresh token) hard-expire at createdAt + JWT_REFRESH_EXPIRES_IN.

Pricing parity. The impersonation principal carries the same pricing levers as a normal login — including the customer's per-user pricingTier override (and promoAccessEnabled). So an admin acting as an org-less GOLD partner, or a member whose per-user override diverges from their org, is quoted and charged exactly the tier that customer would get logging in themselves; the tier frozen into the booking's pricingSnapshot matches too. Both principals are built from one shared helper, so they cannot drift apart.

Route confinement (least privilege) ​

An impersonation token is valid only on the customer checkout-complete surface — everything the impersonated custom-booking + payment flow needs, and nothing that mutates the customer's credential or moves money:

  • …/custom-ota/* — search, availability, calculate
  • …/custom-booking/* — create, manage, cancel, detail
  • …/invoice/:id/generate-payment, …/invoice/:id/available-gateways, …/invoice/:id/payment-options
  • GET …/auth/profile — read only, the exact path (surfaces partner.registrationNumber + pricingTier). The …/auth/profile/* subtree stays blocked: it carries change-identifier/* and add-identifier/* (mutate the login credential) and contact-person (PATCH).
  • GET …/invoice/:id, GET …/invoice/:id/download, GET …/invoice/:id/payments — the invoice being paid, its PDF data, and its payment attempts. Read-only.
  • The whole …/payments/* subtree (broad, method-blind — deliberate). Today the only controller mounted under bare /payments/* is manual-transfer: GET …/payments/:paymentId/manual-transfer (read the instruction — bank details
    • payable amount + proof status) and POST …/payments/:paymentId/manual-transfer/proof (upload the transfer proof). This is the one write the allowlist grants today: safe because the controller is guest-reachable (OptionalAuthGuard) and the service scopes every non-ADMIN caller to their own invoice (payment.invoice.userId === user.id, else 403) — so the impersonated customer can only act on their own payment, exact parity with logging in. ⚠️ Unlike the other entries this is a subtree wildcard, not a by-name path: any future route mounted under /payments/* is auto-granted to impersonation tokens for all verbs. Every new /payments/* handler MUST therefore be owner-scoped (or otherwise safe for an impersonated customer), or be mounted under a different path root. /admin/payments/* and the singular /payment root are NOT reached by this pattern.
  • GET …/exchange-rate/current, GET …/exchange-rate/history — read-only rate reads. getCurrentRateForOrg scopes the rate to the impersonated principal's own resolved tier via resolveUserPricingContext — exact parity with that customer logging in. So the rate widget (header + calculate page) shows the customer's tier rate during impersonation instead of the guest/holder peg. Both handlers are GET-only; the anchored current|history match does not reach the :id detail route or any future write/admin-adjacent route under the module.

Excluded on purpose: GET …/invoice (the list — checkout targets a specific id), …/wallet/*, …/user/bank-details/*, every profile/identifier write above, the singular …/payment/* and …/payment-gateway/* roots, and every /admin/* route.

Method-blind matching. The allowlist grants a path, every verb on it. The invoice, profile, and exchange-rate paths added here are GET-only today. The manual-transfer proof path is the lone write, and it is owner-scoped in the service (above), so method-blind matching grants no privilege the customer lacks on their own login. The …/payments/* entry is a subtree wildcard (not a by-name path), so it also auto-grants any future /payments/* route — see the warning on that bullet above. …/invoice/:id also matches …/invoice/stats, which is harmless — that route is RolesGuard + @Roles(ADMIN, B2B), so a B2C impersonation is refused and a B2B one sees only its own org's stats (the same it would get logging in).

Every other route — all of /admin/* and any other customer route — rejects it with 403 Forbidden. Two layers enforce this:

  1. The principal's role is the customer's own role (B2B or B2C, never ADMIN), so every @Roles(ADMIN) route already refuses it.
  2. JwtStrategy explicitly allowlists the paths above and 403s anything else (defense-in-depth against future customer routes).

An impersonation token therefore cannot mint another impersonation token — that endpoint is admin-gated and refuses a B2C principal.

Revocation (instant, both tokens) ​

The ImpersonationSession row is the source of truth; a Redis key (impersonation:session:<sid> = current jti) is the fast per-request check.

  • Stop (DELETE …/:id) flips the session to REVOKED, deletes the Redis key, and clears the refresh hash → the access token and refresh token die immediately.
  • Refresh rotates the jti and overwrites the Redis key, so a pre-rotation access token stops validating at once, and a revoked session can never be refreshed (refresh re-checks status === ACTIVE).

Endpoints ​

Start acting as a customer ​

Endpoint: POST /admin/impersonation — mitra host only

Request Body:

json
{ "customerUserId": "019f632e-0d8f-756b-96c5-d6a31a2f5433" }

Validation:

  • Host must be the mitra host → else 403.
  • Target must exist (404 otherwise), be a customer (B2C/B2B, never ADMIN/SUPPORT → 403), be active, and be mitra-eligible on this host → else 403.

Response: 201 Created

json
{
  "accessToken": "<impersonation access JWT>",
  "refreshToken": "<opaque refresh token>",
  "reused": false,
  "conflictingSessions": [],
  "session": {
    "id": "019f6903-08dc-757e-be6a-7d38c0e5db72",
    "admin":    { "id": "019c9105-311a-732f-a1c5-da44758a7e5b", "name": "System Admin", "email": "admin@ahlaan.co.id" },
    "customer": { "id": "019f632e-0d8f-756b-96c5-d6a31a2f5433", "name": "Example Customer", "email": "partner@example.com" },
    "status": "ACTIVE",
    "host": "preprod.mitra.ahlaan.co.id",
    "createdAt": "2026-07-16T03:40:34.376Z",
    "expiresAt": "2026-08-15T03:40:34.375Z",
    "lastUsedAt": null
  }
}

Writes an IMPERSONATION_START audit row (actor = admin, subject = customer). Rate limited to 10/min.

Calling start twice: you get your session back, not a twin ​

If you already hold a live session on this customer with more than 24h left, that session is returned instead of a new one being created:

  • reused: true;
  • the access token carries the same jti, so an impersonation tab you already had open keeps working until its access token expires (default 1h) — you are not logged out of your own session;
  • the refresh token is always rotated. Only its hash is stored, so the original cannot be handed back. Any refresh token you were holding stops working now;
  • expiresAt is NOT pushed forward. The hard stop stays 30 days from your first start on that customer. Returning repeatedly does not extend it;
  • an IMPERSONATION_REUSE audit row is written.

With under 24h left, the old session is revoked (IMPERSONATION_STOP) and a fresh one minted with a new 30-day window (reused: false). Either way every gate — host, non-staff target, active, mitra-eligible PARTNER — is re-applied. Reuse is not a bypass.

⚠️ On the under-24h path your already-open tabs stop working immediately. This is the exact opposite of the reuse path above, and it is easy to be caught out by it. Revoking the old session deletes its Redis current-jti key, so every impersonation tab still holding the old access token starts returning 401 at once — there is no grace period and no warning in the old tab. Reload those tabs with the tokens from the new response. Nothing is lost: the customer, the booking and the invoice are all unchanged; only the token in that tab is dead. The alternative — silently extending a session that was nearly over — would defeat the bounded-credential rule that expiresAt is never pushed forward.

409 on a double-click. Two start calls for the same admin on the same customer at the same moment are serialized by a short Redis lock; the loser gets 409 Conflict with "already being started". Just retry — the retry normally lands on the reuse path and returns the session the first call made. The lock is scoped to the admin + customer pair, so a different admin starting on the same customer is never blocked by it (that stays a reported conflict, see below). It also fails open: if Redis is unreachable the start still proceeds unserialized, which at worst reproduces the old behaviour — an occasional twin, visible in the list below and closable by any admin.

Someone else is already acting as this customer ​

If a different admin holds a live session on the same customer, the session is still created — two admins on one customer is supported, because that is exactly what a handoff needs. You are told about it:

json
"conflictingSessions": [
  {
    "sessionId": "019f68aa-1f22-70b1-9c3e-55a1d2c4e881",
    "adminId": "019c9105-311a-732f-a1c5-da44758a7e5b",
    "adminName": "Admin B",
    "adminEmail": "adminb@ahlaan.co.id",
    "startedAt": "2026-07-29T02:10:11.000Z",
    "lastUsedAt": "2026-07-29T04:55:02.000Z"
  }
]

Use lastUsedAt to judge whether the other admin is actually mid-flow. If they are not, sessionId is the revoke target for the takeover below.

List active sessions ​

Endpoint: GET /admin/impersonation

Query params: mine (optional, true = only sessions started by the calling admin).

Response: 200 OK — array of session objects (same shape as session above; never includes raw tokens).

Returns live sessions only: ACTIVE and not yet past expiresAt, so unswept rows never appear as active. Defaults to all admins' sessions — that default is the point, it is the shared operational picture for a handoff.

Judge staleness from lastUsedAt, not createdAt. lastUsedAt now advances on impersonated requests (throttled to once per minute per session), so a session used ten minutes ago is distinguishable from one abandoned in the same hour it started. A session that has never been used since creation reports null.

An hourly job on the ENABLE_CRON worker host flips ACTIVE rows past expiresAt to EXPIRED and clears their refresh hash, so the stored status agrees with what this endpoint shows.

Stop acting as a customer ​

Endpoint: DELETE /admin/impersonation/:id

Revokes the session. Idempotent (a non-ACTIVE session returns success without change). Writes an IMPERSONATION_STOP audit row.

Response: 200 OK

json
{ "success": true, "status": "REVOKED" }

Cross-admin takeover is intentional ​

Any admin holding impersonation:stop may revoke any session, including one started by a different admin. There is no ownership check, and this is a deliberate supervisor primitive rather than an oversight — use it to close a colleague's forgotten or stuck session.

It is fully attributed: revokedByUserId records who did it, and the IMPERSONATION_STOP audit row names the acting admin. If you revoke a colleague's session, expect that to be visible.

Refresh impersonation tokens ​

Endpoint: POST /auth/impersonation/refresh

Mirrors /auth/refresh but for impersonation tokens — it lives on the customer surface so the frontend can keep the session alive.

Headers: Authorization: Bearer <impersonation access token> (may be expired).

Request Body:

json
{ "refreshToken": "<opaque impersonation refresh token>" }

Validation: session must be ACTIVE, not past expiresAt, on the mitra host, with a matching refresh-token hash and an active customer → else 401. Rotates the jti + refresh token and re-mints the access token (preserving scope/act/sid). Writes an IMPERSONATION_REFRESH audit row.

Response: 201 Created

json
{ "accessToken": "<new access token>", "refreshToken": "<new refresh token>" }

Booking attribution ​

Bookings created while impersonating are owned by the customer (appear in their list) and stamped with handledByAdminId = the acting admin (set once, at create). This is surfaced admin-only:

  • Admin list (GET /admin/custom-booking) — each row carries handledByAdmin ({ id, name, email } or null).
  • Admin detail (GET /admin/custom-booking/:id) — same field.
  • Never exposed on any customer-facing response.

Audit trail ​

Every relevant action attributes to the admin with the customer as subject in metadata:

ActionWhen
IMPERSONATION_STARTSession minted
IMPERSONATION_STOPSession revoked
IMPERSONATION_REFRESHToken pair rotated
CUSTOM_BOOKING_IMPERSONATION_CREATEBooking created while impersonating
CUSTOM_BOOKING_IMPERSONATION_CANCELBooking cancelled while impersonating
CUSTOM_BOOKING_IMPERSONATION_UPDATE_PASSENGERSPassengers updated while impersonating
CUSTOM_BOOKING_IMPERSONATION_CONFIRM_RECEIVEDTicket receipt confirmed while impersonating
IMPERSONATION_REUSEstart returned an existing session instead of minting a twin
MANUAL_TRANSFER_PROOF_IMPERSONATION_UPLOADTransfer proof submitted while impersonating

The IMPERSONATION_* actions have entity ImpersonationSession; the custom-booking ones have entity CustomBooking; the proof upload has entity ManualTransferProof. All carry metadata.impersonated = true and the customer id as subject.

Beyond the audit log, an impersonated proof upload is also recorded durably on the row: ManualTransferProof.uploadedByAdminId holds the acting admin's id (null for a genuine self-serve customer or guest upload). The admin review surfaces expose it next to reviewerId, so a reviewer can read "submitted by admin X acting as the customer, reviewed by admin Y" without correlating timestamps against audit rows.

Runbook: act as customer, end to end ​

The exact sequence for driving one custom booking from creation to settled payment, including which surface answers which question. A second admin can pick this up at step 8 knowing nothing but the customer's email.

The table below is the sequence as executed and verified end to end against preprod, by two different admins where the second started with no identifier the first had produced. Every row was run; the notes are what actually happened, not what the shape suggests. Real request/response bodies for every step are in Worked example below.

Two admins on one booking is normal ​

The common shape in practice is not one admin doing everything. It is a handoff:

  • Admin A — the booking desk. Finds the customer, starts acting as them, searches, prices, creates the booking, uploads the manifest, generates the payment. Then hands the customer over — often just by saying "booking 2WUUPCE is waiting for payment".
  • Admin B — the finance desk. Starts acting as the same customer, finds the booking, reads the payment id off the invoice, uploads the transfer proof, and then approves that proof with their own admin JWT.

The system supports this on purpose, and three behaviours exist specifically for it:

  1. Two live sessions on one customer are allowed. POST /admin/impersonation never blocks because another admin holds a session — it reports it in conflictingSessions[] with that admin's name, email, sessionId and lastUsedAt. Blocking would break exactly the handoff described above. Read the array before you start typing; it tells you a colleague is mid-flow.
  2. Admin B needs no identifier from Admin A. Only the customer's email. Every id (customerUserId → bookingId → invoiceId → paymentId) is rediscoverable through the calls in the table, in that order. If you find yourself asking a colleague to paste a payment id into chat, you are working around a surface that exists.
  3. The trail records both admins separately. On a proof uploaded by an impersonating admin and approved by another, the invoice detail carries manualTransfer.uploadedByAdminId (who uploaded, acting as the customer) and manualTransfer.reviewerId (who approved) as distinct fields, plus an audit row per action. When one admin does both, the two ids are simply equal — which is what the worked example below shows.

Two cautions specific to the handoff:

  • The proof file stays owned by the CUSTOMER, not the uploading admin. Proof files are PRIVATE and the customer is handed the fileId back; giving ownership to the admin would 403 the customer on their own receipt. Admins read it through the ADMIN bypass regardless. Attribution lives in uploadedByAdminId and the audit row — never in file ownership.
  • Admin A's tab can die mid-handoff. If Admin A re-starts a session with less than 24h remaining on the old one, the old row is revoked and its Redis current-jti key dropped, so any impersonation tab Admin A already had open starts returning 401 immediately, with no grace period. Above 24h the session is reused and the open tab keeps working. See Start acting as a customer.

Worked example: a real two-admin run ​

Responses are verbatim apart from: JWTs and refresh tokens replaced with placeholders, and person / company / email values replaced with example ones. Ids, amounts, statuses, timestamps and field shapes are exactly as returned.

Step 11 — close the sessions ​

bash
curl -s -X DELETE "$HOST/api/v1/admin/impersonation/019fad74-1b8d-77f8-8c58-45bcd25f1742" \
  -H "Authorization: Bearer $B"

Each admin closes their own; a session left open lives for 30 days. Any admin holding impersonation:stop may also close a colleague's session — the sessionId in conflictingSessions[] is there for exactly that, and the revocation is audited with revokedByUserId.

Where to find a payment id. Two surfaces, and they answer different questions, so they have different shapes on purpose:

  • GET /invoice/:id → payments.attempts[] — admin triage. gateway is the plain code string; ordered oldest first. Reachable with an admin JWT or an impersonation token. This is the one to use in the flow above.
  • GET /invoice/:id/payments — the customer's own attempt history. gateway is {code, name} plus externalId / isDuplicate / qrString / createdAt; ordered newest first. Owner, admin, and impersonating admin may all read it.

Both carry proofStatus — same name, same values, same manual-transfer-only semantics (null on an IN_PERSON attempt that does have a receipt). The extra field that is unique to payments.attempts[] is currency.

Do not expect these to converge — they are allowed to diverge.

GET /invoice/:id/payments is the one invoice surface with NO tiering. Its body is byte-identical for the owner, a real admin, and an admin acting as the customer, so it is the surface to reach for when you need to see exactly what the customer sees. Keep it that way: anything that needs an admin tier belongs on GET /invoice/:id.

What an impersonating admin can see that a customer cannot. manualTransfer and officeSettlementProof on the invoice detail (signed proof download URL, adminNotes, reviewerId, bank account, retry budget) are admin tier: a real admin or an admin acting as the customer. A customer reading their own invoice still gets null. Signed URLs are attributed to the responsible admin, not the impersonated customer.

Two admin-only blocks are deliberately not widened and stay absent from an impersonated view: pricing.supplier (supplier cost) and purpose.

Note on route gating. The customer invoice routes (GET /invoice/:id, GET /invoice/:id/payments) admit any ADMIN principal with no @RequirePermissions check — unlike GET /admin/invoice/:id, which requires INVOICES_READ. That is accepted and consistent with the pre-existing behaviour of those routes (they already served pricing.supplier, purpose and handledByAdmin to any admin principal un-gated). Do not infer that the customer routes are permission-equivalent to the /admin/* ones. Note the un-gating is about reaching the route: only GET /invoice/:id then serves an admin-tier payload; GET /invoice/:id/payments has no tier to serve.

Security summary ​

  • No privilege escalation — the impersonation role is the customer's own (B2B/B2C), never ADMIN; route allowlist + RolesGuard reject it on /admin/* and any non-checkout route. The allowlist grants only READS outside the custom-booking surface (own profile, the invoice being paid) — every credential-mutating and money-moving path stays blocked.
  • Target restriction — cannot impersonate ADMIN/SUPPORT; only active, mitra-eligible customers.
  • Instant revoke — Redis-backed, checked every request; stop kills both tokens atomically.
  • Host gated — generation and refresh both require the mitra host.
  • Throttled — start 10/min, refresh 10/min, stop 20/min, list 60/min.
  • Replay-resistant — jti rotates on every refresh; the old one stops validating immediately.
  • Fully auditable — who (admin), whom (customer), when, from where. Payment and proof actions are attributed too, so a cross-admin handoff is reconstructable from the log alone.
  • No new secrets — reuses jwt.secret, REDIS_CLIENT, and existing TTL env.
  • Bounded window, not extended by returning — a session's expiresAt is set once, at first start, and reuse never pushes it forward.

Standing caveat on the 30-day TTL. Sessions inherit jwt.refreshTokenExpiresIn (default 30d), so every "act as customer" session is a 30-day bearer credential able to act as a partner customer. Nothing in this document changes that — the compensating controls are reuse-instead-of-mint, the expiry filter + sweeper, lastUsedAt, and the fact that any admin can close a forgotten session. Close your sessions when you are done. If the live ACTIVE count keeps climbing, the TTL is the thing to revisit.

Frontend integration flow ​

  1. Admin (on mitra host) calls POST /admin/impersonation with the target customerUserId.
  2. Frontend stores the returned accessToken + refreshToken as the active session and drives the customer custom-booking UI as that customer.
  3. On 401 from an expired access token, call POST /auth/impersonation/refresh and retry.
  4. To end, call DELETE /admin/impersonation/:id; discard both tokens.
