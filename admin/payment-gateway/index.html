Payment Gateway Management Guide ​

This guide explains how administrators can configure payment gateways for processing bookings and wallet top-ups.

Quick Overview ​

FeatureDescription
PurposeConfigure payment gateways for booking payments and wallet top-ups
Supported GatewaysXendit (primary), Midtrans (backup), Stripe (international)
Payment MethodsQRIS, Bank Transfer, E-Wallet, Credit Card

Current Runtime Restriction

XENDIT remains the default gateway, but it currently accepts BANK_TRANSFER only.

All other Xendit payment methods are rejected at runtime.

Seeded Payment Gateways ​

The system comes with pre-configured payment gateways:

CodeNameStatusSupported Methods
XENDITXendit Payment GatewayACTIVEQRIS, BANK_TRANSFER, EWALLET
MIDTRANSMidtrans Payment GatewayINACTIVEQRIS, BANK_TRANSFER, CARD, EWALLET
STRIPEStripe Payment GatewayINACTIVECARD
MANUAL_TRANSFERManual Bank TransferACTIVEBANK_TRANSFER
IN_PERSONIn-Person Office SettlementACTIVECASH

IN_PERSON is the SAR in-person office-settlement rail (MITRA-10). It is registered in the gateway factory and is reachable through POST /invoice/:id/generate-payment — what keeps it away from ordinary customers is the eligibility gating in InvoiceService (feature flag + mitra host + admin/acting-as-admin principal), not absence from the gateway map. It surfaces on payment-options (as an inPerson block with an enabled flag) and on available-gateways (present or omitted). Settlement is then recorded by an admin via POST /admin/invoice/:id/office-settlement, either against the payment the customer already created or by minting one. See In-Person Office Payment for the full rail.

Partner identity also surfaces on the manual-transfer admin proof list/detail views — nested on payment.invoice as partnerRegistrationNumber / partnerName (the same invoice snapshot behind the Xendit partner_number / partner_name metadata keys) — so finance can reconcile which partner a transfer belongs to. See Manual Transfer → Partner identity on proofs.

Gateway Descriptions ​

Xendit (Primary Gateway)

  • Primary payment gateway for Indonesia
  • Supports QRIS, Bank Transfer, and E-Wallet
  • Low transaction fees with wide coverage
  • Runtime note: only BANK_TRANSFER is currently accepted even though seeded gateway metadata still lists other methods

Midtrans (Backup Gateway)

  • Alternative payment gateway for Indonesia
  • Additional payment method options
  • Can be activated if Xendit has issues

Stripe (International Cards)

  • International payment gateway
  • Primarily for credit card payments
  • For customers outside Indonesia

Endpoints ​

Active gateways

There is no admin endpoint that lists or toggles payment gateways. The active gateways available for a given invoice surface per-invoice via GET /invoice/{id}/available-gateways.

The admin endpoints for configuring Xendit credentials are documented under Admin Configuration Endpoints below.

Admin Configuration Endpoints ​

These endpoints allow administrators to configure payment gateway credentials dynamically.

Base URL ​

/api/v1/admin/payment-gateway

Authentication ​

All endpoints require:

  • JWT Token in Authorization header
  • ADMIN role in user account
http
Authorization: Bearer <your-admin-jwt-token>

1. Get Xendit Configuration ​

Endpoint: GET /admin/payment-gateway/xendit

Retrieves the current Xendit configuration with masked credentials for security.

Response: 200 OK

json
{
  "secretKey": "xnd_...****",
  "webhookToken": "your...****",
  "updatedAt": "2026-01-20T12:00:00.000Z"
}

Response Fields:

FieldTypeDescription
secretKeystringXendit API secret key (masked for security)
webhookTokenstringXendit webhook verification token (masked for security)
updatedAtDateLast updated timestamp

Notes:

  • If credentials are not configured in the database, returns "Not configured (using env var)"
  • Keys are masked showing only first 4 and last 4 characters

2. Update Xendit Secret Key ​

Endpoint: PATCH /admin/payment-gateway/xendit/secret-key

Updates the Xendit API secret key used for all payment requests.

Request Body:

json
{
  "secretKey": "xnd_development_..."
}

Request Fields:

FieldTypeRequiredDescription

Response: 200 OK

Xendit invoice payload ​

What the backend sends to Xendit when a customer calls POST /invoice/:id/generate-payment with paymentGatewayCode: "XENDIT".

description (customer-visible) ​

Rendered on the hosted Xendit checkout page.

InvoiceDescription
Custom booking (promo surface) carrying a partner snapshot{invoiceNumber} · {partnerRegistrationNumber} {partnerName} — e.g. INV-000123 · MG.0007 PT Mitra Gold
Partner with a name but no number (legacy org){invoiceNumber} · {partnerName}
Everything else (OTA, BlockSeat, wallet top-up, manually-created invoice, non-mitra customer)Payment for {invoiceNumber} (unchanged)

The gate is the promo surface, not merely the snapshot

Partner identity is surfaced only when the invoice's payment source is CUSTOM_OTA — the mitra / promo surface. A mitra buying a regular OTA or BlockSeat ticket gets the legacy description and no partner metadata.

generateFromBooking (OTA + BlockSeat) no longer writes the snapshot at all, so those invoices carry partner: null — see Invoice → partner. The promo gate here is therefore a second, independent line of defence: it also neutralises the rows that WERE stamped during the MITRA-5 window, which are deliberately not backfilled. It is always the invoice's own partner, never another org's.

source is used rather than the request host because it is durable and request-free: invoices are also generated inside the BullMQ ticketing processor (no request at all), and custom bookings are created by an admin on the admin host (MITRA-4), so a request-host check would switch the feature off exactly where it is meant to fire. PROMO_BASE_DOMAIN is documented as tracking the custom-OTA host, and XENDIT_REDIRECT_URL_CUSTOM_OTA routes these same payments to the mitra frontend — so source === 'CUSTOM_OTA' is the promo host.

Manually-created invoices never carry a snapshot, so they keep the legacy description even when their organizationId belongs to a mitra org.

The partner name is applicant-supplied. Before it is sent, control characters and Unicode bidi overrides are stripped and the composed description is truncated to 255 characters (Xendit's limit) — truncation eats the partner suffix, never the leading invoice number.

metadata (webhook reconciliation) ​

Invoice-level metadata, echoed back on every Xendit webhook — it ties a paid invoice to the buying partner and the originating booking without a DB lookup.

Sent only on a partner-bearing promo-surface invoice. Every other invoice — OTA, BlockSeat, wallet top-up, non-mitra customer — is sent to Xendit with no metadata field at all, exactly as before MITRA-7. The block is withheld wholesale rather than emptied of its partner keys, so an off-promo payload is byte-identical to the original.

KeySource
invoice_numberInvoice.invoiceNumber
partner_numberInvoice.partnerRegistrationNumber
partner_nameInvoice.partnerName
custom_booking_idCustomBooking.id
booking_codeBooking.bookingCode, falling back to CustomBooking.bookingCode

The metadata block is only emitted for a partner-bearing invoice, and those are custom-booking invoices — which link via customBookingId and leave bookingId NULL. So booking_code is in practice always the custom booking's code; the Booking branch exists only so the key stays correct if a partner identity is ever attached to an OTA invoice again.

Within a partner invoice, individually null keys are still dropped.

Source of truth

Both blocks are built from the partner identity snapshotted on the invoice at generation time, never from a client-supplied value — see the reserved-key warning under Invoice → Generate Payment.

items[] ​

The invoice lineItems are forwarded verbatim as Xendit items[] (name ← description, price ← unitPrice, quantity ← quantity). For custom bookings this is the per-pax breakdown (Economy Adult SUB - MED, quantity: 2, …). Xendit renders items as price × quantity. Note price is the IDR unitPrice: the authoritative charged figure is the top-level amount, which may differ from the item subtotal by up to (quantity − 1) rupiah on the one line that absorbs the IDR rounding residual. (The SAR figures tie out exactly — the drift is an IDR-only artefact of ceil-converting per pax type against an IDR total that is a single floor of the whole-booking SAR.) See Invoice → Custom-booking line items.
