Audit Logs Guide ​

This guide explains how administrators can browse, filter, and export audit logs for every admin mutation captured by the system.

Quick Overview ​

FeatureDescription
PurposeTrack every admin write operation (create / update / delete) for compliance and forensics
AccessAdmin plus Access Role: reads (list, per-user, per-entity, stats) need audit-logs:read, and CSV/JSON export needs audit-logs:export. See Access Roles
ScopeAll admin mutations across the application — captured automatically by a global interceptor
StorageAuditLog table in PostgreSQL, indexed by userId, userEmail, action, (entity, entityId), and createdAt

Base URL ​

All audit log endpoints use:

/api/v1

Authentication ​

All audit log endpoints require:

  • JWT Token in Authorization header
  • ADMIN role in user account
http
Authorization: Bearer <your-admin-jwt-token>

How Audit Logging Works ​

Audit logging is fully automatic for admin write operations. You do not need to instrument controllers — the global AuditLogInterceptor does it for you.

What Gets Logged ​

The interceptor records an audit entry when all of the following are true:

  1. The authenticated user has the ADMIN role.
  2. The HTTP method is not GET (only mutations are recorded — POST, PATCH, PUT, DELETE).
  3. The request URL is not under /audit-logs (prevents recursion).
  4. The execution context is a real controller (internal NestJS contexts are skipped).

What Each Entry Captures ​

For every mutation, the interceptor stores:

FieldDescription
userIdThe acting admin's user ID
userEmailThe acting admin's email (denormalized for filtering)
actionDerived from the HTTP method and entity (e.g., CREATE_USER, UPDATE_TARIFF, UPDATE_PRICING). Failed requests are suffixed with _FAILED
entityThe resource type (e.g., user, organization, tariff) — resolved from the AUDIT_ENTITY_CONFIG registry, with a URL-segment fallback
entityIdThe resource ID extracted from the trailing URL path segment when it looks like an ID (alphanumeric/-/_, length ≥ 5) and is not a known sub-route name (e.g., stats, export, approve, reject)
oldValueFor PATCH / PUT / DELETE, the entity state fetched before the mutation (sensitive fields redacted). Captured even when the mutation later throws, so failed-action entries still record the prior state
newValueThe HTTP response body (sensitive fields redacted; list responses are summarized to dataCount + meta). null for failed actions
metadata{ method, url, body, duration, ip, userAgent } (duration in milliseconds). Errors include metadata.error = { message, status }
ipAddressCaller IP from request.ip or socket fallback
userAgentCaller User-Agent header
createdAtTimestamp of the recorded action

Failure Behavior ​

Audit logging is non-blocking. If the audit write itself fails, the original request still succeeds and the failure is logged at error level with a correlation ID for investigation.

Sensitive Field Redaction ​

Each entity in AUDIT_ENTITY_CONFIG declares its sensitiveFields. Those fields are replaced with the literal string "[REDACTED]" in both oldValue and the request body portion of metadata.

For entities not in the registry, redaction behavior differs by field:

  • metadata.body — falls back to a default redaction list of password, token, secret, apiKey.
  • oldValue — always null for unconfigured entities (no pre-fetch happens without a config).
  • newValue — logged without redaction (the default list applies only to the request body, not the response).

Transactional Audit Writes (Internal) ​

For compliance-critical operations (e.g., capital price corrections), services may call AuditLogsService.create(data, tx) directly with a Prisma transaction client so the audit row is committed or rolled back together with the underlying change. This is in addition to the interceptor — not a replacement for it.

Consequence: one request produces two rows, and only one of them is queryable by entity id. The custom-booking capital routes are the live example. PATCH /admin/custom-booking/:id/capital-price writes:

Transactional rowInterceptor row
actionCUSTOM_BOOKING_CAPITAL_PRICE_UPDATEUPDATE_CUSTOM-BOOKING
entityCustomBookingcustom-booking
entityIdthe booking UUIDcapital-price — the last URL segment
oldValuenullnull
newValuethe capitalPriceHistory entrynull
metadatanullbody, url, method, ip, userAgent, duration

CustomBooking is not in the registry below, so the interceptor falls back to URL-segment resolution and its entityId is the route suffix rather than the record. The booking id survives only inside metadata.url. Filter compliance queries for these routes on entity=CustomBooking — the interceptor rows cannot be narrowed to a single booking.

The same pattern applies to .../source (CUSTOM_BOOKING_SOURCE_UPDATE + UPDATE_CUSTOM-BOOKING / entityId: "source") and .../recompute-capital (CUSTOM_BOOKING_CAPITAL_RECOMPUTE + CREATE_CUSTOM-BOOKING / entityId: "recompute-capital" — CREATE_ because the route is a POST).

Refused calls appear only in the interceptor rows. Every guard on these routes throws before the transaction opens, so a rejected edit leaves no CUSTOM_BOOKING_* row at all — it shows up as UPDATE_CUSTOM-BOOKING_FAILED / CREATE_CUSTOM-BOOKING_FAILED with the status and message under metadata.error. An audit review that reads only the transactional rows sees successful writes but no attempts.

entityIdstringFilter by exact entity ID

5. Export Audit Logs ​

Endpoint: GET /admin/audit-logs/export

Export audit logs as JSON or CSV. The response body is the raw export (no pagination wrapper).

Query Parameters:

ParameterTypeDescription
formatcsv | jsonOutput format (default: json)
userIdstringFilter by exact admin user ID
actionstringFilter by exact action
entitystringFilter by exact entity name
sourceBOOKING | STANDARD | BLOCKSEAT | CUSTOM_BOOKINGSame booking-source filter as the list endpoint. STANDARD = /admin/ota/bookings/*, BLOCKSEAT = /admin/blockseat-bookings/*, BOOKING = OTA umbrella over both, CUSTOM_BOOKING = /admin/custom-booking/*. Omit for all
startDatestring (ISO 8601)Lower bound on createdAt. Required if you want to bound by date
endDatestring (ISO 8601)Upper bound on createdAt. Only applied when startDate is also provided — passing endDate alone is silently ignored on this endpoint

Example — JSON:

bash
GET /admin/audit-logs/export?format=json&entity=tariff&startDate=2026-04-01

Example — CSV:

bash
GET /admin/audit-logs/export?format=csv&entity=tariff&startDate=2026-04-01

CSV columns (in order):

ID, User ID, User Email, Action, Entity, Entity ID, IP Address, Created At

The export endpoint returns the full filtered result set in a single response — no pagination and no server-side row cap. Apply tight startDate / endDate bounds for large entities to avoid loading excessive data into memory.

Action Naming Convention ​

Actions are derived from HTTP method + entity by the interceptor:

MethodPatternExample
POSTCREATE_<ENTITY>CREATE_USER
PATCH / PUTUPDATE_<ENTITY>UPDATE_TARIFF
DELETEDELETE_<ENTITY>DELETE_USER

When the underlying request throws, the action is suffixed with _FAILED (e.g., UPDATE_TARIFF_FAILED) and the thrown error's message and status are written into metadata.error.

The entity slug is the value resolved from AUDIT_ENTITY_CONFIG. Entities not in the registry fall back to a heuristic singularization of the URL path segment (e.g., /admin/foos/:id → foo).

Registered Audit Entities ​

The following entity types are registered in src/common/config/audit-entity.config.ts for full pre-mutation snapshots and field redaction. Entities not listed here are still logged via the URL-fallback path, but oldValue will be null for PATCH / PUT / DELETE.

URL prefixEntitySensitive fields redacted
admin/usersuserpassword, token, refreshToken
admin/organizationsorganizationapiKey, secretKey
admin/b2b-applicationsb2b-application—
auth/b2b *b2b-application—
auth/register *userpassword, token, refreshToken
admin/pricing-rulespricing-rule—
admin/tax-rulestax-rule—
admin/exchange-ratesexchange-rate—
admin/system-configsystem-configvalue
admin/payment-gatewayspayment-gatewayapiKey, secretKey, webhookSecret
admin/admin-rolesadmin-role—
admin/tariffstariff—
admin/bank-detailsbank-detail—
admin/wallet-bank-detailswallet-bank-detail—

Prefix-match caveat. A registry row only takes effect when the request URL starts with its declared prefix. Three prefixes above are registered defensively but do not match the live routes, so those entities resolve via the URL-segment fallback instead:

Registered prefixActual routeResolved action / entity
admin/pricing-rulesadmin/pricing/rulesUPDATE_PRICING / pricing
admin/tax-rulesadmin/tax/rulesUPDATE_TAX / tax
admin/exchange-ratesadmin/exchange-rate/**_EXCHANGE-RATE / exchange-rate (fallback)

Consequently, filtering by action=CREATE_PRICING-RULE or action=UPDATE_TAX-RULE returns zero results — use action=UPDATE_PRICING / action=UPDATE_TAX instead. admin/system-config does match its registry prefix, so UPDATE_SYSTEM-CONFIG resolves through the registry as documented.

* The auth/* rows are registered for completeness, but the interceptor only logs requests where req.user.role === ADMIN. They take effect only when an authenticated admin hits these paths (e.g., admin-initiated registration); ordinary unauthenticated /auth/* traffic is not audited.

To add a new entity to the registry, edit AUDIT_ENTITY_CONFIG in src/common/config/audit-entity.config.ts. Provide model, prismaDelegate, identifierField, optional relations to include in oldValue, and optional sensitiveFields to redact.

Common Workflows ​

Investigate a Suspicious Change to a Tariff ​

bash
# 1. Get the full audit trail for the tariff
GET /admin/audit-logs/entity/tariff/<tariff-id>

# 2. Pull the acting admin's recent activity
GET /admin/audit-logs/user/<userId>?limit=100

Review All Admin Activity in a Window ​

bash
GET /admin/audit-logs?startDate=2026-04-15T00:00:00Z&endDate=2026-04-16T00:00:00Z&limit=100

Find Failed Mutations ​

bash
GET /admin/audit-logs?action=UPDATE_USER_FAILED

Monthly Compliance Export ​

bash
GET /admin/audit-logs/export?format=csv&startDate=2026-04-01&endDate=2026-05-01

Operational Notes ​

  • GET requests are not audited. Reads do not change state and are intentionally excluded to keep the audit table focused on mutations.
  • Customer / B2B users are not audited by the interceptor. Only requests where req.user.role === ADMIN produce entries.
  • Public-API key callers are tracked separately via PublicAuditInterceptor / PublicApiAuditService and do not appear in this admin audit log.
  • Pagination defaults. The list and per-user endpoints default to page=1, limit=50. There is currently no server-side maximum on limit — pass conservative values for large queries. The entity-trail endpoint returns all rows with no pagination — be careful on hot entities.
  • Indexes. The AuditLog table is indexed on userId, userEmail, action, (entity, entityId), and createdAt. Filter on these fields for fast queries.
