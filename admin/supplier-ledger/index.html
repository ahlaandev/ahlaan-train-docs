Carrier Balance (Supplier Ledger) ​

We hold a prepaid account with the OTA carrier. Every ticket issued draws it down, every carrier refund puts money back, and finance tops it up by bank transfer.

The carrier publishes no endpoint for that balance, so this service keeps its own books:

opening + deposits + carrier refunds - ticket issuance = balance

The ledger is append-only. Nothing is ever edited or deleted; a correction is a new row.

This balance never blocks anything

No code path refuses to ticket, and no write fails, because the balance is low or negative. The number is an estimate of the carrier's, and it cannot see every charge the carrier makes. Treating an estimate as a gate would turn a counting error into a customer who never receives a ticket, inside a 30-minute carrier deadline.

Reading the balance ​

GET /api/v1/admin/supplier-ledger/balance

json
{
  "balanceSAR": "295528.25",
  "perKindSAR": {
    "OPENING": "50000.00",
    "DEPOSIT": "15000.50",
    "TICKET_ISSUE": "276676.10",
    "REFUND_CREDIT": "63818.90",
    "ADJUSTMENT": "-107.52",
    "RECONCILE": "443492.47"
  },
  "kindDirections": {
    "OPENING": "credit",
    "DEPOSIT": "credit",
    "TICKET_ISSUE": "debit",
    "REFUND_CREDIT": "credit",
    "ADJUSTMENT": "signed",
    "RECONCILE": "signed"
  },
  "entryCount": 261,
  "lastReconciledAt": "2026-09-06T00:00:00.000Z"
}

Read lastReconciledAt before acting on the figure. Because the carrier has no balance endpoint, an export is uploaded by hand on no fixed schedule. Until that happens the balance is our arithmetic, not the carrier's. null means it has never been checked against the carrier at all.

GET /api/v1/admin/supplier-ledger/entries lists movements, newest first, and takes kind, from, to, pnr, bookingCode, bookingId, page and limit.

Entries are ordered by occurredAt — when the carrier moved the money — which is not createdAt, when we recorded it. A carrier refund credits the account well after we mark a customer refund done.

Each row carries its booking's bookingCode and otaBookingRef (the PNR). The carrier writes its account export against the PNR, so that is the key to join the two sides on when building a comparison.

json
{
  "data": [
    {
      "id": "01a07b9e-0992-77e5-8fe8-f02e518e9e54",
      "kind": "REFUND_CREDIT",
      "amountSAR": "179.4",
      "bookingId": "019e8bb5-9d82-719f-9e7f-6060b98342cf",
      "sourceType": "refund",
      "sourceId": "019e8ccb-c495-73f2-9f5b-242b68189129",
      "occurredAt": "2026-06-03T09:23:44.917Z",
      "createdAt": "2026-09-07T11:25:49.842Z",
      "createdBy": "system",
      "grossRefundSAR": "224.25",
      "penaltySAR": "39",
      "penaltyVatSAR": "5.85",
      "refundPercentage": "80",
      "note": null,
      "metadata": null,
      "booking": { "bookingCode": "YWBZJCK", "otaBookingRef": "KZUS5Y" }
    }
  ],
  "meta": { "page": 1, "limit": 1, "total": 64, "totalPages": 64 }
}

On a REFUND_CREDIT, amountSAR is what the carrier actually returned and grossRefundSAR is that plus the penalty and its VAT — above, 179.4 + 39 + 5.85 = 224.25. A TICKET_ISSUE row carries sourceType: "booking" and leaves all four refund fields null.

createdBy is system on the two automatic kinds and the admin's user id on the manual ones.

Two amount formats in one response

amountSAR on an entry is the stored decimal, so it prints as 15000.5. perKindSAR and balanceSAR are fixed to two places, so the same amount reads 15000.50 there. Format for display rather than comparing the two as strings.

perKindSAR is unsigned

It holds absolute sums, so TICKET_ISSUE reads positive there while the balance subtracts it. kindDirections in the same response says which way each kind moves the balance — read that instead of hardcoding the rule.

Entry kinds ​

KindSignWritten by
OPENING+An admin, once, to seed the balance
DEPOSIT+An admin, per top-up
TICKET_ISSUE−Automatically, when a booking's tickets are issued
REFUND_CREDIT+Automatically, when the carrier refunds a cancellation
ADJUSTMENT±An admin, for a movement with no row to derive it from
RECONCILE±An admin, from the carrier's own statement

ADJUSTMENT and RECONCILE are the only kinds whose amount may be negative, because a correction has to be able to go either way.

Recording the opening balance ​

Do this once, before anything else.

POST /api/v1/admin/supplier-ledger/deposits

json
{
  "amountSAR": 50000,
  "reference": "TRF-8157603042235842",
  "occurredAt": "2026-03-09T12:56:01.000Z",
  "isOpeningBalance": true,
  "note": "Initial funding of the carrier account"
}

The opening figure is total ever deposited, not what is left today

Enter every top-up ever sent to the carrier since the account was opened, not the balance the carrier shows now. The historical bookings and refunds are then replayed behind it to arrive at today's figure. Entering the current remaining balance instead double-counts the entire trading history.

Recording a top-up ​

Same endpoint, without isOpeningBalance.

amountSAR is the SAR the carrier credited. It is entered by the admin and taken as authoritative — nothing here reads an exchange rate or converts a currency. If a top-up is wired in another currency, still enter the SAR the carrier credited and put the wire details in note.

reference is the idempotency key. Submitting the same reference twice records nothing the second time rather than doubling the balance; the response's created field says which happened.

json
{
  "created": true,
  "entry": {
    "id": "01a07b9b-527b-702a-a380-d485ec712568",
    "kind": "DEPOSIT",
    "amountSAR": "15000.5",
    "bookingId": null,
    "sourceType": "manual",
    "sourceId": "TRF-8157603042235842",
    "occurredAt": "2026-06-01T09:00:00.000Z",
    "createdAt": "2026-09-07T11:22:51.899Z",
    "createdBy": "019c9105-311a-732f-a1c5-da44758a7e5b",
    "note": "June top-up",
    "metadata": null
  }
}

Re-sending it returns "created": false with that same entry — same id, same createdAt. A second isOpeningBalance is refused outright with 400 An opening balance is already recorded. rather than returning created: false.

Replaying history ​

POST /api/v1/admin/supplier-ledger/replay

Run this once after the opening balance is recorded. It writes the debits and credits that predate the automatic hooks, so the balance is right the first time anyone reads it instead of showing a number that silently omits history.

Safe to run again at any time: every write is keyed on the movement, so anything already recorded is skipped rather than doubled.

json
{
  "debits":  { "scanned": 193, "debited": 193, "credited": 0,  "skipped": 0,  "hasMore": false },
  "credits": { "scanned": 77,  "debited": 0,   "credited": 64, "skipped": 13, "hasMore": false }
}

The counts are writes actually made, not rows looked at. A skipped credit is normally a refund with no carrier refund order, which needs a manual ADJUSTMENT. hasMore: true means the pass filled its batch and there is more to do — run it again. Running it a second time against the same data returns debited: 0 and credited: 0.

It cannot recover what neither system records — see What this cannot see.

Reconciling against the carrier ​

This is the important one, and the only thing that can tell you the balance has gone wrong.

Step 1 — upload the export. Ask finance for the carrier account export (CSV) and upload it:

POST /api/v1/admin/supplier-ledger/reconcile/preview (multipart, field file)

This writes nothing. It reports:

  • PNRs the carrier charged that we hold no booking for
  • bookings we debited that the export never mentions
  • PNRs where the carrier's net and ours differ
  • rowsWithNoPnr — export lines belonging to no booking, such as a top-up, so every line in the file is accounted for somewhere in the report

The file is first checked against itself: its running Balance column must agree with the row-by-row sum. A file that does not add up is rejected, because it cannot be used to reconcile anything else.

Export the account from the beginning, not a date range

That self-check adds the rows up starting from zero, so the file has to cover the account from the day it was opened. A period statement that opens on a carried-forward balance is rejected on its first row with The export does not add up at row 1.

Amounts are netted per PNR, never matched row to row. The carrier posts a PURCHASE for every ticketing attempt and auto-reverses the failures seconds later, so a booking that retried four times shows five purchases and four refunds. Only the net matters.

Each perPnr line also carries carrierRows and ourEntries: the lines that produced each net. They are there so a person looking at a difference can see what caused it — not to be paired up. The two sides can hold different numbers of rows, which is the same reason the nets are what get compared.

Anything after the export's period end is not drift

The report includes periodEnd. A booking ticketed after that moment is simply outside the file, not a discrepancy.

Step 2 — record the outcome.

POST /api/v1/admin/supplier-ledger/reconcile

json
{
  "closingBalanceSAR": 38449.46,
  "asOf": "2026-09-03T09:34:19.000Z",
  "reference": "52783"
}

This writes one RECONCILE entry carrying the difference and moves our balance onto the carrier's. A second reconciliation against an unchanged ledger records zero rather than repeating the first.

The figure is supplied here, not read out of the upload, so that a file can never move the balance on its own.

asOf decides which of our movements the comparison counts: the carrier's figure is true as of that moment, so ours is summed up to the same moment. Set it to the last operation in the export. Anything ticketed after it is spend, not drift, and is left out of the difference.

json
{
  "created": true,
  "entry": {
    "id": "01a07ba0-1f2c-7d31-9c44-6b1f0f5b1a77",
    "kind": "RECONCILE",
    "amountSAR": "443492.47",
    "sourceType": "manual",
    "sourceId": "52783",
    "occurredAt": "2026-09-06T00:00:00.000Z",
    "createdBy": "019c9105-311a-732f-a1c5-da44758a7e5b",
    "note": "Carrier statement balance 295909.47; ledger at that date -147583.00",
    "metadata": {
      "carrierBalanceSAR": "295909.47",
      "ledgerBalanceSAR": "-147583.00"
    }
  }
}

metadata.ledgerBalanceSAR is our balance at asOf, which is not the figure GET balance returns afterwards — that one includes everything since.

Corrections ​

POST /api/v1/admin/supplier-ledger/adjustments

For a carrier movement with no row on our side to derive it from. Two real examples:

  • The carrier refunded a booking but our system never created a refund record, so nothing exists to credit from. Enter a positive adjustment.
  • The carrier kept a charge for a booking whose tickets were never issued. Enter a negative adjustment.

reason is required. An adjustment is the one place a person can move the balance with no external proof, so the reason, the recorded author, and the fact that rows are never edited are the whole audit trail.

A recorded correction. A TICKET_ISSUE debit took one halala more than the carrier charged, because the supplier cost was frozen through a float ceil, so a positive adjustment gives it back:

json
{
  "amountSAR": 0.01,
  "reference": "float-ceil-fix-S9PL2O",
  "occurredAt": "2026-05-10T12:38:47.256Z",
  "reason": "TICKET_ISSUE debited 2080.06; carrier charged 2080.05. The supplier cost was frozen through the pre-Decimal ceil, which turned 2080.05*100 into 208005.00000000003 and added a halala. Returns the 0.01 the debit over-took.",
  "bookingId": "019e11e0-7ad2-7192-8395-8928950d006a"
}

The row it wrote:

{
  "created": true,
  "entry": {
    "id": "01a086a3-aed1-762a-baf3-a78262f50445",
    "kind": "ADJUSTMENT",
    "amountSAR": "0.01",
    "bookingId": "019e11e0-7ad2-7192-8395-8928950d006a",
    "sourceType": "manual",
    "sourceId": "float-ceil-fix-S9PL2O",
    "occurredAt": "2026-05-10T12:38:47.256Z",
    "createdAt": "2026-09-09T14:47:49.201Z",
    "createdBy": "019cb8ae-4a27-71ae-8036-333bb378b9c0",
    "grossRefundSAR": null,

    "penaltyVatSAR": null,

    "metadata": null
  }
}

reference is stored as sourceId and is unique per kind, so it is also the idempotency key: sending the same one again answers created: false with the row already there instead of correcting the balance twice.

occurredAt is when the carrier moved the money, which here is the ticket issue being corrected — months before createdAt, the moment the correction was entered. Entry listings sort on occurredAt, so the correction lands beside the debit it fixes rather than at the top.

What this cannot see ​

Be honest with these numbers. The ledger is accounting, not detection.

  • A charge for a booking that never ticketed. If the carrier bills us and the booking never reaches TICKETED, there are no ticket numbers, no transition, and nothing in the carrier's per-booking API either. It exists only in the account export. Reconciliation is the only way to find it — though suspected charges narrows down where to look for one shape of it.
  • A carrier refund we never recorded. Every automatic credit is derived from a refund record on our side, so a refund the carrier makes that we never wrote down is invisible here by construction.
  • Reissue and change fees, if the carrier bills any.

All three show up as reconciliation drift, but the report can only say the numbers disagree — it cannot always say which booking caused it.

Suspected charges ​

GET /api/v1/admin/supplier-ledger/suspected-charges

Ticketing pays from the prepaid carrier account, and the endpoint that does it offers no idempotency key. When a ticketing call goes unanswered — the request was sent and no reply came back — we cannot say whether the carrier charged us. The booking is parked rather than re-issued, because a second attempt on an uncollected answer buys a second ticket.

This lists those bookings: ticketing was abandoned and the booking never reached TICKETED.

On a healthy deployment the list is empty, and that is what you should normally see. Captured from staging on 2026-09-08:

json
{ "entries": [], "count": 0, "hasMore": false }

A populated response, captured from the same deployment while one row was seeded to exercise the query:

json
{
  "entries": [
    {
      "bookingId": "01a06b45-817d-722f-a8ca-0e07c26769c0",
      "bookingCode": "5JKNHF4",
      "otaBookingRef": "BEHWFE",
      "bookingStatus": "CONFIRMED",
      "occurredAt": "2026-09-08T08:55:06.418Z",
      "reason": "Ticketing ticketing outcome unknown (ECONNABORTED); not retried automatically: Ticketing outcome unknown for BEHWFE: timeout of 120000ms exceeded",
      "supplierTotalFareSAR": "190.61"
    }
  ],
  "count": 1,
  "hasMore": false
}

The booking, the PNR and the 190.61 are real staging data; the history row that put it on the list was written by hand, because an unanswered carrier call cannot be produced on demand.

How to use a row. Look otaBookingRef up in the carrier's account export. If a purchase stands against that PNR with no matching reversal, record what the export shows as an ADJUSTMENT, with the PNR in the note.

Never post supplierTotalFareSAR as the amount

That figure is our own frozen cost for the booking — what the carrier would have charged. It is not confirmed by anyone, and the carrier's own figure is the only one worth recording. Nothing on this endpoint writes to the ledger.

An empty list is not proof that nothing was lost. A booking appears here only if the abandonment was recorded against it, so this narrows the search rather than closing it. The reconciliation report remains the thing that says whether our number and the carrier's disagree.

The list is bounded at 200 rows, newest first. hasMore says the bound was hit — on normal data it never is, because an unanswered ticketing call is rare.

Granted by supplier-ledger:reconcile, the same code as the export upload: it is the same person, doing the same job, on the same afternoon.

Measured on staging 2026-09-08 with a role holding supplier-ledger:read-balance and nothing else: GET balance 200, GET entries 200, GET suspected-charges403. So a role built to read the balance does not pick this up.

Permissions ​

No supplier-ledger:* is offered: the role builder lists these five codes one by one, so granting one is a deliberate act rather than a side effect of ticking a group.

CodeGrants
supplier-ledger:read-balanceView the balance and entries
supplier-ledger:depositRecord the opening balance and top-ups
supplier-ledger:adjustRecord corrections
supplier-ledger:reconcileUpload the export, record the outcome, and read suspected charges
supplier-ledger:backfillReplay historical movements

The read code is spelled read-balance, not read, on purpose: a role built as "read-only, harmless" must not come to hold our cost basis with the carrier. It follows the same rule as invoices:read-supplier-cost. A *:read grant does not reach it, because the action segment is not literally read.

Not offering a wildcard is not the same as refusing one

The builder will not mint a supplier-ledger:* row, but the API accepts one if it is sent: POST /admin/roles with "permissions": ["supplier-ledger:*"] is valid, and a role holding it reaches all five codes, adjust included. The * that Super Admin holds reaches them too. Treat the five codes as the thing to audit, not the absence of a wildcard row in the picker.
