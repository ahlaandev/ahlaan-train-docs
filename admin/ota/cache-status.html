Cache Refresh ​

This guide explains how administrators can manually refresh the train availability cache for optimal performance.

Quick Overview ​

FeatureDescription
PurposeInvalidate and re-warm the station/route + train availability cache
AccessAdmin only
ScopeAffects availability-range endpoint performance

How Cache Works ​

Cache Architecture ​

┌─────────────────┐     ┌──────────────────┐     ┌─────────────┐
│     Client      │────▶│  Availability    │────▶│ Redis Cache │
│                 │     │  Range Endpoint  │     │             │
└─────────────────┘     └──────────────────┘     └─────────────┘
                               │                        │
                               │ (cache miss)           │ (hit)
                               ▼                        ▼
                        ┌──────────────┐        ┌─────────────┐
                        │   OTA API    │        │   Response  │
                        │ (per date)   │        │             │
                        └──────────────┘        └─────────────┘

Cache Key Format ​

train_availability:{origin}:{destination}:{date}

Example: train_availability:MKX:DMX:2026-02-15

Cache Warming ​

The system automatically pre-warms cache for ALL available routes:

  1. Schedule: Every 30 minutes (configurable via TRAIN_AVAILABILITY_CACHE_INTERVAL_MINUTES)
  2. Routes: All routes from the station cache
  3. Days Ahead: Next 7 days by default (configurable via TRAIN_AVAILABILITY_CACHE_DAYS_AHEAD)

Configuration ​

Cache behavior is controlled via System Configuration:

KeyDefaultDescription
TRAIN_AVAILABILITY_CACHE_INTERVAL_MINUTES30Cache TTL in minutes
TRAIN_AVAILABILITY_CACHE_DAYS_AHEAD7Days to pre-warm (1-30)

See System Configuration for details on updating these values.

Endpoint ​

Refresh Cache ​

Manually refresh the station/routes cache and the train availability cache. This is the only cache-management endpoint — it both invalidates and re-warms in a single synchronous call.

What it does:

  1. Refreshes the station/routes cache from the OTA API.
  2. Invalidates the existing availability cache (and the OTA search cache) for every route over the next 7 days.
  3. Pre-warms the availability cache for all routes by fetching fresh data.

Endpoint: POST /api/v1/admin/ota/cache/refresh

Headers:

http
Authorization: Bearer <admin-token>

Request Body: None.

Response: 200 OK

json
{
  "message": "Cache refresh completed successfully",
  "stationCache": {
    "stationCount": 4,
    "routeCount": 6
  },
  "cacheInvalidated": 84
}

Response Fields:

FieldTypeDescription
messagestringHuman-readable result message
stationCache.stationCountnumberNumber of stations in the refreshed station cache
stationCache.routeCountnumberNumber of routes in the refreshed station cache
cacheInvalidatednumberTotal number of availability + search cache keys invalidated before re-warming

Note: This runs synchronously and may take 30–60 seconds to complete, as it re-fetches fresh availability data for every route across the next 7 days.

Common Workflows ​

Force a Full Refresh ​

After major pricing changes, schedule updates, or when stale data is suspected:

bash
curl -X POST /api/v1/admin/ota/cache/refresh \
  -H "Authorization: Bearer <token>"

This single call refreshes the station/routes cache, invalidates the existing availability + search caches, and re-warms availability for all routes.

Use Cases:

  • New routes added and need immediate visibility
  • Cache issues suspected (stale data)
  • After system maintenance or configuration changes

Troubleshooting ​

Issue: Low Cache Hit Rate ​

Symptoms: Slow availability-range responses

Causes:

  1. Cache TTL too short
  2. Cache warm-up not running
  3. Redis memory issues

Solutions:

  1. Increase TRAIN_AVAILABILITY_CACHE_INTERVAL_MINUTES
  2. Check cron job logs for cache warm-up
  3. Monitor Redis memory usage

Issue: Stale Pricing Data ​

Symptoms: Prices don't match OTA system

Causes:

  1. Exchange rate changed but cache not refreshed
  2. Cache TTL not yet elapsed after a non-pricing change

Note: Pricing-config changes — tax rules, custom route prices, and pricing rules — now flush the OTA search cache (ota:search:summarized:v1:* and ota:search:raw:v2:*) automatically on every create/update/deactivate, so those changes take effect on the next search. The manual refresh below is only needed for cases that do not auto-flush (e.g. exchange-rate refresh).

Solutions:

  1. Trigger a full cache refresh via POST /api/v1/admin/ota/cache/refresh

Issue: Missing Routes in Cache ​

Symptoms: Some routes always return cache miss

Causes:

  1. New routes not in station cache
  2. Route temporarily unavailable

Solutions:

  1. Trigger a full cache refresh to reload the station cache
  2. Wait for next scheduled warm-up

Best Practices ​

  1. Peak Periods: Reduce cache interval to 15 minutes during high-traffic periods (Hajj season, holidays)

  2. Off-Peak: Increase to 60 minutes during low-traffic periods to reduce API load

  3. Schedule Changes: After OTA schedule updates, trigger a manual cache refresh

  4. Monitoring: Check availability responses daily during peak booking periods
