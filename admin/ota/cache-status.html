Train Availability Cache Management ​

This guide explains how administrators can monitor and manage the train availability cache for optimal performance.

Quick Overview ​

FeatureDescription
PurposeMonitor and manage train availability cache
AccessAdmin only
ScopeAffects availability-range endpoint performance

How Cache Works ​

Cache Architecture ​

┌─────────────────┐     ┌──────────────────┐     ┌─────────────┐
│     Client      │────▶│  Availability    │────▶│ Redis Cache │
│                 │     │  Range Endpoint  │     │             │
└─────────────────┘     └──────────────────┘     └─────────────┘
                               │                        │
                               │ (cache miss)           │ (hit)
                               ▼                        ▼
                        ┌──────────────┐        ┌─────────────┐
                        │   OTA API    │        │   Response  │
                        │ (per date)   │        │             │
                        └──────────────┘        └─────────────┘

Cache Key Format ​

train_availability:{origin}:{destination}:{date}

Example: train_availability:MKX:DMX:2026-02-15

Cache Warming ​

The system automatically pre-warms cache for ALL available routes:

  1. Schedule: Every 30 minutes (configurable via TRAIN_AVAILABILITY_CACHE_INTERVAL_MINUTES)
  2. Routes: All routes from the station cache
  3. Days Ahead: Next 7 days by default (configurable via TRAIN_AVAILABILITY_CACHE_DAYS_AHEAD)

Configuration ​

Cache behavior is controlled via System Configuration:

KeyDefaultDescription
TRAIN_AVAILABILITY_CACHE_INTERVAL_MINUTES30Cache TTL in minutes
TRAIN_AVAILABILITY_CACHE_DAYS_AHEAD7Days to pre-warm (1-30)

See System Configuration for details on updating these values.

Endpoints ​

Get Cache Status ​

Check the current state of the train availability cache.

Endpoint: GET /api/v1/admin/ota/cache/status

Headers:

http
Authorization: Bearer <admin-token>

Response: 200 OK

json
{
  "totalRoutes": 12,
  "cacheTtl": 1800,
  "daysAhead": 7,
  "warmedKeys": 84,
  "routes": [
    { "origin": "MKX", "destination": "DMX" },
    { "origin": "DMX", "destination": "MKX" },
    { "origin": "MKX", "destination": "JXD" },
    { "origin": "JXD", "destination": "MKX" }
  ]
}

Response Fields:

FieldTypeDescription
totalRoutesnumberTotal routes being cached
cacheTtlnumberCache TTL in seconds
daysAheadnumberDays ahead being pre-warmed
warmedKeysnumberCurrently cached route-date combinations
routesarrayList of all routes being monitored

Invalidate Cache ​

Manually invalidate cache for a specific route and date range.

Endpoint: POST /api/v1/admin/ota/cache/invalidate

Headers:

http
Authorization: Bearer <admin-token>
Content-Type: application/json

Request Body:

json
{
  "origin": "MKX",
  "destination": "DMX",
  "startDate": "2026-02-15",
  "endDate": "2026-02-20"
}

Response: 200 OK

json
{
  "success": true,
  "deletedKeys": 6,
  "message": "Invalidated 6 cache keys for MKX->DMX"
}

Trigger Cache Warm-up ​

Manually trigger a full cache warm-up for all routes.

Endpoint: POST /api/v1/admin/ota/cache/warm

Headers:

http
Authorization: Bearer <admin-token>

Response: 200 OK

json
{
  "success": true,
  "message": "Cache warm-up triggered",
  "estimatedDuration": "2-5 minutes"
}

Common Workflows ​

Workflow 1: Check Cache Health ​

Monitor cache coverage before peak periods:

bash
curl -X GET /api/v1/admin/ota/cache/status \
  -H "Authorization: Bearer <token>"

Expected: warmedKeys should equal totalRoutes × daysAhead

Workflow 2: Invalidate Stale Data ​

If pricing appears incorrect for a route:

bash
curl -X POST /api/v1/admin/ota/cache/invalidate \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "origin": "MKX",
    "destination": "DMX",
    "startDate": "2026-02-15",
    "endDate": "2026-02-21"
  }'

Workflow 3: Force Full Refresh ​

After major pricing changes or schedule updates:

bash
curl -X POST /api/v1/admin/ota/cache/warm \
  -H "Authorization: Bearer <token>"

Monitoring ​

Expected Cache Coverage ​

MetricExpected Value
Cache Hit Rate> 90%
Warm Coverage100% of routes × days ahead
Average Response Time< 100ms (cached), < 2s (miss)

Cache Statistics Formula ​

Expected Keys = Total Routes × Days Ahead
Coverage % = (Warmed Keys / Expected Keys) × 100

Example: 12 routes × 7 days = 84 expected keys

Troubleshooting ​

Issue: Low Cache Hit Rate ​

Symptoms: Slow availability-range responses

Causes:

  1. Cache TTL too short
  2. Cache warm-up not running
  3. Redis memory issues

Solutions:

  1. Increase TRAIN_AVAILABILITY_CACHE_INTERVAL_MINUTES
  2. Check cron job logs for cache warm-up
  3. Monitor Redis memory usage

Issue: Stale Pricing Data ​

Symptoms: Prices don't match OTA system

Causes:

  1. Cache not invalidated after pricing update
  2. Exchange rate changed but cache not refreshed

Solutions:

  1. Manually invalidate cache for affected route
  2. Trigger full cache warm-up

Issue: Missing Routes in Cache ​

Symptoms: Some routes always return cache miss

Causes:

  1. New routes not in station cache
  2. Route temporarily unavailable

Solutions:

  1. Check station cache status
  2. Wait for next scheduled warm-up

Best Practices ​

  1. Peak Periods: Reduce cache interval to 15 minutes during high-traffic periods (Hajj season, holidays)

  2. Off-Peak: Increase to 60 minutes during low-traffic periods to reduce API load

  3. Schedule Changes: After OTA schedule updates, trigger manual cache warm-up

  4. Monitoring: Check cache status daily during peak booking periods
