Special Custom B2B Pricing ​

Selected B2B organizations can receive discounted custom-OTA / custom-booking prices through the Special Custom B2B Pricing feature. Pricing rules are shared across all enrolled organizations (no per-org overrides for now).

Overview ​

FeatureDetails
ScopeCustom-OTA search, calculate, and custom-booking only (not standard OTA or BlockSeat)
AccessAdmin + Access Role: reads need special-b2b-pricing:read, and config/route-price/economy-tier writes plus the ECONOMY tier auto-update trigger need special-b2b-pricing:update. See Access Roles
HostApplied only on the promo host promo.ahlaan.co.id (and subdomains). Any other host prices enrolled orgs as normal — see Host gating
SelectionAdmin manually enables per organization — customers cannot self-enroll
Shared rulesAll enrolled orgs use the same route-price table and exchange-rate reducer
Pricing levers(1) Per-route priceReducer (SAR, ECONOMY only) — sourced per fare tier level: level-1 uses the base CustomRoutePrice reducer, level-2+ use SpecialCustomB2BRoutePrice (see Per-fare reducer source); (2) exchangeRateReducer (IDR sell rate, applies to both ECONOMY and BUSINESS IDR conversion); (3) ECONOMY price cap (level-3 → level-2), unconditional for gold since 2026-07-07 (no longer gated on economyPriceCapEnabled)
FallbackIf no route rule exists, priceReducer = 0; the exchange-rate reducer still applies to every leg's IDR conversion
ClassesThe SAR priceReducer is ECONOMY-only; the exchangeRateReducer applies to both classes. BUSINESS legs keep their standard markup+tax SAR price, but their SAR→IDR conversion now uses the reduced effectiveSellRate (same as ECONOMY)

Pricing tiers (HOLDER / SILVER / GOLD) ​

The special-pricing gate is expressed as an explicit pricing tier rather than a single boolean. Every promo-host caller resolves to exactly one tier:

TierWhoPricing
HOLDEROff the promo host, a guest, or a caller who is not promo-eligibleNo reduced rate, no USD peg — the standard holder pricing
SILVERPromo-eligible, non-special (regular promo customer, incl. B2C / org-less)Identity IDR sell rate, default USD rate 3.72, cap off
GOLDPromo-eligible, specialReduced effectiveSellRate (via exchangeRateReducer), special USD rate 3.75, ECONOMY price cap. Equivalent to the former isSpecialB2B = true

pricingTier is the source of truth. Each organization carries an Organization.pricingTier (SILVER default, GOLD for special orgs). The older specialCustomPricingEnabled boolean is kept only as a deprecated mirror (GOLD ⇔ true), written in lockstep by the tier setter so existing readers keep working; new logic should read pricingTier.

A B2C user can now be GOLD. Special pricing is no longer strictly org-scoped: a per-user override (User.pricingTier) wins over the org tier, so an admin can put an individual B2C customer on GOLD (or force a member down to SILVER despite a GOLD org). See Set a user's pricing tier. The tier is only honoured after the promo-access gate passes — a tier is inert for a caller without promo access.

Tier resolution precedence: promo host? → promo-eligible? → per-user pricingTier override (if set) → else org pricingTier. effectiveOrgId still nulls the org axis for B2C, but the per-user override bypasses it, which is how a B2C user reaches GOLD.

Host gating (promo.ahlaan.co.id) ​

All special custom B2B pricing — the per-route priceReducer, the exchangeRateReducer, and the ECONOMY price cap — is applied only when the request arrives on the promo host: promo.ahlaan.co.id or any of its subdomains (e.g. staging.promo.ahlaan.co.id). On any other host (tiket.ahlaan.co.id, blockseat.ahlaan.co.id, localhost, …) an enrolled organization is priced exactly like a normal org — no route reducer, no rate reducer, no cap — even though specialCustomPricingEnabled is true.

  • A host-less internal caller (cron job, queue worker, server-to-server call with no Host header) also gets no special pricing — it is treated like a non-promo host, so background re-pricing never silently applies the discounts.
  • The promo base domain is configurable via the PROMO_BASE_DOMAIN env var (default promo.ahlaan.co.id); the gate matches that domain and any subdomain of it.

Enrollment (specialCustomPricingEnabled) is necessary but not sufficient: the org must be enrolled and the request must come from the promo host for any lever to engage.

Pricing Flow ​

When a user whose organization has specialCustomPricingEnabled = true calls a custom-OTA or custom-booking endpoint on the promo host (see Host gating):

  1. exchangeRateReducer is subtracted from the live IDR sell rate to form the reduced rate: effectiveSellRate = max(0, liveSellRate − exchangeRateReducer). This reduced rate applies to both ECONOMY and BUSINESS legs: the IDR payable of every leg converts at effectiveSellRate. (#373 had briefly restricted the rate lever to ECONOMY; it now covers BUSINESS too.) The SAR price is unchanged — a BUSINESS leg keeps its full custom markup + custom tax SAR amount, and any FIXED-IDR markup/tax is still converted into SAR at the full live rate; only the final SAR→IDR display conversion uses the reduced rate. The whole-booking IDR is the per-leg sum Σ floor(legSAR × effectiveSellRate). SAR and USD are unaffected by this lever. The strikethrough ("before discount") IDR keeps using the full live rate, so the discount is visible as the gap between strikethrough and payable.
  2. For each ECONOMY leg, the SAR route priceReducer is selected per fare brand by its tier level (see Per-fare reducer source): a level-2 fare uses SpecialCustomB2BRoutePrice.priceReducer, a level-1 fare uses the base CustomRoutePrice.priceReducer, and any other brand (level 3, unmapped, or a route with no active tier) keeps the SpecialCustomB2BRoutePrice.priceReducer. This SAR route reducer is ECONOMY-only.
  3. If no active route rule matches the selected table, that fare's priceReducer = 0 (leg prices at raw supplier cost), but the exchangeRateReducer still applies to every leg's IDR conversion.

Enrolled orgs may still book BUSINESS. There is no hard ECONOMY-only gate (unlike BlockSeat). A BUSINESS leg receives the exchangeRateReducer (reduced-rate IDR conversion) but not the SAR priceReducer: its SAR price stays at standard custom markup + custom tax.

Gold BUSINESS markup + tax are differentiated. A gold (enrolled specialCustomPricingEnabled) BUSINESS fare resolves its markup and tax from the dedicated special-B2B tables, falling back per lever to the base CustomMarkupRule / CustomTaxRule when no special rule matches; silver and no-auth BUSINESS use the base rules only. Manage these via Special Custom B2B Markup and Special Custom B2B Tax.

Per-fare reducer source (level-1 → base reducer) ​

Owner rule (2026-06-30). Within special-B2B ECONOMY, the SAR priceReducer source depends on the fare's tier level (the same level map used by the ECONOMY price cap):

Fare tier levelReducer table used
Level 1 (cheapest brand)base CustomRoutePrice.priceReducer
Level 2SpecialCustomB2BRoutePrice.priceReducer
Level 3 (capped down to level 2)SpecialCustomB2BRoutePrice.priceReducer
Unmapped brand / route with no active tierSpecialCustomB2BRoutePrice.priceReducer (prior behavior)

This split engages whenever an active tier exists for the route — it is an independent lever from the price cap and does not require economyPriceCapEnabled. With no active tier (or a non-special org), every ECONOMY fare keeps the special reducer exactly as before, so only level-1 fares on tier-mapped routes change. Selection is per fare within a search (each brand in a cabin can resolve a different reducer); the cap's level-3 swap does not alter the fare's fareReference, so a capped level-3 fare still classifies as level 3 and keeps the special reducer. A level-1 fare on a route with no active CustomRoutePrice rule gets priceReducer = 0 (sells at supplier cost).

Partially-discovered tiers (2026-07-22). The reducer split (and its per-level columns below) now engages on an active tier even before auto-discovery has found all three fare-brands — a route that genuinely sells one or two brands classifies whatever levels it has (auto-discovery fills L1→L2→L3 ascending, so a partial tier has a level-1 brand and null level-2/3 refs). Previously the whole level map was withheld until the tier reached isComplete, silently charging the flat reducer and leaving admin per-level config dead on single-brand routes. The L3→L2 price cap still requires a fully-discovered tier — a partial tier has no level-3 brand, so the cap can never engage on it. A fare's classified level can re-rank as discovery fills in (today's lone level-1 brand becomes level-2 once a cheaper brand appears); this is inherent to auto-discovery and fails closed (unknown level → flat reducer).

Per-fare-level reducer columns (2026-07-07). The owner-rule table above is now the fallback layer — each route-price row additionally carries optional per-level reducer columns that OVERRIDE the flat reducer for a matching level:

TierTableColumnsL1 unset falls back toL2/L3 unset falls back to
Silver (promo, non-special)CustomRoutePricepriceReducerLevel1/2/3flat CustomRoutePrice.priceReducerflat CustomRoutePrice.priceReducer
Gold (special-B2B)SpecialCustomB2BRoutePricepriceReducerLevel1/2 (L2 also serves L3)base CustomRoutePrice.priceReducer (owner rule)flat SpecialCustomB2BRoutePrice.priceReducer

All columns are nullable; a null column reproduces the exact pre-existing number, so an all-null row behaves identically to before (zero-shift, no backfill). The per-level path is promo-host-only (silver is gated on the promo host; gold is already special-B2B-only) and ECONOMY-only. Gold's L3 uses the L2 column (its fare is also capped down to L2 — see below). Per-level columns apply on partially-discovered (active) tiers too (2026-07-22), so an admin's L1 column takes effect on a single-brand route without waiting for the tier to complete.

The reducer source applied to each booked leg is recorded in the admin-only pricingSnapshot.economyReducerSource ({ "outbound": "BASE" | "SPECIAL", "return"?: … }). The entire pricingSnapshot is admin-only — omitted wholesale from customer responses (...(isAdmin && { pricingSnapshot }), #389), not stripped key-by-key.

Real staging snapshot — special-B2B DMX→MKX ECONOMY booking of the live SAB2MINECO brand (unmapped → keeps the SpecialCustomB2BRoutePrice reducer of 16), admin GET …/admin/custom-booking/:id pricingSnapshot (subset):

json

The top-level isSpecialB2B column is a separate first-class field and stays customer-visible (it mirrors the snapshot flag). A level-1 brand on the same route would instead record economyReducerSource: { "outbound": "BASE" } with the base CustomRoutePrice reducer.

Payable IDR uses effectiveSellRate = 4850 − 250 = 4600; the strikethrough IDR stays at the full 4850. USD is unaffected by exchangeRateReducer.

A BUSINESS leg now also uses exchangeRateReducer for its IDR conversion: for the same enrolled org, a BUSINESS SAR fare of 227 (unchanged custom markup + custom tax) converts at the reduced 4600 → 1,044,200 IDR (not the full-rate 227 × 4850 = 1,100,950). On a mixed round-trip both the ECONOMY leg and the BUSINESS leg convert at 4600, summed per leg. The BUSINESS SAR price itself is unchanged — only its SAR→IDR conversion is discounted.

Audit snapshot (recomputable from the row alone) ​

Every custom-booking persists the special-pricing levers into pricingSnapshot at create time (#373), so the charged IDR is reconstructable without consulting the mutable global config or the org's specialCustomPricingEnabled flag:

FieldMeaning
isSpecialB2BWhether the booking was priced under special B2B at create time
baseSellRateFull live IDR sell rate at create time — the ExchangeRate row the booking's exchangeRateId FK points at. Note: the exchangeRate.sellRate on the admin custom-booking detail and exchangeRate.rate on the invoice render the effective rate, not this one — see Which rate is displayed where
effectiveSellRateRate actually applied to all legs — ECONOMY and BUSINESS (baseSellRate − exchangeRateReducerIDR). A negative reducer (surcharge) makes this higher than baseSellRate
exchangeRateReducerIDRThe signed IDR rate adjustment in effect at create (0 for a non-special booking). Positive = shave (lowers the effective rate); negative = surcharge (raises it). Stored verbatim as baseSellRate − effectiveSellRate
economyReducerSourcePer-leg SAR-reducer table used — { "outbound": "BASE" | "SPECIAL", "return"?: … }. BASE = level-1 fare priced off CustomRoutePrice; SPECIAL = SpecialCustomB2BRoutePrice. Present only on special-B2B bookings (see Per-fare reducer source).

Per-leg, the existing outbound.pricingMode / return.pricingMode (REDUCER = ECONOMY reducer pricing, MARKUP_TAX = BUSINESS markup+tax pricing) identifies how each leg's SAR price was formed. The exchangeRateReducer now applies to both modes, so every leg converts at effectiveSellRate: the per-leg sum Σ floor(legSAR × effectiveSellRate) == totalPriceIDR holds for all bookings.

Which rate is displayed where ​

The booking's exchangeRateId FK always points at the BASE ExchangeRate row; the reduced figure lives only on pricingSnapshot.effectiveSellRate. The amounts have always been correct — they are built from the effective rate — but which rate a response renders depends on the surface:

SurfaceRate renderedNotes
Invoice detail + list — exchangeRate.rateEffectiveCustomer- and admin-visible. Falls back to base for legacy rows with no snapshot field
Admin custom-booking detail — exchangeRate.sellRateEffectiveOther columns (buyRate, source, fetchedAt) pass through untouched
Custom-OTA search / calculate — exchangeRate.sellRateEffectivePre-existing behaviour; see custom-OTA
Plain OTA search / calculate — exchangeRate.sellRateBaseThe reducer applies to the custom flows only
GET /exchange-rate/current and admin exchange-rate endpointsBase, except getCurrentRateForOrg which reduces for GOLDSee Exchange Rate
Wallet top-up, BlockSeatBaseThese rails never reduce
Customer custom-booking detail(no rate value)Exposes exchangeRateId only; the customer sees the rate on their invoice

All display sites resolve through one shared helper, resolveEffectiveSellRate (src/common/utils/effective-sell-rate.util.ts), which reads the frozen snapshot and falls back to the base rate. It never re-derives the rate at read time: exchangeRateReducer is a mutable global singleton, so re-deriving would silently re-price historical invoices whenever an admin edits the config.

Top-level isSpecialB2B column (customer-visible). Beyond the admin-only snapshot copy above (the entire pricingSnapshot is omitted from customer responses — #389), the booking also carries a denormalized isSpecialB2B boolean column returned at the top level on both admin and customer custom-booking responses — so a customer can see their booking was priced under special B2B without exposing the rate internals. It is also an admin list filter: GET /admin/custom-booking?isSpecialB2B=true|false. Existing rows were backfilled from pricingSnapshot.isSpecialB2B by the 20260701000000_add_is_special_b2b_to_custom_booking migration.

Update exchange rate reducer ​

http
PATCH /api/v1/admin/special-custom-b2b-pricing/config
Authorization: Bearer <admin-token>
Content-Type: application/json

{
  "exchangeRateReducer": 250
}

Sets how much (in IDR) is subtracted from the live sell rate for all special custom B2B organizations. Set to 0 to disable the exchange rate discount while keeping route rules. Symmetric bound: minimum -1000, maximum 1000. A negative value is a surcharge — it raises the effective sell rate (effectiveSellRate = sellRate − reducer).

Update the tiered USD rates ​

http
PATCH /api/v1/admin/special-custom-b2b-pricing/config
Authorization: Bearer <admin-token>
Content-Type: application/json

{
  "specialUsdSarRate": 3.75,
  "defaultUsdSarRate": 3.72
}

SAR-per-USD rates used to convert SAR → USD (USD = SAR ÷ rate) in the promo custom-ota / custom-booking flow:

  • specialUsdSarRate (default 3.75, gold) — applied to a promo-eligible org with specialCustomPricingEnabled.
  • defaultUsdSarRate (default 3.72, silver) — applied to any other promo-eligible caller on the promo host: a B2C, org-less, or non-special-org customer. It is not gated on having an organization — the only requirement is promo eligibility (promoAccessEnabled) and the absence of the gold flag.

A higher rate yields a cheaper USD figure. Both must be > 0 (max 100). A guest / not-promo-eligible caller, off the promo host, and host-less callers (cron/queue) use the global admin-managed USD rate holder instead (unchanged). The same tiering is surfaced on GET /api/v1/exchange-rate/current?currency=USD (see the Exchange Rate doc) so the endpoint mirrors what custom pricing charges. The rate in effect at booking time is frozen into pricingSnapshot.usdSarRate / usdRateTier (SPECIAL | DEFAULT | HOLDER) — a promo-eligible non-special booking records DEFAULT (silver).

Baseline tier reducer (baselinePriceReducer) ​

http
PATCH /api/v1/admin/special-custom-b2b-pricing/config
Authorization: Bearer <admin-token>
Content-Type: application/json

{
  "baselinePriceReducer": 4.31
}

The flat SAR reducer for the promo-host baseline tier — the always-present reference tier in promoTierPrices (see Promo-host tiered prices). The baseline price is:

baselinePrice = supplier − baselinePriceReducer   (per passenger)

Unlike the ECONOMY route priceReducer, the baseline reducer:

  • Applies to ALL classes — ECONOMY and BUSINESS are forced into reducer mode for the baseline tier (no markup + tax; business is not priced markup-first in this tier).
  • Is applied per passenger and is UNFLOORED (kept at full float precision — it is a reference figure, never the charged price).
  • Uses the identity sell rate and the default USD tier (defaultUsdSarRate, 3.72) — it never picks up the exchange-rate reducer or the special USD rate.

Decimal, default 4.31, symmetric bound minimum -1000, maximum 1000 (a negative value is a surcharge — it raises the baseline). It is a singleton config value edited via the same PATCH …/config partial update and returned by GET …/config. The baseline tier is the primary (quoted) price for a no-auth promo caller, so a negative value (surcharge) raises what those callers are quoted. For authenticated silver/gold callers the baseline is only the reference/strike figure carried in promoTierPrices and does not change their charged price.

ECONOMY Price Cap (level-3 → level-2) ​

A third lever (opt-in, off by default) caps the ECONOMY price an enrolled org can pay. The supplier exposes up to three ECONOMY fare brands per route, identified by fareReference (level 1 = cheapest … level 3 = most expensive). On any given day only a random subset appears; over a week all three show. With the cap on, a fare classified as level 3 is re-priced to level 2 — the customer never pays the top ECONOMY tier. BUSINESS, non-special orgs, and standard OTA / BlockSeat are never affected. The cap is a ceiling: level-1 and level-2 fares are untouched (never raised).

ConceptDetail
ScopeSpecial-B2B ECONOMY only (custom-OTA search, calculate, custom-booking). Per leg on a mixed round-trip.
Level sourcePer-route fareReference→level map (SpecialCustomB2BEconomyTier), auto-discovered only — supplier-probed, never hand-mapped (source is always AUTO). The same level map also drives the per-fare reducer source (level-1 → base reducer), which engages independently of economyPriceCapEnabled.
Cap targetThe live level-2 fare seen in the same supplier search; falls back to the configured level2PriceSAR when no level-2 fare is present that day.
EngagementUnconditional for gold (2026-07-07, decision 2). Engages for any special-B2B (gold) caller whenever an isActive + isComplete tier exists for the route — it no longer honours economyPriceCapEnabled (that toggle is now inert for the cap on the gold pricing path). Silver and no-auth callers are never capped (they carry a tier map for per-level reducers but the cap is keyed on the gold signal). Behavior change: an enrolled gold org that previously ran with the cap off now has its level-3 fares capped to level 2.
MarkingCapped bookings carry economyPriceCapped = true (queryable column) plus admin-only pricingSnapshot.economyPriceCapped + economyPriceCapDetail (the whole pricingSnapshot is omitted from customer responses — #389).

Fare-tier map — auto-discovery only ​

Tiers are discovered, never hand-mapped. There is no manual create or level-edit endpoint. The brand→level map and the level*PriceSAR values come solely from the supplier probe (auto-update below); source is always AUTO. The only field an admin controls is isActive (activate a reviewed tier / deactivate one).

http
GET    /api/v1/admin/special-custom-b2b-pricing/economy-tiers
GET    /api/v1/admin/special-custom-b2b-pricing/economy-tiers/:id
PATCH  /api/v1/admin/special-custom-b2b-pricing/economy-tiers/:id     (body: { "isActive": true|false })
DELETE /api/v1/admin/special-custom-b2b-pricing/economy-tiers/:id     (soft-delete → isActive=false)

Admin workflow

  1. Discover a route — POST …/economy-tiers/auto-update { "scope": "ROUTE", originCode, destinationCode }. Probes the supplier and upserts the row (source: AUTO, inactive if new).
  2. Review — GET …/economy-tiers / …/:id.
  3. Activate — PATCH …/:id { "isActive": true }.
  4. Deactivate / re-enable — PATCH …/:id { "isActive": false|true }; DELETE …/:id is a soft-delete (isActive=false, returns { "success": true }). To re-enable a soft-deleted tier, PATCH { "isActive": true }.

PATCH accepts only isActive (required) — any level*FareRef / level*PriceSAR, or an empty body, is rejected with 400. Routes are directional: DMX→MKX and MKX→DMX are independent rows with independent fares/caps. The pricing cap lookup resolves the exact queried direction only — the reverse is a separate, separately-discoverable tier, and the two price independently. The admin list filter (GET …/economy-tiers?originCode=&destinationCode=) is convenience-symmetric, however: filtering by a station pair returns both directional rows (each labelled with its own stored direction) so you see the full route in one query. (Contrast the route-price priceReducer above, whose lookup and pricing both remain symmetric.)

Auto-discovery ​

The probe searches 1 adult over the next autoUpdateMaxDays (≤ 7) days, accumulating distinct ECONOMY fareReferences until three are found, then ranks them by price into level 1/2/3:

http
POST /api/v1/admin/special-custom-b2b-pricing/economy-tiers/auto-update
{ "scope": "ROUTE", "originCode": "DMX", "destinationCode": "MKX" }   // sync, returns the result
{ "scope": "ALL" }                                                    // background, 202; sweeps every ordered active-station pair (both directions)

scope: ROUTE response (202) — synchronous; found is the distinct ECONOMY brand count from this probe, daysScanned the window scanned, outcome how the run resolved (below). isComplete is the resulting row's completeness — it equals found >= 3 only when the probe overwrote the row. On a keep-last-known-good PARTIAL (a probe that found fewer brands than the stored row already holds) the prior complete map is kept, so isComplete stays true while found is < 3.

Real staging probe (POST …/economy-tiers/auto-update {"scope":"ROUTE","originCode":"DMX","destinationCode":"MKX"}) of an already-complete DMX→MKX row that surfaced a single brand that day — the 1-brand result is discarded as a regression and the complete map kept (found: 1 yet isComplete: true, outcome: PARTIAL):

json
{
  "scope": "ROUTE",
  "result": {
    "originCode": "DMX",
    "destinationCode": "MKX",
    "found": 1,
    "daysScanned": 7,
    "isComplete": true,
    "outcome": "PARTIAL"
  }
}

For a brand-new or still-incomplete route the same shape returns isComplete: false (the probe stored its progress), e.g. { "found": 2, "isComplete": false, "outcome": "PARTIAL" }.

scope: ALL response (202) — fire-and-forget; in the background it sweeps every ordered pair of active stations (origin→destination AND destination→origin), skipping any direction whose tier is deactivated. This is the sole seeding path — a fresh deploy with no tier rows still discovers every route:

json
{ "scope": "ALL", "accepted": true }

A newly-discovered route is saved inactive — review, then activate.

Run outcomes (lastAutoOutcome) ​

Every run sets lastAutoUpdatedAt (heartbeat). It resolves to one of:

OutcomeWhenEffect
CHANGEDA complete (3-brand) discovery differs from the stored levels, or the route's first complete mapLevels overwritten, lastAutoChangedAt bumped, an audit-log entry written (old→new).
NO_CHANGEA complete discovery equals the stored levelsHeartbeat only — levels and lastAutoChangedAt untouched, no audit entry.
PARTIALFewer than 3 brands found that dayKeep-last-known-good — a probe that found fewer brands than the row already holds is discarded (a transient short window never wipes accumulated brands or knocks a complete tier inert); an empty probe on a brand-new route persists nothing. Only a same-or-more-brand partial is stored (to show progress). Heartbeat only, no audit.

So the FE can show "last checked lastAutoUpdatedAt, last changed lastAutoChangedAt" and lastAutoOutcome distinguishes a no-op from a partial day. The AuditLog (SPECIAL_CUSTOM_B2B_ECONOMY_TIER_AUTO_UPDATE) is the level-change history — written only on CHANGED (no daily-cron spam), with metadata.trigger = ADMIN (manual) or CRON.

Daily cron ​

When autoUpdateCronEnabled = true, the worker re-runs scope: ALL once a day at autoUpdateTimeAST (HH:MM Arabia Standard Time, UTC+3, no DST). Configure via PATCH …/config:

json
{
  "economyPriceCapEnabled": true,
  "autoUpdateCronEnabled": true,
  "autoUpdateTimeAST": "00:01",
  "autoUpdateMaxDays": 7
}

The cron only fires on the cron worker host (ENABLE_CRON=true); a daily-once guard (lastAutoUpdateAt) prevents re-runs. Since tiers are auto-only, the cron refreshing active rows is the intended single source — there is no hand-curated data for it to overwrite, and a transient partial-brand day is kept-last-known-good.

Worked example ​

Route DMX→MKX, three ECONOMY brands LET001ORM=2325 (L1), LET002ORI=3025 (L2), LET003ORX=3710 (L3). With the cap on, a special org booking the LET003ORX fare is charged 3025 (the live L2 price) instead of 3710, and the booking is marked economyPriceCapped = true. An org booking LET001ORM still pays 2325 (untouched). A non-special org pays the real fare for every brand.

Cap source: LIVE_L2 vs CONFIG_FALLBACK ​

The cap re-prices a level-3 leg to level 2 by one of two sources, recorded per capped leg in the admin-only pricingSnapshot.economyPriceCapDetail:

capSourceWhenApplied price
LIVE_L2The level-2 brand is present in the same supplier search that dayThe live per-pax level-2 fare (only the per-pax fare is swapped; the booked qty is kept, so a 10-passenger leg is charged 10 × L2, not 1 × L2)
CONFIG_FALLBACKThe level-2 brand is absent that day (e.g. only one ECONOMY brand bookable)The configured level2PriceSAR per adult, with child/infant scaled by the same ratio

In both cases the cap is a ceiling — if the level-3 fare is already ≤ level 2, the leg is left unchanged (capped: false).

Real economyPriceCapDetail (admin-only, from a CONFIG_FALLBACK capped booking):

json
[
  {
    "leg": "OUTBOUND",
    "capSource": "CONFIG_FALLBACK",
    "originalFareRef": "SAB2MINECO",
    "originalPerAdultSAR": 224.25,
    "appliedPerAdultSAR": 150
  }
]

A 10-adult ONE_WAY booking of this leg is charged 10 × 150 = 1500 SAR. The calculate response surfaces a top-level economyPriceCapped: true (no detail); the customer-facing booking response omits the entire pricingSnapshot (admin-only — #389), so neither economyPriceCapped nor economyPriceCapDetail is exposed there.

Cache Invalidation ​

  • Route price lookups are cached in Redis per route+class (TTL 300s). Cache is invalidated on create / update / delete.
  • Exchange rate reducer is cached per singleton key (TTL 300s). Cache is invalidated on update.
  • Organization enrollment status is cached per org (TTL 300s). Cache is invalidated when specialCustomPricingEnabled changes.

Notes ​

  • The SAR priceReducer is ECONOMY-only; the exchangeRateReducer applies to both ECONOMY and BUSINESS legs. BUSINESS legs keep their standard custom markup + custom tax SAR price, but their SAR→IDR conversion now uses the reduced effectiveSellRate (any FIXED-IDR markup/tax is still converted into SAR at the full live rate; only the final SAR→IDR display conversion is discounted). All of this is gated to the promo host — see Host gating.
  • Setting a priceReducer larger than the supplier fare results in a 0 SAR payable for that leg (floor at 0).
  • The ECONOMY price cap is a separate, opt-in lever (above) — a ceiling on the ECONOMY brand, applied AFTER the route + exchange-rate reducers. It is off by default (economyPriceCapEnabled = false) and only engages for routes with an active, complete tier map.
  • To stop all special discounts immediately: set exchangeRateReducer = 0, economyPriceCapEnabled = false, and deactivate all route rules (or unenroll all orgs).
