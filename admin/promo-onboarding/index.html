Promo Customer Onboarding Guide ​

End-to-end workflow for giving customers access to the promo frontend (promo.ahlaan.co.id and its subdomains). Promo login and booking are closed registration — only promo customers can log in and book there.

Whether a user is a promo customer is decided by their effective promo access, a coalesce of a per-user override with their organization's flag:

User.promoAccessEnabled (override)Effective promo access
trueON — even with no organization, or a non-promo org
falseOFF — even inside a promo-enabled organization
null (default)inherit Organization.promoAccessEnabled — only for a B2B member; a B2C user (or an org-less user) ⇒ OFF

So a promo customer does not need an organization — the org flag is just an optional bulk grant. specialCustomPricingEnabled remains a separate, org-only pricing lever, orthogonal to access.

B2C users do not inherit the org flag

Org-inherited promo access (override = null) applies only to genuine B2B org members. A B2C user ignores all organization-scoped rules, so the org's promoAccessEnabled flag does not grant them access. A B2C promo customer must be given an explicit per-user promoAccessEnabled = true. (This also means a member auto-demoted to B2C when their org was deactivated loses org-inherited promo access.)

Quick Overview ​

FeatureDescription
PurposeGrant / revoke promo-host login + booking access, per user or in bulk per org
AccessAdmin only (ADMIN role)
ControlEffective promo access = per-user override coalesced with the org flag
Orthogonal tospecialCustomPricingEnabled — pricing only, does not grant access

Onboarding paths ​

Path A — a single customer, no organization ​

Grant the per-user override directly. No org required.

bash
# create the customer with the override on
curl -X POST "/api/v1/admin/users" \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "customer@example.com",
    "name": "Promo Customer",
    "role": "B2C",
    "promoAccessEnabled": true
  }'

Or flip an existing account on:

bash
curl -X PATCH "/api/v1/admin/users/<user-id>/promo-access" \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{ "enabled": true }'

B2B/B2C users are passwordless — the customer then logs in on the promo host via OTP or Google/Apple.

Path B — a whole organization (bulk grant) ​

Enable the org flag; every B2B member with override null (the default) inherits access. B2C members do not inherit the org flag — grant them individually via Path A (explicit promoAccessEnabled = true).

bash
curl -X PATCH "/api/v1/admin/organizations/<org-id>/promo-access" \
  -H "Authorization: Bearer <admin-jwt>" \
  -H "Content-Type: application/json" \
  -d '{ "enabled": true }'

Attach users to that org via POST /admin/users (or PATCH /admin/users/:id) with organizationId. Toggle audit-logged as PROMO_ACCESS_ENABLED / PROMO_ACCESS_DISABLED, throttled 30/min.

Excluding one member of a promo org ​

Set that user's override to false — it wins over the org's bulk grant:

bash
curl -X PATCH "/api/v1/admin/users/<user-id>/promo-access" \
  -d '{ "enabled": false }'

The per-user override endpoint ​

http
PATCH /api/v1/admin/users/:id/promo-access
{ "enabled": true | false | null }
  • true → force promo access ON, false → exclude, null → clear the override (re-inherit the org flag).
  • Audit-logged as USER_PROMO_ACCESS_SET. Throttled 30/min. 404 on unknown user.

You can also set promoAccessEnabled inline on POST /admin/users and PATCH /admin/users/:id.

Auto-reset on org-membership change ​

Whenever a user's organization membership changes — attach, switch, or detach — the per-user override is reset to null so the user re-inherits the new context. A grant or exclusion made for a previous org never leaks onto a new one.

  • Applies to PATCH /admin/users/:id (attach/switch/detach), user creation, and B2B application approval (which attaches the approved user to a new org).
  • Exception: if the same request also sends an explicit promoAccessEnabled, that value wins (attach-and-grant, or attach-and-exclude, atomically).
  • A no-op org value (unchanged id, or empty string) does not reset.
  • Consequence: detaching or switching an org clears any per-user grant — a standalone promo customer who later gets attached/detached must be re-granted with the override.

Kick a user from an organization ​

http
PATCH /api/v1/admin/users/:id      { "organizationId": null }
  • Send explicit null; "" is a no-op; omitting the field = no change.
  • Detach clears the org grant and resets the override to null (per the rule above) → the user's effective promo access drops to OFF unless re-granted.

Seeing who is a promo customer ​

Customer list / detail (GET /admin/users, GET /admin/users/:id) expose:

  • promoAccessEnabled — the raw per-user override (true / false / null).
  • effectivePromoAccess — the resolved boolean the gate actually enforces.
  • nested organization.promoAccessEnabled — the org's bulk-grant flag.

Filter customers by effective promo access:

GET /api/v1/admin/users?promoAccessEnabled=true    # promo customers
GET /api/v1/admin/users?promoAccessEnabled=false   # everyone else

The filter is on effective access — it matches both override-true users and override-null users inheriting a promo-enabled org.

Filter organizations:

GET /api/v1/admin/organizations?promoAccessEnabled=true
GET /api/v1/admin/organizations?specialCustomPricingEnabled=true

Both flags are also shown on the org list/detail responses.

Downgrading ​

  • One user: PATCH /admin/users/:id/promo-access { "enabled": false } (hard exclude) or { "enabled": null } (inherit — OFF if org-less / non-promo org).
  • A whole org: PATCH /admin/organizations/:id/promo-access { "enabled": false }. Members with override null lose access; members with override true keep it (org-independent grant).
  • Revoking promo access does not strand in-flight bookings — booking lifecycle endpoints (list/detail, passenger updates, ticket download, cancel) are not promo-gated.

Deploy note ​

The migration adds User.promoAccessEnabled as NULL (inherit) for every user and Organization.promoAccessEnabled=false for every org — so at deploy all customers are blocked from promo login/booking, by design. Immediately after migrating, grant access per user (Path A) or per org (Path B). Every org already promo-enabled keeps granting its members (override defaults to inherit).
