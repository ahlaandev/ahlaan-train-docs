Partners Management Guide ​

This guide explains how administrators create banking-integrator partners and issue / revoke the API credentials those partners present when calling Ahlaan's public API through the ahlaan-api-for-partners service.

Quick Overview ​

FeatureDescription
PurposeManage partner organizations (e.g., banking apps) and the API keys they present
Admin AccessAdmin endpoints require the ADMIN role plus Access Role permissions: partner reads need partners:read, partner create/update need partners:manage, API key reads need api-keys:read, and API key issue/update/revoke need api-keys:manage. See Access Roles
Consumed ByThe ahlaan-api-for-partners Go service reads Partner / PartnerApiKey directly from the shared Neon database (no internal endpoint)
ScopePartner CRUD, API key issuance, revocation, audit logging
Out of scope (this slice)Partner-consumer endpoints (search / book / tickets), Booking.partnerId attribution, contactPerson account linking, partner wallet & settlement, outbound webhooks

Partners are distinct from B2B customer organizations. B2B customers self-register through the B2B Application flow and use JWT auth. Partners are admin-provisioned only and authenticate via opaque API keys.

Base URL ​

All partner management endpoints use:

/api/v1

Authentication ​

All admin partner endpoints require:

  • JWT Token in Authorization header
  • ADMIN role on the calling user
http
Authorization: Bearer <your-admin-jwt-token>

The ahlaan-api-for-partners Go service does not call hhr-api on the request path — it reads partner credentials directly from the shared database. See Partner service credential access below.

Concepts ​

Partner ​

A row in the Partner table. Identifies a banking integrator (e.g., Bank Mandiri). Fields:

FieldNotes
codeUPPER_SNAKE_CASE, 3–50 chars, unique. E.g., BANK_MANDIRI. Immutable after creation.
nameFree-text display name.
statusACTIVE / SUSPENDED / TERMINATED.
contactEmail / contactPhoneOptional operations contacts.
notesFree-form admin notes (≤ 4000 chars).

Partner API Key ​

A row in the PartnerApiKey table. Each row represents one issued credential.

FieldNotes
nameHuman-readable admin label (e.g., "Bank Mandiri Production").
prefixFirst 20 chars of the raw key, plaintext for UI / log display. Not a secret.
hashedKeySHA-256 hex of the raw key. The raw key itself is never stored.
scopesSubset of the scope catalog.
rateLimitPerMinuteOptional per-key cap. Null = no per-key cap configured.
expiresAtOptional ISO 8601 future date. Null = no expiry.
revokedAt / revokedReasonSet on revocation. Revoked keys cannot be updated.

Raw key reveal ​

The raw key (raw field) appears exactly once — in the response to POST /admin/partners/{partnerId}/api-keys. It cannot be retrieved later. If a partner loses the raw key, issue a new one and revoke the old.

Key format ​

  • Prefix ahlaan_live_ in production, ahlaan_test_ in non-production.
  • 32 random bytes encoded as base62.
  • Total length ≈ 55 chars.

The same prefix is also used by customer-facing public API keys (when that feature lands on prod). The two key spaces are namespaced by which table is queried, not by prefix inspection — see SECURITY_POSTURE.md and plan/partner-credentials.md.

Scope catalog ​

The full set of scopes a partner key may carry. The Go consumer service enforces scope per endpoint.

ScopePurpose
ota:searchPOST /partner/ota/search — list available trains
ota:calculatePOST /partner/ota/calculate — calculate booking price
ota:routesGET /partner/ota/routes — list available train routes
ota:orders.writePOST /partner/ota/orders — create a travel order from a previously-issued schedule_id
ota:orders.readPOST /partner/ota/orders/search and GET /partner/ota/orders/{bookingCode} — list a customer's orders and read order detail
ota:orders.cancelPOST /partner/ota/orders/{bookingCode}/cancel — cancel an existing order
ota:orders.ticketGET /partner/ota/orders/{bookingCode}/tickets — download or retrieve issued tickets
ota:orders.modifyPATCH /partner/ota/orders/{bookingCode} — change an order and its passengers

GET /admin/partners/scope-catalog returns the live catalog with descriptions for UI dropdowns.

2. Create a partner ​

Endpoint: POST /admin/partners

Body:

json
{
  "code": "BANK_MANDIRI",
  "name": "PT Bank Mandiri (Persero) Tbk",
  "contactEmail": "integration@bankmandiri.co.id",
  "contactPhone": "+622152997777",
  "notes": "Production contract signed 2026-04-01."
}

Validation:

  • code must match /^[A-Z][A-Z0-9_]{2,49}$/.
  • name 1–255 chars.
  • contactEmail RFC 5322; contactPhone E.164.

Response: 201 Created

json
{
  "id": "0192f...",
  "code": "BANK_MANDIRI",
  "name": "PT Bank Mandiri (Persero) Tbk",
  "status": "ACTIVE",
  "contactEmail": "integration@bankmandiri.co.id",
  "contactPhone": "+622152997777",
  "notes": "Production contract signed 2026-04-01.",
  "holderUserId": "0192f...",
  "allowedCurrencies": ["IDR"],
  "createdBy": "admin-user-id",
  "createdAt": "2026-05-13T06:13:07Z",
  "updatedAt": "2026-05-13T06:13:07Z"
}

holderUserId is the system placeholder user provisioned for the partner (satisfies Booking.userId before a booking is claimed to a real customer). allowedCurrencies is the list of ISO-4217 currencies the partner may transact in; it defaults to ["IDR"] when omitted on create.

Errors:

  • 409 Conflict — duplicate code.
  • 400 Bad Request — invalid DTO.

4. Get partner detail ​

Endpoint: GET /admin/partners/{partnerId}

Response: 200 OK (Partner object) or 404 Not Found.

5. Update partner ​

Endpoint: PATCH /admin/partners/{partnerId}

Patchable: name, status, contactEmail, contactPhone, notes. code is immutable.

Status transitions:

From → ToEffect
ACTIVE → SUSPENDEDKeys remain in DB; the partner service resolves them as PARTNER_SUSPENDED on its next shared-DB read, bounded by its short cache TTL.
ACTIVE → TERMINATEDAll active keys are atomically revoked with reason Partner terminated.
SUSPENDED → ACTIVEKeys resume normal operation once the partner service's cache TTL elapses.
TERMINATED → anythingAllowed (admin override); keys remain revoked — they are not auto-restored.

Errors:

  • 400 Bad Request — invalid DTO.
  • 404 Not Found — partner missing.

6. Issue an API key ​

Endpoint: POST /admin/partners/{partnerId}/api-keys

Headers:

http
Authorization: Bearer <admin-jwt>
Idempotency-Key: 0a96a2c6-7e3e-4f76-9c61-9d8c89e3f8b1

Idempotency-Key is required (UUID v4 recommended). Replays within 24 h return the original response body and add Idempotent-Replayed: true to the response headers.

FE: generate the key automatically — don't make admins type it

Why this header exists. Issuing a key is a non-idempotent create, and the raw secret is returned only once (the DB stores a hash). If the request reaches the server but the response is lost — timeout, dropped connection, proxy retry, an impatient double-click — a naive retry would mint a second live key whose raw value nobody ever received. That orphan credential is valid in the DB, cannot be identified by its prefix alone, and has to be hunted down and revoked. The idempotency key collapses every retry of the same issue action into one key and replays the original raw back to the caller.

FE guidance. Do not surface this header to the admin or ask them to paste a UUID. Generate one UUID v4 per issue action when the form mounts (or on first submit), reuse that same value for every retry of that action, and generate a fresh UUID only when the admin deliberately starts a new issue action.

ts
// On issue form mount — one key per logical "Issue API Key" action.
const idempotencyKey = crypto.randomUUID(); // UUID v4

async function issueApiKey(partnerId: string, body: IssueKeyBody) {
  const res = await fetch(`/admin/partners/${partnerId}/api-keys`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${adminJwt}`,
      'Idempotency-Key': idempotencyKey, // SAME value on every retry of this action
    },
    body: JSON.stringify(body),
  });

  if (res.headers.get('Idempotent-Replayed') === 'true') {
    // Not a new key — the original response was replayed.
    // Safe: don't show a second "key created" toast; just render the returned key.
  }
  return res.json();
}

Rules of thumb for FE:

  • One UUID per user action, not per HTTP attempt. Retries reuse it.
  • Regenerate the UUID only when the admin intentionally issues another key.
  • Idempotent-Replayed: true ⇒ "already issued" — render the returned key, suppress duplicate success UX.
  • Don't reuse a key after 24 h for a different action; the server no longer dedupes it.

Body:

json
{
  "name": "Bank Mandiri Production",
  "scopes": ["ota:search", "ota:calculate", "ota:routes"],
  "rateLimitPerMinute": 600,
  "expiresAt": "2027-05-13T00:00:00Z"
}

Response: 201 Created

{
  "id": "01abc...",

Raw key shown once

The raw field appears only in this response. Store it securely now — there is no way to retrieve it later. If lost, issue a new key and revoke the old one.

Errors:

  • 400 Bad Request — missing Idempotency-Key, unknown scope, expiresAt not in the future, invalid DTO.
  • 404 Not Found — partner missing.
  • 409 Conflict — partner is SUSPENDED or TERMINATED; or a concurrent request is already processing the same Idempotency-Key (retry once the first call completes).

9. Update partner API key ​

Endpoint: PATCH /admin/partners/{partnerId}/api-keys/{keyId}

Patchable fields:

FieldNotes
name1–100 chars
scopesMust be a subset of the scope catalog
rateLimitPerMinute1–10000, or null to clear
expiresAtISO 8601 future date, or null to clear

Immutable fields (prefix, hashedKey, createdBy, revokedAt, …) are rejected silently by the global validation pipe.

The change is written to the shared database; ahlaan-api-for-partners picks it up on its next read, bounded by its short cache TTL.

Errors:

  • 400 Bad Request — unknown scope, expiresAt not in the future.
  • 404 Not Found — partner or key missing.
  • 409 Conflict — key is already revoked (revoked keys are immutable).

10. Revoke partner API key ​

Endpoint: POST /admin/partners/{partnerId}/api-keys/{keyId}/revoke

Body:

json
{ "reason": "Key suspected leaked via support ticket #4521" }

reason is required (1–500 chars) and recorded in the audit log.

Response: 204 No Content

Revocation is idempotent — re-revoking an already-revoked key returns 204 and does not change revokedAt / revokedReason.

Revocation is written to the shared database; the partner service stops resolving the key on its next read, bounded by its short cache TTL.

Credential propagation ​

hhr-api is the system of record for Partner / PartnerApiKey. The ahlaan-api-for-partners Go service reads those tables directly from the shared Neon database and caches resolutions for a short TTL (30–60 s). Any admin mutation (issue, update, revoke, status change) becomes visible to the partner service on its next read after that TTL — there is no synchronous call back into hhr-api and no internal endpoint.

A legacy Redis pub/sub channel partner-api-key:invalidated is still emitted by the mutation paths but has no consumer under the shared-DB model. It is inert and slated for removal in a separate cleanup; the cache TTL is the correctness guarantee.

Partner service credential access ​

There is no internal resolution endpoint. ahlaan-api-for-partners (Go) authenticates partner traffic by reading the shared Neon database directly:

  • Look up PartnerApiKey by sha256(rawKey), join Partner.
  • Reject when the key is missing, revoked, expired, or the partner is SUSPENDED / TERMINATED. The Go edge collapses every failure to a single 401 INVALID_API_KEY toward the bank's app; the specific reason stays server-side for support visibility.
  • Results are cached locally for a short TTL (30–60 s), so steady-state traffic does not hit the database per request and hhr-api is never on the request path.

Auth at the partner edge: API key + HMAC-signed webhooks per hhr-bank-integration-spec.md. mTLS is deferred, not removed — there is no internal hhr-api↔Go request hop today, so it is moot; revisit only if bank compliance later mandates it.

lastUsedAt is no longer stamped server-side (the resolve path is gone). If last-use telemetry is needed, the partner service updates it against the shared table.

Audit log ​

Every mutation writes one AuditLog row through the existing recorder. Audit-write failure aborts the request — no silent swallow.

ActionResourceMetadata
partner.createPartner:<id>{ code, name, status }
partner.updatePartner:<id>{ changed: { field: { from, to }, ... } }
partner.api_key.issuePartnerApiKey:<id>{ partnerId, partnerCode, prefix, scopes, rateLimitPerMinute, expiresAt }
partner.api_key.updatePartnerApiKey:<id>{ partnerId, changed: { ... } }
partner.api_key.revokePartnerApiKey:<id>{ partnerId, prefix, reason }

Raw keys are never logged. A unit test asserts that the audit metadata for an issue never contains the raw key string.

GROUP passenger names reaching the carrier ​

A partner books a GROUP order against placeholder travelers and submits the real traveler names later, through its own API. Those names land in the shared booking row; getting them to the carrier is this service's job.

How a name push happens

  1. The partner service writes the names and publishes partner:booking:passengers-updated. The subscriber picks it up, but the order is normally still unpaid at that point, so nothing is sent yet.
  2. When the order settles and the booking flips to CONFIRMED, the settlement path pushes the names immediately — this is the usual moment they travel.
  3. A five-minute sweep (worker host only, ENABLE_CRON=true) catches anything the first two missed: a restarted worker, an upstream blip, a lost race.

Only one of those three ever sends per booking. Each claims Booking.partnerPassengersSyncedAt before calling the carrier, so a booking never receives two modification requests for the same names.

When it did not work

ColumnMeaning
partnerPassengersSyncedAtThe claim, taken before the carrier is called and cleared again if that call fails. Set means a push either succeeded or is in flight; empty means nothing has claimed the booking yet.
partnerPassengersSyncFailedAtSet on a rejection that a retry cannot fix. The sweep skips this booking from then on.
partnerPassengersSyncErrorWhy it was rejected — a passed modification deadline, or the field the stored data is missing.

A booking carrying partnerPassengersSyncFailedAt needs a human: read the error, fix the cause (usually the submitted data), then clear both failure columns so the next sweep retries it.

Tickets are issued before the names arrive, because a GROUP reservation is ticketed against its placeholder travelers by design. A name change on a TICKETED GROUP booking is therefore allowed, subject to the carrier's modification deadline.

Operational notes ​

Onboarding a new partner ​

  1. POST /admin/partners — create the row with the agreed contact details.
  2. POST /admin/partners/:id/api-keys with a UUID Idempotency-Key — capture the raw field and hand it to the partner's app team via your secure channel (1Password / signed email / Bitwarden Send / etc.). Never email the raw key in plaintext.
  3. Confirm the partner has stored the key, then mark the integration as live.

Rotating a key ​

  1. Issue a new key with the same scopes (POST /admin/partners/:id/api-keys).
  2. Hand the new raw key to the partner.
  3. Confirm the partner has switched.
  4. POST /admin/partners/:id/api-keys/:keyId/revoke on the old key with a reason describing the rotation.

Incident response: leaked key ​

  1. Revoke immediately: POST /admin/partners/:id/api-keys/:keyId/revoke with reason mentioning the leak source.
  2. The partner service stops resolving the key on its next shared-DB read; the consumer cache TTL (30–60 s) bounds the exposure window.
  3. Issue a replacement key if the partner still has an active integration.
  4. Verify the revocation in the audit log.

Suspending vs terminating ​

  • SUSPENDED — temporary halt (e.g., payment overdue, compliance review). Keys are not destroyed; resolutions return 404 PARTNER_SUSPENDED. Re-activation restores access without re-issuing keys.
  • TERMINATED — permanent. All active keys are auto-revoked. Re-issuing requires a new contract decision.
