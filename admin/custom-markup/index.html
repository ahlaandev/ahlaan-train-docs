Custom Markup Management Guide ​

This guide explains how administrators configure custom markup rules for the custom-ota / custom-booking product line.

Status: Custom markup is wired into custom-ota / custom-booking pricing for BUSINESS class only (owner 2026-06-15). A BUSINESS-class fare is priced as raw supplier base + custom markup + custom tax, with no strikethrough (originalPrice = 0) and fare type STANDARD. ECONOMY (and any non-business) class is unaffected — it keeps the per-route reducer and the retail strikethrough; custom markup is never applied to it. A markup rule scoped to a non-business class (or to no class) therefore only takes effect on the BUSINESS legs that also match its route scope.

Quick Overview ​

FeatureDescription
PurposeConfigure flat markup rules for custom bookings, independent of the OTA pricing engine
AccessAdmin + Access Role: reads need custom-markup:read, and create/update/delete need custom-markup:update. See Access Roles
ScopeOptional per-route (originId / destinationId / tripClass / tripType) or global default
Markup TypesPercentage (e.g. 15%) or Fixed amount (SAR / IDR)
SelectionMost route-specific active rule wins; ties broken by priority (highest first)

This is separate from the OTA Pricing & Markup engine (PricingRule). Custom markup is a deliberately simpler, flat configuration: no date/time/passenger/volume/target conditions.

How Custom Markup Rules Work ​

┌─────────────────────────────────────────────────────────────────┐
│                 CUSTOM MARKUP RESOLUTION                          │
├─────────────────────────────────────────────────────────────────┤
│  1. Collect all ACTIVE custom markup rules                       │
│                        ↓                                          │
│  2. Keep rules whose route scope matches the request:           │
│     a null scope field is a wildcard (matches anything)         │
│                        ↓                                          │
│  3. Rank survivors:                                              │
│     ├─ most route-specific first (more non-null scope fields)   │
│     └─ then highest priority                                     │
│                        ↓                                          │
│  4. Apply the single top rule (PERCENTAGE or FIXED)             │
└─────────────────────────────────────────────────────────────────┘

A rule with no route scope (all of originId, destinationId, tripClass, tripType omitted) is the global default.

Custom Markup Rule Fields ​

FieldTypeRequiredDescription
namestring✅Display name (max 255 chars, no HTML)
descriptionstring-Detailed description (max 1000 chars)
originIdstring-Route origin location code, e.g. DMX (max 7 chars). This is the Location.code, not a Location UUID (contrast Tariff / Custom Route Price, where originId is a real Location id).
destinationIdstring-Route destination location code, e.g. MKX (max 7 chars). The Location.code, not a Location UUID.
tripClassenum-ECONOMY or BUSINESS
tripTypeenum-ONE_WAY or ROUND_TRIP
markupTypeenum✅PERCENTAGE or FIXED
markupValuenumber✅Percentage (e.g. 15.5) or fixed amount (≥ 0)
currencyenum⚠️SAR or IDR. Required when markupType is FIXED
prioritynumber✅Higher = applied first (0–999999)
isActiveboolean✅Enable/disable this rule

Base URL & Authentication ​

/api/v1

All endpoints require a JWT token with the ADMIN role:

http
Authorization: Bearer <your-admin-jwt-token>

Endpoints ​

1. Create Custom Markup Rule ​

Endpoint: POST /admin/custom-markup/rules

json
{
  "name": "Custom Mecca-Medina Markup",
  "description": "Flat markup for custom bookings on this route",
  "originId": "DMX",
  "destinationId": "MKX",
  "tripClass": "ECONOMY",
  "markupType": "PERCENTAGE",
  "markupValue": 15.5,
  "priority": 100,
  "isActive": true
}

Response: 201 Created — the persisted rule (including generated id, createdBy, timestamps).

2. List Custom Markup Rules ​

Endpoint: GET /admin/custom-markup/rules

Query ParameterTypeDescription
originIdstringFilter by route origin
destinationIdstringFilter by route destination
isActivebooleanFilter by active status
pagenumberPage number (default: 1)
limitnumberItems per page (default: 20)

Response: 200 OK — { data: [...], meta: { total, page, limit, totalPages } }.

3. Get Custom Markup Rule by ID ​

Endpoint: GET /admin/custom-markup/rules/:id — 200 OK or 404 if not found.

4. Update Custom Markup Rule ​

Endpoint: PUT /admin/custom-markup/rules/:id (all fields optional) — 200 OK.

Partial updates respect the FIXED⇒currency rule. markupType and currency may be sent independently. The currency-required-for-FIXED constraint is re-asserted against the effective post-update rule (the persisted value for whichever field is omitted), so clearing currency on a FIXED rule — or flipping a currency-less rule to FIXED without supplying one — is rejected with 400. Resend a valid currency (SAR/IDR) in the same request.

5. Deactivate Custom Markup Rule ​

Endpoint: DELETE /admin/custom-markup/rules/:id — soft delete (isActive: false). Returns { "success": true }.

Common Workflows ​

Global default markup ​

bash
curl -X POST /api/v1/admin/custom-markup/rules \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{
    "name": "Custom Default 10%",
    "markupType": "PERCENTAGE",
    "markupValue": 10,
    "priority": 0,
    "isActive": true
  }'

Route-specific fixed markup (overrides the default) ​

bash
curl -X POST /api/v1/admin/custom-markup/rules \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{
    "name": "DMX→MKX Fixed",
    "originId": "DMX",
    "destinationId": "MKX",
    "markupType": "FIXED",
    "markupValue": 50,
    "currency": "SAR",
    "priority": 100,
    "isActive": true
  }'

A request for DMX → MKX resolves to the route-specific rule (more specific); any other route falls back to the global default.

Cache & Propagation ​

Active rules are cached (custom-markup:rules:active, 15-minute TTL) for fast in-memory resolution. Creating, updating, or deactivating a rule flushes that cache so the change takes effect on the next resolution. This cache is scoped to this module only — it does not touch the OTA search cache, because custom markup is not part of OTA pricing.
