Ticket Channel Management ​

This guide explains how administrators manage ticket channels — the companies that issue physical tickets for custom bookings (e.g. HHR).

Confirming a booking no longer requires a channel. A channel is attached by its own route, PATCH /admin/custom-booking/:id/source, which needs the custom-bookings:write-capital permission. PATCH /admin/custom-booking/:id/status writes the status alone and does not accept a ticketChannelId at all, so a booking can reach CONFIRMED — and the customer can be emailed and invoiced — with no channel and capitalPriceTotalSAR: 0. Attaching one is a separate, later step, and nothing in the backend enforces that it happens.

That status route runs on custom-bookings:update, with one exception: closing a booking (status: COMPLETED) additionally needs custom-bookings:complete, checked inside the handler. A ticket upload no longer closes anything, so the person who files the ticket and the person who certifies it can be held apart. The split now reaches the customer too: an upload emails nobody, and the customer only hears about their ticket once a second admin releases it under custom-bookings:verify-ticket — a code neither custom-bookings:upload-ticket nor custom-bookings:complete confers. See Release or Reject a Ticket.

The admin ticket-upload screen sends that same route as its first leg, which is why a ticketing operator's role needs custom-bookings:write-capital even though the operator never edits pricing. That is a property of the screen, not of the upload: POST /admin/custom-booking/:id/ticket reads no ticket channel and uploads fine against a booking that has none — see Upload Ticket.

Permission-gated (Access Roles). The admin routes above (channels and their route prices) require the ADMIN role plus a fine permission: create, update and delete need ticket-channels:update, and the reads (list, get — on both channels and route prices) accept either ticket-channels:read orticket-channels:update. The editor code is on the reads because the role builder renders this resource action-by-action, so a role ticked as editor alone would otherwise be able to patch rows it could not list. The public list is not gated. See Access Roles.

The two channel reads — GET /admin/ticket-channels and GET /admin/ticket-channels/:id — additionally accept custom-bookings:write-capital, any one code alone being enough. That operator sets a booking's capital source with PATCH /admin/custom-booking/:id/source, which takes a ticketChannelId, and no wildcard reachable from custom-bookings matches a ticket-channels: code — custom-bookings:* stays inside its own resource, and the two cross-resource forms, * and *:read, are not what such a role holds — so the picker that supplies the id used to answer 403. The widening stops at those two routes: the route-price reads refuse the capital code, and every write still needs ticket-channels:update, so the capital code buys the channel list and nothing priced.

Authentication ​

All admin/ticket-channels endpoints require:

  • JWT Token in the Authorization header
  • ADMIN role on the user account
http
Authorization: Bearer <admin-jwt-token>

The public GET /ticket-channels endpoint accepts an optional bearer token but does not require one.

7. Channel Route Prices (capital-price basis) ​

Per-channel capital price rows keyed by (ticketChannelId, originId, destinationId, tripClass, tripType). A single row defines what one adult ticket on this channel actually costs the business for a given route + class + trip type. Read by PATCH /admin/custom-booking/:id/source and POST /admin/custom-booking/:id/recompute-capital to populate CustomBooking.capitalPriceTotalSAR and per-leg pricingSnapshot.outbound.capitalPriceSAR / pricingSnapshot.return.capitalPriceSAR — never by a status transition. See the Custom Booking admin guide for how the snapshot is consumed.

Lookup semantics on the two capital routes:

  • The booking's tripType is passed through as-is (so ROUND_TRIP bookings look up tripType: ROUND_TRIP rows on both legs; ONE_WAY bookings look up tripType: ONE_WAY).

  • tripClass is taken per leg from the booking's outbound/return flight payload.

  • For the return leg of a ROUND_TRIP booking, originId and destinationId are looked up swapped — the row must exist for the reversed direction.

  • Only rows with isActive: true participate in the lookup.

  • Missing rows behave differently on each of the two surfaces, and the split is the whole point — do not read either half as the general rule:

    • On the two admin capital routes (PATCH /admin/custom-booking/:id/source and POST /admin/custom-booking/:id/recompute-capital) a missing or deactivated row is fatal: the call is refused with 400, names the exact lookup tuple, and writes nothing. Add the row here first (with capitalPrice: 0 if the seats are genuinely free), or re-activate the deactivated one, then retry. There is no per-request override.
    • No status transition derives capital at all — PATCH /:id/status writes the status and nothing else. It used to snapshot the basis when a ticketChannelId was supplied on a CONFIRMED transition, recording an unresolvable leg as pricingSnapshot.capitalResolutionGap rather than refusing. That path is gone: the field is no longer accepted and the gap marker is historical only — bookings that went through the old path still carry it and the capital routes still clear it, but nothing writes it any more.

    So a 400 from .../source is a pricing-config gap to close, not an outage — confirming a booking never touches a route price, so it cannot start failing because of one. An admin can still correct any booking by hand with PATCH /admin/custom-booking/:id/capital-price, which is accepted at every status except CANCELLED / EXPIRED / NOT_AVAILABLE.

    ⚠️ For the ticket desk it is an outage — because of the screen, not the upload route. "Not an outage" above is about confirmation only. The admin ticket-upload screen chains PATCH .../source before it sends the file, so a missing or deactivated route-price row for the booking's (channel, origin, destination, tripClass, tripType) blocks that screen entirely, and force: true does not bypass the 400 — forcing only releases the pinned-capital 409. The operator sees a failed ticket upload with no hint that the cause is a pricing table. Add the row here (with capitalPrice: 0 if the seats are genuinely free) or re-activate the deactivated one, then have them retry. A pinned booking (pricingSnapshot.manualOverride: true) blocks the same screen with a 409 instead, which does need force: true.

    POST /admin/custom-booking/:id/ticket itself is reachable throughout: it never resolves a route price and never consults the pin, so the file and its ticketedPaxCount can be recorded while the pricing gap is still open.

Each create/update/delete writes an AuditLog entry under entity = "TicketChannelRoutePrice" with action one of TICKET_CHANNEL_ROUTE_PRICE_CREATE / _UPDATE / _DELETE.

7.1 Create a Route Price ​

http
POST /admin/ticket-channels/:channelId/route-prices
Authorization: Bearer <admin-token>
Content-Type: application/json

Request Body ​

FieldTypeRequiredRules
originIdUUIDYesMust reference an existing Location.
destinationIdUUIDYesMust reference an existing Location.
tripClassenumYesECONOMY or BUSINESS.
tripTypeenumYesONE_WAY or ROUND_TRIP.
capitalPricenumberYesSAR per adult, ≥ 0, max 2 decimals.

The combination (channelId, originId, destinationId, tripClass, tripType) is unique; duplicates return 409 Conflict.

  -d '{
    "originId": "loc-origin-1",
    "destinationId": "loc-dest-1",
    "tripClass": "ECONOMY",
    "tripType": "ONE_WAY",
    "capitalPrice": 300.00
  }'

Response (201) ​

json
{
  "id": "tcrp-1",
  "ticketChannelId": "0190abc1-...",
  "originId": "loc-origin-1",
  "originCode": "MECCA",
  "originName": "Mecca",
  "destinationId": "loc-dest-1",
  "destinationCode": "MEDINA",
  "destinationName": "Medina",

Every route-price response embeds the resolved origin/destination Location — originCode / originName and destinationCode / destinationName — alongside the raw originId / destinationId, so callers can render the route without a second lookup.

Errors ​

  • 404 Not Found — channel or origin/destination location does not exist.
  • 409 Conflict — a row already exists for this combination.

7.5 Delete a Route Price ​

http
DELETE /admin/ticket-channels/:channelId/route-prices/:id

Hard-delete. The row is removed and an audit entry is written.

Response (200) ​

json
{ "deleted": true, "id": "tcrp-1" }

Errors ​

  • 404 Not Found — row does not exist or belongs to a different channel.

Historical bookings are unaffected. capitalPrice is snapshotted onto the booking when its capital source is set — deleting or editing the source row never rewrites past bookings. Two endpoints correct an already-confirmed one: PATCH /admin/custom-booking/:id/capital-price to type a figure by hand (accepted at every status except CANCELLED, EXPIRED and NOT_AVAILABLE — PENDING and UPLOADED_MANIFEST included), or POST /admin/custom-booking/:id/recompute-capital to re-derive it from this table after the row is fixed, which is the only route that reaches a COMPLETED booking.
