Manual Bank Transfer — Admin Operations ​

Admin-only guide for managing the manual bank transfer payment method: destination bank accounts, proof review, approvals, and rejections.

Scope: Manual bank transfer is available only for invoices linked to a Custom Booking (Invoice.customBooking). Regular OTA bookings, wallet top-ups, and ad-hoc invoices are excluded so the OTA ticketing pipeline settles through Xendit without admin intervention. This is enforced both in GET /invoice/:id/available-gateways (gateway hidden) and POST /invoice/:id/generate-payment (returns 400 Bad Request if attempted against a non-custom-booking invoice).

All endpoints require:

  • Authorization: Bearer <jwt> with a user that has the ADMIN role.
  • Base path: /api/v1/admin/manual-transfer/*

Permission-gated (Access Roles). Each route also requires a fine permission: proof and bank-account reads need manual-transfers:read, funds verification and its undo need manual-transfers:verify, proof approve and the payment reopen need manual-transfers:approve, proof reject needs manual-transfers:reject, and destination bank-account writes (create / update / toggle-active / delete) need manual-transfers:manage. See Access Roles.

Approval takes two people. A transfer proof cannot be approved until a finance admin has confirmed the money actually landed in our bank account. See Dual approval below - this is the single most important thing to know before working the proof queue.

Overview ​

The manual transfer feature has two concerns:

  1. Bank Account Management — which beneficiary accounts are shown to customers.
  2. Proof Review — inspecting uploaded receipts and approving or rejecting them.

Approvals go through the same settlement path as Xendit webhooks (PaymentSettlementService.settlePayment). This means a single approval transitions the invoice, booking, confirmation email, WhatsApp, and ticketing job in one atomic flow. You do not need to manually trigger any of these downstream steps.

Dual approval - finance verifies, booking management approves ​

Releasing a booking against a bank transfer takes two different people.

StepWhoPermissionTransitionEndpoint
1. Confirm the money landed in our bank accountFinancemanual-transfers:verifySUBMITTED → FUNDS_VERIFIEDPOST /proofs/:id/verify
2. Approve, settle, ticketBooking managementmanual-transfers:approveFUNDS_VERIFIED → APPROVEDPOST /proofs/:id/approve

Both roles can read the proof. Both can reject it. Neither can complete the flow alone.

Why: finance has bank access and can see whether the transfer actually arrived. Booking management does not. Before this split, one admin who could see a receipt image could release a booking on the strength of that image alone - and a convincing-looking receipt is not money in the account.

What this means day to day ​

  • Approving a SUBMITTED proof returns 409. That is not a bug. It means finance has not confirmed the funds yet. Chase finance; do not retry.
  • The gate is enforced in the backend, in the compare-and-swap on the proof row. A disabled button in the admin UI is presentation only, and a direct API call fails the same way.
  • Rejection works from either state. A FUNDS_VERIFIED proof can still be rejected - see Reject.
  • Made a mistake? Un-verify. POST /proofs/:id/unverify walks the proof back to SUBMITTED without costing the customer a retry. See Un-verify.

If one person holds both permissions ​

A role carrying manual-transfers:* (or the * superadmin wildcard) matches both codes, so that admin clicks Verify and then Approve themselves. This is known and accepted: for a wildcard holder the control is a deliberate two-step speed-bump, not segregation of duties. There is no distinct-actor check.

If you want the control to actually hold, audit which roles carry manual-transfers:* and *, and grant the two codes to two separate roles.

Verify ​

bash
POST /api/v1/admin/manual-transfer/proofs/:id/verify
json
{
  "adminNotes": "Matched on the Mandiri statement, 2026-07-31 09:14 WIB"
}

adminNotes is optional. Records fundsVerifiedAt and fundsVerifiedByAdminId on the proof, and nothing else: no payment, invoice, or booking is touched, and no money moves. Both fields surface on the admin review block so a later reader can see who confirmed the funds.

Returns 409 when the proof is not SUBMITTED - already verified, rejected, or approved.

Your note is safe from the next admin. adminNotes is a single column with two writers now, so omitting it never clears it - see what happens to your note. Write the bank-statement line you matched against; the approval that follows will not erase it.

Before you click Verify: open the bank statement, not just the receipt image. This step exists precisely because a receipt file is not proof of receipt. Cross-check amount, sender name, destination account, and timestamp per the operational guidance below.

Un-verify ​

bash
POST /api/v1/admin/manual-transfer/proofs/:id/unverify
json
{
  "adminNotes": "Wrong invoice - that transfer belongs to INV-202607-0031"
}

Same manual-transfers:verify permission: finance undoes its own mistake. Returns the proof to SUBMITTED and clears fundsVerifiedAt / fundsVerifiedByAdminId, so the record never claims a verification that has been withdrawn.

  • Does not consume a retry. retryCount is untouched, and so are the payment and the invoice - the customer did nothing wrong.
  • Returns 409 once the proof is APPROVED. Settlement has already run by then and the money has moved; use the refund flow instead.

What happens to your note ​

adminNotes is one column shared by every review action - verify, un-verify, approve, reject and reopen all write it. Dual approval put a second person on it: finance records the bank-statement line, then booking management approves, normally with an empty body because adminNotes is optional there.

Omitting adminNotes preserves whatever is already on the row. It does not clear it. So the normal two-step flow keeps the finance note intact through the approval that releases the money:

You sendResult
no adminNotes fieldexisting note kept as-is
"adminNotes": "something"replaces the existing note
"adminNotes": ""clears the note

Two consequences worth knowing:

  • An explicit note overwrites the previous one. There is no append and no history on this column. If finance wrote the statement line and you send your own note on approve, finance's line is gone. Quote it back if you need both, or put your remark somewhere with a real timeline - the WebhookLog written by every approval, or the rejection's customer-visible reason.
  • rejectionReason is a separate column and is always written on reject. Rejecting never costs you the note, and the note is never shown to the customer.

Runbook for finance until the admin panel ships a Verify button ​

The admin UI has no Verify control yet. Until it does, finance performs step 1 from Swagger (/api/docs, tag 5. Admin - Manual Transfer Proofs) or curl. Copy the calls below rather than improvising - this step releases money.

1. Find the proofs waiting on you.

bash
curl -s -H "Authorization: Bearer $ADMIN_JWT" \
  "https://<host>/api/v1/admin/manual-transfer/proofs?status=SUBMITTED&pageSize=50"

Each row carries payment.invoice.invoiceNumber, the uniqueAmount to match, and senderAccountName.

2. Open the receipt and check it against the bank statement.

bash
curl -s -H "Authorization: Bearer $ADMIN_JWT" \
  "https://<host>/api/v1/admin/manual-transfer/proofs/<proofId>"

Use signedDownloadUrl to view the uploaded receipt. The receipt is not the evidence - the bank statement is. Match amount, sender name, destination account, and timestamp.

3. Confirm the funds.

bash
curl -s -X POST -H "Authorization: Bearer $ADMIN_JWT" \
  -H "Content-Type: application/json" \
  -d '{"adminNotes":"Matched on the Mandiri statement, 2026-07-31 09:14 WIB"}' \
  "https://<host>/api/v1/admin/manual-transfer/proofs/<proofId>/verify"

Booking management takes it from there.

4. Verified the wrong one? Un-verify immediately - it costs the customer nothing:

bash
curl -s -X POST -H "Authorization: Bearer $ADMIN_JWT" \
  -H "Content-Type: application/json" \
  -d '{"adminNotes":"Wrong invoice - that transfer belongs to INV-202607-0031"}' \
  "https://<host>/api/v1/admin/manual-transfer/proofs/<proofId>/unverify"

Every verification is attributed (fundsVerifiedByAdminId) and reversible until approval, which is what makes a hand-driven interim acceptable.

Other ways to settle are gated too ​

Two admin endpoints used to reach a settled manual-transfer invoice without any finance check. Both now refuse while the finance step is outstanding:

EndpointBehaviour
POST /admin/payment/:id/manual-confirm400 when the payment carries a manual-transfer proof that is not yet FUNDS_VERIFIED / APPROVED. Payments on every other rail are unaffected and this stays their stuck-payment rescue path.
PUT /admin/invoice/:id/mark-paid and PUT /admin/invoice/:id with {"status":"PAID"}400 while the invoice has a live manual-transfer attempt (a PENDING payment) whose proof is not yet FUNDS_VERIFIED / APPROVED. The PENDING half of that predicate is what keeps the gate off attempts that are genuinely dead - but read the stuck-attempt case below before assuming an abandoned attempt clears itself. On current production settings it does not. On an invoice with more than one attempt, do not follow the proof id in the message.

Do not blindly follow the proof id in the 400 ​

Both messages embed a POST /proofs/<id>/verify URL. On an invoice with one attempt that pointer is exactly right. On an invoice with several, the two gates answer about different rows, and the invoice one can name a proof you cannot act on:

  • manual-confirm is payment-scoped. It names the proof belonging to the payment you called it on. Always the right one.
  • The invoice gates are invoice-scoped. They block on any live attempt and report the first one found, which may be a different attempt than the one you are looking at.

A custom-booking invoice collects extra attempts easily - switching gateway mints a new payment row and never expires the old one - so this is ordinary, not exotic. Observed on preprod: mark-paid reported an AWAITING_UPLOAD proof while manual-confirm on the same invoice reported the SUBMITTED one.

The trap: verify on an AWAITING_UPLOAD proof returns 409, because verify accepts SUBMITTED only. Follow the URL from an invoice-gate 400 and you can land on a proof with no receipt on it and read the 409 as a bug.

What to do instead. Treat the invoice-gate 400 as "this invoice has at least one unfinished attempt", not as an instruction. List the attempts and decide from the full picture:

bash
curl -s -H "Authorization: Bearer $ADMIN_JWT" \
  "https://<host>/api/v1/invoice/<invoiceId>/payments" | jq '.[] | {id, status, proofStatus}'

An attempt whose proofStatus is SUBMITTED is the one finance can verify. If every live attempt is AWAITING_UPLOAD, nothing is verifiable yet and you are in the stuck-attempt case below - the escape route there, not a retry, is what clears it.

When the money arrived but no receipt was ever uploaded ​

Read this before working a support ticket about a bank transfer that will not settle.

A customer can pick manual transfer, actually send the money, and never upload the receipt. The payment then sits PENDING and its proof sits AWAITING_UPLOAD, and in that combination every settlement route refuses:

CallResultWhy
POST /admin/payment/:id/manual-confirm400proof is not FUNDS_VERIFIED / APPROVED
PUT /admin/invoice/:id/mark-paid400live attempt, proof not verified
PUT /admin/invoice/:id with {"status":"PAID"}400same gate
POST /proofs/:id/verify409verify accepts SUBMITTED only
POST /proofs/:id/approve409approve accepts FUNDS_VERIFIED only
POST /proofs/:id/reject409reject accepts SUBMITTED / FUNDS_VERIFIED only

The attempt does not expire its way out of this on current settings. The only thing that moves a custom-booking manual-transfer payment off PENDING is the payment-expiration job, and CUSTOM_BOOKING_PAYMENT_EXPIRY_JOB_ENABLED is false by default in .env.example and in every docker-compose*.yml. While that kill switch is off the payment stays PENDING indefinitely, and so does the block. The same applies to a stale attempt the customer walked away from on an invoice they later paid another way.

This is accepted and deliberate. The alternative is letting one admin declare "the money landed" on an invoice where nothing was ever uploaded, which is the exact hole dual approval exists to close. The escape below keeps both signatures.

Escape route - reopen, upload on the customer's behalf, then verify and approve ​

  1. Reopen the payment so the upload window is open again. A lapsed expiresAt makes the upload fail with 409 on its own.

    bash
    curl -s -X POST -H "Authorization: Bearer $ADMIN_JWT" \
  -H "Content-Type: application/json" \
  -d '{"addMinutes":120,"reason":"Funds received; customer never uploaded a receipt"}' \
  "https://<host>/api/v1/admin/manual-transfer/payments/<paymentId>/reopen"

  2. Upload the receipt as the customer, via act as customer, using POST /api/v1/manual-transfer/proof. If the customer has no receipt of their own, upload the bank-statement extract showing the incoming transfer. The proof moves to SUBMITTED and the row records uploadedByAdminId, so the audit trail shows an admin supplied the file rather than the customer.

  3. Finance verifies against the bank statement (POST /proofs/:id/verify) and booking management approves (POST /proofs/:id/approve), exactly as for any other transfer. Two signatures, unchanged.

Do not reach for office-settlement here. It is a different rail (IN_PERSON / CASH) and would record the money as an office cash payment, which it was not.

One door is deliberately left open. POST /admin/invoice/:id/office-settlement still drives an invoice to PAID on the IN_PERSON rail with no finance verification, and it sits on invoices:update. Two things narrow it: it is inert unless OFFICE_SETTLEMENT_ENABLED is on, and it writes a visibly different payment (IN_PERSON / CASH, with its own receipt), so the workaround is legible in the audit trail rather than indistinguishable from a normal approval. Mitigation is organisational: keep invoices:update off the booking-management role if you want the control to hold.

SAR has two rails (MITRA-10) ​

A SAR custom-booking invoice can be settled two ways. USD is unchanged (manual transfer only); IDR is unchanged (Xendit).

RailActorHow
Manual transfer (unchanged)Customer uploads a transfer proof → admin approvesThe proof-review flow documented below.
In-person office settlement (NEW)Admin records a SAR payment settled in person at the Ahlaan officePOST /api/v1/admin/invoice/:id/office-settlement (see below).

Both rails produce the same durable outcome — invoice PAID via the SAR anchor, booking advanced to WAITING_FOR_TICKET, ticketing + confirmation notifications fired — because both run through the shared settlePayment routine.

POST /api/v1/admin/invoice/:id/office-settlement ​

Admin-only. Records an in-person SAR office settlement against a custom-booking invoice. Accepts multipart/form-data so an optional receipt file can be attached.

The endpoint resolves the payment to settle in three modes (precedence order — explicit id, then auto-reuse, then mint):

ModeWhen to useBehaviour
Settle existing (paymentId supplied)The admin has the exact payment id in hand (e.g. from the customer rail).Settles that payment in place. It must belong to this invoice, be on the IN_PERSON gateway, and still be PENDING. amountSAR is ignored — the SAR anchor is recorded.
Auto-reuse (paymentId omitted, an open row exists)The normal counter flow. The admin settles from the invoice screen with no payment id, and the customer already started an in-person payment on the in-person rail.Looks up the customer's own open PENDING IN_PERSON row (newest first) and settles that — no twin is minted. amountSAR is ignored; the SAR anchor is recorded.
Mint and settle (paymentId omitted, no open row)A genuine walk-in the customer never started online.Creates a fresh IN_PERSON / CASH Payment and settles it immediately. Unchanged original behaviour.

Auto-reuse fixes the old stranded-PENDING caveat. No admin read surface emits the customer's payment id, so the admin settling from the invoice screen never has one. The empty-body path used to always mint a second attempt, leaving the customer's original row PENDING forever — their instruction page kept telling them to pay an already-settled invoice. Now the empty body reuses that open row instead, so the customer's own payment is the one that settles. Rows stranded before this change are cleaned up by POST .../invoice/reconcile-orphan-in-person.

jsonc
// multipart/form-data — all parts optional
{
  "paymentId": "019f776e-221a-75cc-b67a-cb2928f60c89", // settle the customer's existing payment
  "amountSAR": 5000,          // defaults to the full SAR anchor (Invoice.baseTotalAmountSAR); ignored when paymentId is set
  "receiptRef": "RCP-2026-0142",
  "notes": "Settled at Jeddah office counter",
  "file": "<binary>"          // optional receipt: JPG/PNG/WebP/PDF, ≤ 5 MB
}

A second call against an already-settled invoice is rejected:

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Invoice is already settled.",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}
  • Gated by OFFICE_SETTLEMENT_ENABLED (off by default) — returns 400 with "Office settlement is currently disabled." when disabled (verified live on preprod; the flag check runs before the invoice is loaded). See System Config.
  • 400 if the invoice is already settled, is not a custom-booking invoice, or the IN_PERSON gateway row is missing/inactive.
  • The settlement is a single full settlement: the invoice is marked fully PAID regardless of the numeric amountSAR (the SAR anchor is authoritative). Partial/installment office settlements are out of scope.
  • Optional proof file — a receipt image or PDF (image/jpeg, image/png, image/webp, application/pdf; ≤ 5 MB, the same allowlist as customer proofs). Stored privately in R2; pointers persisted on the Payment (proofFileId / proofFileMimeType / proofFileSizeBytes). Upload happens before settlement, so a storage failure returns 400 "Failed to store settlement proof." and leaves no settled orphan; an invalid/oversized/wrong-type file is rejected up front before any Payment row is created. Admins retrieve it as a signed URL via the officeSettlementProof block on GET /api/v1/admin/invoice/:id (see the Invoice admin guide).
  • Records an AuditLog (action='OFFICE_SETTLEMENT', entity='Invoice', newValue.proofFileId when a file was attached) capturing the settling admin, amount, and receiptRef, alongside the settlement WebhookLog (OfficeSettlement / payment.office_settlement).

Custom-booking payment expiry (new) ​

Custom bookings now have a write-side payment expiry:

RailBeforeNow
XenditExpired, but only via its own payment.expired webhook. A lost callback stranded the booking forever.Unchanged in the happy path. A delayed safety-net job fires at expiresAt + grace (default 10 min) if the webhook never arrives, and logs a warning so a lost callback is finally visible.
Manual transferNever expired in the database. mapProofStatus derived "expired" at read time only, so the API said expired while the row stayed WAITING_FOR_PAYMENT forever.Expires at 30 minutes: payment EXPIRED, booking EXPIRED, invoice ISSUED -> OVERDUE.
In-person officen/a (new rail)Expires at 60 minutes, same three writes.

Off by default. Gated on CUSTOM_BOOKING_PAYMENT_EXPIRY_JOB_ENABLED (default false); only the literal string true enables it. It ships dark because manual transfer is already live: switching it on means bookings that used to sit in WAITING_FOR_PAYMENT indefinitely will start moving to EXPIRED. Turn it on deliberately and watch.

The invoice is marked OVERDUE, not a new EXPIRED status. OVERDUE already existed with correct readers (it counts in the pending bucket) and, critically, is not a settled status, so a reopened payment can still be paid without any extra unblocking step.

Recovering an expired booking is the existing two-step counter flow:

bash
POST /api/v1/admin/manual-transfer/payments/:paymentId/reopen
POST /api/v1/admin/invoice/:id/office-settlement   { "paymentId": "..." }

Reopen reverses all three writes: payment back to PENDING with a fresh window, booking EXPIRED -> WAITING_FOR_PAYMENT, invoice OVERDUE -> ISSUED.

What is deliberately NOT expired ​

  • A payment whose proof is under review. Once a receipt is uploaded the payment is waiting on us, not on the customer, so the expiry job defers instead of expiring it while the proof is SUBMITTED or FUNDS_VERIFIED. It re-checks every 30 minutes (CUSTOM_BOOKING_PAYMENT_EXPIRY_REVIEW_RECHECK_MINUTES) and expires the payment normally as soon as the proof leaves review - a rejection, for instance. This matters more under dual approval, which makes the review window materially longer.

    It re-checks rather than simply skipping because the expiry job is one-shot: nothing but payment creation and admin reopen ever schedules it, and reject does not. A bare skip would leave the payment PENDING with a lapsed window, no expiry left anywhere in the system, and an invoice that never reaches OVERDUE.

    This does not make such a payment immortal. Rejection returns the proof to REJECTED and the very next re-check expires it, and expiresAt still governs whether the customer may upload.

  • A booking whose proof is under review. Only WAITING_FOR_PAYMENT is expired, never WAITING_PAYMENT_REVIEW. A submitted proof sitting in the admin queue is us being slow, not the customer failing to pay - and since EXPIRED is terminal and settlement only advances a booking that is still awaiting payment or review, expiring it would have produced a PAID invoice against a permanently dead booking. This guard predates the deferral above and is independent of it: the booking has always been protected, the deferral protects the Payment row.

  • A booking whose invoice still has another open payment. A customer who generated a Xendit link and then switched to the office rail has two payments with different windows. The shorter one lapsing must not kill a booking the customer is still on their way to pay for.

Paying an expired booking ​

Once a booking is EXPIRED, payment and settlement are refused. That is deliberate: without the guard a customer could pay a second time, the proof would look normal in the admin queue, approval would mark the invoice PAID, and the booking would stay EXPIRED forever with the money already taken.

Reopen is the route back. It reverses booking EXPIRED -> WAITING_FOR_PAYMENT and invoice OVERDUE -> ISSUED, and it does so whatever state the payment itself is in.

Known gap. A custom booking that expired on a XENDIT-only invoice has no reopen path today, because reopen deliberately refuses XENDIT (reopening it would extend our window while Xendit's own invoice stays dead). Such a booking is blocked rather than payable - the safer failure, but it needs a rail-independent admin "reopen booking" action to resolve properly.

Known accepted race (Xendit only) ​

If a Xendit paid webhook lands after expiresAt + grace, the job has already expired the booking and marked the invoice OVERDUE. The late webhook still settles, because settlement's compare-and-set is status: { not: PAID } and OVERDUE is deliberately not a settled status. Net result: a PAID invoice against an EXPIRED booking.

This is a state mismatch, not money loss: the payment is captured and the invoice is correct; only the booking status disagrees. The admin reopen flow is the repair. If the safety-net warning starts firing on healthy webhooks, the grace is tuned too tight - raise CUSTOM_BOOKING_EXPIRY_SAFETY_GRACE_MINUTES (config, no code change).

IDR is a payable manual-transfer currency ​

A custom-booking invoice can now be settled by an IDR bank transfer, reviewed through the same proof queue as SAR and USD. Xendit is unchanged and remains the instant IDR option; this is the offline one.

Three things about it differ from the foreign rails, all for one underlying reason — an IDR payment is the same currency as the invoice, so settlement sums it onto totalPaid instead of anchoring off SAR:

  • It is billed the full invoice total, never a remainder. So it is refused with 400 on any invoice that has already received something, and GET /invoice/:id/payment-options withholds the IDR option in that state. Without that guard, settling it would drive totalPaid past totalAmount and land on PAID — and because the duplicate check reads the balance before the new amount is added, nothing would be flagged: no OVERPAID status, no DUPLICATE_PAYMENT audit row, no duplicate-payment email. The customer would simply be out the extra money and it would reach you as a support ticket rather than an alert. Send a customer with a partial payment to Xendit for the balance.
  • Repeated presses no longer mint duplicates. An open, unexpired manual-transfer payment in the same currency, still quoting the same amount, is handed back instead of a second one being created — so one intended transfer produces one proof in your queue rather than one per button press. Switching currency, an expired window, or a booking re-priced mid-window each mint a fresh instruction instead. Applies to SAR and USD too; only the double-count risk was IDR-specific.
  • The reconciliation suffix stays off (see Configuration). Two customers transferring the identical rupiah amount in the same window are separated by the uploaded proof and the payer's account name, exactly as for SAR/USD today. Do not enable the suffix to fix this: settlement credits payment.amount while the customer is told to transfer uniqueAmount, so the bank would receive up to Rp 999 per transfer that the system never records.

Settlement, measured ​

An IDR transfer sums onto totalPaid rather than anchoring off SAR — but it still writes the SAR anchor. Full preprod run on INV-202608-0009-93P (5 adults, SAR 800 / IDR 3,816,000):

Read surfaces disagree once anything is paid. payment-options withholds the IDR entry as soon as totalPaid > 0 and reports manualTransfer.enabled: false on a settled invoice; available-gateways does neither and keeps advertising MANUAL_TRANSFER with a destination account at remainingAmount: 0. No money can move through it — generate-payment still answers 400 "Invoice is already fully paid." — so this is a stale option in the customer's UI, not a settlement risk. Tracked as #532.

Bank Account Management ​

One selected destination per currency ​

Each manual-transfer currency has exactly one destination bank account, and an admin chooses it. That account carries isSelected: true, and a database unique index allows only one selected account per currency — so customer money can never split between two accounts of the same currency.

This replaces the old rule, where the destination was whichever active account of that currency had the highest priority. That rule left the invariant undeclared in the data: a mis-set priority, or a priority tie broken by createdAt, silently rerouted customer money to a different bank account with no error anywhere. priority still exists and still orders this admin list — it no longer decides where any money goes.

Two consequences to know before you touch an account:

  • A newly created account is unselected, so creating the first account for a currency does not switch that currency on. Create, then select. Two steps, deliberately.

  • Deactivating the selected account does not clear the mark. The currency goes dead until someone selects deliberately, and generate-payment answers "No destination bank account is selected for USD. Ask an admin to select one." That is the intended outcome: falling back to some other account is exactly the silent reroute this design exists to prevent, and the mark left in place is also the record of what the destination used to be.

    Verified end-to-end on preprod. Toggling the selected USD account inactive left the row at {"isActive": false, "isSelected": true}; USD disappeared from payment-options.manualTransfer.currencyOptions (leaving only SAR and IDR); and generate-payment with currency: "USD" returned the 400 above rather than rerouting to any other account. Toggling it back restored {"isActive": true, "isSelected": true} with no re-selection needed.

Clears the previous selection for that currency and sets this one, inside a single transaction, so the currency is never left with no destination halfway through.

Create ​

bash
POST /api/v1/admin/manual-transfer/bank-accounts
json
{
  "bankCode": "BCA",
  "bankName": "Bank Central Asia",
  "accountNumber": "1234567890",
  "accountName": "PT Haramain",
  "currency": "IDR",
  "priority": 100,
  "notes": "Primary account"
}

  • The account is created unselected and no customer can reach it yet. Follow with POST :id/select. An admin who creates an account, sees nothing change on the customer side, and assumes a bug is missing this second step.

  • priority is display order for the admin list only. It does not choose the destination — see One selected destination per currency.

  • isActive defaults to true.

  • currency is the routing key. Manual transfer supports SAR, USD and IDR for custom bookings, and each currency routes to its own selected account. To enable a currency, create one account for it and then select it:

    • SAR → Bank Mandiri ({"bankCode":"MANDIRI","currency":"SAR", ...}) → POST :id/select
    • USD → Bank CIMB Niaga ({"bankCode":"CIMB","currency":"USD", ...}) → POST :id/select
    • IDR → Bank Mandiri ({"bankCode":"MANDIRI","currency":"IDR", ...}) → POST :id/select

    The customer is told to transfer that currency's amount to the matching account. GET /invoice/:id/payment-options surfaces exactly the currencies that have a selected account — a currency with none is hidden from the FE note, and IDR is additionally hidden once the invoice has received a payment (see IDR is a payable manual-transfer currency). (bankCode must already exist in /admin/banks.)

  • Reconciliation suffix: the unique 3-digit suffix would apply to IDR only (whole-rupiah), but it is disabled and must stay disabled — see IDR is a payable manual-transfer currency. In practice every proof on every currency is stored with amountSuffix=0, so admins match the receipt by amount + sender directly.

List / Get / Update / Toggle / Select / Delete ​

Verb + PathPurpose

Business rules:

  • MANUAL_TRANSFER is automatically hidden from customers when a currency has no selected account, or when that account is inactive or deleted. Toggle the selected account off and the rail disappears end-to-end for that currency — useful for a short maintenance window, and reversible by toggling it back on with no re-selection needed.

  • Changing an account's currency clears its selection. The row would otherwise move into the target currency's slot and collide with that currency's own selected account. Re-select afterwards.

  • Deleting the selected account returns 409 when its currency has another active account — select that one first, then delete. The message names the account to select, so it is directly actionable (live preprod response):

    json
    {
  "message": "This account is the selected destination for IDR. Select another IDR account first (POST /admin/manual-transfer/bank-accounts/019dae1c-3871-77a9-be5f-548dee427a49/select), then delete this one.",
  "error": "Conflict",
  "statusCode": 409
}

    When the selected account is the only one of its currency, the delete goes through and the currency is left unarmed. The asymmetry is deliberate: one account per currency is now the normal shape, so a flat refusal would make the last account of every currency permanently undeletable, with no escape, since toggle-active does not clear the mark either.

  • MANUAL_TRANSFER is also hidden for any invoice not linked to a Custom Booking, regardless of bank-account configuration. Regular OTA booking invoices, wallet top-ups, and ad-hoc invoices will never surface the gateway — customers on those flows must pay via Xendit.

Who submitted this proof? ​

uploadedByAdminId sits next to reviewerId and answers a question the proof row could not previously answer: was this uploaded by the customer, or by an admin acting as the customer?

ValueMeaning
nullA genuine self-serve upload — the customer or a guest submitted it themselves. Also null on rows created before the column existed.
an admin user idThat admin submitted the proof while impersonating the customer ("act as customer").

Read with reviewerId, this makes a cross-admin handoff legible on one screen: submitted by admin X acting as the customer, reviewed by admin Y. Previously the two were indistinguishable and recovering the truth meant correlating an IMPERSONATION_START audit row against proof timestamps.

The value is rewritten on every upload, including a re-upload after a rejection, so it always describes the proof currently on the row rather than an earlier attempt.

The stored receipt file stays owned by the customer either way. Proof files are PRIVATE and private-file access is owner-only, so reassigning ownership to the acting admin would lock the customer out of their own receipt while giving admins nothing — an admin already reads any file. Attribution lives in this column and the audit row, not in file ownership.

Approve ​

bash
POST /api/v1/admin/manual-transfer/proofs/:id/approve
json
{
  "adminNotes": "Amount matches; transfer dated 2026-04-20",
  "paidAt": "2026-04-20T13:05:00.000Z"
}

Both fields optional. paidAt defaults to "now" if omitted. Omitting adminNotes keeps the note finance left; sending one replaces it - see what happens to your note before you overwrite the bank-statement line somebody relied on.

Requires FUNDS_VERIFIED. Approving a proof that is still SUBMITTED returns 409 with a message naming the finance step. A finance admin must run Verify first. See Dual approval.

What happens on success:

  1. Proof → APPROVED, reviewedAt + reviewerId populated. These are the decision fields and stay distinct from fundsVerifiedAt / fundsVerifiedByAdminId, which record the finance step - so the review screen can show "funds confirmed by admin X, approved by admin Y".
  2. PaymentSettlementService.settlePayment runs with trigger: 'MANUAL_TRANSFER_APPROVAL', which:
    • Marks Payment.status = PAID.
    • Recomputes Invoice.status (PAID / PARTIALLY_PAID / OVERPAID) — transitioning out of WAITING_PAYMENT_REVIEW. For a cross-currency payment (SAR/USD payment on an IDR invoice) the invoice is marked PAID via the SAR anchor (totalPaidSAR = baseTotalAmountSAR), and the invoice-currency totalPaid is derived from that anchor: totalPaid = totalAmount × (totalPaidSAR / baseTotalAmountSAR), which equals totalAmount on a full pay and is capped there. The foreign amount is never summed onto the invoice-currency column — the actual SAR/USD figure received stays on the Payment row. Duplicate detection is status-aware: approving a second foreign-currency proof on an already-settled invoice records it as OVERPAID (and queues the duplicate-payment notice) without re-advancing the booking or mixing currencies.
    • Why derived, not converted. totalPaid comes from the SAR anchor rather than SAR × sellRate because a GOLD booking is priced at the reduced rate — converting at the base sell rate would overstate the total and flip the invoice to a false OVERPAID.
    • Cross-currency is detected structurally, from the data. A payment is cross-currency when its currency differs from the invoice currency (payment.currency !== invoice.currency, case-insensitive) — not via a payment-gateway allowlist, and not by which admin endpoint ran settlement. Foreign rails (MANUAL_TRANSFER SAR/USD proof, IN_PERSON SAR office settlement) are the usual source, but keying off the gateway previously let a foreign amount slip onto the invoice-currency total whenever the gateway relation was absent or mislabeled. So the generic POST /admin/payment/:id/manual-confirm stuck-payment fix (trigger MANUAL_ADMIN) and the in-person office settlement (trigger OFFICE_SETTLEMENT) settle a foreign amount identically to this proofs/approve path. When the payment currency is unknown it falls back to the invoice currency and is treated as same-currency (the safe default: sum, do not strand).
    • Transitions any linked CustomBooking.status from WAITING_FOR_PAYMENT or WAITING_PAYMENT_REVIEW → WAITING_FOR_TICKET (skip-PAID; guarded by updateMany scoped to those two states, so bookings already advanced are left untouched).
    • Transitions Booking.status to CONFIRMED and inserts BookingStatusHistory.
    • Queues booking confirmation email + WhatsApp (if the booking has otaTimeLimits.updateTravellersTimeLimit).
    • Cancels any pending booking-expiration jobs.
    • Queues OTA ticketing unless the payment is a duplicate.
    • Writes a WebhookLog entry with webhookType='ManualTransferApproval' so the audit trail matches the Xendit path.

Ordering and failure handling. Approval flips the proof FUNDS_VERIFIED → APPROVED through a guarded updateMany first, and only then settles: a concurrent second approval loses that compare-and-swap, gets 409, and never reaches settlement.

If settlement fails, the approval call rethrows and the proof is rolled back to FUNDS_VERIFIED - not to SUBMITTED, and the finance stamp is left intact. The money did arrive and finance already confirmed it, so a transient settlement error must not send the proof back for a re-check it never needed. The admin can retry the approval once the underlying cause is resolved.

Reject ​

bash
POST /api/v1/admin/manual-transfer/proofs/:id/reject
json
{
  "reason": "Amount transferred does not match the unique total (expected 1,250,037 IDR; received 1,250,000 IDR)"
}

reason is required.

Accepts either review state - SUBMITTED or FUNDS_VERIFIED. Rejecting a proof whose funds finance already confirmed is a real case, not an edge case: the money arrived, and then booking management sees the booking itself is wrong (wrong flight, duplicate, wrong passenger). Funds having landed must not force an approval. Refund the customer through the refund flow after rejecting. A proof in any other status (APPROVED, REJECTED, AWAITING_UPLOAD) returns 409.

What happens:

  1. retryCount is incremented atomically.
  2. Proof → REJECTED, rejectionReason populated.
  3. If retryCount > maxRetryCount (default 3 re-uploads allowed after the initial submission — i.e. the 4th rejection), Payment.status = FAILED; otherwise payment stays PENDING and the customer may re-upload.
  4. Invoice.status is reverted from WAITING_PAYMENT_REVIEW → ISSUED and any linked CustomBooking.status is reverted from WAITING_PAYMENT_REVIEW → WAITING_FOR_PAYMENT (guarded by updateMany so a concurrently-settled invoice is not clobbered). This happens for both non-final and final rejections, so admins see a clean "payment failed, awaiting customer action" state either way.
  5. A rejection email is queued to the invoice user (or guest email).

Authoring rejection reasons: Be specific. The FE surfaces this text verbatim in a banner, so "amount mismatch — transfer IDR 1,250,037 exactly" is far more actionable than "wrong amount".

reason and adminNotes are different columns. reason is customer-visible and always written. adminNotes is internal, optional, and preserved when omitted — rejecting a FUNDS_VERIFIED proof does not wipe the note finance left. See what happens to your note.

Reopen for re-upload ​

bash
POST /api/v1/admin/manual-transfer/payments/:paymentId/reopen
json
{
  "addMinutes": 120,
  "resetRetries": false,
  "reason": "Customer transferred late; granting 2h to upload proof."
}

Note the path is keyed on paymentId (a payment-level operation), not the proof id used by approve/reject.

Re-enables proof upload for a payment that the customer-facing guard would otherwise block. That guard rejects an upload when the payment is not PENDING, when expiresAt is in the past, or when the re-upload budget is exhausted (retryCount > maxRetryCount). Reopen clears these so the admin can grant another attempt without the customer starting a new payment.

FieldRequiredEffect
addMinutesyes1–43200 (30 days). Sets expiresAt = now + addMinutes and flips the payment back to PENDING. The cap is an anti-typo guard, not a policy limit.
resetRetriesno (default false)Returns the proof to REJECTED (re-uploadable) and zeroes retryCount. Required to reopen a FAILED payment — without it the retry guard would immediately re-block the upload, so the request is rejected with 400.
reasonnoAudit note (≤500 chars), stored on ManualTransferProof.adminNotes and logged.

What happens:

  1. Loads the payment's manual-transfer proof. Missing → 404.
  2. PAID / REFUNDED → 409 (terminal; cannot reopen).
  3. FAILED without resetRetries → 400.
  4. A guarded payment.updateMany (CAS on status IN (PENDING, EXPIRED, FAILED)) sets status = PENDING, expiresAt = now + addMinutes. If it matches nothing (the payment transitioned concurrently, e.g. settled to PAID) → 409.
  5. The proof's adminNotes is stamped with reason; with resetRetries, the proof also goes REJECTED and retryCount → 0.
  6. EXPIRED only: the linked CustomBooking.status is reversed EXPIRED → WAITING_FOR_PAYMENT (guarded updateMany). A FAILED reopen needs no booking reversal — rejectProof already left the booking in WAITING_FOR_PAYMENT.

No customer notification. Reopen sends no email or WhatsApp. Admins coordinate the reopened window with the customer directly.

State Machine ​

          user uploads          finance verifies         booking mgmt approves
  AWAITING_UPLOAD ────────► SUBMITTED ──────────────► FUNDS_VERIFIED ────────► APPROVED ──► settlement
         ▲                      │   ▲                       │
         │                      │   └───── unverify ────────┘
         │                      │                           │
         │          admin rejects│                          │ admin rejects
         │                      ▼                           ▼
         │                   REJECTED  ──► if retryCount ≤ max: customer re-uploads → SUBMITTED
         │                              └► if retryCount > max: Payment.status = FAILED
         │
         └─── (a fresh payment creates a new proof row)

  Both review states (SUBMITTED, FUNDS_VERIFIED) are rejectable. Only
  FUNDS_VERIFIED is approvable. A re-upload after a rejection clears any earlier
  finance verification, because it replaces the receipt file that was verified.

  Settlement failure rolls the proof back to FUNDS_VERIFIED, never to SUBMITTED.

  Admin reopen (POST .../payments/:paymentId/reopen) re-enables upload out-of-band:
    Payment PENDING/EXPIRED/FAILED ──► PENDING (expiresAt = now + addMinutes)
      EXPIRED  also reverses CustomBooking EXPIRED → WAITING_FOR_PAYMENT
      FAILED   requires resetRetries → proof REJECTED, retryCount 0

Operational Guidance ​

  • Verify the amount first. Cross-reference the uniqueAmount on the instruction payload with the amount shown on the receipt.
  • Reconciliation handle depends on the unique-suffix toggle. The runtime MANUAL_TRANSFER_ENABLE_UNIQUE_SUFFIX flag is managed through the admin system-config API (see "Runtime toggle" below). When enabled, the last three digits of the unique total are the reconciliation handle — two concurrent same-amount payments are disambiguated automatically. When disabled (the default), uniqueAmount equals the raw base amount and amountSuffix=0, so two concurrent same-amount payments on the same bank account cannot be distinguished by amount alone — always cross-check sender name, receipt timestamp, and booking code as well.
  • Verify the sender. senderAccountName on the proof should reasonably match the name shown on the transfer receipt.
  • Verify the destination. Confirm the receipt's beneficiary account matches bankAccount.accountNumber.
  • Time-box review. The customer's payment expires on a fixed window — 30 minutes by default from payment creation, configurable per environment via CUSTOM_BOOKING_MANUAL_TRANSFER_EXPIRY_MINUTES. The window is enforced at proof upload time: once expiresAt passes, a new upload or re-upload is rejected (409, message Payment has expired; please start a new payment.). A proof that was already submitted before the window closed stays approvable — admin approval has no expiresAt guard, so a real transfer that landed in time still settles even if review runs past expiresAt. Rejection forcing a re-upload, however, eats into the remaining window. If your review SLA needs longer than the default, raise this env so the window covers transfer → upload end-to-end.
  • Duplicate detection is automatic. If the invoice was already paid (e.g., double-submission via Xendit), settlePayment flags the payment as a duplicate and suppresses re-ticketing — but you should still investigate and refund if needed.

Runtime toggle — unique-suffix feature ​

Flip the feature at runtime through the generic system-config API:

bash
PATCH /api/v1/admin/system-config
{
  "key": "MANUAL_TRANSFER_ENABLE_UNIQUE_SUFFIX",
  "value": "true"   // or "false"
}
  • Effect is immediate on the pod that serves the request; other pods converge within the Redis cache TTL (≤5 minutes).
  • Existing proofs are unaffected — the flag only governs new proofs (gateway payment creation) and the REJECTED → SUBMITTED re-upload flip.
  • When the feature is false, the partial unique index on (bankAccountId, uniqueAmount) is scoped to amountSuffix <> 0, so multiple zero-suffix in-flight proofs on the same bank account coexist. Reconciliation must fall back to sender + timestamp.

See System Configuration Guide → Manual Transfer Settings for the full schema.

Audit Trail ​

  • Every funds verification stamps fundsVerifiedAt and fundsVerifiedByAdminId on the proof row and logs via the NestJS Logger with the proof id and admin user id. Un-verifying clears both columns and logs the withdrawal. These columns are the durable record of who confirmed the money, and they sit next to reviewerId on the admin review block so a single screen shows both signatures.
  • Every approval writes a WebhookLog with webhookType='ManualTransferApproval' and the admin user id. This matches the existing webhook dashboard query so the audit timeline is unified with Xendit events.
  • Every rejection logs via the NestJS Logger with the proof id, retry count, and final-or-not flag.
  • Every reopen logs via the NestJS Logger with the payment id, admin user id, source status, addMinutes, and resetRetries. The reason is additionally persisted to ManualTransferProof.adminNotes.
  • Every impersonated upload writes an audit row: action MANUAL_TRANSFER_PROOF_IMPERSONATION_UPLOAD, entity ManualTransferProof, actor = the acting admin, with the customer id, payment id, invoice id and impersonation session id in metadata. A self-serve customer or guest upload writes nothing. The durable counterpart is uploadedByAdminId on the row itself — the audit log is the history, the column is the fact the review screen renders. Audit failures are logged and swallowed: losing the row must never lose the payment.
