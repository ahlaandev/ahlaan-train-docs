Payment Management Guide ​

This guide explains how administrators can manage payments, process refunds, and reconcile payment issues.

Quick Overview ​

FeatureDescription
PurposeManage payments, refunds, webhooks, and reconciliation
AccessAdmin only
ScopeAll payments across the platform

Base URL ​

All payment management endpoints use:

/api/v1

Authentication ​

All payment endpoints require:

  • JWT Token in Authorization header
  • ADMIN role in user account
http
Authorization: Bearer <your-admin-jwt-token>

Endpoints ​

1. Refund a Payment ​

Endpoint: POST /admin/payment/:id/refund

Process a refund for a payment. The payment ID comes from the URL path; both amount and reason are optional. When supplied, amount must be at least 1000 (@Min(1000)).

Request Body:

json
{
  "amount": 1000,
  "reason": "Customer requested refund"
}

Response: 200 OK

json
{
  "success": true,
  "refundAmount": 1000,
  "xenditRefundId": "refund-uuid",
  "message": "Refund processed successfully"
}

2. Manual Confirm Payment ​

Endpoint: POST /admin/payment/:id/manual-confirm

Manually confirm a booking payment when webhook failed.

⚠️ Important: For wallet top-ups, use /wallet-topup/:id/reconcile instead.

Manual transfers: this endpoint runs the shared PaymentSettlementService.settlePayment routine, so it settles a manual-transfer payment correctly even when the payment currency differs from the invoice currency. A SAR/USD transfer against an IDR custom-booking invoice is settled cross-currency via the SAR anchor (totalPaidSAR = baseTotalAmountSAR, IDR totalPaid left untouched), the invoice becomes PAID, and the booking advances to WAITING_FOR_TICKET — identical to approving the proof. Cross-currency behaviour keys off the payment gateway (MANUAL_TRANSFER) plus a currency mismatch, not the admin entry point, so both paths produce identical state. Prefer the proofs/approve flow for normal review; reach for manual-confirm only as the generic stuck-payment fix.

Response: 200 OK

json
{
  "success": true,
  "payment": {
    "id": "payment-uuid",
    "status": "PAID"
  },
  "booking": {
    "id": "booking-uuid",
    "status": "CONFIRMED"
  }
}

5. Reconcile Wallet Top-Up ​

Endpoint: POST /admin/payment/wallet-topup/:id/reconcile

Manually process a wallet top-up payment when webhook failed.

This will:

  1. Mark payment as PAID
  2. Mark invoice as PAID
  3. Credit wallet with pre-calculated SAR amount

Reports ​

9. Get Payment Reports ​

Aggregated payment analytics for dashboards and finance review. Returns summary KPIs, time-series chart data, and breakdowns by method and status — including webhook delivery health.

http
GET /api/v1/admin/payment/reports?preset=THIS_MONTH&groupBy=day
Authorization: Bearer <admin-token>

Query Parameters ​

ParameterTypeDefaultDescription
presetstringTHIS_MONTHDate range preset: TODAY, YESTERDAY, LAST_7_DAYS, LAST_30_DAYS, THIS_MONTH, LAST_MONTH, CUSTOM
fromstring-Start date (YYYY-MM-DD) — required when preset=CUSTOM
tostring-End date (YYYY-MM-DD) — required when preset=CUSTOM
groupBystringdayChart grouping: day, week, month
paymentMethodstring-Filter by method (e.g. QRIS, WALLET, BANK_TRANSFER); exact match
statusstring-Filter by status (e.g. PAID, PENDING, FAILED, EXPIRED); exact match
sourceenum-Filter by source: BOOKING (any OTA-derived — STANDARD + BLOCKSEAT), STANDARD (native ota/* only), BLOCKSEAT (blockseat-* wholesale only), or CUSTOM_BOOKING. Omit for all. webhookStats is gateway-level and is not affected by this filter.

The endpoint does not paginate — it always returns all aggregated data for the period.

summary.totalAmountnumberSum of payment.amountSAR (SAR source-of-truth) across all matched rows

byMethodarrayPer-method totals; null payment methods are bucketed as UNKNOWN
byStatusarrayPer-status totals (raw status string from the database)

Use Cases ​

Daily payments dashboard:

bash
curl -X GET "/api/v1/admin/payment/reports?preset=TODAY" \
  -H "Authorization: Bearer <admin-token>"

QRIS performance drill-down:

bash
curl -X GET "/api/v1/admin/payment/reports?preset=LAST_30_DAYS&paymentMethod=QRIS" \
  -H "Authorization: Bearer <admin-token>"

Failure analysis:

bash
curl -X GET "/api/v1/admin/payment/reports?preset=THIS_MONTH&status=FAILED" \
  -H "Authorization: Bearer <admin-token>"

Monthly trend (custom range):

bash
curl -X GET "/api/v1/admin/payment/reports?preset=CUSTOM&from=2026-01-01&to=2026-04-30&groupBy=month" \
  -H "Authorization: Bearer <admin-token>"

Notes ​

  • Currency. Payments are dual-currency: payment.amount follows the user-chosen currency (SAR / IDR / USD / etc.), while payment.amountSAR is the SAR source-of-truth (populated from the parent invoice's baseTotalAmountSAR on creation). Reports aggregate amountSAR so totals stay comparable across mixed-currency payments. Legacy rows created before this field existed fall back to amount (which is SAR for all current data).
  • Webhook stats are computed from webhookLog, independent of the paymentMethod and status filters — they reflect overall webhook health for the period.
  • paymentMethod and status filters apply as exact string matches and are not validated against an enum; unknown values simply return empty results.
  • No caching layer; queries run live against the database on every request.

Wallet Top-Up Reconciliation Workflow ​

When webhook processing fails for wallet top-ups:

1. Check pending payments
   GET /admin/payment/wallet-topup/pending?status=PENDING

2. Verify payment details
   GET /admin/payment/wallet-topup/:id

3. Reconcile after verification
   POST /admin/payment/wallet-topup/:id/reconcile
   {
     "reason": "Verified with gateway",
     "gatewayReference": "REF-123"
   }
