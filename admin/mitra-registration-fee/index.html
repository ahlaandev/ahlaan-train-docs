Mitra Registration Fee Guide ​

This guide explains how to set what a partner pays to register — per tier, with an optional limited promo.

⚠️ The price an applicant sees is locked to them when they submit.

Changing a price here never reprices anyone who already applied. Their amount was frozen onto their registration at submit, and the receipt issued at approval uses that frozen amount. This is deliberate: approval often happens days later, and billing someone for a price they never agreed to is not a rounding error.

Overview ​

Permission-gated (Access Roles). All routes require the ADMIN role plus a fine permission: reads need mitra-registration-fee:read, and setting a price needs mitra-registration-fee:update. See Access Roles.

This is a separate permission from mitra-registrations:review. Approving partners and pricing registration are different jobs, and one does not imply the other.

Two tiers are priced independently:

TierWhat the amount isReturned to the partner?
SILVERa registration feeNo — it is revenue
GOLDa security depositYes, it is a refundable liability

That difference matters when you set a GOLD promo: the promo amount becomes the amount that partner is owed back. Two GOLD partners onboarded in different months can be owed different deposits, and the authority is always the registration's own feeChargedSAR — never a figure quoted from memory.

Nothing is configured by default ​

The table ships empty. Until you create a row, these built-in prices apply:

TierBuilt-in price
SILVER100 SAR
GOLD50,000 SAR

GET /admin/mitra-registration-fees?tier=SILVER reports isDefault: true while that is the case. Read the live values from GET .../defaults rather than copying the numbers above.

How a promo works ​

A promo is a second, lower price on the same row, limited by a date window, a taker quota, both, or neither. Whichever limit runs out first ends the promo.

FieldMeaningOmit it to mean
promoPriceSARthe promo priceno promo at all
promoStartDatewhen it beginsalready running
promoEndDatewhen it endsopen-ended
promoQuotahow many applicants may take itunlimited
promoLabelfree text the site may showno label

Three rules the API enforces:

  1. promoPriceSAR must be strictly below priceSAR. A "discount" at or above the normal price is rejected, because it renders as a strikethrough advertising a saving nobody receives. 0 is accepted and means free.
  2. promoStartDate must be before promoEndDate when both are given.
  3. Each limit is independent. A promo with no dates and no quota is legal, and runs until you replace the row.

The quota is per tier, not a shared pool ​

promoQuota: 20 on SILVER means 20 SILVER promos. A GOLD row with its own quota of 20 adds 20 more — 40 partners in total, not 20. Each tier counts its own.

A slot is spent at submit and never returned ​

The counter moves when someone submits, not when they are approved. Rejecting or abandoning an application does not return the slot, so a quota of 20 may onboard fewer than 20 partners.

This is deliberate. Counting at approval would mean the price could not be locked at submit, which reopens the gap this whole design closes: a receipt claiming money that never moved. A wasted slot is cheap; a wrong receipt is not.

The counter survives an edit ​

When you save a new price, the new row carries promoUsedCount forward from the row it replaces. Fixing a typo in a label therefore cannot hand out a fresh batch of promo slots by accident.

Starting a genuinely new campaign? Send resetPromoCounter: true to restart at 0.

Timezones — send a full timestamp, always ​

promoStartDate and promoEndDate must carry an offset or Z. The API never guesses a timezone.

A bare "2026-08-31" is read as midnight UTC, which is 03:00 on the 31st in Asia/Riyadh. An admin who means "runs through the end of the 31st" and sends a bare date closes the promo about 21 hours early, and nothing in the response reveals it.

You meanSend
End of 31 August, Asia/Riyadh2026-08-31T20:59:59.000Z
Start of 1 August, Asia/Riyadh2026-07-31T21:00:00.000Z

Converting an operator's chosen day into an instant is the admin UI's job — it is the only layer that knows which timezone the operator is sitting in.

There is no edit — every change is a new row ​

There is no PUT. Saving a price deactivates the current row for that tier and inserts a new one, so the table is its own audit history: every price ever set, who set it, and when, are all still there. GET /history reads it.

Only the named tier is touched. Repricing SILVER never disturbs GOLD.

Endpoints ​

/api/v1/admin/mitra-registration-fees?tier=SILVERGET:readActive price for one tier

promoUsedCount against promoQuota is how you see how much of a promo is left. Once they are equal the promo stops applying: new applicants are recorded at priceSAR, and the public pricing endpoint reports type: "STANDARD" again.

Set a price ​

bash
curl -X POST "$BASE/admin/mitra-registration-fees" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "tier": "SILVER",
    "priceSAR": 100,
    "promoPriceSAR": 50,
    "promoStartDate": "2026-08-01T21:00:00.000Z",
    "promoEndDate": "2026-08-31T20:59:59.000Z",
    "promoQuota": 20,
    "promoLabel": "Promo Kemerdekaan"
  }'

To end a promo early, save the row again without the promo fields:

bash
curl -X POST "$BASE/admin/mitra-registration-fees" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "tier": "SILVER", "priceSAR": 100 }'

400 responses

Every message below was captured from a live 400, not paraphrased.

CauseMessage
Promo not below normalpromoPriceSAR must be strictly less than priceSAR
Window reversedpromoStartDate must be earlier than promoEndDate
More than 2 decimals, negative, or too largepriceSAR must be a number with at most 2 decimal places, between 0 and 9999999999999.99
promoQuota below 1promoQuota must not be less than 1

An amount written in exponential notation (1e-7) is rejected by the same rule that catches three decimal places — it is a 400, not a server error.

History ​

bash
curl "$BASE/admin/mitra-registration-fees/history?tier=SILVER&limit=20" \
  -H "Authorization: Bearer $ADMIN_TOKEN"

Active and inactive rows, newest first. limit is capped at 100 — asking for 500 returns meta.limit: 100, it does not error.

What the applicant sees ​

The public, unauthenticated GET /auth/mitra/registration/pricing serves both tiers. The site reads it instead of hardcoding amounts, so your change takes effect without a deploy.

The number of remaining promo slots is deliberately not published there: the route needs no login, and a remaining count tells anyone how fast partners are signing up. You can see it here, on promoUsedCount.

Rolling out a price change safely ​

  1. Set the normal prices first and confirm GET .../pricing reports type: "STANDARD" at the amounts you expect.
  2. Make sure the site is reading that endpoint rather than its own copy of the numbers.
  3. Only then set a promo.

Doing step 3 before step 2 means the website advertises one price while registrations are recorded at another.
