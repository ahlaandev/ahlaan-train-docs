Admin Notification Management ​

This guide explains how administrators can manage and send notifications through the HHR platform.

Quick Overview ​

FeatureDescription
PurposeManage, send, and track notifications to users and organizations
AccessADMIN accounts holding a notifications: permission
ChannelsIn-app, Email, WhatsApp, Push (configurable)

Permission-gated. Every route on this controller requires an Access Role permission — reads need notifications:read, sending and resending need notifications:send, and deleting needs notifications:delete. These routes previously ran on the plain ADMIN/SUPPORT role check with no permission at all, so any admin account reached them regardless of its Access Roles, including the send route that queues a real email to a customer. The three write routes are recorded in the audit log against the calling admin. See Access Roles.

Base URL ​

All notification management endpoints use:

/api/v1

Authentication ​

All notification endpoints require:

  • JWT Token in Authorization header
  • ADMIN role
  • an Access Role granting the permission the route needs — notifications:read to view, notifications:send to send or resend, notifications:delete to delete. notifications:* grants all three.
http
Authorization: Bearer <your-admin-jwt-token>

Endpoints ​

1. List All Notifications ​

Endpoint: GET /admin/notifications

Get all notifications with filtering support.

Query Parameters:

ParameterTypeDescription
pagenumberPage number (default: 1)
limitnumberItems per page (default: 20, max: 100)
userIdstringFilter by user ID
organizationIdstringFilter by organization ID
isReadbooleanFilter by read status
typestringFilter by notification type
prioritystringFilter by priority (LOW, NORMAL, HIGH, URGENT)
channelstringFilter by channel (IN_APP, EMAIL, WHATSAPP, PUSH)
startDateISO dateFilter from date
endDateISO dateFilter to date
searchstringSearch in title/body

Example:

bash
GET /admin/notifications?priority=HIGH&isRead=false&limit=50

5. Send Custom Notification ​

Endpoint: POST /admin/notifications

Create and send a custom notification to a specific user.

Request Body (real request sent to preprod.mitra.ahlaan.co.id, 2026-08-11):

json
{
  "userId": "019ff0ee-cde2-721b-8cc3-6cbabb559c69",
  "type": "SYSTEM_ANNOUNCEMENT",
  "priority": "NORMAL",
  "title": "Docs capture",
  "body": "Real response capture for the docs page",
  "channels": ["IN_APP"]
}

Request Fields:

FieldTypeRequiredDescription
userIdstringYesTarget user ID
organizationIdstringNoOrganization context (for B2B)
typestringYesNotification type from templates
prioritystringNoLOW, NORMAL, HIGH, or URGENT (default: NORMAL)
titlestringYesNotification title
bodystringYesNotification body/message
dataobjectNoAdditional data payload
channelsarrayNoDelivery channels (default: all)
attachmentUrlsstring[]NoURLs to attach to the notification. Applied to the EMAIL channel only

  "organizationId": null,
  "type": "SYSTEM_ANNOUNCEMENT",

  "title": "Docs capture",

  "data": null,
  "isRead": false,
  "readAt": null,
  "channels": ["IN_APP"],
  "emailSent": false,
  "emailSentAt": null,

6. Resend Notification ​

Endpoint: POST /admin/notifications/:id/resend

Resend an existing notification. Optionally specify different channels.

This does not re-dispatch the row named in the URL — it COPIES it into a new Notification row and dispatches that. The response therefore carries a new id, and the row named in the URL is still there afterwards. The link between the two survives only in the audit log: NOTIFICATION_RESENT records entityId = the new row and metadata.originalId = the id from the URL.

Request Body:

json
{
  "channels": ["EMAIL"]
}
FieldTypeRequiredDescription
channelsarrayNoOverride channels (default: the original notification's channels)

Response: 201 Created — real body from resending 019ff0f5-5b6c-70b8-b640-c3c44e683bda with an empty request body, so the channels fell back to the original's:

7. Delete Notification ​

Endpoint: DELETE /admin/notifications/:id

Delete a notification by ID. This is a hard delete — the row is removed, not flagged, so a later GET on the same id answers 404 and the audit row is the only surviving record of what was destroyed. NOTIFICATION_DELETED therefore carries metadata: { targetUserId, type } beside the id.

Response: 200 OK

json
{
  "deleted": true
}

Common Workflows ​

Workflow 1: Send Maintenance Announcement ​

bash
curl -X POST /api/v1/admin/notifications \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "userId": "user-456",
    "type": "SYSTEM_MAINTENANCE",
    "priority": "HIGH",
    "title": "Scheduled Maintenance",
    "body": "System maintenance scheduled for Feb 20, 2026",
    "channels": ["IN_APP", "EMAIL"]
  }'

Workflow 2: Resend Failed Email Notification ​

bash
curl -X POST /api/v1/admin/notifications/notif-123/resend \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "channels": ["EMAIL"]
  }'

Workflow 3: Get Unread High-Priority Notifications ​

bash
curl -X GET "/api/v1/admin/notifications?priority=HIGH&isRead=false" \
  -H "Authorization: Bearer <token>"

Error Responses ​

404 User Not Found ​

json
{
  "statusCode": 404,
  "message": "User not found",
  "error": "Not Found"
}

404 Notification Not Found ​

json
{
  "statusCode": 404,
  "message": "Notification not found",
  "error": "Not Found"
}

403 Forbidden (missing the route's notifications: permission) ​

The guard answers before the handler, so the body is the framework's, not a message naming the code you lack:

json
{
  "message": "Forbidden resource",
  "error": "Forbidden",
  "statusCode": 403
}

Probed on preprod 2026-08-11: an admin holding notifications:read got this on POST, on POST :id/resend and on DELETE; an admin holding notifications:send + notifications:delete but not :read got it on the list, stats and templates reads.
