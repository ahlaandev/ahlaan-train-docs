Custom Booking Shortfall Settlements (Admin) ​

This guide covers the admin endpoints that record money returned to a customer for the passengers a ticket source could not ticket, and that move the booking from TICKET_UPLOADED_PARTIAL to SHORTFALL_REFUNDED.

For the upload that creates the shortfall in the first place, see Custom Booking → §5 Upload Ticket. For bank refunds against a cancelled booking — a different record type on the same screen — see Refund Management.

Permission-gated (Access Roles). Beyond the ADMIN role, these routes require a fine-grained permission. Creating a settlement needs its own dedicated code, refunds:shortfall-settlement (PERMISSIONS.REFUNDS_SHORTFALL_SETTLEMENT); both reads need refunds:read, the same code that gates bank-refund reads.

Why its own code, instead of reusing refunds:approve. Approving a bank refund pays out against a Refund row. This writes the booking into SHORTFALL_REFUNDED — a state no route can leave except by closing or cancelling the booking. That is a different act with a harder-to-undo consequence than approving a refund, so it should be granted deliberately rather than inherited from the refund-approval code.

No existing role has this code. It must be granted explicitly before any role can use this endpoint — a refunds:* wildcard holder does inherit it, but no seeded role lists it individually. See Access Roles.

⛔ This is the only writer of SHORTFALL_REFUNDED.PATCH /admin/custom-booking/:id/status refuses that value outright with a 400, deliberately: a status asserting that money moved must not be settable without a record of the money moving. There is no way to mark a booking settled without creating a settlement row.

What a shortfall settlement is ​

A ticket source under-delivers. The admin uploads what arrived and records how many passengers it actually covers, and because that count is below the seated total (adultCount + childCount; infants excluded from this basis by business rule) the booking lands in TICKET_UPLOADED_PARTIAL, optionally carrying a free-text shortfallReason and a supporting attachment. Both are optional, so a booking can reach this status with no explanation recorded at all.

The customer has paid for passengers who were never ticketed. Finance transfers that money back by hand, outside this system. This endpoint is the record of that transfer. It writes a settlement row, moves the booking to SHORTFALL_REFUNDED, and writes an audit entry naming the admin who did it.

TICKET_UPLOADED_PARTIAL is the only status a settlement can be created from — it is the one status with a shortfall outstanding. Every other status either has nothing owed or has already dealt with it, and COMPLETED in particular has no outgoing transition, so settling there would leave a closed booking asserting that money moved with no way to reflect it.

New: the four destination fields. All optional, and null on every settlement written before they existed. A shortfall refund is frequently handed over rather than transferred, so finance is not made to invent an account number in order to record one — reference stays the required field.

⚠️ Nothing verifies the account, and there is no approver on this record type (see No second approver), so a typo sends money to a stranger. They are a record of where the money went, not a check on it.

proofFile accepted types: application/pdf, image/jpeg, image/png. Anything else answers 400 naming the rejected type. The file is stored in R2 with entityType: custom_booking_shortfall_proof, visibility: PRIVATE, attached to the booking — the customer never sees it.

It cannot be deleted, including by an admin. DELETE /storage/:fileId answers 403 for custom_booking_shortfall_proof, for custom_booking_shortfall_attachment and for the retired custom_booking_shortfall_report: each is evidence behind a refund, that route carries no permission check and writes no audit row, and the R2 delete is irrecoverable. Correct a wrong file by uploading a replacement. The rollback path is unaffected — a settlement whose status write loses the race still has its orphaned proof removed, because that runs internally rather than through the storage route.

Size limit. The request may carry at most 1 file part, capped at MAX_FILE_SIZE (default 52428800 bytes = 50 MiB). Multer uses memory storage and aborts the stream at the threshold rather than buffering the whole part and rejecting it afterwards; an oversized file answers 413. A second file part hits a different Multer limit (LIMIT_FILE_COUNT / LIMIT_UNEXPECTED_FILE) and Nest maps those to 400, not 413 — the size cap is the only 413 here.

Every scalar arrives as a string. The global pipe runs with enableImplicitConversion: false, so the DTO converts each number field explicitly. Send them as ordinary form fields — -F "shortfallAmountSAR=500" — and do not quote-wrap them as JSON.

A misspelled field is silently dropped, not rejected (whitelist: true, forbidNonWhitelisted: false). ⚠️ Now that the rate is optional, a typo'd settlementRateToSar does not 400 at all — the request succeeds and the settlement records the rate the booking froze instead of the one you sent. settlementRateSource on the response is the tell: it reads ADMIN only when your rate actually arrived. A misspelled settlementAmount still 400s on USD and IDR, because that field stayed required.

The currency contract ​

shortfallAmountSAR is what is owed. The three settlement fields describe what physically moved. They are separate on purpose: money can leave at an effective rate that no published rate row carries.

⚠️ Rate direction. Send settlementRate, written the way the admin exchange-rate screen already shows that currency: IDR as IDR per ONE SAR (4166.67), USD as SAR per ONE USD (3.75), SAR as exactly 1.

The direction is fixed by settlementCurrency and is not selectable. The right number under the wrong direction is the same defect as the wrong number, recorded as though it were deliberate — so there is no field here to get wrong.

A rate outside the accepted window for the currency (USD 2–8, IDR 200–20000 by default) is a 400, always. This is the check that catches an inverted or thousand-fold-wrong value. It is separate from the reconcile tolerance below, which never blocks.

settlementRateToSAR is the legacy spelling and still accepted: SAR per ONE unit (1 IDR = 0.00024 SAR), inverted onto the canonical direction before the window is applied, so both fields are judged against one set of numbers. Send one or the other, never both.

⚠️ Supported, not scheduled for removal — removal was considered under issue #614 and decided against, matching the same call on the bank refund's payoutRateToSAR. A client already sending it does not have to migrate. Prefer settlementRate in new code: a mistyped field name is dropped silently rather than refused, so settlementRateToSar with a small r records the booking's own rate instead of yours, and settlementRateSource reading anything other than ADMIN is the only sign it happened.

Stored at 8dp (Decimal(18,8)) alongside a settlementRateDirection column recording which way the stored number is written. ⛔ Rows written before that column existed are FOREIGN_TO_SAR whatever their currency, and nothing is backfilled — direction is a property of the row, never of the currency.

SAR — the identity case. Omit both figures.

shortfallAmountSAR: 500,  settlementCurrency: "SAR"
→ stored settlementAmount 500, settlementRate 1,
  settlementRateDirection FOREIGN_TO_SAR, settlementReconciled true

They are filled in as the SAR amount itself at a rate of 1. Sending them explicitly (500 and 1) is accepted and identical.

USD and IDR — the amount is required, the rate is optional.

500 SAR owed, paid in USD at 3.75 SAR per USD
settlementCurrency "USD", settlementAmount 133.33, settlementRate 3.75
→ direction FOREIGN_TO_SAR, so MULTIPLY
→ 133.33 × 3.75 = 499.9875 SAR   |diff| 0.0125 → settlementReconciled true

53 SAR owed, paid in IDR at 4250 IDR per SAR
settlementCurrency "IDR", settlementAmount 225250, settlementRate 4250
→ direction SAR_TO_FOREIGN, so DIVIDE
→ 225250 ÷ 4250 = 53 SAR exactly   |diff| 0 → settlementReconciled true

The IDR figures above are a real preprod settlement (booking 2WUUPCE, 2026-08-11); its response is the second worked capture below. That settlement was a test record and has since been removed — the figures stand, the row does not.

The amount may not be omitted. A bank refund can fall back on a suggestion stored when the payout was initiated; a shortfall settlement never had one, because nothing here ever computed an amount. An omitted amount would store a null figure alongside a reconciled flag that means nothing.

When the rate is omitted ​

Send settlementCurrency and settlementAmount and leave the rate out. The server fills it in from what the booking froze when it was priced, and says which rung answered in settlementRateSource on the response:

CurrencyWhere the rate comes from, in ordersettlementRateSource
SARAlways exactly 1IDENTITY
IDRpricingSnapshot.effectiveSellRate (the GOLD-reduced figure where there is one) → the booking's linked base rate row → the current published SAR rateBOOKING_SNAPSHOT → BOOKING_RATE_ROW → LIVE
USDpricingSnapshot.usdSarRate → totalPriceSAR ÷ totalPriceUSD → the current global USD holderBOOKING_SNAPSHOT → IMPLIED → LIVE

A rate you send yourself is stored as-is and reported as ADMIN.

Why the booking's rate and not today's. The GOLD discount is a reducer on a mutable global config, not a rate row of its own. Reading it live would re-price a historical settlement the moment an admin edits that config, so the same shortfall would pay differently depending on when finance got round to it. Frozen also means the rate the customer was charged at, so returning part of what they paid hands back the currency they paid in.

Resolving the customer's tier live would not merely be worse here, it would be wrong: the special-pricing context is gated to the promo host and this request arrives on the admin host, so a GOLD booking would silently resolve to the holder peg and settle at the unreduced rate.

⚠️ A legacy booking whose snapshot predates the frozen rate falls to the base rate row, which for a GOLD booking is the unreduced rate — it returns marginally more IDR than the customer paid. The reducer in force at create was never persisted, so it cannot be recovered from the row. Measured on preprod 2026-08-11: 133 of 228 custom bookings are in that state, none of them carries a frozen pricing tier, and none of the bookings that had reached a settlement was among them.

⚠️ A derived IDR rate is the GOLD-reduced one. The same figure is withheld from custom-booking responses without custom-bookings:read-capital-markup, because subtracting the public base rate from it gives the tier reducer. The settlement records it regardless: this row states what rate money actually moved at, and putting a rate the customer was never charged at onto a financial record to protect a config number is the worse trade. Deliberate, not an oversight.

Two surfaces echo that rate back, and they gate on different codes. These routes, on refunds:read; and the shortfallSettlement block embedded in GET /admin/custom-booking/{id}, on custom-bookings:read-pricing — that key is stripped by the SELL list, not the cost list. So a role holding read-pricing without read-capital-markup reaches the reduced rate there too, which is the direction the money split is otherwise meant to hold. That block also carries no settlementRateSource, so on that screen a derived rate and a typed one look alike; read these routes when the provenance matters.

⛔ A non-SAR settlement whose rate cannot be derived at all is a 400, not a silent rate of 1. An IDR settlement recorded at 1 would claim the customer was handed one rupiah per riyal owed. The message names settlementRate as the way through.

Derived example, taken from preprod on 2026-08-11 — booking GXJVC82 (a test settlement, since removed), whose snapshot froze effectiveSellRate 4750 against a baseSellRate of 4900. One passenger of ten was unticketed on a 1860 SAR booking, so 186 SAR was owed:

settlementCurrency "IDR", settlementAmount 883500   (no rate sent)
→ rate 4750 taken from the booking, direction SAR_TO_FOREIGN
→ 883500 ÷ 4750 = 186 SAR exactly  → settlementReconciled true
→ settlementRateSource "BOOKING_SNAPSHOT"

The USD ladder was exercised the same day on booking B2D56JW (likewise a test settlement, since removed) (pricingSnapshot.usdSarRate 3.75, 189 SAR owed): settlementAmount 50.40 with no rate returned payoutRate 3.75, payoutRateDirection FOREIGN_TO_SAR and the same BOOKING_SNAPSHOT source.

Because the amount now comes from the bank slip and the rate from the booking, the reconcile check below finally compares two independent numbers — an amount entered ten times too small shows up as settlementReconciled: false instead of agreeing with a rate the same person computed.

⚠️ The same independence makes settlementReconciled: false ordinary on an older booking. The money leaves the bank at today's rate while the record back-converts it through the booking's, so any FX movement since the booking was priced shows up as a divergence. 500 SAR sent as 2,100,000 IDR at a current 4200, on a booking frozen at 4770, back-converts to 440.25 SAR — a 59.75 SAR gap against a ±1 SAR tolerance. Nothing is wrong with either figure. Send settlementRate explicitly when you want the record to reconcile against the rate the transfer actually used.

Reconciliation is recorded, never enforced.

The pair is checked against the owed SAR with a tolerance of 1 SAR, widened by |settlementAmount| × 1e-8 to absorb the pure storage error introduced by back-multiplying an 8dp rate against a high-magnitude IDR figure. For SAR and USD that slack is sub-cent and effectively a no-op; real divergences stay orders of magnitude above it.

A pair that falls outside tolerance is stored with payoutReconciled: false and a server-side warning — it is never rejected:

500 SAR owed, settlementCurrency "USD", settlementAmount 10, settlementRate 3.75
→ 10 × 3.75 = 37.5 SAR   |diff| 462.5  → settlementReconciled false, 201 Created
(the RATE is in window — only the AMOUNT diverges, which is what gets recorded)

Why a divergence is not a 400. The money has already left. A bank fee or a rounding decision is a fact about the transfer, not grounds to refuse the record of it — refusing would leave the transfer real and unrecorded, which is strictly worse than recording it with a flag. Treat payoutReconciled: false as a review queue, not as a failure.

Rate provenance. settlementExchangeRateId says which published rate row the stored figure was reached against. It is never read back to re-derive the amount; the row's own rate and direction stay authoritative. The id is not emitted in the response.

Which row gets named follows the rate itself:

  • a rate you sent — the current rate row is looked up, because that is the screen the number was read off. If none resolves, the create still succeeds with a null pointer and a logged warning;
  • a rate derived for IDR at the BOOKING_RATE_ROW rung — the booking's own exchangeRateId, because there the stored rate is that row's value;
  • a rate derived at the BOOKING_SNAPSHOT rung — null. The snapshot rate is the row's rate minus the tier reducer, so naming the row would invite a reconciliation to join the two and find a few percent it cannot explain;
  • a rate derived at the LIVE rung — the id of the current rate row that answered, which is not the booking's;
  • a rate derived for USD — always null. The BOOKING_SNAPSHOT and IMPLIED rungs come off the booking's own frozen figures, which no rate row holds, so naming one would be false provenance. The LIVE rung reads the in-process USD holder, and that holder is hydrated from a toCurrency = 'USD' row — but the branch stores null there too rather than looking one up, because the holder also refreshes over Redis and the row that last fed it is not resolved on this path. The number stays recoverable from the booking.

⛔ For IDR, the lookup deliberately asks for the SAR rate row, not an IDR one. Rates are stored keyed on toCurrency, and there is no toCurrency = 'IDR' row — the SAR row is the IDR pair (its sellRate is IDR-per-SAR). resolveRateProvenance aliases IDR → SAR before calling getCurrentRate; calling getCurrentRate('IDR') directly would find nothing, so every IDR settlement would store a null pointer regardless of whether a current rate exists. USD is looked up as itself — only IDR gets the alias.

What this endpoint deliberately does NOT do ​

⛔ It suggests nothing, and the only check that compares the AMOUNT to the booking is the ceiling: it may not exceed the booking total. The remaining checks on the figure are format-level — positive, at most two decimals, within the column's range. (The route has other booking-derived rejections — status, a missing recorded count, nothing outstanding, a booking with no value — but none of them looks at the amount you sent.) There is no expectedAmountSAR field on this request, on this response, or on the settlement row in the database. Whatever finance types is what is recorded.

The booking detail does carry a per-leg refund estimate (shortfallRefundTotalSAR — see Custom Booking). It exists so the customer's "Berita Acara Realisasi" can be printed, and this endpoint neither reads it nor compares the submitted amount to it. It could not usefully do either, because the estimate is knowingly imprecise:

  • ticketedPaxCount is one number. It says how many passengers were ticketed, never which ones. A booking short by one passenger does not record who that passenger was.
  • Adult and child prices differ. pricePerAdultSAR and pricePerChildSAR are separate figures, so "one passenger's worth" has no single value until you know which passenger was missed — which the previous point says you do not. The estimate resolves this by pricing every missing seat at the adult fare, which over-refunds a mixed booking on purpose.

Treated as an authority, that figure would be a guess wearing the authority of a computed number, and a wrong guess here sends the wrong amount of real money. So finance types the figure and amountReason keeps their reason for it. The document the customer receives says the same thing in its own footnote — "Nilai final akan menyesuaikan hasil konfirmasi dari pihak Finance".

No second approver ​

⚠️ Every settlement response carries requiresApproval: false and approvedBy: null. No dual-control flow exists for this record type. The admin who creates the settlement is the only human on the record.

This matters because of where these rows are rendered. The response field names deliberately overlap the bank-refund response so one frontend row component can render a Refunds screen with a bank-refund tab and a shortfall tab — and a bank refund on the neighbouring tab genuinely does carry a second approver. On a shared screen, a settlement nobody countersigned must never be mistaken for an approved bank refund. requiresApproval and approvedBy are what tell them apart; they are emitted on every row precisely so the FE never has to infer it from which tab it happens to be on.

The approvedBy column exists in the database and is written as an explicit null rather than left unset, so a later dual-control flow needs a code change and not a migration.

The frozen counts ​

The settlement row stores its own copy of expectedTicketCount, ticketedPaxCount and unticketedPaxCount rather than reading through to the booking.

This record has to keep saying what was owed on the day the money left, so it freezes the three figures at settlement time. NOT NULL columns, all three.

A round trip additionally freezes unticketedOutboundPaxCount and unticketedReturnPaxCount. The booking-level count is a min, so it cannot say which LEG the money was for — and a later upload that swaps the shortfall from one leg to the other would leave the settled record and the live booking disagreeing about it. Nullable, because a ONE_WAY settlement has no second leg and rows written before per-leg settlement have no such figure; on a booking recorded before per-leg tracking they fall back to the booking-level count for both legs, which is the only honest reading of a booking never measured per leg.

Freezing is belt-and-braces rather than the only defence: once a settlement exists the booking's ticketedPaxCount may no longer move at all. An upload may restate the same count to replace a bad file, but a raised or lowered count is refused on every status, including after a manager has closed the booking — see Custom Booking → §5. The frozen copies survive a hand-fixed row, which that guard cannot.

The infant figures are the cross-check on this row's shortfall

The seated shortfall a settlement froze is the figure the money was sized from, and nothing beside it used to say how many infant tickets arrived. That matters because the two are easy to merge: an admin looking at a booking of 10 seated passengers and 3 infants, told that 11 of 13 documents arrived, can record the two missing infant tickets by lowering the seated count to 8. 8 of 10 is a legal seated figure, so the shortfall estimate then prices two adult fares for two passengers who cost nothing.

unticketedInfantPaxCount is what makes that visible. A seated shortfall matched by an equal infant shortage on the same row is the shape of the mistake — worth a question before the money moves. Nothing is owed for an infant either way.

⚠️ These figures are live, not frozen, and null means never recorded. There is no backfill for a row settled before the columns existed. The ticket upload refuses to move a recorded infant figure once a settlement exists, so a row that has them keeps them; see Upload a ticket.

expectedTicketCount is adultCount + childCount. Infants are excluded — an infant sits outside it by business rule, so nothing was ever owed for one and there is no shortfall to size. An infant IS issued a ticket, and it arrives together with the adult ticket, so a short delivery still shows up in this count. A 8 + 2 + 3 booking has an expected count of 10, not 13.

Order of checks ​

Worth knowing when debugging a 400, because the first failure wins:

  1. Validation — the DTO, before the handler runs.
  2. Proof MIME type — in the controller, before anything reaches R2 and before the booking is even loaded. An unsupported proof on a non-existent booking answers the MIME 400, not the 404.
  3. Booking exists → 404.
  4. Status is TICKET_UPLOADED_PARTIAL → 400.
  5. A ticketed count was recorded → 400.
  6. Something is actually outstanding → 400.
  7. shortfallAmountSAR does not exceed the booking total → 400.
  8. The currency contract → 400: a rate without an amount, a non-SAR settlement with no amount, both rate spellings at once, a rate outside the currency window (sent or derived), or a non-SAR settlement whose rate could not be derived. All of it runs before the proof reaches R2, so a rejected settlement never orphans a file.
  9. Rate provenance lookup (non-fatal), then the proof upload to R2, then the transaction: settlement row + status write + audit entry, together or not at all — plus the settlement table's own unique constraint, which turns a concurrent duplicate create into a 409 on the insert rather than a 500, before the status compare-and-set below even runs.

If the transaction fails — including on a lost race — any proof already uploaded is taken back out of storage, best-effort. An R2 call cannot take part in a database transaction, so the object goes up first and the cleanup catches it on the way down.

cURL ​

Every sample below settles a ONE_WAY booking, which is why each sends shortfallAmountSAR. On a ROUND_TRIP that field is refused and the two per-leg figures are sent instead — see the last sample.

  -F "customBookingId=019f6ef6-8e81-724f-9faf-7e664b9bceee" \
  -F "shortfallAmountSAR=500" \
  -F "settlementCurrency=SAR" \
  -F "reference=TRF-99" \
  -F "amountReason=1 of 10 passengers unticketed; adult fare, outbound leg"

Partner identity on the row ​

partnerRegistrationNumber, partnerName and partnerTier name the mitra the settled booking belongs to. They are resolved live on every read — the booking organization's own registration first, then the booking user's own approved numbered one. Three nulls is the normal answer for a booking that belongs to no mitra; render -.

The settlement row itself carries neither a user id nor an organization id, so these resolve through the booking. That is also why the list can filter by partner while it cannot filter by customer.

⚠️ Live, so this can disagree with the invoice — and both are right. The partner pair on the booking's invoice is frozen at issue time. After a partner is renamed, the settlement row says who they are now and the invoice says who it was issued to. The same split already exists on the admin booking detail.

⚠️ partnerName can be non-null while partnerRegistrationNumber is null. An organization's own registration is taken as-is — the approved-and-numbered filter is applied to the user's registrations, not to the org's linked row. So a booking whose organization is not yet approved, or holds no number yet, shows a name beside a null number. Such a row is not returned by a partner search, because the filters match numbered registrations only. Branch on the number, not on the name, when you need "is this a numbered partner".

Present on every response that returns a settlement row, not just the list — POST /, GET / and GET /:id each carry the three keys. ⚠️ This differs from the refund tab, where they are present on the list only and absent (not null) elsewhere. A component shared across both tabs must therefore branch on presence when it renders a refund and may read the keys directly when it renders a settlement.

Unlike the ticket upload's audit — written after the fact and best-effort, because that path holds an R2 call open — a failure here rolls the whole settlement back.

  • 400 Bad Request — shortfallAmountSAR (600) exceeds what was paid for this booking. A shortfall returns part of what was paid, so it cannot be larger than the whole booking. Only the figure you sent is interpolated. Neither message names the booking total, deliberately: totalPriceSAR is stripped from every custom-booking response unless the caller holds custom-bookings:read-pricing, and this route is reachable with refunds:shortfall-settlement alone — quoting it back in a rejection would hand it over in a single request. A sanity ceiling, not an expectation — it isn't sizing the shortfall. Nothing else compares the figure to the booking; the remaining checks are format-level (positive, at most two decimals, within the column's range). A shortfall only ever returns part of what the customer already paid, so the figure can never exceed the booking total regardless of which passenger or leg was missed.
  • 400 Bad Request — settlementRate was sent without settlementAmount. The amount is what physically moved; the rate only describes it. The reverse is no longer an error: an amount without a rate is derived.
  • 400 Bad Request — settlementAmount is required for a IDR settlement. Only a SAR settlement can omit it, where the amount is the SAR figure itself at a rate of 1. The currency name is interpolated (USD reads the same way).
  • 400 Bad Request — No rate could be derived for this IDR settlement — the booking froze none, it has no linked exchange-rate row, and no current rate is published.   • 400 Bad Request — Rate <n> is outside the accepted window for IDR (200 to 20000, read as IDR per 1 SAR). Check the rate is not inverted or off by a factor of a thousand. The currency, both bounds and the direction phrase are interpolated, so a USD breach names the USD window instead. It says "Rate" and names no field on purpose — the same check runs on the bank-refund proof upload, where the input is called payoutRate rather than settlementRate. ⚠️ When the offending rate was derived rather than sent, a second sentence is appended naming the source and telling you to send settlementRate explicitly: the advice to check for an inverted value is about a number a human typed, and nobody typed this one.
  • 400 Bad Request — A SAR transfer is the identity case and its rate must be exactly 1, not <n>.
  • 400 Bad Request — Send settlementRate or settlementRateToSAR, not both. settlementRateToSAR is the deprecated spelling.
  • 404 Not Found — Custom booking not found.
  • 409 Conflict — two distinct causes, both translated from what would otherwise be a raw 500:
    • Cannot settle: booking ABC1234 moved while this request was in flight. Both its status and its recorded ticketed count are checked, so re-read the booking before retrying — the status alone may look unchanged. The status write is pinned to both the status and the recorded ticketed count. ⚠️ A concurrent ticket upload lands here too: a late top-up moves the booking to TICKET_UPLOADED_FULL and rewrites ticketedPaxCount, and a status-only pin would still match a row whose count had gone from 9 to 10 — freezing a stale unticketedPaxCount into a record claiming more money than was ever owed. So a booking that looks unchanged can still lose the race.
    • A settlement for booking 019f6ef6-8e81-724f-9faf-7e664b9bceee was recorded by another request. Re-read the booking before retrying — its shortfall may already have been settled. A concurrent duplicate create — two requests racing to settle the same booking. This one fires on the settlement table's unique constraint at insert time, before the status compare-and-set above ever runs, so it pre-empts the "booking moved" conflict rather than compounding it. Note the message quotes the raw customBookingId (the UUID), not the bookingCode the other 409 uses — a deliberate reminder that this is a different code path, not the same message with different values. Either way, any proof already uploaded is taken back out of storage.

Aborted mid-stream by multer rather than buffered and rejected — the same status the edge proxy returns for an oversized body, so the app and the edge agree on the answer. Size only — sending more than 1 file part is a different Multer limit (LIMIT_FILE_COUNT / LIMIT_UNEXPECTED_FILE), which Nest maps to 400 Bad Request, not 413.

2. List Shortfall Settlements ​

http
GET /api/v1/admin/shortfall-settlements

Paginated, newest settlement first. Throttled at 60 req / 60s. Needs refunds:read.

There is deliberately no customer or organization filter. A settlement hangs off the booking, not off a user, and the row carries neither a user id nor an organization id — adding those filters would mean joining through the booking to answer a question the record does not model. Filter by customBookingId or bookingCode instead; get the booking ids from the custom-booking list, which does filter by customer and organization.

The two partner filters are the deliberate exception, and for the opposite reason: a partner is not a property of the settlement either, but it is the question the Refunds screen is actually asked, and the refund tab beside this one already answers it. Both terms resolve through the booking.

The partner filters follow the same precedence the column does — the booking organization's registration first, the booking user's own approved numbered one otherwise. Where the filter and the column part:

  1. A booking whose organization's registration is not approved or not numbered shows a partner name with a null number, and a search for that name does not return it. The filters answer about numbered partners.
  2. A user holding several approved numbered registrations matches on any of them, while the column shows the one resolved newest-reviewed-first — so a returned row can name a different number than the one searched for. Reproducing that ordering in SQL would tie the filter to the resolver's precedence, which is the trade taken.

Both terms combine with each other and with bookingCode / customBookingId — every term sent must hold.

The date filter targets settledAt, not createdAt. settledAt is the business date — the column this list sorts by, and the only one of the two the model indexes. createdAt is when the row was typed. The two are written by the same insert today, because nothing back-dates a settlement, so filtering on either currently returns the same rows; settledAt is used because it is the column that carries the meaning, and it stays correct if back-dating is ever added.

⚠️ settledOn=D and settledFrom=D&settledTo=D are NOT the same window. The pair resolves in UTC and is inclusive at both ends; settledOn resolves on the Riyadh clock and is half-open at the top, so no settlement can fall in two days. For 2026-08-21 the pair selects [2026-08-21T00:00:00Z, 2026-08-21T23:59:59.999Z] while settledOn selects [2026-08-20T21:00:00Z, 2026-08-21T21:00:00Z) — a three-hour shift. Pick the one that matches how your report defines a day and use it consistently. The refund list behaves identically, by design.

4. Download the Transfer Proof ​

http
GET /api/v1/admin/shortfall-settlements/:id/proof

Streams the bank receipt uploaded with the settlement — the evidence that the money owed for the unticketed passengers actually left. Throttled at 30 req / 60s. Needs refunds:read.

Always Content-Disposition: attachment; this route never renders inline. The Content-Type is derived from the file bytes, not from the type recorded at upload — that recorded type is a string the uploading client chose, so nothing here trusts it. The bankProof.mimeType on the read shapes reports the recorded label, which is why a client must not branch on it to predict what a download will send.

A settlement carries at most one proof and there is no route that replaces or deletes it, so this always serves the file the settlement was created with.

The filename is sent in both forms — a plain ASCII filename for old clients and the RFC 5987 filename* for everything else. They read the same here because this name is plain ASCII. 5. Mint a No-Login Link to the Proof ​

http
POST /api/v1/admin/shortfall-settlements/:id/proof/link

For when the receipt has to appear in an <img src> or a plain browser tab, which the authenticated route above cannot do — an <img> sends no Authorization header, gets 401, and renders a broken-image box. Throttled at 20 req / 60s. Needs refunds:read.

Returns:

json
{
  "token": "f6cff8780de6d08f3eb8d72c",
  "expiresAt": "2026-08-13T08:35:41.758Z",

⛔ Anyone holding that URL can read the file, with no login and no permission check, until it expires. The proof is internal evidence about money returned to a customer, so treat the link exactly like the file: a URL pasted into a group chat is readable by everyone in that chat for the rest of the day. DELETE on the same path kills every live link for that settlement at once.

⚠️ A PDF proof downloads; it does not preview. Only bytes that prove to be a PNG, JPEG or WebP are served inline — everything else, PDF included, is forced to attachment. Uploads accept PDF, so a scanned receipt and a photographed one behave differently through the same link. If the screen needs a preview pane, expect it to work for phone photos and to trigger a download for scans.

The token resolves to this settlement's proof and nothing else, so a leaked token cannot be edited into another settlement's file. It is also not interchangeable with a token from POST /api/v1/storage/{fileId}/token: each redeem route accepts only its own, and the wrong one answers 404. See Storage.

Each redemption is logged with the settlement id and the admin who minted the link. In the audit-log copy of this response both token and url are stored as [REDACTED] — the URL carries the token verbatim, so redacting one without the other would leave the link readable — while expiresAt is kept. Reading the audit trail therefore does not hand anyone a live link.

7. Open a Minted Link (no authentication) ​

http
GET /api/v1/custom-booking/shortfall-proof/:token

⛔ This route takes no authentication. The token in the path is the entire capability. Throttled at 60 req / 60s. Documented in full on the customer surface, because it lives on that controller — see Custom Booking → Open a minted shortfall-proof link.

  • 200 — the file. inline for verified raster images, attachment otherwise.
  • 400 — the link has expired.
  • 404 — unknown token, a token belonging to a different rail, a file no longer stored, or a token whose settlement no longer points at it. One answer for all of them, so a holder cannot tell which.

Notes for frontend ​

  • Money fields are not gated here. The custom-booking routes hide their selling prices behind custom-bookings:read-pricing and their cost basis behind custom-bookings:read-capital-markup; neither is applied to any route on this page. Money owed back to a customer is not margin data, and these responses carry no selling price, cost or capital figure.
  • payoutReconciled: false is a review signal, not an error. The settlement is valid and the booking has moved. Surface it; do not retry it.
  • requiresApproval and approvedBy are the only things distinguishing a settlement from an approved bank refund in a shared row component. Render them.
  • Render the proof from bankProof, never from a file id. The block gives you filename, mimeType, sizeBytes, uploadedAt and a downloadUrl that is API-root-relative — prefix it with your API origin and call it with the admin bearer token. bankProofUploaded stays as the cheap boolean for a list badge.
  • An <img src> needs a minted link, not downloadUrl. The authenticated route answers 401 to an <img> tag, which sends no Authorization header. Mint one with POST :id/proof/link and use its url. ⚠️ Only bytes that really are a JPEG, PNG or WebP preview; a PDF downloads whatever you do — and bankProof.mimeType is the recorded label rather than the verified type, so it cannot tell you in advance which you will get. Handle both: render the link in an <img> and give the user a plain download link beside it.
  • After a settlement the booking is SHORTFALL_REFUNDED, from which the only moves are COMPLETED (a verification step needing custom-bookings:complete; it emails nobody, and neither does the settlement itself — the customer was mailed their tickets when the first ones were uploaded) or CANCELLED. A re-upload against a settled booking may restate the same count to replace a bad file but may not change it in either direction — see Custom Booking → §5.
