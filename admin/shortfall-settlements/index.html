Custom Booking Shortfall Settlements (Admin) ​

This guide covers the admin endpoints that record money returned to a customer for the passengers a ticket source could not ticket, and that move the booking from TICKET_UPLOADED_PARTIAL to SHORTFALL_REFUNDED.

For the upload that creates the shortfall in the first place, see Custom Booking → §5 Upload Ticket. For bank refunds against a cancelled booking — a different record type on the same screen — see Refund Management.

Permission-gated (Access Roles). Beyond the ADMIN role, these routes require a fine-grained permission. Creating a settlement needs its own dedicated code, refunds:shortfall-settlement (PERMISSIONS.REFUNDS_SHORTFALL_SETTLEMENT); both reads need refunds:read, the same code that gates bank-refund reads.

Why its own code, instead of reusing refunds:approve. Approving a bank refund pays out against a Refund row. This writes the booking into SHORTFALL_REFUNDED — a state no route can leave except by closing or cancelling the booking. That is a different act with a harder-to-undo consequence than approving a refund, so it should be granted deliberately rather than inherited from the refund-approval code.

No existing role has this code. It must be granted explicitly before any role can use this endpoint — a refunds:* wildcard holder does inherit it, but no seeded role lists it individually. See Access Roles.

⛔ This is the only writer of SHORTFALL_REFUNDED.PATCH /admin/custom-booking/:id/status refuses that value outright with a 400, deliberately: a status asserting that money moved must not be settable without a record of the money moving. There is no way to mark a booking settled without creating a settlement row.

Which wildcards satisfy them. * and refunds:* confer both codes. *:read confers refunds:read only — that wildcard matches actions literally named read, so a read-only role can list and inspect settlements but gets 403 on create. No seeded role carries refunds:shortfall-settlement on its own — it has to be granted before the create route can be used.

Rate limits. Create is throttled on the shared file-upload bucket at 10 req / 60s; both reads are throttled at 60 req / 60s.

What a shortfall settlement is ​

A ticket source under-delivers. The admin uploads what arrived and records how many passengers it actually covers, and because that count is below the seated total (adultCount + childCount; infants take no seat and are issued no ticket) the booking lands in TICKET_UPLOADED_PARTIAL with the signed shortfall report ("Berita Acara") attached.

The customer has paid for passengers who were never ticketed. Finance transfers that money back by hand, outside this system. This endpoint is the record of that transfer. It writes a settlement row, moves the booking to SHORTFALL_REFUNDED, and writes an audit entry naming the admin who did it.

TICKET_UPLOADED_PARTIAL is the only status a settlement can be created from — it is the one status with a shortfall outstanding. Every other status either has nothing owed or has already dealt with it, and COMPLETED in particular has no outgoing transition, so settling there would leave a closed booking asserting that money moved with no way to reflect it.

1. Record a Shortfall Settlement ​

http
POST /api/v1/admin/shortfall-settlements
Authorization: Bearer <admin-token>
Content-Type: multipart/form-data

Multipart, because the proof of transfer rides along in the same request.

Body Fields ​

FieldTypeRequiredNotes
customBookingIduuidYesThe booking whose shortfall is being settled. Must currently be in TICKET_UPLOADED_PARTIAL.
shortfallAmountSARnumberYesWhat the customer is owed, in SAR. The canonical accounting figure — every report and total reads it, and the settlement leg only describes how it physically moved. Max 2 decimal places, must be positive.
settlementCurrencyenumYesSAR, USD or IDR. The currency actually transferred.
settlementAmountnumberConditionalAmount transferred, in settlementCurrency. Max 2dp, positive. Must be sent together with settlementRateToSAR — see The currency contract.
settlementRateToSARnumberConditionalSAR per ONE unit of settlementCurrency. Stored at 8dp, but the smallest value you can SEND is 0.000001 — anything below that is written in exponential notation by the time it is validated and is rejected. Ample for every supported currency (IDR settles near 0.00024). Upper bound 9999999999. Same pairing rule.
referencestringYesBank transfer reference for the money that moved. Free text, max 255 chars, must not be empty. The only handle finance has on the transaction — the settlement record stores no destination account.
amountReasonstringNoHow the figure was reached — bank fee absorbed, goodwill, rounding, which passengers. Max 2000 chars. The only explanation the record carries.
proofFilefileNoProof of the transfer — normally a bank receipt or a screenshot.

proofFile accepted types: application/pdf, image/jpeg, image/png. Anything else answers 400 naming the rejected type. The file is stored in R2 with entityType: custom_booking_shortfall_proof, visibility: PRIVATE, attached to the booking — the customer never sees it.

It cannot be deleted, including by an admin. DELETE /storage/:fileId answers 403 for custom_booking_shortfall_proof and for custom_booking_shortfall_report: both are the evidence behind a refund, that route carries no permission check and writes no audit row, and the R2 delete is irrecoverable. Correct a wrong file by uploading a replacement. The rollback path is unaffected — a settlement whose status write loses the race still has its orphaned proof removed, because that runs internally rather than through the storage route.

Size limit. The request may carry at most 1 file part, capped at MAX_FILE_SIZE (default 52428800 bytes = 50 MiB). Multer uses memory storage and aborts the stream at the threshold rather than buffering the whole part and rejecting it afterwards; an oversized file answers 413. A second file part hits a different Multer limit (LIMIT_FILE_COUNT / LIMIT_UNEXPECTED_FILE) and Nest maps those to 400, not 413 — the size cap is the only 413 here.

Every scalar arrives as a string. The global pipe runs with enableImplicitConversion: false, so the DTO converts each number field explicitly. Send them as ordinary form fields — -F "shortfallAmountSAR=500" — and do not quote-wrap them as JSON.

A misspelled field is silently dropped, not rejected (whitelist: true, forbidNonWhitelisted: false). A typo'd settlementRateToSar therefore does not 400 on the typo — it 400s on settlementAmount and settlementRateToSAR must be provided together., which is the same error a genuinely missing rate produces. Check the spelling before assuming the pairing rule is wrong.

The currency contract ​

shortfallAmountSAR is what is owed. The three settlement fields describe what physically moved. They are separate on purpose: money can leave at an effective rate that no published rate row carries.

⚠️ Rate direction. settlementRateToSAR is SAR per ONE unit of settlementCurrency, so that settlementAmount × settlementRateToSAR ≈ shortfallAmountSAR.

This is the inverse of the SAR→IDR rate shown elsewhere in the admin UI. That surface shows 1 SAR = 4166.67 IDR; this field wants 1 IDR = 0.00024 SAR. Sending 4166.67 here claims a transfer worth roughly nine billion SAR — it is recorded anyway (see below), so the mistake surfaces as payoutReconciled: false rather than as a rejection. Stored at 8dp (Decimal(18,8)) precisely to keep IDR usable at that magnitude.

SAR — the identity case. Omit both figures.

shortfallAmountSAR: 500,  settlementCurrency: "SAR"
→ stored settlementAmount 500, settlementRateToSAR 1, settlementReconciled true

They are filled in as the SAR amount itself at a rate of 1. Sending them explicitly (500 and 1) is accepted and identical.

USD and IDR — both figures are required.

500 SAR owed, paid in USD at 3.75 SAR per USD
settlementCurrency "USD", settlementAmount 133.33, settlementRateToSAR 3.75
→ 133.33 × 3.75 = 499.9875 SAR   |diff| 0.0125 → settlementReconciled true

500 SAR owed, paid in IDR
settlementCurrency "IDR", settlementAmount 2083333, settlementRateToSAR 0.00024
→ 2083333 × 0.00024 = 499.99992 SAR   |diff| 0.00008 → settlementReconciled true

Neither may be omitted. A bank refund can fall back on a suggestion stored when the payout was initiated; a shortfall settlement never had one, because nothing here ever computed an amount. "Neither" would store a null amount alongside a reconciled flag that means nothing.

Reconciliation is recorded, never enforced.

The pair is checked against the owed SAR with a tolerance of 1 SAR, widened by |settlementAmount| × 1e-8 to absorb the pure storage error introduced by back-multiplying an 8dp rate against a high-magnitude IDR figure. For SAR and USD that slack is sub-cent and effectively a no-op; real divergences stay orders of magnitude above it.

A pair that falls outside tolerance is stored with payoutReconciled: false and a server-side warning — it is never rejected:

500 SAR owed, settlementCurrency "USD", settlementAmount 10, settlementRateToSAR 3.75
→ 10 × 3.75 = 37.5 SAR   |diff| 462.5  → settlementReconciled false, 201 Created

Why a divergence is not a 400. The money has already left. A bank fee or a rounding decision is a fact about the transfer, not grounds to refuse the record of it — refusing would leave the transfer real and unrecorded, which is strictly worse than recording it with a flag. Treat payoutReconciled: false as a review queue, not as a failure.

Rate provenance. For a non-SAR settlement the current rate row's id is resolved and stored as settlementExchangeRateId — provenance only, saying which published rate the figure was reached against. It is never read back to re-derive the amount; settlementRateToSAR on the row stays authoritative. If no rate row can be resolved the create still succeeds with a null pointer and a logged warning. The id is not emitted in the response.

⛔ For IDR, the lookup deliberately asks for the SAR rate row, not an IDR one. Rates are stored keyed on toCurrency, and there is no toCurrency = 'IDR' row — the SAR row is the IDR pair (its sellRate is IDR-per-SAR). resolveRateProvenance aliases IDR → SAR before calling getCurrentRate; calling getCurrentRate('IDR') directly would find nothing, so every IDR settlement would store a null pointer regardless of whether a current rate exists. USD is looked up as itself — only IDR gets the alias.

What this endpoint deliberately does NOT do ​

⛔ It computes nothing, suggests nothing, and validates the amount against nothing except that it is positive. There is no expectedAmountSAR field anywhere — not on the request, not on the response, not in the database. Whatever finance types is what is recorded.

The data needed to size a shortfall correctly is not on the booking:

  • ticketedPaxCount is one number. It says how many passengers were ticketed, never which ones. A booking short by one passenger does not record who that passenger was.
  • Adult and child prices differ. pricePerAdultSAR and pricePerChildSAR are separate figures, so "one passenger's worth" has no single value until you know which passenger was missed — which the previous point says you do not.
  • The stored per-passenger prices cover the outbound leg only. A round-trip shortfall cannot be sized from them without knowing which leg went unticketed.

Any figure this endpoint suggested would therefore be a guess wearing the authority of a computed number, and a wrong guess here sends the wrong amount of real money. So finance types the figure and amountReason keeps their reason for it. That free-text note is the only explanation the record carries — there is nothing to diff the number against.

No second approver ​

⚠️ Every settlement response carries requiresApproval: false and approvedBy: null. No dual-control flow exists for this record type. The admin who creates the settlement is the only human on the record.

This matters because of where these rows are rendered. The response field names deliberately overlap the bank-refund response so one frontend row component can render a Refunds screen with a bank-refund tab and a shortfall tab — and a bank refund on the neighbouring tab genuinely does carry a second approver. On a shared screen, a settlement nobody countersigned must never be mistaken for an approved bank refund. requiresApproval and approvedBy are what tell them apart; they are emitted on every row precisely so the FE never has to infer it from which tab it happens to be on.

The approvedBy column exists in the database and is written as an explicit null rather than left unset, so a later dual-control flow needs a code change and not a migration.

The frozen counts ​

The settlement row stores its own copy of expectedTicketCount, ticketedPaxCount and unticketedPaxCount rather than reading through to the booking.

This record has to keep saying what was owed on the day the money left, so it freezes the three figures at settlement time. NOT NULL columns, all three.

Freezing is belt-and-braces rather than the only defence: once a settlement exists the booking's ticketedPaxCount may no longer move at all. An upload may restate the same count to replace a bad file, but a raised or lowered count is refused on every status, including after a manager has closed the booking — see Custom Booking → §5. The frozen copies survive a hand-fixed row, which that guard cannot.

expectedTicketCount is adultCount + childCount. Infants are excluded — an infant takes no seat, so the ticket source issues nothing for one and nothing was ever owed for one. A 8 + 2 + 3 booking has an expected count of 10, not 13.

Order of checks ​

Worth knowing when debugging a 400, because the first failure wins:

  1. Validation — the DTO, before the handler runs.
  2. Proof MIME type — in the controller, before anything reaches R2 and before the booking is even loaded. An unsupported proof on a non-existent booking answers the MIME 400, not the 404.
  3. Booking exists → 404.
  4. Status is TICKET_UPLOADED_PARTIAL → 400.
  5. A ticketed count was recorded → 400.
  6. Something is actually outstanding → 400.
  7. shortfallAmountSAR does not exceed the booking total → 400.
  8. The currency pairing rule → 400.
  9. Rate provenance lookup (non-fatal), then the proof upload to R2, then the transaction: settlement row + status write + audit entry, together or not at all — plus the settlement table's own unique constraint, which turns a concurrent duplicate create into a 409 on the insert rather than a 500, before the status compare-and-set below even runs.

If the transaction fails — including on a lost race — any proof already uploaded is taken back out of storage, best-effort. An R2 call cannot take part in a database transaction, so the object goes up first and the cleanup catches it on the way down.

The refund-shaped names are deliberate, and the columns underneath are named differently. The database columns are shortfallAmountSAR, reference, settledAt, settledBy, settlementCurrency, settlementAmount, settlementRateToSAR, settlementReconciled, proofFileId. The response renames them to the refund vocabulary so one frontend row component renders both tabs. Do not "fix" the mapping to match the schema — the divergence is the feature.

Not emitted: proofFileId, settlementExchangeRateId, updatedAt, and — as above — anything resembling expectedAmountSAR.

Side Effect — Audit log ​

Every settlement writes an audit entry inside the same transaction as the settlement row and the status write, so the record of the money and the record of who moved it commit together or not at all.

action: CUSTOM_BOOKING_SHORTFALL_SETTLED, entity: CustomBooking, entityId = the booking id, with a newValue carrying settlementId, settlementSequence, shortfallAmountSAR, settlementCurrency, settlementAmount, settlementRateToSAR, settlementReconciled, expectedTicketCount, ticketedPaxCount, unticketedPaxCount, reference, proofFileId, statusBefore and statusAfter.

Unlike the ticket upload's audit — written after the fact and best-effort, because that path holds an R2 call open — a failure here rolls the whole settlement back.

Errors ​

Verbatim messages, with the interpolated values shown for a 10-seated-passenger booking with 9 ticketed (ABC1234, one passenger short):

  • 403 Forbidden — fires before every message below, because the permission guard runs ahead of the handler. The caller is not an ADMIN, or the role lacks refunds:shortfall-settlement. Body: {"message":"Forbidden resource","error":"Forbidden","statusCode":403}. ⚠️ A role holding only *:read gets this on create while both GETs succeed — the read-only wildcard confers refunds:read and nothing else.
  • 400 Bad Request — validation, raised by the pipe before the handler: customBookingId must be a UUID, shortfallAmountSAR must not be less than 0.01, shortfallAmountSAR must not be greater than 9999999999999.99, shortfallAmountSAR must be a number conforming to the specified constraints (more than 2 decimal places), settlementCurrency must be one of the following values: SAR, USD, IDR, reference should not be empty, reference must be shorter than or equal to 255 characters, amountReason must be shorter than or equal to 2000 characters. ⚠️ Not must be a positive number any more. The field dropped @IsPositive for a @Min(0.01) / @Max(9999999999999.99) pair — the DECIMAL column's ceiling, so an out-of-range insert 400s at the DTO instead of 500-ing on a numeric overflow inside the transaction. settlementAmount carries the same pair; settlementRateToSAR carries its own (@Min(0.000001) / @Max(9999999999)), each producing the matching must not be less/greater than <bound> message for that field.
  • 400 Bad Request — Unsupported proof type "application/zip". Allowed: application/pdf, image/jpeg, image/png. Raised by the controller before the file reaches storage and before the booking is loaded; the rejected type is echoed back.
  • 400 Bad Request — Cannot settle a shortfall when booking status is "PAID". Only TICKET_UPLOADED_PARTIAL has a shortfall outstanding. The quoted status is whatever the booking actually holds. Every non-partial status hits this, including SHORTFALL_REFUNDED itself — a second settlement against an already-settled booking is refused here.
  • 400 Bad Request — Booking ABC1234 is TICKET_UPLOADED_PARTIAL but has no recorded ticketed count, so there is no shortfall to size a settlement against. Defensive: only an upload writes that status and an upload always records a count, but the frozen columns are NOT NULL and this row is the basis of a refund, so it verifies rather than assumes.
  • 400 Bad Request — Booking ABC1234 has all 10 passenger(s) ticketed, so nothing is owed back. Fires when the recorded count has caught up with the expected count.
  • 400 Bad Request — Booking ABC1234 has no recorded value, so there is nothing for a shortfall to return part of. A booking whose totalPriceSAR is not a finite positive number is refused outright rather than having the ceiling skipped — skipping would leave the column maximum as the only bound on the figure.
  • 400 Bad Request — shortfallAmountSAR (600) exceeds what was paid for this booking. A shortfall returns part of what was paid, so it cannot be larger than the whole booking. Only the figure you sent is interpolated. Neither message names the booking total, deliberately: totalPriceSAR is stripped from every custom-booking response unless the caller holds custom-bookings:read-pricing, and this route is reachable with refunds:shortfall-settlement alone — quoting it back in a rejection would hand it over in a single request. A sanity ceiling, not a computed expectation — it doesn't contradict "nothing is computed" above, because it isn't sizing the shortfall. A shortfall only ever returns part of what the customer already paid, so the figure can never exceed the booking total regardless of which passenger or leg was missed.
  • 400 Bad Request — settlementAmount and settlementRateToSAR must be provided together. One without the other, in either direction, in any currency.
  • 400 Bad Request — settlementAmount and settlementRateToSAR are required for a IDR settlement. Only a SAR settlement can omit them, where the amount is the SAR figure itself at a rate of 1. The currency name is interpolated (USD reads the same way).
  • 404 Not Found — Custom booking not found.
  • 409 Conflict — two distinct causes, both translated from what would otherwise be a raw 500:
    • Cannot settle: booking ABC1234 moved while this request was in flight. Both its status and its recorded ticketed count are checked, so re-read the booking before retrying — the status alone may look unchanged. The status write is pinned to both the status and the recorded ticketed count. ⚠️ A concurrent ticket upload lands here too: a late top-up moves the booking to TICKET_UPLOADED_FULL and rewrites ticketedPaxCount, and a status-only pin would still match a row whose count had gone from 9 to 10 — freezing a stale unticketedPaxCount into a record claiming more money than was ever owed. So a booking that looks unchanged can still lose the race.
    • A settlement for booking 019f6ef6-8e81-724f-9faf-7e664b9bceee was recorded by another request. Re-read the booking before retrying — its shortfall may already have been settled. A concurrent duplicate create — two requests racing to settle the same booking. This one fires on the settlement table's unique constraint at insert time, before the status compare-and-set above ever runs, so it pre-empts the "booking moved" conflict rather than compounding it. Note the message quotes the raw customBookingId (the UUID), not the bookingCode the other 409 uses — a deliberate reminder that this is a different code path, not the same message with different values. Either way, any proof already uploaded is taken back out of storage.
  • 413 Payload Too Large — the proof file exceeded MAX_FILE_SIZE (default 52428800 bytes). Aborted mid-stream by multer rather than buffered and rejected — the same status the edge proxy returns for an oversized body, so the app and the edge agree on the answer. Size only — sending more than 1 file part is a different Multer limit (LIMIT_FILE_COUNT / LIMIT_UNEXPECTED_FILE), which Nest maps to 400 Bad Request, not 413.

2. List Shortfall Settlements ​

http
GET /api/v1/admin/shortfall-settlements

Paginated, newest settlement first. Throttled at 60 req / 60s. Needs refunds:read.

Query Parameters ​

ParamTypeDefaultNotes
pageinteger1Min 1.
limitinteger20Min 1, max 100 — inherited from the shared pagination DTO. The refund module's own list DTO does not inherit it and can be asked for an unbounded page; this one cannot.

Each row is the same shape as the create response, field for field — verified live by comparing this row against GET :id for the same settlement: the two bodies were byte-identical.

The envelope is { data, meta }, matching the rest of the admin API rather than the refund list's flat shape. meta.totalPages is guarded against a zero limit and reads 0 rather than Infinity — the refund list divides unconditionally.

Errors ​

  • 403 Forbidden — not an ADMIN, or the role lacks refunds:read.
  • 400 Bad Request — validation on the query params (a non-UUID customBookingId, a limit above 100, an unrecognised sortBy).

3. Get a Shortfall Settlement ​

http
GET /api/v1/admin/shortfall-settlements/:id

Returns the same shape as one list row, matching how the refund module already works. Throttled at 60 req / 60s. Needs refunds:read.

cURL ​

bash
curl -X GET /api/v1/admin/shortfall-settlements/019fd9e4-31ae-711b-bbef-604c25e086e2 \
  -H "Authorization: Bearer <admin-token>"

Errors ​

  • 403 Forbidden — not an ADMIN, or the role lacks refunds:read.
  • 404 Not Found — Shortfall settlement not found.

Notes for frontend ​

  • Money fields are not gated here. custom-bookings:read-pricing hides supplier cost and margin on the custom-booking routes; it is not applied to any route on this page. Money owed back to a customer is not margin data, and these responses carry no selling price, cost or capital figure.
  • payoutReconciled: false is a review signal, not an error. The settlement is valid and the booking has moved. Surface it; do not retry it.
  • requiresApproval and approvedBy are the only things distinguishing a settlement from an approved bank refund in a shared row component. Render them.
  • bankProofUploaded is a boolean with no file id behind it. There is no download link to build from this response.
  • After a settlement the booking is SHORTFALL_REFUNDED, from which the only moves are COMPLETED (which is what emails the customer their tickets, and needs custom-bookings:complete) or CANCELLED. A re-upload against a settled booking may restate the same count to replace a bad file but may not change it in either direction — see Custom Booking → §5.
