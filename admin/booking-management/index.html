StatusDescriptionCan CancelCan Modify
PENDINGAwaiting paymentYesLimited

Note: PENDING bookings have a payment expiry time. If payment is not completed before payment.expiresAt, the booking is automatically cancelled.

Admin cancel endpoint: The Can Cancel column above describes the overall booking lifecycle. The admin Cancel Booking endpoint specifically accepts only CONFIRMED and TICKETED bookings — PENDING cancellations are handled by payment-expiry auto-cancellation, not by manual admin cancel.

Booking Types ​

REGULAR Bookings ​

Standard bookings created with complete passenger information from the start.

  • Created with individual passenger details (names, documents, etc.)
  • Can be ticketed immediately after payment confirmation
  • Passenger data remains consistent throughout booking lifecycle

GROUP Bookings ​

Special bookings designed for B2B users who need to reserve capacity before collecting passenger details.

  • Created with passenger quantities only (no individual names)
  • Passenger names must be added later via modification
  • Can only be ticketed after all passenger data is complete
  • Includes completion tracking to monitor progress

http
GET /api/v1/admin/ota/bookings/:id/tickets
Authorization: Bearer <your-admin-jwt-token>

Path Parameters ​

ParameterTypeRequiredDescription
idstringYesThe booking ID (UUID). Resolve a booking code to its ID via GET /api/v1/ota/bookings/code/:bookingCode.

Response ​

Success (200 OK): Returns a ZIP file containing one PDF ticket (with a QR code) per passenger. The download filename is <bookingCode>.zip.

Content-Type: application/zip
Content-Disposition: attachment; filename=ABC1234.zip

Error Responses:

StatusDescription

Cancel Booking ​

Cancel a CONFIRMED or TICKETED booking on behalf of a user and process any applicable refund. This endpoint bypasses ownership restrictions, so admins can action customer cancellation requests, fraud cases, or policy violations.

http
POST /api/v1/admin/ota/bookings/:id/cancel
Authorization: Bearer <your-admin-jwt-token>
Content-Type: application/json

Path Parameters ​

ParameterTypeRequiredDescription
idstringYesThe booking ID (UUID)

Request Body ​

json
{
  "reason": "Customer requested cancellation via support ticket #12345",
  "skipRefund": false,
  "notifyUser": true
}
FieldTypeRequiredDefaultDescription
reasonstringYes—Cancellation reason, recorded in the audit trail. Max 1000 characters.
skipRefundbooleanNofalseSkip automatic refund queuing (use for manual/offline refund handling).
notifyUserbooleanNotrueSend cancellation email(s) to the booking contact.

Response ​

Success (200 OK):

json
{
  "bookingId": "01920a3b-7c4d-7e8f-9a0b-1c2d3e4f5a6b",
  "status": "CANCELLED",
  "refundStatus": "QUEUED",
  "cancelledBy": "ADMIN",
  "cancelledAt": "2026-01-30T10:00:00.000Z"
}
FieldTypeDescription
bookingIdstringCancelled booking ID
statusstringAlways CANCELLED on success
refundStatusstringQUEUED when a refund job is queued, QUEUE_FAILED if queuing failed (needs manual refund). Omitted when no refund applies or skipRefund is set.
cancelledBystringAlways ADMIN
cancelledAtstringISO 8601 cancellation timestamp

Allowed Statuses ​

Only CONFIRMED and TICKETED bookings can be cancelled through this endpoint.

Current StatusResult
CONFIRMEDCancelled; held funds released, refund queued if already charged
TICKETEDCancelled; refund queued per policy (may be partial)
CANCELLED400 — "Booking already cancelled"
PENDING / TICKETING_IN_PROGRESS / FAILED / EXPIRED400 — only CONFIRMED or TICKETED bookings can be cancelled

Time-limit override: Cancellation deadlines (the OTA-provided cancellationTimeLimit, or the fallback rule of 7 days before departure) are enforced for customers but bypassed for admins. The override is logged for audit.

Refund Behavior ​

PaymentBehavior
Wallet — funds only HELDReleased back to the wallet automatically (no refund job)
Wallet — already charged (DEBIT)Refund job queued (refundStatus: QUEUED)
Bank / QRIS / CardRefund job queued only when the invoice is PAID

skipRefund: true suppresses all refund queuing. Held wallet funds are still released.

OTA Cancellation Outcomes ​

If the booking has an OTA reference, the cancellation is forwarded to GO7 (Worldticket):

CaseBehavior
OTA accepts (or booking already cancelled on OTA)Booking cancelled locally
Non-ticketed booking + OTA 4xx hard reject (e.g. bad booking state)Cancelled locally anyway — no tickets were issued
Ticketed booking + any OTA error, or any OTA 5xxCancellation blocked — error passed through with error: "Cancellation Rejected". Retry once OTA recovers.

Error Responses ​

StatusDescription
400 Bad RequestBooking status not cancellable / already cancelled
401 UnauthorizedMissing or invalid token
403 ForbiddenAdmin role required
404 Not FoundBooking not found
4xx / 5xxOTA rejected the cancellation (error: "Cancellation Rejected")

Payment Expiry & Auto-Cancellation ​

Administrators should understand the automatic payment expiry system that handles unpaid bookings.

How Payment Expiry Works ​

  1. Dynamic Time Limit: Payment expiry is calculated from OTA ticketTimeLimit minus a 2-minute buffer
  2. Default: 24 hours if no OTA time limit is provided
  3. Scheduled Jobs: Each booking gets a BullMQ delayed job scheduled for expiry
  4. Auto-Cancellation: At expiry time, if payment is still PENDING, booking is cancelled automatically
  5. Webhook Backup: Xendit webhooks also trigger expiry handling for redundancy

Why 2-Minute Buffer? ​

The 2-minute buffer before GO7's ticketing deadline ensures:

  • Late webhooks from Xendit can still be processed
  • System can safely cancel the booking before GO7's hard limit
  • Prevents failed ticketing attempts after payment window closes

Identifying Auto-Cancelled Bookings ​

When filtering bookings, auto-cancelled bookings will have:

  • status: "CANCELLED"
  • payment.status: "EXPIRED" in the payments array
  • payment.expiresAt timestamp in the past

Admin Actions for Expired Payments ​

Can I extend a payment time limit?

No, payment time limits are enforced by the payment gateway (Xendit) and cannot be extended. Customers must create a new booking.

Can I recover an auto-cancelled booking?

No, once a booking is auto-cancelled due to payment expiry, it cannot be recovered. The inventory is released back to OTA.

Common customer inquiries:

Customer QuestionAdmin Response
"Why was my booking cancelled?""Payment was not completed within the time limit. Please create a new booking."
"Can I get more time to pay?""Payment time limits are set by the system and cannot be extended."
"My payment expired, can you restore my booking?""Once expired, bookings cannot be restored. Please create a new booking."

Monitoring Payment Expiry ​

To monitor payment expiry issues:

bash
# Find all auto-cancelled bookings from last 7 days

// API Functions

async function getAllBookings(
  filters?: {
    page?: number;
    limit?: number;
    search?: string;
    status?: string;
    bookingCode?: string;
    userId?: string;
    organizationId?: string;
    createdDateFrom?: string;
    createdDateTo?: string;
    departureDateFrom?: string;
    departureDateTo?: string;
    sortBy?: string;
    sortOrder?: 'asc' | 'desc';
  }
): Promise<AdminBookingsResponse> {
  const params = new URLSearchParams({
    page: String(filters?.page || 1),
    limit: String(filters?.limit || 20),
    ...(filters?.search && { search: filters.search }),
    ...(filters?.status && { status: filters.status }),
    ...(filters?.bookingCode && { bookingCode: filters.bookingCode }),
    ...(filters?.userId && { userId: filters.userId }),
    ...(filters?.organizationId && { organizationId: filters.organizationId }),
    ...(filters?.createdDateFrom && { createdDateFrom: filters.createdDateFrom }),
    ...(filters?.createdDateTo && { createdDateTo: filters.createdDateTo }),
    ...(filters?.departureDateFrom && { departureDateFrom: filters.departureDateFrom }),
    ...(filters?.departureDateTo && { departureDateTo: filters.departureDateTo }),
    ...(filters?.sortBy && { sortBy: filters.sortBy }),
    ...(filters?.sortOrder && { sortOrder: filters.sortOrder }),
  });

  const response = await fetch(
    `/api/v1/admin/ota/bookings?${params}`,
    {
      method: 'GET',
      headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${getAdminToken()}`,
      },
    }
  );

  if (!response.ok) {
    throw new Error(`Failed to fetch bookings: ${response.statusText}`);
  }

  return await response.json();
}

Stuck Booking Management ​

Bookings can become "stuck" in intermediate states when the ticketing process fails or is interrupted. The system automatically detects and attempts to recover stuck bookings, but manual intervention may be required in some cases.

Understanding Stuck Bookings ​

Two types of stuck bookings:

TypeStatusThresholdDescription
Ticketing In ProgressTICKETING_IN_PROGRESS> 15 minutesBooking started ticketing but never completed
Confirmed Not TicketedCONFIRMED> 10 minutesPayment received but ticketing never started

Why bookings get stuck:

  1. Incomplete Passenger Data (B2B GROUP bookings) - User must complete passenger names first
  2. Max Retries Exceeded - System tried 3 times but failed
  3. OTA System Errors - GO7 API temporarily unavailable
  4. Non-Retryable Errors - Duplicate passenger ID, invalid data, etc.

Admin Follow-Up Trail ​

A structured log of what an admin has done about a booking. The system never auto-notifies customers about stuck bookings — every action recorded here is admin-initiated.

The trail is a pure audit record: what was done, by whom, when. It does not suppress the stuck queue. Each item in GET /bookings/queue/stuck exposes the most recent entry via latestFollowUp so admins can see at a glance whether a booking has already been chased.

Common Stuck Booking Scenarios ​

Scenario 1: B2B GROUP Booking - Incomplete Passenger Data ​

Symptoms:

  • Status: CONFIRMED_NOT_TICKETED
  • passengerCompletionCount < passengerCount
  • isPassengerDataComplete: false

Action:

  1. Contact B2B customer to complete passenger names
  2. Or use PATCH /bookings/:id/modify to add passenger names (Type 40)
  3. Ticketing will auto-trigger once data is complete

Scenario 2: Max Retries Exceeded ​

Symptoms:

  • ticketingRetryCount: 3 (or max value)
  • latestFollowUp is null or shows prior unsuccessful actions
  • Status history shows persistent failures across retries

Action:

  1. Pull GET /admin/ota/bookings/:id/status-history to see what each attempt did — the reason and metadata fields explain the failure pattern.
  2. For raw OTA error payloads (HTTP status, OTA error codes), pull GET /admin/third-party-errors?bookingId=<id>.
  3. If the error was temporary (OTA timeout, 5xx) and the cause is now fixed → retry manually via POST /bookings/:id/retry-ticketing (this bypasses the auto-retry cap).
  4. If the error is permanent (duplicate ID, invalid passport, fare expired) → cancel with refund via POST /bookings/:id/cancel.

Scenario 3: Stuck in TICKETING_IN_PROGRESS ​

Symptoms:

  • Status: TICKETING_IN_PROGRESS for > 15 minutes
  • May have partial tickets issued

Action:

  1. Check if any tickets were issued (download tickets endpoint)
  2. If partial success, retry to complete remaining
  3. If no tickets, investigate error before retrying

How It Works ​

List All Bookings ​

  1. Query Building: Constructs database query based on provided filters
  2. Search: If search is provided, searches across booking code, user name, user email, organization name, and organization code
  3. Pagination: Applies page and limit for efficient data retrieval
  4. Sorting: Sorts results by specified field and order

Download Tickets (Admin) ​

  1. Authorization: Verifies the user has ADMIN role
  2. Booking Lookup: Finds the booking by booking code
  3. OTA Reference Check: Ensures the booking has an OTA booking reference
  4. Download: Fetches tickets from GO7 API and returns as PDF

Resend Cancellation Email ​

  1. Fetch Booking: Retrieves booking with user and organization details
  2. Validate Status: Verifies the booking is in CANCELLED status
  3. Check OTA Reference: Ensures the booking has an OTA booking reference (GO7 record locator)
  4. Determine Recipients: Uses provided emails or defaults to the booking user's email
  5. Call GO7 API: Sends the request to GO7's /notifications/cancellation-email endpoint
  6. Create Audit Log: Records the action with admin user details and email recipients

Resend Ticket Confirmation Email ​

  1. Fetch Booking: Retrieves booking with user and organization details
  2. Validate Status: Verifies the booking is in TICKETED status
  3. Check OTA Reference: Ensures the booking has an OTA booking reference (GO7 record locator)
  4. Extract Passengers: Extracts passenger names from booking data (REGULAR or GROUP booking structure) if not provided in request
  5. Determine Recipients: Uses provided emails or defaults to the booking user's email
  6. Call GO7 API: Sends the request to GO7's /notifications/email endpoint with passenger data
  7. Create Audit Log: Records the action with admin user details, email recipients, and passenger count

  3. Use the "Download Tickets" endpoint to get the PDF

  1. Find the booking using the "List All Bookings" endpoint
  2. Verify the booking status is CANCELLED
  3. Use the "Resend Cancellation Email" endpoint
  4. Optionally add your email as CC to verify delivery

curl -X POST "/api/v1/admin/ota/bookings/:id/resend-cancellation-email" \
  -H "Authorization: Bearer <token>" \

Ticket Confirmation Email Issues ​

When a customer reports they didn't receive their ticket confirmation email:

  1. Find the booking using the "List All Bookings" endpoint
  2. Verify the booking status is TICKETED
  3. Use the "Resend Ticket Confirmation Email" endpoint
  4. Optionally add your email as CC to verify delivery

Stuck Booking Recovery ​

When a booking is stuck in TICKETING_IN_PROGRESS:

  1. Check stuck bookings queue:

    bash
    curl -X GET "/api/v1/admin/ota/bookings/queue/stuck" \
  -H "Authorization: Bearer <token>"

  2. Get booking details to investigate:

    bash
    curl -X GET "/api/v1/admin/ota/bookings/:id" \
  -H "Authorization: Bearer <token>"

  3. Inspect the ticketing/lifecycle trail to see what each attempt did and why it failed:

    bash
    curl -X GET "/api/v1/admin/ota/bookings/:id/status-history" \
  -H "Authorization: Bearer <token>"

    For raw OTA error payloads (HTTP status, OTA error codes, request/response bodies), also pull:

    bash
    curl -X GET "/api/v1/admin/third-party-errors?bookingId=:id" \
  -H "Authorization: Bearer <token>"

  4. Retry ticketing (if the underlying cause is fixed):

    bash
    curl -X POST "/api/v1/admin/ota/bookings/:id/retry-ticketing" \
  -H "Authorization: Bearer <token>"

  5. Monitor for completion (check booking status after a few minutes)

B2B GROUP Booking - Passenger Data Incomplete ​

When a B2B booking is stuck due to incomplete passenger data:

  1. Identify the booking:

    bash
    curl -X GET "/api/v1/admin/ota/bookings/queue/stuck" \
  -H "Authorization: Bearer <token>"

  2. Contact B2B customer to complete passenger names in their portal

  3. Or add passenger names via admin modify API:

    bash
    curl -X PATCH "/api/v1/admin/ota/bookings/:id/modify" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "modificationType": 40,
    "passengers": [
      {
        "rph": "1",
        "firstName": "John",
        "lastName": "Doe",
        "idType": "PASSPORT",
        "idNumber": "A12345678",
        "nationality": "ID"
      }
    ]
  }'

  4. Ticketing will auto-trigger once all passenger data is complete

Cancel Booking After Max Retries ​

When a booking has exceeded max retries and cannot be ticketed:

  1. Verify the booking status and retry count

  2. Cancel with refund:

    bash
    curl -X POST "/api/v1/admin/ota/bookings/:id/cancel" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "reason": "Ticketing failed after max retries - system error",
    "skipRefund": false,
    "notifyUser": true
  }'

  3. Notify customer about the cancellation and refund

The system uses OTA-provided refund data as the source of truth when available:

SourceDescription

FieldTypeDescription

5-50 SARwarningPolicy differences, logged for review
> 50 SARerrorSignificant discrepancy, flagged for admin review
