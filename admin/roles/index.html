Access Roles & Permissions Guide ​

This guide explains how administrators manage Access Roles, fine-grained permissions, and admin assignments.

Product term: "Access Role". The API model is still named AdminRole, but the product/UI term is Access Role to avoid confusion with the coarse account-type. There are two distinct layers:

  • Account type — the UserRole enum (ADMIN vs customer). Decides who may log into the admin surface at all.
  • Access Role — a named permission bundle (Super Admin, Kurs Inputter, …). Decides what an admin can do.

Every admin is one ADMIN account plus one-or-more Access Roles. A new job function (e.g. "Kurs Inputter") is a new Access Role bundle created at runtime, not a new account-type.

Quick Overview ​

FeatureDescription
PurposeManage Access Roles and fine-grained permissions
AccessAdmin only; mutating endpoints require roles:manage / roles:assign
ScopeAll admin users and their permissions

Enforcement & Protections ​

Permissions are enforced by PermissionsGuard, which layers inside the account-type gate: jwt → RolesGuard (ADMIN) → PermissionsGuard.

  • Default-allow rollout. A route with no @RequirePermissions decorator passes any ADMIN through (so un-migrated routes keep working). A route only locks down once its decorator is added. Enforcement is being rolled out controller-by-controller. Today the Access Roles, Users, Exchange Rate, and the finance controllers are permission-gated: Refunds (incl. Refund Bank Eligibility), Payments, Manual Transfer (proofs, payments, bank accounts), Payment Gateway config + fees, Wallet (admin routes only), Invoices (admin routes only), and Banks. The pricing controllers are now gated too: Tax, Special B2B Tax, Custom Tax, Tariff (tariffs + pricing config + deprecated locations), Custom Markup, Special B2B Markup, Pricing, Special B2B Pricing (incl. the ECONOMY tier auto-update trigger), Custom Route Price, Mitra Pricing Config, Ticket Channels (channels + route prices), and Scraper Price. The bookings and operations controllers are now gated too: Custom Booking, Custom Booking Manifests, BlockSeat Bookings, OTA Bookings (incl. reports, cancellation/ticket-email resends, retry-ticketing, follow-ups, and cache refresh), Fare Preferences, Organizations (incl. pricing-tier, promo-access, and public API access toggles), Impersonation (act as customer), Partners, and Partner API Keys. The reference, system, and comms controllers are now gated too: Railway Stations, Office Locations, System Config (incl. the hidden fee/tax/wallet-topup endpoints), WhatsApp (management via whatsapp:manage, sandbox test-sends via whatsapp:send), Email (raw provider send via email:send), Audit Logs (read via audit-logs:read, export via audit-logs:export), and the ADMIN-only Third-Party Error detail route (third-party-errors:read). The partner-onboarding review controllers are now gated too: Mitra Registrations (mitra-registrations:read / :review) and B2B Applications (b2b-applications:read / :review). For both, the two GET routes need :read while mark-under-review, approve, and reject share :review — so granting :review also grants provisioning (creating the organization and wallet, and for mitra the registration number and pricing-tier flags). The public applicant endpoints for both are on separate controllers and stay ungated.
  • Notifications and Third-Party Errors are now gated. Both areas used to run on the plain ADMIN/SUPPORT role check with no permission decorator, which PermissionsGuard serves to any caller — its default is to allow a route that requires nothing. Notifications take notifications:read / :send / :delete; the error log takes third-party-errors:read for the list, stats and detail routes and third-party-errors:update for the two status writes. The deferral used to be justified by keeping SUPPORT accounts working, but no such account can hold a permission in the first place: PermissionsGuard refuses any caller whose role is not ADMIN.
  • GET users/me/permissions is never gated — every admin can read their own effective permissions so the FE can render menus/buttons.
  • Live read. Effective permissions are read from the DB per gated request, so assigning/revoking a role or editing its permissions takes effect immediately — no re-login.
  • Self-healing Super Admin bootstrap. On every boot the service idempotently ensures the Super Admin role exists and that admin@ahlaan.co.id holds it, so enabling enforcement can never lock the operator out — even on a DB where the seed never ran.

How a permission is matched ​

A gated route declares one or more required codes. The guard grants access if the admin's effective permissions satisfy any of them, checked in this order:

  1. * — super admin, matches everything.
  2. Exact match — the required code is present verbatim.
  3. <resource>:* — matches any action on that resource.
  4. *:read — matches only when the required action is literally read.

An admin with no Access Role has effective permissions [], so every gated route returns 403. This is the usual cause of "my ADMIN account suddenly gets 403": the account type is fine, the Access Role is missing.

Denied response shape ​

Every permission denial is a plain 403 from the guard, before the route handler runs:

json
{
  "message": "Forbidden resource",
  "error": "Forbidden",
  "statusCode": 403
}

Because the guard runs first, a denied caller cannot distinguish a real record from a missing one. Holding the permission and hitting an unknown id returns the handler's 404 instead — this is the practical way to tell "not allowed" from "not found":

CallerPOST /admin/mitra-registrations/<unknown-id>/approve
Has mitra-registrations:review404 {"message":"Mitra registration not found",…}
Lacks it403 {"message":"Forbidden resource",…}

users:* is a customer-administration grant. It does not carry the staff writes in the four rows above: each of those is decided by Super-Admin status (or refused outright), not by a permission code, so widening someone's users: codes never hands them an admin account. The reasoning is in Users Management → staff rows are not ordinary rows.

Every Access Role mutation (create / update / deactivate / assign / revoke) and every admin deactivation writes an audit-log entry (actor, target, before/after permissions).

Workflow: set up a new admin end to end ​

This walkthrough uses the real Kurs Admin on preprod — a live, least-privilege admin whose Access Role grants exactly two permissions. Every request and response is captured verbatim from the running service; only passwords are masked.

Admin accountkurs@ahlaan.co.id ("Kurs Admin"), id 019f8eb3-df30-75c4-bf22-bd725205bedf
Access RoleKurs Manager, id 019f8eb3-a9ce-7628-9cf3-2ffed2fa7961
Permissionsexchange-rates:read, exchange-rates:update

The point of the example: this admin can read and input the exchange rate and nothing else — not even trigger a rate sync, and not the role builder itself.

Step 1 — sign in as an admin who may manage roles ​

Creating roles needs roles:manage; assigning them needs roles:assign. A Super Admin (*) has both.

bash
curl -X POST https://preprod.mitra.ahlaan.co.id/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@ahlaan.co.id","password":"********"}'

201 Created — use accessToken as the bearer token for every call below.

Step 2 — read the permission catalog ​

This is what the role-builder checkbox matrix is built from. It currently returns 43 resources / 124 permission codes.

bash
curl https://preprod.mitra.ahlaan.co.id/api/v1/admin/roles/permissions/catalog \
  -H "Authorization: Bearer $TOKEN"

Requires roles:read. An admin without it — including the Kurs Admin below — gets 403 here. Only admins who may build roles can load the builder.

Step 3 — create the Access Role ​

bash
curl -X POST https://preprod.mitra.ahlaan.co.id/api/v1/admin/roles \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{
    "name": "Kurs Manager",
    "description": "Read and modify exchange rate (kurs) only",
    "permissions": ["exchange-rates:read", "exchange-rates:update"]
  }'

201 Created:

json
{

}

The built-in Kurs Inputter template carries these exact two codes, so this role can equally be created from the template rather than hand-picked. See Get Predefined Role Templates.

Step 4 — create the admin account with the role attached ​

POST /admin/users accepts roleIds, so the account and its Access Role links are created in one transaction. role is the account type; roleIds are the Access Roles. This additionally requires the caller to hold roles:assign.

bash
curl -X POST https://preprod.mitra.ahlaan.co.id/api/v1/admin/users \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{
    "name": "Kurs Admin",
    "email": "kurs@ahlaan.co.id",
    "password": "********",
    "role": "ADMIN",
    "roleIds": ["019f8eb3-a9ce-7628-9cf3-2ffed2fa7961"]
  }'

The response is the created user object — see Users for its full shape. The two-step flow (create the admin, then assign) also works and is covered in Assign Role to User.

Step 7 — confirm the gate actually holds ​

All of the following use the same Kurs Admin token:

RequestStatusWhy

GET /admin/exchange-rate/history200has exchange-rates:read

Note the last three: an admin cannot see the role builder unless it holds roles:read. The 403 body is identical in every case:

json
{
  "message": "Forbidden resource",
  "error": "Forbidden",
  "statusCode": 403
}

exchange-rates:sync returning 403 while the reads return 200 is the whole point — the account type is ADMIN for all of them, and only the Access Role separates them.

Step 8 — widen a role, no re-login needed ​

bash
curl -X PATCH https://preprod.mitra.ahlaan.co.id/api/v1/admin/roles/<role-id> \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"permissions": ["exchange-rates:*"]}'

With the same, already-issued JWT the admin immediately sees the new list from users/me/permissions, and POST /admin/exchange-rate/sync stops returning 403. Verified on preprod with a resource wildcard: it opened the matching routes while every other resource stayed 403, so <resource>:* never leaks sideways.

Permissions are read from the DB on every gated request. Editing a role, assigning it, or revoking it takes effect on the next request. Never cache permissions in the FE beyond a page session, and never require the user to log out and back in.

Step 9 — revoke, and confirm it takes effect immediately ​

bash
curl -X DELETE https://preprod.mitra.ahlaan.co.id/api/v1/admin/roles/users/<user-id>/roles/<role-id> \
  -H "Authorization: Bearer $TOKEN"
json
{ "message": "Role revoked successfully" }

On the very next request with the unchanged JWT, users/me/permissions returns {"permissions":[]} and every gated route returns 403.

Step 10 — deactivating a role revokes it from everyone ​

DELETE /admin/roles/:id is a soft deactivate. The row survives with isActive: false, and affectedUsers reports how many assignments it had:

json
{ "message": "Admin role deactivated successfully", "affectedUsers": 1 }

Afterwards, for every admin who held it:

  • GET /admin/roles/users/:userId/roles → [] (the list filters to active roles)
  • GET /admin/roles/users/me/permissions → {"permissions":[]}
  • every gated route → 403

The assignment rows are not deleted, so re-activating the role with PATCH {"isActive": true} restores access to the same admins.

Endpoints ​

1. Create Admin Role ​

Endpoint: POST /admin/roles

Create a new admin role with specific permissions.

Request Body:

json
{
  "name": "Kurs Manager",
  "description": "Read and modify exchange rate (kurs) only",
  "permissions": ["exchange-rates:read", "exchange-rates:update"]
}

Permissions use the format <resource>:<action> (colon-separated). Wildcards are supported: * (super admin), <resource>:* (all actions on a resource, e.g. invoices:*), and *:read (read access to all resources).

Codes are validated against the catalog. An unknown code — including a well-formed typo like exchange-rates:raed — is rejected with 400 and the offending code is named in the message, so an operator cannot silently create a role that grants nothing. Build the editor from catalog checkboxes anyway; the 400 is a backstop, not a UX.

Errors:

CaseStatusBody
Duplicate name409{"message":"An Access Role named \"Kurs Manager\" already exists","error":"Conflict","statusCode":409}
Empty permissions400{"statusCode":400,"error":"Bad Request","message":["permissions must contain at least 1 elements"],"code":"INPUT_VALIDATION","category":"VALIDATION",…}
Unknown or malformed code400Invalid permissions: <offending codes>

PATCH returns the same 409 when a rename collides with an existing role.

Response: 201 Created

json
{
  "id": "019f8eb3-a9ce-7628-9cf3-2ffed2fa7961",
  "name": "Kurs Manager",
  "description": "Read and modify exchange rate (kurs) only",

6. Deactivate Admin Role ​

Endpoint: DELETE /admin/roles/:id

Soft delete a role by setting isActive to false. affectedUsers reports how many assignments were on the role at deactivation.

Response: 200 OK

json
{
  "message": "Admin role deactivated successfully",
  "affectedUsers": 1
}

It is the only AND-gated code in the admin API. Held apart from update so the admin who uploads the ticket file is not automatically the person who certifies it.

⚠️ A separate code stands between the customer and an unverified file. An upload emails nobody. custom-bookings:verify-ticket gates the release that opens the customer's download and sends their one automatic email (see Release or Reject a Ticket), and custom-bookings:upload-ticket does not confer it. Grant upload-ticket on the understanding that a mistaken upload sits held, downloadable by no one but an admin, until a verify-ticket holder releases or rejects it.

No existing role receives it. Role permissions are literal string arrays, so only holders of * or custom-bookings:* inherit it — everyone else must be granted it explicitly. A manager left without it cannot close any booking. COMPLETED is the only non-cancel exit from three statuses — TICKET_UPLOADED_FULL, SHORTFALL_REFUNDED and the legacy TICKET_RECEIVED — so bookings pile up on whichever of those they reached and are never finalized. On the first two, whether the customer can already download their tickets depends on whether a verify-ticket holder has released the booking — once released, the backlog is internal; until then the customer sees no sign a ticket exists either way. TICKET_RECEIVED predates that flow and no transition enters it. Audit roles before deploying.

Field-level codes — permissions that hide fields, not routes ​

Most codes decide which endpoints a role may call. Three decide which fields come back from an endpoint the role may already call:

CodeHides, when absent
custom-bookings:read-pricingthe top-level SELLING keys on every admin custom-booking response — the six selling prices, the nested invoice, manualTransfer, the per-leg refund estimate and shortfallSettlement. ⚠️ It hides the keys, not the figures, from a caller who also holds read-capital-markup: pricingSnapshot carries the per-leg charged per-pax prices verbatim and yields the three totals. See Custom Booking (Admin).
custom-bookings:read-capital-markupthe COST BASIS on the same responses — capitalPriceTotalSAR, pricingSnapshot and exchangeRate, plus invoice.metadata.exchangeRate, which is a second copy of the effective rate. See Custom Booking (Admin).
invoices:read-supplier-costpricing.supplier and the exchangeRate block on both admin invoice reads. See Invoices (Admin).

⚠️ The two custom-booking codes are independent in both directions. Holding read-pricing does not confer read-capital-markup, and holding read-capital-markup does not confer read-pricing. That is what makes a quote-only role possible: it sees what the customer is charged and never what we paid the channel.

Only that direction is a boundary. The reverse — read-capital-markup without read-pricing — removes the selling-price keys but not the selling prices: pricingSnapshot rides on the cost code, carries the per-leg charged per-pax prices verbatim, and yields the three totals from its frozen rates. Build cost-only roles for tidiness if you like; do not build them for confidentiality.

Three things follow, and they are the ones that trip people up:

  1. The withheld keys are absent, not null. Branch on key presence, not on a null check.

  2. *:read confers none of them. Each uses an action segment that is not literally read (read-pricing, read-capital-markup, read-supplier-cost), and *:read matches only read. That is the whole mechanism — it is what lets a role built as "read-only, harmless" stop carrying our cost basis.

  3. <resource>:* and * still confer them, exactly like any other code. So ticking a single "Custom Bookings" wildcard row grants both custom-booking money codes straight back. That is why both of those resources carry explicitOnly in the catalog: the picker must render them action-by-action, or the code is only ever grantable invisibly.

    refunds and ticket-channels carry explicitOnly for the neighbouring reason rather than this one — they hide no fields, but they hold refunds:shortfall-settlement, which gates a route that moves money, and ticket-channels:update, which writes the route-price rows the capital resolver bills a booking from. A single wildcard row on either would confer those just as invisibly.

Codes that are not self-sufficient ​

The traps above are about a code hiding fields. There is a second class: a code that gates the route it names, while the admin screen that fires it makes an earlier call gated by a different code. Granting only the obvious code produces a role that looks correct in the picker and fails in the UI.

CodeAlso needsWhy
custom-bookings:upload-ticketcustom-bookings:write-capital — in the UI onlyThe admin ticket-upload screen is two calls: PATCH /admin/custom-booking/:id/source to attach the ticket channel, then POST .../ticket with the file. The first is a capital route. A role holding only upload-ticket gets 403 on it and never reaches the upload. The upload route itself needs no capital code, so this dependency disappears the day the screen stops chaining the calls.
custom-bookings:completecustom-bookings:updateClosing a booking is PATCH .../status, whose guard demands custom-bookings:update. A role holding only complete never reaches the handler that checks it — the two are an AND, and complete alone gates nothing.

Two codes that look like they belong in this table are resolved in the guard instead. The capital screen lists ticket channels before it patches one, and so does the channel-edit screen; rather than pair each role with a second code, the routes accept the codes those screens already hold:

  • GET /admin/ticket-channels and GET /admin/ticket-channels/:id accept ticket-channels:read, ticket-channels:update or custom-bookings:write-capital.
  • The route-price reads under a channel accept ticket-channels:read or ticket-channels:update — never the capital code.

So do not add ticket-channels:read to a capital role to "fix" a 403 on the channel picker, and especially not the ticket-channels wildcard, which carries ticket-channels:update and with it the route-price writes. See Ticket Channels.

For upload-ticket, the two 403 bodies are byte-identical, so the operator reports "ticket upload is broken" while the upload permission is in fact correct — diagnose by which request failed, not by the response body. The complete pair is the opposite: the guard's 403 is the generic Forbidden resource, while the missing-complete 403 carries its own message, so the two are told apart by the body alone.

Recipe — a ticket-upload role that sees zero money:

custom-bookings:read
custom-bookings:write-capital
custom-bookings:upload-ticket
custom-manifests:read

No read-pricing, no read-capital-markup, no invoices:read. The role gets the booking summary, the passengers, the manifest and the ticket — and no figure anywhere.

write-capital is in the list because of the two-call chain above, not because this role edits pricing. It confers neither read code, so the zero-money property survives: the role may write a cost basis it cannot read back. It does confer the two channel reads, which is what makes the picker on that screen work, and those return no money either — a channel is id, name, isActive and timestamps, and the route prices hanging off it take a ticket-channels code this role holds neither of. Drop write-capital and the role can no longer upload through the admin screen — the POST .../ticket route itself still accepts it, so a client that uploads without attaching a channel works on the remaining three codes.

Recipe — a verifier who closes bookings but never uploads:

custom-bookings:read
custom-bookings:update
custom-bookings:complete

Deliberately no upload-ticket: the point of the split is that the person who files the ticket is not the person who certifies it. Add custom-bookings:read-pricing only if this role is also meant to see selling prices, and custom-bookings:read-capital-markup on top of that only if it is meant to see the cost basis too.

Recipe — booking support that quotes prices off the booking screen but never sees our margin:

custom-bookings:read
custom-bookings:read-pricing

Every selling figure on the booking detail is visible — the per-pax prices, the three totals, the invoice block, the manual-transfer amount and the refund estimate — while capitalPriceTotalSAR, pricingSnapshot and exchangeRate are absent. This is what custom-bookings:read-capital-markup was added for.

Two things this role gives up, both of them deliberate:

  • the per-leg price breakdown, which lives inside pricingSnapshot rather than at the top level. Quoting works off the six top-level selling figures.
  • the "SAR Exchange Rate" and "Total Refund (IDR)" lines of the Berita Acara sheet, which read exchangeRate.sellRate. A role that prints that document needs read-capital-markup as well — see Custom Booking (Admin).

Recipe — the same question answered from the invoice instead:

custom-bookings:read
invoices:read

The invoice amount is visible; supplier cost, the effective exchange rate, the capital price and the pricing snapshot are not. Prefer the recipe above when the figures are being read off the booking screen; this one is for a role whose work already lives in the invoice module.

Predefined Role Templates ​

Templates are blueprints, not live rows. GET /admin/roles/templates returns 7 suggested bundles for the "create role from template" UI. They are not the roles in your database — those come from GET /admin/roles. Editing a template in code changes only what a newly created role is pre-filled with; it never retro-fits an existing role. To change what an existing role grants, PATCH /admin/roles/:id.

None of the 7 templates includes mitra-registrations:* or b2b-applications:*. Now that those two controllers are gated, a role built from any template other than Super Admin cannot approve or reject mitra registrations or B2B applications, and only Reports Viewer (via *:read) can even list them. Grant the codes explicitly to the reviewers who need them.

Super Admin ​

Full system access - can perform all administrative operations.

Permissions: *

Best for: System owners, CTO, technical founders

  • users:*
  • organizations:*
  • audit-logs:read

  • pricing:*
  • refunds:read

  • refunds:reject

  • audit-logs:read

Permission Merging ​

When a user has multiple roles, permissions are merged:

User: John Admin
Roles: [Finance Admin, Support Agent]

Finance Admin permissions:
  - invoices:*
  - wallets:*

Support Agent permissions:
  - bookings:read
  - users:read

Effective permissions (union):
  - invoices:*
  - wallets:*
  - bookings:read
  - users:read
