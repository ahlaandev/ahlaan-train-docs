Access Roles & Permissions Guide ​

This guide explains how administrators manage Access Roles, fine-grained permissions, and admin assignments.

Product term: "Access Role". The API model is still named AdminRole, but the product/UI term is Access Role to avoid confusion with the coarse account-type. There are two distinct layers:

  • Account type — the UserRole enum (ADMIN vs customer). Decides who may log into the admin surface at all.
  • Access Role — a named permission bundle (Super Admin, Kurs Inputter, …). Decides what an admin can do.

Every admin is one ADMIN account plus one-or-more Access Roles. A new job function (e.g. "Kurs Inputter") is a new Access Role bundle created at runtime, not a new account-type.

FeatureDescription
PurposeManage Access Roles and fine-grained permissions

Enforcement & Protections ​

Permissions are enforced by PermissionsGuard, which layers inside the account-type gate: jwt → RolesGuard (ADMIN) → PermissionsGuard.

  • Default-allow rollout. A route with no @RequirePermissions decorator passes any ADMIN through (so un-migrated routes keep working). A route only locks down once its decorator is added. Enforcement is being rolled out controller-by-controller. Today the Access Roles, Users, Exchange Rate, and the finance controllers are permission-gated: Refunds (incl. Refund Bank Eligibility), Payments, Manual Transfer (proofs, payments, bank accounts), Payment Gateway config + fees, Wallet (admin routes only), Invoices (admin routes only), and Banks. The pricing controllers are now gated too: Tax, Special B2B Tax, Custom Tax, Tariff (tariffs + pricing config + deprecated locations), Custom Markup, Special B2B Markup, Pricing, Special B2B Pricing (incl. the ECONOMY tier auto-update trigger), Custom Route Price, Mitra Pricing Config, Ticket Channels (channels + route prices), and Scraper Price. The bookings and operations controllers are now gated too: Custom Booking, Custom Booking Manifests, BlockSeat Bookings, OTA Bookings (incl. reports, cancellation/ticket-email resends, retry-ticketing, follow-ups, and cache refresh), Fare Preferences, Organizations (incl. pricing-tier, promo-access, and public API access toggles), Impersonation (act as customer), Partners, and Partner API Keys. The reference, system, and comms controllers are now gated too: Railway Stations, Office Locations, System Config (incl. the hidden fee/tax/wallet-topup endpoints), WhatsApp (management via whatsapp:manage, sandbox test-sends via whatsapp:send), Email (raw provider send via email:send), Audit Logs (read via audit-logs:read, export via audit-logs:export), and the ADMIN-only Third-Party Error detail route (third-party-errors:read).
  • Not yet gated (deferred). Two areas stay on the plain ADMIN/SUPPORT role check and are intentionally left ungated: Notifications (every route is reachable by SUPPORT, whom PermissionsGuard would lock out), and the SUPPORT-reachable Third-Party Error routes (list, stats, status updates). Only that module's ADMIN-only GET :id detail route is gated. These wait on the guard learning to pass SUPPORT through.
  • GET users/me/permissions is never gated — every admin can read their own effective permissions so the FE can render menus/buttons.
  • Live read. Effective permissions are read from the DB per gated request, so assigning/revoking a role or editing its permissions takes effect immediately — no re-login.
  • Self-healing Super Admin bootstrap. On every boot the service idempotently ensures the Super Admin role exists and that admin@ahlaan.co.id holds it, so enabling enforcement can never lock the operator out — even on a DB where the seed never ran.

Protection rules ​

RuleBehaviour
Delete Super Admin roleBlocked (400)
Revoke the last active Super AdminBlocked (400)
Deactivate an ADMIN/SUPPORT accountSuper-Admin-only (not delegable via users:delete); a regular admin gets 403
Deactivate the last active Super AdminBlocked (403) even for a Super Admin
Deactivate your own accountBlocked (403)

Every Access Role mutation (create / update / deactivate / assign / revoke) and every admin deactivation writes an audit-log entry (actor, target, before/after permissions).

Endpoints ​

1. Create Admin Role ​

Endpoint: POST /admin/roles

Create a new admin role with specific permissions.

Request Body:

json
{
  "name": "Finance Manager",
  "description": "Can manage invoices and payments",
  "permissions": [
    "invoices:create",
    "invoices:read",
    "invoices:update",
    "wallets:read"
  ],
  "isActive": true
}

Permissions use the format <resource>:<action> (colon-separated). Wildcards are supported: * (super admin), <resource>:* (all actions on a resource, e.g. invoices:*), and *:read (read access to all resources).

Response: 201 Created

json
{
  "id": "role-uuid",
  "name": "Finance Manager",
  "description": "Can manage invoices and payments",
  "permissions": [
    "invoices:create",
    "invoices:read",
    "invoices:update",
    "wallets:read"
  ],
  "isActive": true,
  "createdBy": "admin-uuid",
  "createdAt": "2026-01-31T10:00:00Z",
  "updatedAt": "2026-01-31T10:00:00Z"
}

description is nullable — omitting it in the request stores null.

6. Deactivate Admin Role ​

Endpoint: DELETE /admin/roles/:id

12. Get Permission Catalog (for the role-builder UI) ​

Endpoint: GET /admin/roles/permissions/catalog

Requires: roles:read

Returns every selectable permission grouped by resource with human labels. The FE builds the Access Role builder checkbox matrix from this, and drives admin menu/button visibility by cross-referencing a user's effective permissions (GET admin/roles/users/me/permissions). Single source of truth for both.

Only concrete resource:action codes are listed — wildcards (*, resource:*, *:read) are a granting shorthand, not UI checkboxes.

Response: 200 OK

json
{
  "resources": [
    {
      "resource": "exchange-rates",
      "label": "Exchange Rate (Kurs)",
      "permissions": [
        { "code": "exchange-rates:read", "label": "View rates" },
        { "code": "exchange-rates:update", "label": "Input rate" },
        { "code": "exchange-rates:sync", "label": "Trigger sync" }
      ]
    }
  ]
}

One-step admin provisioning ​

POST /admin/users accepts an optional roleIds: string[] when creating an ADMIN account. When present, the admin and its Access Role links are created in a single transaction. This additionally requires the caller to hold roles:assign (Super Admins have it via *). roleIds is ignored for non-ADMIN roles. The two-step flow (create admin, then assign) still works.

Available Permissions ​

Permissions follow the format <resource>:<action>. Wildcards: <resource>:* grants all actions on a resource, *:read grants read access to every resource, and * grants everything (super admin).

The authoritative, machine-readable permission list is served by GET /admin/roles/permissions/catalog (see section 12). Build role/permission pickers against that endpoint rather than hardcoding the tables below, which are a human-readable snapshot and can drift.

Predefined Role Templates ​

Super Admin ​

Full system access - can perform all administrative operations.

Permissions: *

Best for: System owners, CTO, technical founders

User Manager ​

Manage users and organizations.

Permissions:

  • users:*
  • organizations:*
  • audit-logs:read

Best for: Account/operations managers handling users and organizations

Finance Admin ​

Manage financial operations including wallets, invoices, and pricing.

Permissions:

  • wallets:*
  • invoices:*
  • pricing:*
  • bookings:refund
  • exchange-rates:*
  • audit-logs:read

Best for: Finance team leads, accountants

Support Agent ​

Customer support operations - view and cancel bookings.

Permissions:

  • users:read
  • organizations:read
  • bookings:read
  • bookings:cancel
  • wallets:read
  • invoices:read

Best for: Customer support agents

Read-only access for reporting and analytics.

Permissions:

  • *:read
  • users:stats
  • organizations:stats
  • bookings:stats
  • invoices:stats
  • audit-logs:read

Booking Manager ​

Manage bookings and related operations.

Permissions:

  • bookings:*
  • users:read
  • organizations:read
  • invoices:read
  • audit-logs:read

Kurs Inputter ​

Read and update the exchange rate (kurs) only.

Permissions:

  • exchange-rates:read
  • exchange-rates:update

Best for: Finance/treasury staff who input the daily rate but should not trigger a Mandiri sync or access any other admin area

Permission Merging ​

When a user has multiple roles, permissions are merged:

User: John Admin
Roles: [Finance Admin, Support Agent]

Finance Admin permissions:
  - invoices:*
  - wallets:*

Support Agent permissions:
  - bookings:read
  - users:read

Effective permissions (union):
  - invoices:*
  - wallets:*
  - bookings:read
  - users:read

Need Help? ​

For questions or issues:

  1. Use predefined templates for common roles
  2. Assign minimum required permissions (principle of least privilege)
  3. Regularly review and audit role assignments
  4. Test new roles with a test user first
