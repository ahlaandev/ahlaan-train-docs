Invoice Management Guide ​

This guide explains how administrators can create and manage invoices in the HHR platform.

Quick Overview ​

FeatureDescription
PurposeCreate manual invoices and manage system invoices
AccessAdmin only (management), Guest (payment)
ScopeAll customer and B2B invoices

Guest Payment Access ​

Guests can pay invoices without authentication by providing their contact information:

  • GET /invoice/:id/available-gateways - Get available payment methods
  • POST /invoice/:id/generate-payment - Generate payment link

Guest endpoints accept guestEmail and/or guestPhone parameters for verification. The contact information must match the booking's guest contact.

Base URL ​

All invoice management endpoints use:

/api/v1

Authentication ​

All invoice endpoints require:

  • JWT Token in Authorization header
  • ADMIN role in user account
http
Authorization: Bearer <your-admin-jwt-token>

3. List All Invoices ​

Endpoint: GET /admin/invoice

Get all invoices with optional filtering.

Query Parameters:

ParameterTypeDescription
statusenumFilter by invoice status
userIdstringFilter by user
organizationIdstringFilter by organization
bookingIdstringFilter by exact booking ID
currencystringFilter by currency (SAR/IDR/USD)
sourceenumFilter by invoice source: BOOKING (any OTA booking — STANDARD + BLOCKSEAT), STANDARD (native ota/* only), BLOCKSEAT (blockseat-* wholesale only), CUSTOM_BOOKING (custom booking). Omit for all.
startDateISO-8601Lower bound on issuedAt
endDateISO-8601Upper bound on issuedAt
pagenumberPage number (default 1)
limitnumberItems per page (default 20)

Example:

bash
GET /admin/invoice?status=PENDING&currency=SAR
GET /admin/invoice?source=CUSTOM_BOOKING
GET /admin/invoice?source=BOOKING&status=PAID

source=BOOKING matches invoices with any linked OTA Booking (both STANDARD and BLOCKSEAT variants). source=STANDARD / source=BLOCKSEAT narrow to a single Booking.bookingVariant. source=CUSTOM_BOOKING matches invoices with a linked CustomBooking. An explicit bookingId takes precedence over source=BOOKING.

pricing.supplier block (admin-only):

The nested pricing object carries three blocks. pricing.base and pricing.amount are the SELL price (our markup + tax included) in SAR and the user currency respectively. pricing.supplier is the real amount we pay the OTA supplier — snapshotted at invoice generation from the booking's otaResponse.airReservation.priceInfo.itinTotalFare.

pricing.supplier is admin-only: it is emitted only on the admin invoice endpoints (GET /admin/invoice, GET /admin/invoice/:id, POST /admin/invoice/generate, PUT /admin/invoice/:id) and is never present on any customer or guest invoice response. It is populated for OTA/STANDARD + BlockSeat invoices; custom-booking invoices and bookings without an itinTotalFare report zeros.

json
{
  "pricing": {
    "base": { "subtotal": 32.58, "taxAmount": 3.59, "discountAmount": 0, "totalAmount": 36.17 },
    "amount": { "subtotal": 147686, "taxAmount": 16274, "discountAmount": 0, "totalAmount": 163960 },
    "supplier": { "baseFare": 25.75, "taxAmount": 3.86, "totalFare": 29.61 }
  }
}
FieldTypeDescription
pricing.supplier.baseFarenumberSupplier base fare in SAR (excludes supplier tax)
pricing.supplier.taxAmountnumberSupplier tax/VAT in SAR
pricing.supplier.totalFarenumberSupplier total in SAR (base + tax) — what OTA charges us

Note. pricing.base is our sell price (supplier total + markup + our tax), NOT the supplier cost. For margin, compare pricing.supplier.totalFare (cost) against pricing.base.totalAmount (sell).

9. Backfill Supplier Cost (maintenance) ​

Endpoint: POST /admin/invoice/backfill-supplier-cost

One-off maintenance job that populates pricing.supplier (the supplier*SAR columns) on existing OTA/STANDARD + BlockSeat invoices from the linked booking's otaResponse.airReservation.priceInfo.itinTotalFare. New invoices capture supplier cost automatically at generation, so this is only needed once to fill historical rows.

Body (optional):

json
{ "force": false }
FieldTypeDefaultDescription
forcebooleanfalseWhen true, re-backfills rows that already have a non-zero supplierTotalFareSAR. Otherwise only untouched rows are filled.

Response: 201 Created

json
{ "scanned": 120, "updated": 98, "skippedNoData": 22 }

Best-effort. otaResponse is mutable and may have drifted from the original supplier reply (re-synced after ticketing/modification), so backfilled rows are marked metadata.supplierCostSource = "otaResponse@backfill" (vs "create" for rows captured at generation). Custom-booking invoices are skipped. Rows whose booking has no itinTotalFare count toward skippedNoData.

Reports ​

8. Get Invoice Reports ​

Aggregated invoice analytics for finance dashboards. Returns summary KPIs (total / paid / pending / voided amounts, average payment time, collection rate), a time-series chart, and a per-status breakdown.

http
GET /api/v1/admin/invoice/reports?preset=THIS_MONTH&groupBy=day
Authorization: Bearer <admin-token>

Query Parameters ​

ParameterTypeDefaultDescription
presetstringTHIS_MONTHDate range preset: TODAY, YESTERDAY, LAST_7_DAYS, LAST_30_DAYS, THIS_MONTH, LAST_MONTH, CUSTOM
fromstring-Start date (YYYY-MM-DD) — required when preset=CUSTOM
tostring-End date (YYYY-MM-DD) — required when preset=CUSTOM
groupBystringdayChart grouping: day, week, month
organizationIdstring-Filter to a specific organization (B2B drill-down)
statusstring-Filter by status. One of: DRAFT, ISSUED, WAITING_PAYMENT_REVIEW, PAID, PARTIALLY_PAID, OVERPAID, OVERDUE, VOID, REFUNDED
sourceenum-Filter by invoice source: BOOKING (any OTA — STANDARD + BLOCKSEAT), STANDARD (native ota/* only), BLOCKSEAT (blockseat-* wholesale only), or CUSTOM_BOOKING. Omit for all. Standalone invoices (e.g. wallet top-ups) appear only when source is omitted. A variant filter (STANDARD/BLOCKSEAT) composes with partnerId instead of overriding it. Same semantics as the source filter on the invoice list endpoint.

The endpoint does not paginate — it always returns all aggregated data for the period.

      "date": "2026-04-01",
      "count": 12,

      "paidAmount": 36000.00
    }
  ],
  "byStatus": [
    { "status": "PAID", "count": 256, "amount": 1024000.00 },
    { "status": "ISSUED", "count": 40, "amount": 160000.00 },
    { "status": "OVERDUE", "count": 8, "amount": 32000.00 },

Response Fields ​

All monetary fields are reported in SAR. Monetary fields and percentages in summary are rounded to 2 decimals (SAR convention). Amounts inside chartData and byStatus are returned unrounded — round client-side if you need to display them.

FieldTypeDescription
periodFromstringReport period start (YYYY-MM-DD)
periodTostringReport period end (YYYY-MM-DD)
summary.totalInvoicesnumberCount of invoices in the period (after filters)
summary.totalAmountnumberSum of baseTotalAmountSAR across all invoices
summary.paidAmountnumberSum of totalPaidSAR for invoices in PAID status
summary.pendingAmountnumberSum of baseTotalAmountSAR for ISSUED and OVERDUE invoices only
summary.voidedAmountnumberSum of baseTotalAmountSAR for VOID invoices
summary.avgPaymentTimeDaysnumberAverage days between createdAt and paidAt for paid invoices (per-invoice ceiling, then mean)
summary.collectionRatenumber(paidAmount / totalAmount) * 100, rounded to 2 decimals
chartDataarrayTime-series buckets keyed by groupBy; paidAmount only counts PAID invoices in the bucket
byStatusarrayOne row per status that appears in the result; covers any of the 9 InvoiceStatus values

Use Cases ​

Collection-rate dashboard:

bash
curl -X GET "/api/v1/admin/invoice/reports?preset=THIS_MONTH" \
  -H "Authorization: Bearer <admin-token>"

B2B partner drill-down:

bash
curl -X GET "/api/v1/admin/invoice/reports?preset=LAST_30_DAYS&organizationId=org-uuid" \
  -H "Authorization: Bearer <admin-token>"

Overdue review:

bash
curl -X GET "/api/v1/admin/invoice/reports?preset=THIS_MONTH&status=OVERDUE" \
  -H "Authorization: Bearer <admin-token>"

Monthly trend (custom range):

bash
curl -X GET "/api/v1/admin/invoice/reports?preset=CUSTOM&from=2026-01-01&to=2026-04-30&groupBy=month" \
  -H "Authorization: Bearer <admin-token>"

Notes ​

  • Currency. Invoices are dual-currency: totalAmount follows the user-chosen currency (SAR / IDR / USD / etc.), while baseTotalAmountSAR and totalPaidSAR are the SAR source-of-truth. Reports aggregate the SAR fields so totals stay comparable across mixed-currency invoices.
  • Pending bucket scope. pendingAmount includes only ISSUED and OVERDUE invoices. DRAFT, WAITING_PAYMENT_REVIEW, PARTIALLY_PAID, OVERPAID, and REFUNDED are excluded from this bucket but still contribute to totalAmount and appear under byStatus.
  • Average payment time. Computed only over invoices that have both createdAt and paidAt; per-invoice days are rounded up via Math.ceil, then the mean is rounded to 2 decimals. Returns 0 when there are no paid invoices in the period.
  • In-memory aggregation. All grouping happens in Node.js after a single findMany — large date ranges over high-volume periods will pull a wide result set; prefer narrower windows when running ad hoc.
  • No caching layer; queries run live against the database on every request.

Invoice Statuses ​

StatusDescription
DRAFTInvoice created but not yet sent to customer
PENDINGInvoice sent, awaiting payment
ISSUEDInvoice issued to customer, awaiting payment (manual-transfer and gateway flows)
WAITING_PAYMENT_REVIEWManual-transfer only. Customer submitted a transfer proof; awaiting admin approve/reject. Approve → PAID; reject → back to ISSUED so the customer can re-upload. Xendit and other gateways settle instantly on webhook and never touch this state.
PAIDInvoice fully paid
PARTIALLY_PAIDPartial payment received
OVERPAIDPaid more than required (e.g., duplicate payments)
VOIDInvoice cancelled
OVERDUEPayment deadline passed
