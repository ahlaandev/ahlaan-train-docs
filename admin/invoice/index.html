Invoice Management Guide ​

This guide explains how administrators can create and manage invoices in the HHR platform.

Quick Overview ​

FeatureDescription
PurposeCreate manual invoices and manage system invoices
AccessAdmin + Access Role on the /admin/invoice routes: reads need invoices:read, reports invoices:stats, create/generate invoices:create, edit / mark-paid / office-settlement / backfill / reconcile invoices:update, and void invoices:void. pricing.supplier and the exchangeRate block additionally need invoices:read-supplier-cost — see the migration note below. The customer /invoice controller (guest payment + reads) is NOT permission-gated. See Access Roles
ScopeAll customer and B2B invoices

⚠️ Migrating — supplier cost and the exchange rate need invoices:read-supplier-cost ​

What changed. pricing.supplier used to be decided by the caller's role: every admin saw it, whatever Access Role they held. It now needs its own code, invoices:read-supplier-cost. Two blocks moved behind it:

BlockWhy it is cost data
pricing.supplierbaseFare / taxAmount / totalFare — the real amount we pay the supplier, i.e. our margin against pricing.base
exchangeRateits rate is the EFFECTIVE rate (baseSellRate − exchangeRateReducer). The base rate is publicly reachable, so base − effective hands the reader the tier reducer itself

Both are omitted when the code is absent, on the admin list and the admin detail alike — the two always agree for the same invoice.

What is NOT gated by this code. handledByAdmin, purpose, officeSettlementProof, manualTransfer, amounts, status, payments and line items all stay on invoices:read. In particular handledByAdmin is admin-identity data, not cost, and every admin reader keeps it — the two used to share one internal flag and have been split apart.

Customers and guests are unaffected. The exchangeRate block is served to them today and still is: the gate withholds it only from a real admin who lacks the code. A caller who is not an admin keeps their own rate. (An "act as customer" impersonation token counts as the customer here, not as an admin.)

⚠️ Behaviour change on the customer routes — all four of them. An admin calling a customer invoice read used to receive pricing.supplier, because the check there was on the role and every admin passed it. That controller carries no permission guard, so no code can be read on it at all and the answer is now fail-closed. Both blocks go, not just the supplier one:

Customer routeWhat a real admin loses
GET /invoice (list)exchangeRate on every row
GET /invoice/:idpricing.supplier + exchangeRate
GET /invoice/number/:invoiceNumberpricing.supplier + exchangeRate
GET /invoice/:id/downloadpricing.supplier + exchangeRate (the downloadMetadata block is unaffected)

⚠️ This applies to the super admin too. * grants every permission, but these routes never read a permission list — there is no guard to populate one — so the rule is "not an admin, or holds the code", and a real admin token fails it whatever the role. That is deliberate: the admin surfaces are GET admin/invoice/:id and GET admin/invoice?search=<invoiceNumber>, and both enforce invoices:read-supplier-cost properly.

Everything else still returns — amounts, status, payments, purpose, handledByAdmin — and the lookup itself still works.

Guest Payment Access ​

Guests can pay invoices without authentication by providing their contact information:

  • GET /invoice/:id/available-gateways - Get available payment methods
  • POST /invoice/:id/generate-payment - Generate payment link

Guest endpoints accept guestEmail and/or guestPhone parameters for verification. The contact information must match the booking's guest contact.

3. List All Invoices ​

Endpoint: GET /admin/invoice

Get all invoices with optional filtering.

Query Parameters:

ParameterTypeDescription
statusenumFilter by invoice status
userIdstringFilter by user
organizationIdstringFilter by organization
bookingIdstringFilter by exact booking ID
partnerIdstringFilter to a single partner's invoices, scoped via the booking relation (Booking.partnerId). Composes with a variant source filter (STANDARD/BLOCKSEAT) instead of overriding it. Custom-booking invoices (no booking link) are not matched — consistent with the reports endpoint. Max 36 chars.
currencystringFilter by currency (e.g. SAR/IDR/USD). Case-insensitive — the value is upper-cased before matching.
paymentGatewayenumFilter to invoices with at least one payment on this gateway, via the payments relation. Values: XENDIT (online: QRIS/card/e-wallet), MANUAL_TRANSFER (bank transfer), IN_PERSON (office cash), WALLET, MIDTRANS, STRIPE. Invoices with no payment yet are excluded.
bookingCodestringExact booking code (case-insensitive). Matches a standard Booking or a CustomBooking by its bookingCode. For fuzzy matching use search. Max 36 chars.
searchstringFree-text, case-insensitive. Matches any of: invoice number, customer name/email, organization name/code, partner name, partner registration number, or booking code (standard or custom booking).
sourceenumFilter by related service. BOOKING (any OTA booking — STANDARD + BLOCKSEAT), STANDARD (native ota/* only — this is the "OTA" service bucket), BLOCKSEAT (blockseat-* wholesale only), CUSTOM_BOOKING (custom booking), MITRA_REGISTRATION (standalone mitra registration receipt — no booking; always PAID/SAR). Omit for all.
startDateISO-8601Lower bound on createdAt (invoice creation). Uses createdAt (always set), so DRAFT / unissued invoices are not dropped when a date bound is set.
endDateISO-8601Upper bound on createdAt (invoice creation). Uses createdAt (always set), so DRAFT / unissued invoices are not dropped when a date bound is set.
pagenumberPage number (default 1)
limitnumberItems per page (default 20)

Example:

bash
GET /admin/invoice?status=PENDING&currency=SAR
GET /admin/invoice?search=INV-202607
GET /admin/invoice?search=acme%20travel
GET /admin/invoice?source=CUSTOM_BOOKING
GET /admin/invoice?source=BOOKING&status=PAID
GET /admin/invoice?source=BLOCKSEAT
GET /admin/invoice?partnerId=<partner-uuid>
GET /admin/invoice?partnerId=<partner-uuid>&source=STANDARD
GET /admin/invoice?paymentGateway=MANUAL_TRANSFER
GET /admin/invoice?bookingCode=ABC1234
GET /admin/invoice?paymentGateway=XENDIT&source=STANDARD&startDate=2026-07-01

source=BOOKING matches invoices with any linked OTA Booking (both STANDARD and BLOCKSEAT variants). source=STANDARD / source=BLOCKSEAT narrow to a single Booking.bookingVariant. source=CUSTOM_BOOKING matches invoices with a linked CustomBooking. source=MITRA_REGISTRATION matches standalone registration receipts (Invoice.mitraRegistrationId != null, minted at mitra approval — no booking and no custom booking, always PAID/SAR); it composes with a partnerId scope but returns nothing since these invoices have no booking relation. An explicit bookingId takes precedence over source=BOOKING.

partnerId scopes through the booking relation (Booking.partnerId) — the same input the reports endpoint takes. It composes with a variant source filter (both land on booking.is), so partnerId=<uuid>&source=STANDARD returns that partner's STANDARD-variant invoices. partnerId combined with source=CUSTOM_BOOKING returns nothing (custom invoices have no linked booking), matching the reports endpoint.

search (fuzzy) and bookingCode (exact) each build an OR-group and are combined (AND) with every other filter and with each other, so they narrow within the current scope. search matches booking codes with contains; bookingCode matches one code exactly (equals) against either a standard Booking or a CustomBooking. The customer-facing GET /invoice route reuses the same query DTO, but the server forces the caller's own userId (B2C) or organizationId (B2B) first, so there both search and bookingCode can only match the caller's own invoices.

paymentGateway filters through the payments relation (payments.some.paymentGateway.code) using the DB-enforced PaymentGatewayCode enum, so the OpenAPI dropdown never drifts. It is coarser than the free-text Payment.paymentMethod (it cannot split QRIS vs card vs e-wallet within XENDIT), but it cleanly separates MANUAL_TRANSFER / IN_PERSON / XENDIT / WALLET. This filter is list-only — the reports endpoint does not take it.

Date field. startDate / endDate filter createdAt (invoice creation, always set), matching the reports endpoint — a single canonical date field across both surfaces. The customer-facing GET /invoice route reuses the same DTO, so its date filter now also uses createdAt (previously the list used the nullable issuedAt, which silently dropped unissued invoices).

partner and handledByAdmin are null on a self-serve OTA booking; a partner/impersonated invoice populates them (see the handledByAdmin block and purpose block notes under Get Invoice by ID below). pricing.supplier (admin-only supplier cost) and the admin-only purpose object are always present on admin reads.

Amounts are dual-currency: pricing.base/payments.base are SAR (source of truth), pricing.amount/payments.amount are the invoice's display currency. There is no flat totalAmount/totalPaid field — read pricing.amount.totalAmount and payments.amount.totalPaid.

payments.base.totalPaidSAR on paid invoices. On settlement, the SAR counterpart of the payment is anchored to the invoice SAR face value (pricing.base.totalAmount, from baseTotalAmountSAR) — a full payment writes the full anchor, a partial pro-rates it by the paid/total ratio. This holds for both cross-currency settlements (e.g. a SAR/USD manual transfer against an IDR invoice) and same-currency ones (e.g. an IDR Xendit payment on an IDR invoice). Because the admin reports sum totalPaidSAR, a paid invoice always contributes its SAR value. Historical same-currency rows that predate this behavior read totalPaidSAR: 0 until repaired via Backfill Paid SAR.

payments.amount.totalPaid on cross-currency invoices. A foreign payment is never summed onto the invoice-currency column — the SAR/USD figure lives on the Payment row. The display-currency total is derived from the SAR anchor instead: totalPaid = totalAmount × (totalPaidSAR / baseTotalAmountSAR), capped at totalAmount, so a settled invoice never reports totalPaid: 0 beside a non-zero totalPaidSAR. Historical rows that predate this read totalPaid: 0 until repaired via Backfill Cross-Currency Paid.

exchangeRate.rate is the EFFECTIVE rate. For a custom-booking invoice on the GOLD pricing tier, the rate shown is the reduced rate the amounts were actually built at (baseSellRate − exchangeRateReducer, e.g. 4770 where the live base rate is 4920), not the base rate the invoice's exchangeRateId FK points at. The reduced figure is frozen onto the booking's pricingSnapshot.effectiveSellRate at create time and read back via the shared resolveEffectiveSellRate helper; legacy rows whose snapshot predates that field fall back to the base rate. Non-GOLD bookings snapshot effectiveSellRate == baseSellRate, so nothing changes for them, and non-custom-booking invoices always show the base rate. This is the same convention the custom-OTA search surface uses. Admin exchange-rate endpoints always return the base rate — see Exchange Rate.

The same exchangeRate block is returned by the detail reads (GET /admin/invoice/:id, the customer/guest GET /invoice/:id, GET /invoice/number/:invoiceNumber and GET /invoice/:id/download) and by both lists, with identical values for the same invoice for any caller who receives it at all. Who receives it is no longer "everyone": it is gated on invoices:read-supplier-cost for an admin, and withheld from a real admin entirely on the customer routes — see the migration note at the top of this page. A customer, a guest and an "act as customer" impersonation token keep their own rate unchanged. Before 2026-07-18 the detail reads omitted the key entirely, so a GOLD custom-booking invoice showed 4770 on the list and no rate at all on the detail; clients that worked around this by deriving their own rate should now read the field.

payments.attempts[] — admin tier only ​

Each entry is one payment attempt, and id is the value POST /admin/payment/{id}/manual-confirm and POST /admin/payment/{id}/refund take. Before this block existed there was no supported way to obtain it.

gatewayGateway code as a plain string (MANUAL_TRANSFER, IN_PERSON, XENDIT)
paymentMethodResolved method (BANK_TRANSFER, CASH, …)

proofStatus is on both surfaces, deliberately. The customer payment list carries it so a customer whose proof was rejected can be routed back to the upload page from an invoice id — see Manual Bank Transfer → Returning to an unfinished transfer. One concept, one field name; do not rename it on either side.

On both surfaces null means "no manual-transfer proof row", not "no proof of any kind": the IN_PERSON office-settlement rail keeps its proof on Payment.proofFileId and reports proofStatus: null even when a real receipt has been uploaded. Branch on the gateway before you read it.

Line items are under lineItems (not items), and payments is an object ({ amount, base }), not an array. manualTransfer is present only on Get-by-ID (see below), not on the list endpoint.

For a fresh time-limited link or a shareable no-login token see Storage — Download a File by ID: GET /api/v1/storage/{id}/url and POST /api/v1/storage/{id}/token.

pricing.supplier block (admin-only):

The nested pricing object carries three blocks. pricing.base and pricing.amount are the SELL price (our markup + tax included) in SAR and the user currency respectively. pricing.supplier is the real amount we pay the OTA supplier — snapshotted at invoice generation from the booking's otaResponse.airReservation.priceInfo.itinTotalFare.

pricing.supplier is admin-only: it is emitted only on the admin invoice endpoints (GET /admin/invoice, GET /admin/invoice/:id, POST /admin/invoice/generate, PUT /admin/invoice/:id) and is never present on any customer or guest invoice response. It is populated for OTA/STANDARD + BlockSeat invoices; custom-booking invoices and bookings without an itinTotalFare report zeros.

{ "baseFare": 0, "taxAmount": 0, "totalFare": 0 } on a custom-booking invoice means "not applicable", not "cost us nothing". The three columns are written only when an invoice is generated from an OTA booking, out of that booking's supplier itinTotalFare; custom bookings have no OTA supplier leg, so the columns keep their 0 default by design. The real cost basis for a custom booking is CustomBooking.capitalPriceTotalSAR, written only by the three admin capital routes (PATCH .../capital-price, PATCH .../source, POST .../recompute-capital) — no status transition writes it, so a booking carries 0 until one of them is called — and documented under Custom Booking. It is not exposed on any invoice response — read it from the custom-booking endpoints. Margin on a custom-booking invoice therefore cannot be computed from the invoice payload alone. A 0 on an OTA/STANDARD or BlockSeat invoice means something different: the OTA reply carried no itinTotalFare, which is repairable via Backfill Supplier Cost.

{
  "pricing": {
    "base": { "subtotal": 32.58, "taxAmount": 3.59, "discountAmount": 0, "totalAmount": 36.17 },
    "amount": { "subtotal": 147686, "taxAmount": 16274, "discountAmount": 0, "totalAmount": 163960 },
    "supplier": { "baseFare": 25.75, "taxAmount": 3.86, "totalFare": 29.61 }
  }
}
FieldTypeDescription

Note. pricing.base is our sell price (supplier total + markup + our tax), NOT the supplier cost. For margin, compare pricing.supplier.totalFare (cost) against pricing.base.totalAmount (sell).

partner block (all callers):

Every invoice carries a top-level partner object — the mitra partner identity (registration number + name) of the owning organization, snapshotted at invoice generation from Organization.mitraRegistration (registrationNumber = MS.XXX / MG.XXX; name = the registration's company name for COMPANY applicants, else the applicant name). It is not admin-gated (partner identity is not sensitive) and appears on customer, guest, and admin responses alike. partner is null for non-mitra invoices (no linked mitra registration); partner.registrationNumber is null when the registration has no assigned number yet. Because it is a snapshot, editing the org/registration later does not retro-change already-issued invoices.

Scope: custom-booking invoices only. The snapshot is taken only by the custom-booking generator — the mitra / promo surface. An OTA or BlockSeat invoice (Generate from Booking) returns partner: null even for a mitra, because those are off-promo surfaces and are left exactly as they were before the mitra work. A manually created invoice (Create Manual Invoice) likewise carries no snapshot, even when its organizationId belongs to a mitra org — the same way a manual invoice carries a zeroed pricing.base (SAR) and pricing.supplier block, since none of those snapshots are captured on that path. Do not read partner: null as "this organization is not a mitra partner"; read it as "no partner identity was captured for this invoice".

purpose block (admin-only):

Every invoice read by an admin carries a top-level purpose object that explains what the invoice is for, computed on read from the invoice's source entity. It is admin-only — emitted on GET /admin/invoice/:id and the admin invoice list GET /admin/invoice; omitted entirely on the authenticated-owner and guest invoice reads. No new column, no migration — it is always fresh.

⚠️ purpose used to share one internal flag with pricing.supplier, and this page used to describe them as having the same gate. They were split apart: pricing.supplier moved behind invoices:read-supplier-cost, while purpose stayed on invoices:read because it is what the invoice is for, not cost. A restricted admin therefore keeps purpose and handledByAdmin while losing pricing.supplier and exchangeRate — verified live on preprod.

There is no GET /admin/invoice/number/:number route. Look an invoice number up with GET /admin/invoice?search=<invoiceNumber>; the customer-side GET /invoice/number/:invoiceNumber exists but is not an admin surface.

CUSTOM_BOOKING route names, cabin, and contact person

  • originName / destinationName prefer the stored columns and fall back to the station cache for legacy rows saved before those columns existed. The cache returns the code itself on a miss, so a booking that has a route code always renders a name rather than a bare blank — but, like every other field in details, either one is null when the underlying data is absent. Treat them as nullable. Each side resolves independently: a missing destination never blanks out a resolved origin. The title stays code-only — the names live in details, so no existing consumer's title string shifts.
  • cabin is per leg, never a single value: each leg can be booked in a different class, so a scalar would be wrong on a mixed-cabin round trip. cabin.return is null on a ONE_WAY booking; either leg is null when its stored flight data is missing or unusable. Only className (display, e.g. "Business") and tripClass (token, e.g. "BUSINESS") are exposed — the rest of the stored flight JSON (fareReference, resBookDesigCode, flightNumber) is commercial data and is never emitted here.
  • contactPerson is customer PII (email + phone) and carries no name field — the booking stores only those two keys. It is emitted only under the admin gate; the owner and guest invoice reads omit purpose wholesale, and an impersonation principal is not an admin, so it cannot reach a customer session. It must never be written to logs.

6. Mark Invoice as Paid ​

Endpoint: PUT /admin/invoice/:id/mark-paid

Manually mark an invoice as paid.

Blocked while a manual transfer is awaiting the finance check. Returns 400 when the invoice has a live manual-transfer attempt - a PENDING payment - whose proof has not reached FUNDS_VERIFIED or APPROVED. Marking paid here would otherwise skip the confirmation that the money actually landed in our bank account, which is exactly what this endpoint is documented as being for. Use Verify then Approve instead.

The check only looks at attempts whose payment is still PENDING, so an attempt that has genuinely died does not block. Note that on current production settings a manual-transfer payment does not die on its own - CUSTOM_BOOKING_PAYMENT_EXPIRY_JOB_ENABLED is off by default, so an abandoned attempt keeps this invoice blocked indefinitely. See when the money arrived but no receipt was ever uploaded for the escape route. Invoices with no manual-transfer proof at all (OTA, Xendit, wallet, in-person) are unaffected.

The same gate applies to PUT /admin/invoice/:id with {"status":"PAID"} — both routes perform the identical PAID transition, so guarding only this one would leave the generic route open.

The 400 names a proof id — do not follow it blindly. This check is invoice-scoped: it blocks on any live attempt and reports the first one it finds, which on an invoice with several attempts may not be the one you were working on, and may be a proof that verify will reject with 409. List the attempts with GET /api/v1/invoice/:id/payments and pick the one whose proofStatus is SUBMITTED. See do not blindly follow the proof id in the 400.

11. Backfill Cross-Currency Paid (maintenance) ​

http
POST /api/v1/admin/invoice/backfill-crosscurrency-paid
Authorization: Bearer <admin-token>
Content-Type: application/json

One-off maintenance job. A cross-currency settlement (payment currency != invoice currency, e.g. a SAR bank transfer against an IDR custom-booking invoice) historically anchored only the SAR side, leaving the invoice-currency totalPaid at 0. Such a row reports payments.amount.totalPaid: 0 beside a non-zero payments.base.totalPaidSAR, which reads as unpaid. New settlements derive the figure automatically; this repairs the pre-existing rows with the same formula:

totalPaid = totalAmount × (totalPaidSAR / baseTotalAmountSAR)     (capped at totalAmount)

Why derived, not converted. Deriving from the SAR anchor rather than converting at the sell rate (SAR × sellRate) matters for GOLD: a GOLD booking is priced at the reduced rate, so converting at the base rate would overstate the total and flip the invoice to a false OVERPAID.

This is a DISTINCT job from Backfill Paid SAR, not an extension of it. The two select disjoint row sets: that job's totalPaidSAR: 0 filter can never match a cross-currency row, because such a row anchors the SAR side at settlement.

12. Reconcile Orphan In-Person Payments (maintenance) ​

http

One-off maintenance job. Marked EXPIRED, not settled. No settlePayment runs: no re-credit and no booking / ticket / notification side effects. EXPIRED is the honest "abandoned duplicate attempt" bucket.

Narrow scope. Requires a PAID IN_PERSON sibling. An invoice paid by a different rail with a leftover PENDING in-person row is a different scenario and is left untouched.

B2B partner drill-down:

Monthly trend (custom range):

bash

  -H "Authorization: Bearer <admin-token>"

Notes ​

  • Currency. Invoices are dual-currency: totalAmount follows the user-chosen currency (SAR / IDR / USD / etc.), while baseTotalAmountSAR and totalPaidSAR are the SAR source-of-truth. Reports aggregate the SAR fields so totals stay comparable across mixed-currency invoices.
  • Pending bucket scope. pendingAmount includes only ISSUED and OVERDUE invoices. DRAFT, WAITING_PAYMENT_REVIEW, PARTIALLY_PAID, OVERPAID, and REFUNDED are excluded from this bucket but still contribute to totalAmount and appear under byStatus.
  • Average payment time. Computed only over invoices that have both createdAt and paidAt; per-invoice days are rounded up via Math.ceil, then the mean is rounded to 2 decimals. Returns 0 when there are no paid invoices in the period.
  • In-memory aggregation. All grouping happens in Node.js after a single findMany — large date ranges over high-volume periods will pull a wide result set; prefer narrower windows when running ad hoc.
  • No caching layer; queries run live against the database on every request.

Booking line items (per-pax) ​

Invoices generated from a booking (custom booking, OTA, and BlockSeat alike) are broken down per pax type per leg, not one opaque line per leg. Each line carries the real passenger count as quantity and the per-passenger fare as unitPrice / unitPriceSAR.

Every booking-derived line follows ONE format:

{Cabin class} {Pax type} {origin} - {destination}

The leg direction is encoded by the route order — Economy Adult SUB - MED is the outbound, Economy Adult MED - SUB the return — so there is no (Outbound) / (Return) tag. A round trip emits up to 6 lines, a one-way up to 3. A mixed-class round trip renders each leg's own class: Economy Adult SUB - MED outbound, Business Adult MED - SUB return.

json
"lineItems": [
  { "description": "Economy Adult Surabaya - Madinah",  "quantity": 2, "unitPriceSAR": 500, "amountSAR": 1000, "unitPrice": 1875000, "amount": 3750000 },
  { "description": "Economy Child Surabaya - Madinah",  "quantity": 1, "unitPriceSAR": 300, "amountSAR": 300,  "unitPrice": 1125000, "amount": 1125000 },
  { "description": "Business Adult Madinah - Surabaya", "quantity": 2, "unitPriceSAR": 600, "amountSAR": 1200, "unitPrice": 2250000, "amount": 4500000 }
]

Rules:

  • Zero-count and zero-price pax types emit no line. A free infant produces no line at all (Xendit rejects a zero-priced item).
  • Legacy bookings with no per-pax prices fall back to a single {Cabin class} Ticket {origin} - {destination} line with quantity: 1.
  • The cabin-class token is optional. It is omitted entirely — never guessed, never defaulted, never placeholdered — when the per-leg class cannot be determined, leaving Adult Surabaya - Madinah. This happens on legacy round-trip OTA bookings (whose stored per-leg class cannot be trusted to distinguish the return leg) and on custom bookings whose leg JSON carries no class. Do not treat a missing token as Economy.
  • The format is not uniform across historical rows. lineItems is persisted at generation time and is deliberately not backfilled, so older invoices carry the previous {Pax type} - {origin} to {destination} format, and older ones still an em dash (Adult — Surabaya to Madinah). Render description as-is; never split or match on it to recover the cabin class, pax type, or route. (purpose.title is different — it is derived on every read, so it is uniform.)
  • Prices are tier-final. The per-pax figures are already reducer-adjusted with the caller's tier markup baked in. There is no separate Service Fee / Markup line on this path — supplier cost, reducer and margin stay admin-only (pricingSnapshot).
  • Tax is inclusive. BUSINESS-leg ZATCA tax is not a line item; lines are tax-inclusive and the subtotal/tax split lives in the invoice summary fields (baseTaxAmountSAR / taxAmount).
  • SAR ties out exactly. unitPriceSAR × quantity == amountSAR on every line, and Σ amountSAR equals the booking's totalPriceSAR. The charged per-passenger SAR share is a whole riyal (see ANCHOR_PAX flooring), so the line is an exact integer multiple of it and there is no residual to absorb. This is the same per-passenger SAR figure the customer saw on custom-OTA search, on book/calculate and on their booking.
  • IDR does NOT carry that guarantee. Σ amount still equals the booking's IDR anchor exactly, but that anchor is a single floor of the whole-booking SAR (floor(totalPriceSAR × sellRate)) while these lines are ceil-converted per pax type — and Σ ceil(…) ≠ floor(Σ …), so the two cannot agree line-for-line. The residual is folded into the first line, where unitPrice × quantity may differ from amount by up to (quantity − 1) rupiah. Render amount — never recompute it from unitPrice × quantity.
  • Line items convert at the booking's effectiveSellRate (the gold exchangeRateReducer already applied), frozen on the pricingSnapshot — the same rate the charged IDR total was anchored to, not the raw sellRate.

Legacy rows. Bookings created before the ANCHOR_PAX model (pricingSnapshot.floorMode === 'ANCHOR_LINE') stored a fractional per-passenger share, so for those invoices the SAR tie-out above is not exact and the first line absorbs a sub-riyal residual. Nothing is re-priced.

The same lineItems array is forwarded to Xendit as the invoice items[], so the per-pax breakdown is what the customer sees at checkout.

Registration invoices (mitra) ​

When an admin approves a mitra registration, the approval transaction mints a registration receipt — a formal Invoice documenting the registration payment that already moved off-system. These invoices are distinct from booking invoices:

Registration invoice
statusPAID at creation — the money moved before approval (SILVER proof / GOLD deposit ack). No Payment row and no gateway tender; nothing is paid through it.
currencySAR (SAR-native — every amount equals the fee, no exchange rate).
lineItemsa single line: SILVER Partner Registration Fee (100 SAR) or GOLD Partner Security Deposit (50,000 SAR).
mitraRegistrationIdset to the approved registration (unique — one receipt per registration). Null on every other invoice.
partnerRegistrationNumber / partnerNamethe partner snapshot (MS./MG. number + name), same as on custom-booking invoices.

Retrieve one via the normal GET /admin/invoice/:id (or the customer GET /invoice/:id, which the applicant can call for their own receipt). The id is surfaced as registrationInvoiceId on the mitra get-one / list responses and on the applicant's application/status.

Accounting caveat. GOLD's 50,000 SAR is a refundable security deposit (a liability), not revenue like SILVER's fee. One invoice shape is used for both for FE-PDF simplicity. A deposit ledger and refund treatment are deferred follow-ups; the invoice here is a document, not a tracked balance.

Reserved metadata keys

metadata is not a free passthrough. These keys are sourced from the invoice on the server and overwrite whatever the caller sends:

invoiceNumber · bookingCode · userId · items · partnerRegistrationNumber · partnerName · customBookingId

They are written after the client's metadata is merged, and they are always written — including as null for a non-mitra invoice. A caller therefore cannot forge a partner identity onto a genuine payment by passing partnerRegistrationNumber in the request body.

Xendit invoice description. When a custom-booking invoice (payment source CUSTOM_OTA — the mitra / promo surface) carries a partner identity, the live Xendit invoice the customer pays is described as {invoiceNumber} · {partnerRegistrationNumber} {partnerName} (e.g. INV-000123 · MG.0007 PT Mitra Gold). Everything else — OTA and BlockSeat bookings (including a mitra's own), wallet top-ups, manually-created invoices — keeps the legacy Payment for {invoiceNumber} and carries no partner data at all. See Payment Gateway → Xendit invoice payload.

*At least one is required for guest access.
