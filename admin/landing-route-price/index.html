Landing Route Prices (WhatsApp Landing Page) ​

This guide explains how administrators set the adult price per seat shown on the WhatsApp landing page, and the landing pricing configuration: the child and infant percentages of that price and the SAR to IDR rate source.

The landing page looks like a train search, but the customer does not book in the system: every result is ordered over WhatsApp. Train times and free seats come from the live supplier search; the price of each class comes only from the rows on this page.

These prices are not used by OTA booking, custom booking, BlockSeat or promo pricing.

Quick Overview ​

FeatureDescription
PurposeFixed adult price per seat, per route direction and class, for the Landing Search
AccessAdmin + Access Role: reads need landing-route-price:read; create, update and delete need landing-route-price:update. See Access Roles
KeyoriginCode + destinationCode + tripClass — one row per direction
CurrencySAR. The search converts it to IDR and USD on every request. The SAR to IDR rate is chosen in the pricing configuration; see IDR rate source
No row / inactive rowThat class is hidden on the landing page for that direction
Child / infantA percentage of the adult price, set once for every route. See Child and infant percentages

applyToReverse ​

Each direction is its own row: MKX → DMX and DMX → MKX are two rows. applyToReverse: true writes the reverse direction (same class) in the same transaction:

EndpointWhereEffect
POSTbodyCreates the row and its reverse. If either already exists: 409, nothing written
PUTbodyWrites this row's resulting priceSAR and isActive to the reverse row, creating it if missing
DELETEquery string (?applyToReverse=true)Also deletes the reverse row, if it exists

After the write the two rows are independent: a later edit without the flag changes only one of them.

Removes the row (and, with the flag, its reverse). To hide a price but keep it, set isActive: false instead.

Without the flag, or when the reverse row did not exist:

json

An unknown id is the 404 shown in Get by ID.

Landing pricing configuration ​

One configuration for every route and class. It holds the child and infant percentages and the IDR rate source. It is separate from the Mitra pricing configuration. The landing search and the landing exchange-rate endpoint read it.

FieldTypeDescription
childPricePercentagenumber0–100, at most 2 decimals
infantPricePercentagenumber0–100, at most 2 decimals
idrRateSourcestringBANK_RATE or GLOBAL_RATE. Default BANK_RATE
idrRateBankCodestring^[A-Z0-9_]{2,32}$. Default BCA
idrRateTypestring^[A-Z0-9_]{2,32}$. Default E_RATE

Same access as the route prices: reads need landing-route-price:read, writes need landing-route-price:update.

EndpointDescription
GET /admin/landing-pricing-configThe active configuration. With none: the defaults, "id": "default" and "isDefault": true
POST /admin/landing-pricing-configBody needs both percentages. The IDR rate fields are optional: when left out, they are copied from the previous active configuration, or take the defaults when there is none. Becomes the active configuration; the previous one is deactivated in the same transaction and stays in the history. 201
PUT /admin/landing-pricing-configBody takes any of the fields above. Changes the active configuration in place. 404 when only the defaults apply: use POST first
GET /admin/landing-pricing-config/historyEvery configuration, newest first. Query: page (default 1), limit (default 20, values above 100 count as 100), isActive
GET /admin/landing-pricing-config/defaultsThe built-in values: child 70, infant 0, BANK_RATE, BCA, E_RATE

A percentage below 0, above 100 or with more than 2 decimals is 400. So is an unknown idrRateSource, a code that breaks its rule, or a bank series with no recorded rate (see below).

Child and infant percentages ​

The child and infant price as a percentage of priceSAR. The result is rounded down to a whole riyal. With no configuration, child is 70% and infant is 0%.

Example: priceSAR 220, child 70% → 154 SAR. priceSAR 99.50, child 75% → 74 SAR (74.625 rounded down).

IDR rate source ​

The landing search converts SAR to IDR with one of two rates:

  • BANK_RATE: the sell rate of the newest recorded row of the SAR/IDR series idrRateBankCode + idrRateType, from the bank rates the kurs scraper pushes. The newest row is used however old it is. When the series has no row, the search uses the global rate instead and logs a warning. The warning is logged only when the rate is not cached; see When a change shows.
  • GLOBAL_RATE: the current SAR sell rate of the Exchange Rate module.

The chosen sell rate is rounded up to a whole rupiah before it is used, for example 4841.42 → 4842.

USD is converted the same way with either choice. The landing search and the landing exchange-rate endpoint read this choice.

To see which series exist, call GET /admin/bank-exchange-rates/series?baseCcy=SAR&quoteCcy=IDR (see Bank Exchange Rate); landing-route-price:read is enough.

A POST or PUT whose result is BANK_RATE and that changes idrRateSource, idrRateBankCode or idrRateType is checked: the series must have at least one recorded row, or the request is 400 and nothing is saved. This includes a switch from GLOBAL_RATE back to BANK_RATE with the same bank and rate type. A change to the percentages alone is not checked.

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "No recorded SAR/IDR rate for BCA TT",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

For request examples, see Change the IDR rate.

When a change shows ​

The supplier part (train times and seats) is cached for up to 120 seconds.

The active prices of each route direction are cached for up to 10 minutes. Creating, updating or deleting a price clears the cached prices of every route.

The active configuration (or the defaults, when no row is active) is cached for up to 10 minutes, in one entry that the landing search and the landing exchange-rate endpoint share. Creating or updating the configuration clears it. The admin GET of the active configuration reads the database, not this entry.

The SAR to IDR rate is cached for up to 10 minutes, in one entry that the landing search and the landing exchange-rate endpoint share. The entry is cleared:

  • when the kurs scraper records a new SAR/IDR row. A push that repeats the previous rate of its series records no row and does not clear it;
  • about 2 seconds after the global SAR rate of the Exchange Rate module changes;
  • when this configuration is created or updated.

So a change normally shows on the next request. If a clear fails, or a request reads the old value at the same moment as the change, the old price, configuration or rate can show for up to 10 minutes. A server that reads the same database through its own Redis does not see the clear, so it can show the old value until its own entry expires, up to 10 minutes later.

Audit ​

Each row written or deleted, reverse rows included, is logged as LANDING_ROUTE_PRICE_CREATE, LANDING_ROUTE_PRICE_UPDATE or LANDING_ROUTE_PRICE_DELETE (entity LandingRoutePrice). The log write is best effort: if it fails, the change stays and a warning is logged.

Each POST and PUT of the pricing configuration is logged as LANDING_PRICING_CONFIG_CREATE or LANDING_PRICING_CONFIG_UPDATE (entity LandingPricingConfig), with the percentages, the IDR rate fields and isActive after the change. Same best effort as above. The history list also keeps each created configuration with createdBy and updatedBy; a PUT overwrites the active one in place.
