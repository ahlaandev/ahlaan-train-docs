Payment Gateways by Currency ​

The invoice of a booking made with POST /ota/book is created in IDR. The customer chooses the payment currency when paying, by choosing the gateway:

paymentGatewayCodeBilled inAmountWhat the customer sees
XENDITIDRthe invoice totalXendit's hosted checkout page
MOYASARSARthe invoice's stored SAR price, as is (no conversion from the IDR total)Moyasar's hosted checkout page (card, mada, Apple Pay and whatever else Moyasar shows)

Moyasar is left out of an invoice that carries a discount: the stored SAR price does not include it.

The customer can change their mind: see Switching gateway.

Invoices created before this rule keep the old one, where the invoice currency picked the gateway: a SAR invoice is paid through Moyasar only, and a USD invoice cannot be paid online. The server enforces both rules on the two endpoints below: available-gateways leaves a gateway out, and generate-payment refuses it with a 400.

A gateway is also left out while its gateway row is not ACTIVE, so on an environment where Moyasar is switched off a SAR invoice lists nothing.

Custom bookings are different: their invoice is created in IDR, and they have extra bank-transfer and office-cash options. See Custom bookings.

Base URL ​

/api/v1

Flow ​

1. Create the booking ​

POST /ota/book still accepts currency (IDR, SAR or USD), but it is deprecated and ignored: the invoice is created in IDR whatever is sent. Omit it.

invoice.totalAmount in the booking response is therefore IDR, and pricing is quoted in SAR.

2. List the gateways for the invoice ​

http
GET /invoice/:invoiceId/available-gateways
# Guest: append ?guestEmail=... or ?guestPhone=...

Render one payment button per entry in availableGateways. Do not decide the gateway from the currency on the client: the list also drops a gateway that is switched off, an invoice that can take no more payment (for example one already paid), and (for BlockSeat) a gateway the BlockSeat allow-list excludes.

If availableGateways is empty, the invoice cannot be paid online. Show that instead of a payment button.

Each entry carries currency and amount: what generate-payment bills through that gateway, so each button can show its own price. For example, on an IDR OTA invoice of 787200 whose SAR price is 160: XENDIT → IDR 787200, MOYASAR → SAR 160.

To list only one currency, add ?currency=IDR, SAR or USD (any letter case). The filter keeps the gateways whose currency matches; the invoice-level currency, totalAmount and remainingAmount are unchanged. Without it every available gateway is listed. Any other value answers 400.

http
GET /invoice/:invoiceId/available-gateways?currency=sar

supportedMethods is a display hint, not a choice: Xendit lists ["BANK_TRANSFER"] and Moyasar lists ["CARDS"], but on both the customer picks the actual method on the gateway's own page.

For the button's text, use displayText: a title and a description in each of ID, EN and AR, set by an admin.

json
"displayText": {
  "ID": { "title": "Pembayaran Online (SAR)", "description": "Mendukung mada, Visa/Mastercard, dan Apple Pay" },
  "EN": { "title": "Online Payment (SAR)", "description": "Supports mada, Visa/Mastercard, and Apple Pay" },
  "AR": { "title": "الدفع الإلكتروني (ريال سعودي)", "description": "يدعم مدى وفيزا/ماستركارد وApple Pay" }
}

displayText is null for a gateway no admin has set text for; fall back to your own label then.

3. Create the payment ​

http
POST /invoice/:invoiceId/generate-payment
Content-Type: application/json

{
  "paymentGatewayCode": "MOYASAR",
  "guestEmail": "customer@example.com"
}
  • Send only paymentGatewayCode (plus guestEmail / guestPhone for a guest).
  • Omit paymentMethod: both gateways resolve it to HOSTED_CHECKOUT.
  • Omit currency: the gateway decides the billing currency (table above), and a currency in the body does not change it.

4. Send the customer to paymentUrl ​

Both gateways answer 201 with a paymentUrl. Open it; the customer pays there.

The payment is settled by the gateway's webhook, not by the browser coming back. Confirm the result from the booking or invoice status rather than from the return to your site.

Calling generate-payment again with the same gateway returns the same payment and paymentUrl (same paymentId, attemptNumber unchanged) while that payment is still PENDING, its link has not expired, and it bills the same amount. So a double click does not create a second charge link. Once the link has expired or failed, or the amount has changed, the next call creates a new one.

Two calls that arrive at the same moment are handled the same way: the second one waits for the first and gets its link. If it cannot get its turn within about 20 seconds it answers 409 (see Errors); call again.

Switching gateway ​

On an OTA invoice the customer can go back to the payment screen and pick the other gateway, for example Xendit after opening Moyasar's page. Call generate-payment with the new paymentGatewayCode. The server first cancels the open link on the other gateway, so the old link can no longer be paid, then answers 201 with the new link.

  • If the old link was paid in the meantime, the server records that payment and answers 400 (invoice already paid). Show the booking as paid.
  • If the other gateway cannot confirm the cancel, the server answers 503 and creates nothing. The old link is still the live one: send the customer back to it, or let them try the switch again.
  • An invoice can have at most 4 payment links over its life (the first one plus 3 switches). After that, a new link is refused with 400; the link that is open keeps working until the booking deadline.

Switching does not extend the booking's payment deadline.

Errors ​

If the client sends a gateway that available-gateways did not list, the server refuses it with a 400:

InvoicepaymentGatewayCodeResponse
SAR or USD (created before invoices became IDR-only)XENDIT400 Xendit only supports IDR invoices. Received 'SAR'.
USD, or an IDR invoice not created from an OTA bookingMOYASAR400 Moyasar only supports SAR invoices and IDR OTA booking invoices. Received 'IDR'.
IDR OTA invoice with a discountMOYASAR400 Moyasar is not available for a discounted invoice: …

These responses carry "code": "UNCODED", and the message text is not a stable contract. Do not branch on either. A client that renders only what available-gateways returns does not reach them.

These refusals can reach a correct client:

StatusWhenWhat to do
400paymentMethod is not one the gateway accepts. This is checked on every call, including one that would hand back an open link.Omit paymentMethod.
400A switch found the old link already paid (invoice already paid), or the invoice has had 4 payment links.Show the booking status; for the limit, send the customer to the link that is still open.
409Another request for the same invoice was still creating its payment after about 20 seconds.Call generate-payment again. If the other request created a payment, you get its link.
409A switch found the old link paid for a different amount than it billed.Stop and contact support; an admin must check the payment.
503A switch could not get the other gateway to confirm the cancel. Nothing was created.Keep the old link, or try the switch again.

Use available-gateways for OTA invoices ​

GET /invoice/:invoiceId/payment-options is built for custom-booking invoices. It also answers on an OTA invoice: idr is the Xendit option and sar the Moyasar option with the SAR amount it bills, each null when that gateway cannot take the invoice. It does not drop a gateway that is switched off, so build the OTA payment screen from available-gateways, which carries each gateway's currency and amount itself.

Custom bookings ​

A custom-booking invoice is created in IDR, and Moyasar does not appear on it (Moyasar takes IDR invoices from OTA bookings only). It can be paid by:

OptionWhere it comes fromGuide
Xendit (IDR)available-gateways, and idr in payment-optionsthis page
Manual bank transfer in SAR, USD or IDRmanualTransfer.currencyOptions in payment-optionsManual Bank Transfer
Cash in SAR at an Ahlaan officeinPerson in payment-optionsIn-Person Office Payment

For a custom booking, build the payment screen from payment-options, as the manual transfer guide describes.

Not covered here ​

  • BlockSeat bookings are limited to the gateways in their allow-list; see BlockSeat Bookings.
  • Paying from the wallet (paymentMethod: "WALLET" on POST /ota/book) debits the wallet balance and does not go through a gateway.
  • Wallet top-up (POST /wallet/topup) creates its invoice and payment in one call, without available-gateways.
