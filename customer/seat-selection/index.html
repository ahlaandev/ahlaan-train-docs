Seat Selection ​

This guide explains how a passenger views the seat map for a booking and moves to a different seat.

Quick Overview ​

FeatureDescription
Seat MapGET /api/v1/ota/bookings/:id/seat-map - Every seat on the train, plus the seats this booking holds
Change SeatPATCH /api/v1/ota/bookings/:id/seat - Move one passenger to one seat on one segment
AuthenticationRequired. Both endpoints are scoped to the booking owner
CostNone. The carrier returns no price for a seat and charges nothing for a change

The three rules that decide everything ​

Before building a screen against these endpoints, read this section. Most support questions come from here.

1. Every booking already has a seat ​

The carrier assigns a seat when the booking is created, before any payment, and keeps a party together where it can. A three passenger booking was assigned 137, 138 and 139 on one measurement.

So this feature is change your seat, not choose a seat. The assigned coach and seat are available on the booking detail from the moment the booking exists, and can be shown on a confirmation screen before payment.

2. The seat map only exists after payment ​

The carrier will not release a seat map for an unpaid booking, and there is no seat map for a train in general. It exists only in the context of one paid booking. A request before payment is refused with 400.

There are two refusals here, and they read differently. The service checks the booking's own status first and answers without calling the carrier at all. If that check passes but the carrier still does not consider the booking paid - which happens when an invoice was settled on our side before the money reached the carrier - the carrier refuses instead, and that refusal is translated into our own wording. Both are 400; only the second costs an upstream call.

This means a seat picker cannot be offered during checkout, before the booking is paid for. Place it after payment, or on the booking detail page.

3. The window closes 72 hours before departure ​

The carrier sets a change deadline at exactly 72 hours before the outbound departure. After that, neither the map nor a change is possible.

A booking made inside 72 hours of departure therefore has no window at all - it is already closed when the booking is created. This is a normal, everyday situation for a last minute traveller, not an error. Show the seat section with an explanation rather than hiding it or letting the request fail.

That case gets its own message, because the deadline fell before the booking existed and quoting it would read as though the passenger missed something they could have done:

This booking was made too close to departure, so seats were already closed when it was created. The seat assigned at booking is the one you travel on.

A booking whose window closed after it was made still gets the deadline, which can be shown as-is:

Seat changes are no longer possible for this booking. The window closed at 15 Jul 2026, 16:30 WIB.

Where a seat change sits in the whole journey ​

The seat screen is reachable only in one window of the booking's life. This is the journey end to end, so a client knows what must already have happened before it renders anything.

What a client must take from this

  • Steps 3 and 4 are impossible before step 2 finishes. Not "empty", not "retryable" - refused with 400. The booking carries a seat from step 1, so a pre-payment screen can show the seat it already has; it cannot show the map or offer a change.
  • The window is measured from departure, not from payment. A booking made inside 72 hours of departure goes from step 2 to step 5 with no step 3 or 4 ever available.
  • Step 4 moves one passenger. Two passengers is two requests, each able to fail on its own.
  • Step 5 is the passenger's existing link. Nothing new is issued: the document is rendered on demand and always carries the current seat. A PDF already saved or emailed keeps the old seat forever, which is why the step 4 response says so and the client should show that message rather than a generic success toast.

How much of this is proven. All five steps were exercised end to end on staging against the live carrier, on three bookings paid through the Xendit sandbox: a one-way, a round trip, and a GROUP booking of 11 unnamed passengers. The seat map returned real coaches and seats, a change moved the passenger, the stored seat was refreshed, and the re-downloaded PDF printed the new seat while the old one appeared nowhere in it. On the round trip a change to the return leg left the outbound seat untouched.

One case this run did not cover: a seat change on an infant, which is refused before any carrier call is made.

Authorization: Bearer <token>

Reading the response ​

  • segments carries one entry per leg. A round trip returns two, segmentRph "1" for the outbound and "2" for the return.
  • available is the only field to drive selectability. It is true for exactly one carrier value and false for everything else, including values the carrier's own documentation does not list.
  • occupiedByThisBooking marks a seat one of your own passengers is sitting in. Worth rendering differently from a seat taken by a stranger.
  • currentSeats is the only place that says which passenger holds which seat, and carries each one's passengerType. The map itself marks a seat as taken without naming the holder, so this list cannot be derived from segments.
  • cabinType is the carrier's cabin code. P is business and T is economy.

Size ​

The map is large. A single segment is a few hundred kilobytes at the carrier before it is reduced, and a round trip roughly doubles that. Fetch it when the passenger opens the seat screen rather than eagerly, and do not cache it: a seat taken between render and submit is the case the 409 below exists for.

Change a seat ​

http
PATCH /api/v1/ota/bookings/{bookingId}/seat
Authorization: Bearer <token>
Content-Type: application/json

{
  "segmentRph": "1",
  "travelerRph": 1,
  "seatNumber": "150"
}

Rules ​

  • One seat per request. To move several passengers, send several requests and handle each result separately. There is no batch form.
  • Do not send a coach. The carrier works it out from the seat number, and a move may cross coaches.
  • There is no limit on how many times a seat may change while the window is open.
  • A ticketed booking may still change seats. This is unlike a passenger name, which the carrier refuses to change once tickets are issued.

Response ​

json
{
  "success": true,
  "message": "Seat updated to 150 in coach 006. Open your ticket link again to download the updated ticket - a ticket already saved or emailed still shows the old seat.",
  "currentSeats": [
    {
      "travelerRph": 1,
      "segmentRph": "1",
      "seat": "150",
      "coach": "006",
      "passengerType": "ADT"
    }
  ]
}

Tickets after a seat change ​

The download link the passenger already has keeps working and always shows the current seat - the ticket document is generated fresh each time it is opened, and the e-ticket number never changes.

What does not update is a copy already delivered: a PDF saved to a phone, or the attachment on a confirmation email, was rendered before the change and keeps the old seat forever. That is why the response message tells the passenger to download again, and the client should surface that message rather than replacing it with a generic success toast.

Passengers who cannot be moved ​

PassengerBehaviour
InfantTravels on the accompanying adult's lap and is not allocated a seat of its own - it shares the adult's. currentSeats[].passengerType is INF for one, and it reports the adult's coach and seat, which is why an infant row looks like a duplicate of the adult's. Do not render a seat control for that row. Asking to move one is refused with 400. Moving the adult moves the infant with it
Unnamed GROUP passengerA GROUP booking is created with passenger counts, not names. The carrier refuses a seat change for a passenger who has no name yet, so add the name first. The map is readable regardless, and the rule applies per passenger, so a named passenger may be moved while unnamed ones on the same booking cannot

What a 400 actually looks like ​

Every error carries the service's standard envelope, not a bare message:

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Seats can only be chosen once the booking has been paid.",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

Captured on staging, unchanged:

Casemessage
Booking not paid on our sideSeats are only available once the booking has been paid. Current status: PENDING
Booking paid with us, not yet with the carrierSeats can only be chosen once the booking has been paid.
Window already closedSeat changes are no longer possible for this booking. The window closed at 15 Jul 2026, 16:30 WIB.
Booking made inside the windowThis booking was made too close to departure, so seats were already closed when it was created. The seat assigned at booking is the one you travel on.
Passenger has no name yetThis passenger has no name yet. Add the passenger name before choosing a seat.
Segment not on this bookingSegment 7 is not part of this booking
Body fails validationan array, e.g. ["segmentRph must be a segment reference number, for example \"1\"", "travelerRph must not be less than 1"]

Most of these can be shown to a passenger as they are, but not all of them. Three need handling by the client rather than display:

  • the first one ends in Current status: PENDING, and that word is the internal booking status - it can also read FAILED;
  • Segment 7 is not part of this booking is a client-side mistake, not something a passenger can act on;
  • a validation failure returns an array in message, not a string.

A request with no token returns 401 before any of this.
