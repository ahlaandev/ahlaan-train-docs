Unified 400 Error Envelope (OTA) ​

Every 400 Bad Request returned by the OTA booking surface (POST /ota/book/calculate, POST /ota/book) — and, in practice, every validated endpoint on this API — uses a single, machine-readable envelope so the client can branch on code / category / retryable instead of parsing English message strings.

The legacy fields statusCode, error, and message are preserved verbatim, so older clients that only read those three keep working.

Envelope shape ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Human-readable English string.",
  "code": "FLIGHT_UNAVAILABLE",
  "category": "INVENTORY_MISMATCH",
  "retryable": true,
  "cause": "likely_inventory_change",
  "context": { "leg": "OUTBOUND", "flightNumber": "G503" }
}
FieldTypeNotes
statusCode400Always 400 for this envelope.
error"Bad Request"NestJS-standard label.
messagestringHuman-readable fallback. Do not parse.
codeenum string (see below)Stable across releases. Adding new codes is non-breaking; renaming is breaking.
categoryINVENTORY_MISMATCH | PRICING_DATA | VALIDATIONCoarse routing bucket.
retryablebooleantrue ⇒ re-triggering /ota/search may produce different results. false ⇒ user must change input.
causelikely_inventory_change | likely_client_stale | unknown (optional)Emitted only on INVENTORY_MISMATCH codes; absent on VALIDATION and PRICING_DATA. FE may use for copy variation. Must not branch retry on this.
contextobject (optional)Code-specific extra fields. Never includes PII.

Codes ​

Inventory mismatch — retryable: true ​

codeWhen it firescontext
NO_OUTBOUND_FLIGHTSSearch returned zero outbound flights for the requested route/date.—
NO_RETURN_FLIGHTSROUND_TRIP: search returned zero return flights.—
FLIGHT_UNAVAILABLEOutbound flightSegment no longer matches any flight in fresh search results.{ leg: "OUTBOUND", flightNumber? }
RETURN_FLIGHT_UNAVAILABLEReturn flightSegment no longer matches.{ leg: "RETURN", flightNumber? }
FARE_UNAVAILABLEOutbound fareId not present in fresh fare list.{ fareId, leg: "OUTBOUND" }
RETURN_FARE_UNAVAILABLEReturn fareId not present.{ fareId, leg: "RETURN" }

For FLIGHT_UNAVAILABLE/RETURN_FLIGHT_UNAVAILABLE, cause distinguishes:

  • likely_inventory_change — same flightNumber exists in fresh results at a different time; supplier likely retimed/sold-out the original.
  • likely_client_stale — flightNumber doesn't exist anywhere in fresh results; the client is probably sending an old or wrong segment.

Pricing data — retryable: false ​

codeWhen it firescontext
FARE_DATA_INCOMPLETESupplier returned a fare row missing the fields needed to compute OTA price (outbound).{ leg: "OUTBOUND" }
RETURN_FARE_DATA_INCOMPLETESame, for return leg.{ leg: "RETURN" }

Validation — retryable: false ​

codeWhen it firescontext
INPUT_VALIDATIONDTO validation failed (malformed email, missing required field, wrong enum, etc.).{ fields: [ { path, constraint, message }, … ] }
MALFORMED_BODYRequest body was not valid JSON.—
ROUND_TRIP_RETURN_MISSINGCaller declared ROUND_TRIP but no return flights are available.—
PASSENGER_COUNT_INVALIDTotal passenger count is zero or negative.—
PASSENGER_COUNT_MISMATCHpassengers.length ≠ adults + children + infants.{ arrayCount, quantitiesSum }
MINIMUM_FARE_BELOW_THRESHOLDPer-passenger price below the configured floor.{ priceSar, minimumSar }
GROUP_BOOKING_WITHIN_72_HOURSGROUP booking attempted within 72h of departure.—
UNCODEDLegacy BadRequestException that hasn't yet been migrated to a structured code. Safe to handle as a generic validation failure.—

Example — malformed email ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": ["email must be an email"],
  "code": "INPUT_VALIDATION",
  "category": "VALIDATION",
  "retryable": false,
  "context": {
    "fields": [
      { "path": "contactPerson.email", "constraint": "isEmail", "message": "email must be an email" }
    ]
  }
}

Example — passenger count mismatch ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Passenger count mismatch: 2 in array vs. 3 in quantities.",
  "code": "PASSENGER_COUNT_MISMATCH",
  "category": "VALIDATION",
  "retryable": false,
  "context": { "arrayCount": 2, "quantitiesSum": 3 }
}

Suggested FE handling ​

ts
if (res.status === 400) {
  const body = await res.json();

  switch (body.category) {
    case 'INVENTORY_MISMATCH':
      // Re-run /ota/search and let the user pick again.
      return retryFromSearch({ cause: body.cause });

    case 'PRICING_DATA':
      // Supplier data is missing; surface generic message, no retry.
      return showFatal(body.message);

    case 'VALIDATION':
      if (body.code === 'INPUT_VALIDATION') {
        // Per-field detail in body.context.fields[*]
        return surfaceFieldErrors(body.context.fields);
      }
      return showFatal(body.message);
  }
}

Migration note ​

The envelope is backwards-compatible with the legacy NestJS ValidationPipe shape:

  • For INPUT_VALIDATION the top-level message is still string[] (the flattened class-validator constraint messages). Existing FE code that does Array.isArray(error.message) ? error.message.join(', ') : error.message continues to work unchanged.
  • For all other codes (service-layer throws like FLIGHT_UNAVAILABLE, FARE_UNAVAILABLE, MINIMUM_FARE_BELOW_THRESHOLD, etc.) message is a single string, exactly as before.

New consumers should prefer branching on code and reading structured detail from context.fields[] (for INPUT_VALIDATION) or context.{leg, fareId, flightNumber, …} (for inventory/pricing codes) instead of parsing message text.

This contract applies to every validated endpoint on the API, not only /ota/book*.
