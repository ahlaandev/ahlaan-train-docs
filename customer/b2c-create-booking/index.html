Create Booking (B2C) ​

This guide explains how individual customers (B2C) can create train bookings through the HHR API. Bookings can be made with or without authentication, supporting both guest users and registered accounts.

Key Requirements ​

  • Contact Person Required: contactPerson is required for ALL bookings
  • Booking Type Auto-Determined: Booking type is automatically set based on passenger count:
    • REGULAR: ≤10 passengers (adults + children)
    • GROUP: >10 passengers (adults + children)
  • Infant Rule: Number of infants cannot exceed number of adults (infants sit on adult laps)
  • OTA Reference: Booking references from OTA system are 5-6 characters (e.g., XVW3NR)
  • Authentication: Uses @CurrentUser() decorator with OptionalAuthGuard - works for both guest and authenticated users

Quick Start ​

Minimal Booking (Guest User) ​

bash
# 1. Search for flights
POST /api/v1/ota/search
{
  "origin": "DMX",
  "destination": "JXD",
  "departureDate": "2026-02-01",
  "tripType": "ONE_WAY",
  "passengerQuantities": { "adults": 1, "children": 0, "infants": 0 }
}

# 2. Create booking (use flightSegment and fareId from search response)
POST /api/v1/ota/book
{
  "fareId": "OTAPENALTYB",
  "tripType": "ONE_WAY",
  "origin": "DMX",
  "destination": "JXD",
  "departureDate": "2026-02-01",
  "passengers": [{ /* passenger details */ }],
  "contactPerson": {
    "firstName": "Ahmad",
    "lastName": "Al-Saud",
    "email": "ahmad@example.com",
    "phone": "+966501234567"
  },
  "flightSegment": { /* from search response */ },
  "paymentMethod": "BANK",
  "guestContact": { "email": "...", "phone": "..." }
}

Booking Types (Auto-Determined) ​

Booking type is automatically determined based on passenger count. You do not need to specify bookingType in requests.

TypePassenger CountDetails RequiredUse Case
REGULAR≤10 (adults + children)Full passenger details at bookingIndividual bookings
GROUP>10 (adults + children)Quantities only, names added laterLarge group bookings

Note: Infants don't count toward the passenger limit for booking type determination.

Payment Methods ​

MethodAuth RequiredInitial StatusFlow
BANKNoPENDINGInvoice created → User pays → Booking confirmed
WALLETYesCONFIRMEDWallet charged → Instant confirmation

API Endpoint ​

POST /api/v1/ota/book

Authentication: Optional (guest users can book with guestContact)

  • Uses @CurrentUser() decorator with OptionalAuthGuard
  • JWT token should include sub claim for user identification
  • Missing token = guest booking (requires guestContact)

Request Format ​

Headers ​

Content-Type: application/json
Authorization: Bearer {token}  // Optional, for authenticated users

Body Parameters ​

FieldTypeRequiredDescription

| fareId | string | Yes | From search response (e.g., OTAPENALTYB) | | tripType | string | Yes | ONE_WAY or ROUND_TRIP | | origin | string | Yes | Station code (e.g., DMX) | | destination | string | Yes | Station code (e.g., JXD) | | departureDate | string | Yes | ISO 8601 date (e.g., 2026-02-01) | | returnDate | string | Conditional | Required for ROUND_TRIP | | returnFareId | string | Conditional | Required for ROUND_TRIP | | flightSegment | object | Yes | From search response | | returnFlightSegment | object | Conditional | For ROUND_TRIP | | passengers | array | Conditional | Required for ≤10 passengers | | passengerQuantities | object | Conditional | Required for >10 passengers | | contactPerson | object | Yes | Required for ALL booking types | | paymentMethod | string | No | BANK (default) or WALLET | | guestContact | object | Conditional | For guest users (no auth) | | rememberPassengers | boolean | No | Save to account (auth only) |

Time Limits Explained ​

The timeLimits object contains critical deadlines from the OTA system (EBKS/GO7):

FieldSource SystemPurpose
confirmationTimeLimitEBKSDeadline to confirm the booking with payment
ticketTimeLimitGO7Ticketing deadline after confirmation
cancellationTimeLimitEBKSFree cancellation deadline
updateTravellersTimeLimitEBKSDeadline to update passenger names

All timestamps are in ISO 8601 format (e.g., 2026-01-28T19:20:27Z).

Payment Time Limits & Expiry ​

When a booking is created with paymentMethod: "BANK", a payment link is generated with a time limit for completion.

How Payment Expiry Works:

  1. Dynamic Time Limit: The payment expiry is calculated from the OTA ticketTimeLimit minus a 2-minute buffer
  2. Default: 24 hours if no OTA time limit is provided
  3. Countdown: Payment must be completed before expiresAt timestamp

Payment Response with Expiry:

json
{
  "payment": {
    "id": "pay_456",
    "qrString": "000201010212...",
    "amount": 2181971,
    "status": "PENDING",
    "expiresAt": "2026-01-28T10:43:10.000Z"
  },
  "expiryDisplay": {
    "iso": "2026-01-28T10:43:10.000Z",
    "local": "1/28/2026, 1:43:10 PM",
    "minutesRemaining": 28,
    "message": "Payment must be completed within 28 minutes"
  }
}

Field Descriptions:

FieldDescription
expiresAtISO 8601 timestamp when payment expires
expiryDisplay.isoUTC timestamp in ISO format
expiryDisplay.localFormatted local time for user display
expiryDisplay.minutesRemainingInteger minutes until expiry
expiryDisplay.messageHuman-readable countdown message

What Happens When Payment Expires:

  1. Scheduled Job: A background job checks payment status at expiry time
  2. Auto-Cancellation: If payment is still PENDING, booking is automatically cancelled
  3. Webhook Backup: Xendit webhooks also trigger expiry handling
  4. Safety Net: The 2-minute buffer ensures we can cancel before GO7's hard limit

UI Display Recommendations:

Time RemainingDisplay MessageColor
> 10 minutes"Complete payment within X minutes"Green
5-10 minutes"⚠️ Payment expiring soon!"Orange
2-5 minutes"🔴 Payment expires in X minutes"Red
< 2 minutes"⛔ Payment expires very soon!"Red/Blinking

IMPORTANT: Always show the countdown timer to customers. Payment expiry is enforced automatically - customers will lose their booking if payment is not completed on time.

UAT Test Scenarios ​

The following scenarios have been validated through UAT testing:

TC-RES-01: ONE-WAY Reservation (Without Payment) ​

Scenario: Create a one-way booking from MKX to DMX in Business class (C) without payment.

Steps:

  1. Search for trains: POST /api/v1/ota/search
  2. Create booking with paymentMethod: "BANK"
  3. Status: PENDING with confirmationTimeLimit applied

Result: ✅ Booking created with OTA reference (5-6 characters) and time limits.

TC-RES-02: ROUND-TRIP Reservation (Without Payment) ​

Scenario: Create a round-trip booking (MKX→DMX→MKX) in Economy class (Y) without payment.

Steps:

  1. Search for round-trip trains: POST /api/v1/ota/search with tripType: "ROUND_TRIP"
  2. Create booking with outbound and return flight segments
  3. Status: PENDING with confirmationTimeLimit applied

Result: ✅ Round-trip booking created with both segments reserved.

TC-RES-03: Business Class Booking WITH Payment ​

Scenario: Create a Business class booking with instant wallet payment.

Steps:

  1. Search for Business class flights
  2. Create booking with paymentMethod: "WALLET"
  3. Status: CONFIRMED (instant payment confirmation)

Result: ✅ Booking confirmed immediately, tickets queued for issuance.

TC-RES-04: Economy Class Booking WITH Payment ​

Scenario: Create an Economy class booking with instant wallet payment.

Steps:

  1. Search for Economy class flights
  2. Create booking with paymentMethod: "WALLET"
  3. Status: CONFIRMED (instant payment confirmation)

Result: ✅ Booking confirmed immediately, tickets queued for issuance.

Note: Wallet payment tests require users to have a wallet with sufficient balance. Use BANK payment method for reservations without immediate payment.

TC-RES-05: ONE-WAY with Payment (Business Class) ​

Scenario: Create a one-way Business class booking with wallet payment and verify auto-ticketing.

Steps:

  1. Search for Business class flights (MKX → DMX)
  2. Create booking with paymentMethod: "WALLET"
  3. Verify status: CONFIRMED → TICKETED (auto-ticketing for wallet payments)

Expected Result: ✅ Booking confirmed and auto-ticketed.

TC-RES-06: ROUND-TRIP with Payment (Business Class) ​

Scenario: Create a round-trip Business class booking with wallet payment.

Steps:

  1. Search for round-trip trains: POST /api/v1/ota/search with tripType: "ROUND_TRIP"
  2. Create booking with outbound and return flight segments
  3. Use paymentMethod: "WALLET" for instant confirmation
  4. Verify both segments are ticketed

Expected Result: ✅ Round-trip booking confirmed and auto-ticketed for both segments.

json
{
  "statusCode": 400,
  "message": "Contact person details are required for booking",
  "error": "Bad Request"

json
{
  "statusCode": 400,
  "message": "Insufficient balance. Required: 500 SAR, Available: 200 SAR",
  "error": "Bad Request"

Solution: Use BANK payment or add funds to wallet.

401 Unauthorized - Invalid Token ​

json
{
  "statusCode": 401,
  "message": "Invalid token payload",
  "error": "Unauthorized"
}

Solution: Ensure JWT token has valid sub claim and user exists in database.

500 Internal Server Error - OTA Unavailable ​

json
{
  "statusCode": 500,
  "message": "Failed to create booking after multiple attempts",
  "error": "OTA_BOOKING_FAILED"
}

Solution: OTA system may be temporarily unavailable. The system automatically retries up to 3 times with exponential backoff.

Important Notes ​

Contact Person Requirement ​

  • contactPerson is required for ALL booking types (REGULAR and GROUP)
  • This is the primary contact for booking communications
  • Separate from passenger data and guest contact information
  • Used for OTA system CTC (Contact) entity

Passenger Limits & Booking Type ​

  • REGULAR bookings: ≤10 passengers (adults + children)
  • GROUP bookings: >10 passengers (adults + children)
  • Infants don't count toward the limit for booking type determination
  • Booking type is automatically determined based on passenger count

Infant Rule ​

  • Number of infants cannot exceed number of adults
  • Infants sit on adult laps (no separate seat)
  • Infants are not included in the 10-passenger B2C limit

Time Limits ​

  • Monitor confirmationTimeLimit and ticketTimeLimit
  • Bookings auto-cancel if not confirmed by deadline
  • Free cancellation before cancellationTimeLimit

Payment Expiry ​

  • Payment links have a strict time limit (shown in expiresAt field)
  • Default expiry: 24 hours (or shorter based on OTA time limits)
  • Countdown timer: Display expiryDisplay.minutesRemaining to customers
  • Auto-cancellation: Unpaid bookings are automatically cancelled when payment expires
  • The system uses a 2-minute buffer before GO7's ticketing deadline to ensure safe cancellation

Authentication Details ​

  • Uses JWT with HS256 algorithm
  • Token payload requires sub claim (user ID)
  • OptionalAuthGuard allows both guest and authenticated bookings
  • Authenticated users get user.id populated from JWT validation
  • Guest bookings require guestContact information

Retry Logic ​

  • OTA API calls automatically retry up to 3 times
  • Exponential backoff: 1s → 2s → 4s (max 10s delay)
  • Retries on transient errors (timeouts, temporary failures)
  • No retry on 4xx client errors or 5xx server errors
