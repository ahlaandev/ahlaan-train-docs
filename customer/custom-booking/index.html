Custom Booking (Customer) ​

This guide covers the customer-facing endpoints for creating and managing a custom booking — the flow that follows a Custom OTA search and price calculation. It supports both authenticated users and guests.

For the pricing/search step that precedes this flow, see the Custom OTA guide. For status semantics and ticket confirmation after receipt, see the Custom Booking Status guide.

Quick Overview ​

ActionEndpointAuth
Create bookingPOST /api/v1/custom-bookingOptional (guest OK)
Get by IDGET /api/v1/custom-booking/:idAuthenticated or guest (email + phone)
Get by booking codeGET /api/v1/custom-booking/code/:bookingCodeAuthenticated or guest (email + phone)
Update passengers (manifest)PATCH /api/v1/custom-booking/:id/passengersOpen (booking ID acts as capability)
Confirm ticket receivedPATCH /api/v1/custom-booking/:id/confirm-receivedAuthenticated or guest (email + phone)

End-to-End Flow ​

[1] Search            POST /custom-ota/search
[2] Calculate price   POST /custom-ota/book/calculate
[3] Create booking    POST /custom-booking                  ← this guide
[4] Fill manifest     PATCH /custom-booking/:id/passengers  ← this guide
[5] Upload manifest   POST  /custom-booking/:id/manifests   (see custom-manifest guide)
[6] Await confirm     GET   /custom-booking/:id             (poll status)
[7] Receive ticket    Email + status TICKET_RECEIVED
[8] Confirm receipt   PATCH /custom-booking/:id/confirm-received

Authentication ​

All customer custom-booking endpoints use OptionalAuthGuard:

  • Authenticated customer: send Authorization: Bearer <token>. The booking is linked to the user's account (userId populated).
  • Guest: omit the bearer token. The system finds-or-creates a user record from contactPerson.email + contactPerson.phone, and the booking is linked to that guest account. To read or act on the booking later, the guest must supply the same email and phone as query parameters for verification.

B2B users: organizationId is auto-resolved from the user's organization membership; you do not need to (and should not) set it in the request body.

Base URL ​

/api/v1

1. Create a Custom Booking ​

POST /custom-booking

Creates a CustomBooking in status PENDING using flight and pricing data returned by the Custom OTA calculate endpoint. The server resolves the price itself from CustomRoutePrice / ScraperPriceRecord — the client does not send prices. Mismatches between what the user saw and the live price are re-computed server-side.

Request Body (ONE_WAY) ​

json
{
  "origin": "DMX",
  "originName": "Madinah",
  "destination": "JXD",
  "destinationName": "Jeddah",
  "tripType": "ONE_WAY",
  "departureDate": "2026-04-17",
  "outboundFlight": {
    "flightNumber": "1121",
    "departureDateTime": "2026-04-17T12:30:00.000+03:00",
    "arrivalDateTime": "2026-04-17T14:11:00.000+03:00",
    "className": "Business",
    "tripClass": "BUSINESS",
    "resBookDesigCode": "C",
    "fareReference": "DMX:JXD",
    "sequenceNumber": 0
  },
  "contactPerson": {
    "email": "user@example.com",
    "phone": "628515001838"
  },
  "adultCount": 1,
  "childCount": 0,
  "infantCount": 0,
  "exchangeRateId": "exchange-rate-uuid"
}

Request Body (ROUND_TRIP) ​

For ROUND_TRIP, both returnDate and returnFlight are required.

json
{
  "origin": "DMX",
  "destination": "JXD",
  "tripType": "ROUND_TRIP",
  "departureDate": "2026-04-17",
  "returnDate": "2026-04-20",
  "outboundFlight": { "...": "same shape as above" },
  "returnFlight":   { "...": "same shape, return leg" },
  "contactPerson":  { "email": "...", "phone": "..." },
  "adultCount": 2,
  "childCount": 1
}

2. Get Booking by ID ​

GET /custom-booking/:id

Authenticated ​

bash
curl -X GET /api/v1/custom-booking/booking-uuid \
  -H "Authorization: Bearer <token>"

Guest ​

Both email and phone must match the contactPerson stored on the booking.

bash
curl -X GET "/api/v1/custom-booking/booking-uuid?email=user@example.com&phone=628515001838"

Response (200) ​

Same shape as the create response, plus:

  • invoice — populated once status reaches CONFIRMED / later
  • manifests — array of uploaded manifest file metadata (see custom-manifest guide)

Errors ​

StatusWhen
401Guest request missing email or phone
403Authenticated user does not own this booking
404Booking not found or guest email/phone don't match (intentionally indistinguishable)

3. Get Booking by Booking Code ​

GET /custom-booking/code/:bookingCode

Identical behavior to GET /:id, but looks up by the 7-character bookingCode instead. Useful for customer-support flows where the user knows the code from their confirmation email but not the UUID.

bash
curl -X GET "/api/v1/custom-booking/code/ABC1234?email=user@example.com&phone=628515001838"

4. Update Passenger Manifest ​

PATCH /custom-booking/:id/passengers

Fills in the passenger list (Step 3 of the booking flow). The count and breakdown must match the booking's adultCount + childCount + infantCount.

This endpoint is not behind a bearer-token check — possession of the booking ID is the capability. The booking must already exist.

Request Body ​

json
{
  "passengers": [
    {
      "passengerTypeCode": "ADT",
      "title": "MR",
      "firstName": "John",
      "middleName": "Michael",
      "lastName": "Doe",
      "idType": "PASSPORT",
      "idNumber": "A12345678",
      "idExpirationDate": "2030-12-31",
      "nationality": "SA",
      "countryOfResidence": "SA",
      "dateOfBirth": "1990-01-15",
      "gender": "Male",
      "phone": "966501234567",
      "email": "passenger@example.com"
    }
  ]
}

Passenger Fields ​

FieldTypeRequiredNotes
passengerTypeCodeADT | CHD | INFyesMust match counts exactly
titlestring (≤20)yese.g., MR, MRS, MISS
firstNamestring (≤100)yes
middleNamestring (≤100)no
lastNamestring (≤100)yes
idTypePASSPORT | NATIONAL_IDyesUppercased server-side

Validation Rules ​

  • Total passenger count must equal adultCount + childCount + infantCount.
  • The number of ADT entries must equal adultCount exactly (same for CHD/INF).
  • A BadRequestException with a specific mismatch message is returned otherwise.

Response (200) ​

Updated booking with passengers populated.

Errors ​

StatusWhen
400Expected N passengers (A ADT, B CHD, C INF), but received M
400Expected N adult passengers, but received M (or child / infant)
400DTO validation error on any passenger field
404Booking not found

5. Confirm Ticket Received ​

See the Custom Booking Status guide for the PATCH /custom-booking/:id/confirm-received endpoint. It transitions the booking from TICKET_RECEIVED → COMPLETED once the customer confirms they received the ticket.
