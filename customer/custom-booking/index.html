Custom Booking (Customer) ​

This guide covers the customer-facing endpoints around a custom booking — the flow that follows a Custom OTA search and price calculation.

⚠️ MITRA-4 — writes are admin / act-as-customer only. A pure customer (a real end-user, not impersonated) is now read-only on custom booking: they may search, list, view detail, and download invoices/tickets, but they cannot create, edit the manifest, or cancel. Every write is reserved for an admin, or an admin acting as the customer via an impersonation token (see the impersonation guide). A pure customer hitting a write route receives 403. The anonymous email + phone path no longer authorizes those writes (they require a JWT). Exception: confirm-received is unchanged for now (still customer- accessible) — its lock is deferred to a later slice.

Legacy guest bookings remain readable via email + phone on the read endpoints.

For the pricing/search step that precedes this flow, see the Custom OTA guide. For status semantics and ticket confirmation after receipt, see the Custom Booking Status guide.

End-to-End Flow ​

[1] Search            POST /custom-ota/search
[2] Calculate price   POST /custom-ota/book/calculate
[3] Create booking    POST /custom-booking                  ← admin / act-as-customer
[4] Fill manifest     PATCH /custom-booking/:id/passengers  ← admin / act-as-customer
                      └─ auto-confirms the booking (status → CONFIRMED) and
                         emails the customer a confirmation
[5] Choose method     POST /invoice/:id/generate-payment    (Xendit, or SAR/USD transfer)
                      └─ matching instructions sent via WhatsApp (or email)
[6] Pay               Open the Xendit link, or transfer to the bank account sent
[7] Track status      GET /custom-booking/:id               (customer-readable)
[8] Ticket uploaded   Status TICKET_UPLOADED_FULL (all passengers ticketed) or
                      TICKET_UPLOADED_PARTIAL (the airline short-delivered).
                      └─ sends nothing: your booking still reports
                         WAITING_FOR_TICKET and shows no ticket until a
                         second admin reviews it
                      └─ that admin's release is what emails you and opens
                         your download — not the upload. A rejection instead
                         emails nobody and changes nothing you can see
[9] Booking closed    Status COMPLETED — blocked while an uploaded ticket is
                      still awaiting release; once released, closing itself
                      still sends nothing

Steps [3]/[4] (and cancel) are performed by an admin, or an admin acting as the
customer via impersonation — a pure customer is read-only (MITRA-4).

Auto-confirm. Filling the passenger manifest (step 4) normally confirms the booking immediately and emails you a confirmation — you do not wait for a manual admin review. If the platform operator has disabled auto-confirm, the booking stays at UPLOADED_MANIFEST until an admin confirms it. Payment instructions are not sent on confirmation; you receive them only after you pick a method via generate-payment (step 5).

Note. Step POST /custom-booking/:id/manifests (uploading a manifest file) is a separate, optional action and does not change the booking status — see the custom-manifest guide. It is the passenger list in step 4 that drives confirmation.

Legacy note. Bookings that reached TICKET_RECEIVED under the previous flow still need PATCH /custom-booking/:id/confirm-received — or the hourly auto-complete cron — to reach COMPLETED. New bookings never enter TICKET_RECEIVED: they are closed by an admin after the uploaded ticket is verified.

Authentication ​

Write routes are admin / act-as-customer only (MITRA-4). POST /custom-booking (create), PATCH /custom-booking/:id/passengers (manifest), and PATCH /custom-booking/:id/status (cancel) require a JWT belonging to either:

  • a real admin (role === ADMIN), or
  • an admin acting as the customer via an impersonation token (the principal is the customer, tagged with the acting admin — see the impersonation guide).

A pure customer (authenticated end-user, not impersonated) receives 403 on those routes; the anonymous email + phone path does not authorize them. On create, the impersonated customer must additionally be promo-eligible (effective promoAccessEnabled — the per-user override coalesced with the organization flag; admin-managed via Promo Customer Onboarding and Promo-Host Access Enrollment), while a real admin bypasses that check. Guest checkout was removed.

  • Missing / invalid bearer token on a write route → 401 Unauthorized.
  • Authenticated pure customer on a write route → 403 (writes are admin-on-behalf).
  • On create, an impersonated customer whose effective promo access resolves off → 403 Promo access is not enabled for your account. Please contact support.

An act-as-customer write is recorded in the audit log under CUSTOM_BOOKING_IMPERSONATION_* (audited actor = the acting admin, metadata.impersonated = true).

The read endpoints (list/detail/code/ticket GETs) and confirm-received (lock deferred) keep their existing guards and are not promo-gated — revoking an organization's promo access never strands an in-flight booking:

  • Authenticated customer: send Authorization: Bearer <token>. Access follows booking ownership (userId).
  • Guest (legacy bookings): bookings created as guests under the previous flow remain readable by supplying the same email and phone as query parameters for verification.

organizationId is always resolved server-side from the authenticated user's organization membership. Any organizationId sent in the request body is ignored — a client cannot set or spoof the booking's organization, so a B2C user can never tag a booking to an org they don't belong to.

⛔ A real admin token is refused on three of these routes ​

These routes are for customers. An admin used to be waved straight through them to any booking with no permission consulted — which meant an admin token holding no permissions at all could read a booking's full cost basis using only a booking code, and booking codes appear in every customer email.

Three routes now answer 403 to a token whose role is ADMIN, because each already has an admin equivalent that gates booking money on its own permission codes — custom-bookings:read-pricing for the selling prices and custom-bookings:read-capital-markup for the capital price and the markup:

Customer routeUse this instead
GET /custom-booking/:idGET /api/v1/admin/custom-booking/:id
GET /custom-booking/code/:bookingCodeGET /api/v1/admin/custom-booking?bookingCode=<code>, then the detail route with the returned id
PATCH /custom-booking/:id/statusPATCH /api/v1/admin/custom-booking/:id/status

The 403 body names the replacement route. Real response from preprod:

bash
curl https://preprod.mitra.ahlaan.co.id/api/v1/custom-booking/019f744b-098f-7664-b70d-1289f8171c4e \
  -H "Authorization: Bearer <ADMIN_TOKEN>"
json
{
  "message": "This customer route does not serve admin callers. Use GET /api/v1/admin/custom-booking/:id instead, which gates booking money behind custom-bookings:read-pricing and custom-bookings:read-capital-markup.   "error": "Forbidden",
  "statusCode": 403
}

The refusal happens before the service is reached, so nothing is read and — on PATCH :id/status — nothing is written: the booking's status is unchanged after a refused call. It applies to every real admin token, including a * super admin, because these routes carry no permission guard and so consult no permission at all.

"Act as customer" is unaffected. An impersonation token carries the customer's own role, so all three routes still work through it — which is the supported way for an admin to act on a customer's behalf here. Customers and guests see no change at all.

Two routes stay open to a real admin, because there is no admin equivalent to send them to: PATCH /custom-booking/:id/passengers (admin-only by design) and PATCH /custom-booking/:id/confirm-received. On those an admin caller gets the normal response with every money field removed — the six selling prices, capitalPriceTotalSAR, pricingSnapshot and the whole invoice block. invoiceId and exchangeRateId still return. Customers, guests and impersonation tokens are again unaffected.

GET /custom-booking ("my bookings") and GET /custom-booking/:id/ticket are not affected: the first is scoped to the caller's own userId, and the second returns a file.

1. Create a Custom Booking ​

POST /custom-booking

Admin / act-as-customer only (MITRA-4). This endpoint requires a bearer token for a real admin or an admin acting as the customer via impersonation — a pure customer receives 403. The impersonated customer must still have effective promo access on (per-user promoAccessEnabled override coalesced with the org flag; an org is not required); a real admin bypasses that check. 401 without a valid token. See Authentication. Guest checkout was removed by the promo customer separation.

Creates a CustomBooking in status PENDING from the flight data returned by the Custom OTA search/calculate endpoints. The server prices the booking itself from the live OTA pipeline and allocates the route's CustomRoutePrice.priceReducer per passenger by fare ratio (an adult discount; child/infant scaled by their per-pax fare share) on the supplier cost (HHR markup + HHR tax excluded; the supplier's own VAT is kept, as it is cost) — the client never sends prices. The reducer is resolved per leg. The full derivation is captured server-side in an admin-only pricingSnapshot that is not returned on customer responses (it exposes internal cost/margin basis); priceSource is OTA_PRICE. Each per-passenger payable is floored to a whole riyal, so the per-passenger columns re-sum exactly to the totalPriceSAR anchor that the invoice charges against (no sub-riyal residual).

Business class (owner 2026-06-15). A BUSINESS-class leg is priced with the Custom Markup + Custom Tax rules instead of the reducer: payable = floor(base + customMarkup) + floor(customTax) per passenger, with no strikethrough (otaGrandTotalSAR = 0 for that leg). The admin-only snapshot records pricingMode: "MARKUP_TAX", legSubtotalSAR, legTaxSAR, customTaxCode, and the applied markupRuleId / taxRuleId; the customer still sees the broken-out tax because the invoice breaks it out (subtotal + tax = total, ZATCA). ECONOMY legs are unchanged (reducer + retail strikethrough, sold tax-free). A round trip may mix classes — each leg is priced by its own class. A zero-base passenger (e.g. a free infant, supplier base 0) is markup-AND-tax-free and charged 0, even for a FIXED markup/tax (owner 2026-06-15).

Gold (special-pricing) callers (mitra host). For a caller whose resolved pricingTier is GOLD (specialCustomPricingEnabled is a deprecated mirror of that tier), when the create request arrives on mitra.ahlaan.co.id (or a subdomain), a BUSINESS leg's SAR price is unchanged (still custom markup + custom tax) but its SAR→IDR conversion now uses the reduced exchange rate (sellRate − exchangeRateReducer), the same rate applied to ECONOMY legs. The per-route SAR reducer remains ECONOMY-only, and on any other host the org is priced normally. See Special Custom B2B Pricing.

USD is likewise tiered on the promo host: SAR → USD uses specialUsdSarRate (default 3.75, gold) for a promo-eligible special org and defaultUsdSarRate (default 3.72, silver) for any other promo-eligible caller — including a B2C or org-less customer (not just an enrolled org), instead of the global USD holder rate (used off the promo host or for a not-promo-eligible caller). A booking always comes from a promo-eligible, authenticated user (the endpoint requires PromoAccessGuard), so a non-special booking records the silver tier. The rate + tier in effect at create are frozen into the booking's pricingSnapshot (usdSarRate / usdRateTier = SPECIAL | DEFAULT | HOLDER) alongside the frozen totalPriceUSD. The resolved pricingTier (HOLDER / SILVER / GOLD / RESELLER) is also frozen in the snapshot, next to the legacy isSpecialB2B boolean (GOLD ⇔ true, so a RESELLER booking freezes false).

On the HOLDER branch the global holder rate itself is now frozen into usdSarRate. It used to be written as null there, which left the frozen totalPriceUSD with no rate it could be divided back out by. usdRateTier still reports HOLDER for that case — it names where the rate came from, and that has not changed.

Minimum group size (tier-dependent). Seated passengers (adultCount + childCount, infants excluded as lap) must meet the configured minimum. rememberPassenger works here too. No exchange-rate value is returned here — only exchangeRateId, which references the base rate row. On the GOLD tier the booking is priced at the reduced rate (sellRate − exchangeRateReducer), so resolving that ID against a rate endpoint will not reproduce the amounts on this booking. To show the rate the booking was actually billed at, read exchangeRate.rate from the booking's invoice — that field carries the effective rate.

That is the SAR→IDR rate. The SAR→USD rate is a separate mechanism and is carried separately, as usdSarRate on the embedded invoice block — see The invoice block.

  • DMX → JXD, ECONOMY, 1 adult, active priceReducer = 30. Per-pax model (supplier cost, HHR markup + HHR tax excluded): the raw supplier cost 189.75 (no HHR markup/tax; factor 1 here) − reducer 30 = 159.75, floored to a whole riyal → pricePerAdultSAR 159. totalPriceSAR is the exact sum of the integer per-pax shares (159 × 1 = 159). The per-passenger columns re-sum exactly to totalPriceSAR — no floor residual for the invoice to reconcile. The intermediate figures (raw supplier fare, reducer, strikethrough grand total) are recorded only in the admin-only pricingSnapshot, not on customer responses.
  • pricingSnapshot is not part of the customer response. It is admin-only (returned on the admin custom-booking endpoints) because it exposes internal cost/margin basis — supplier fare, reducer, capital price, and special-B2B FX levers. Customers see only the final payable columns (pricePerAdultSAR, pricePerChildSAR, pricePerInfantSAR, totalPriceSAR / IDR / USD).
  • isSpecialB2B is true when the booking was priced with special-B2B (GOLD-tier) pricing at create time (a GOLD org or a per-user GOLD override, booking on the promo host); otherwise false. It is returned on both the detail and list responses (a top-level column, independent of the admin-only snapshot). The equivalent pricingTier is frozen inside the admin-only pricingSnapshot.
  • bookingCode is a 7-character uppercase code. Share this with the customer — it's how they look the booking up later without knowing the UUID.
  • passengers is the submitted manifest when supplied at create time; null when omitted (fill later via PATCH /custom-booking/:id/passengers).
  • ticketedPaxCount (number | null) is how many of your passengers currently have a ticket on file — recorded by our team when the ticket is uploaded. null means no count has ever been recorded (every booking created before this field existed, and every booking still waiting for its ticket); read it as "unknown", never as zero. It is returned on this response, on GET /custom-booking/:id, and on the booking-code lookup.
  • priceSource is OTA_PRICE — the booking is priced from the live OTA pipeline with the priceReducer allocated per passenger (by fare ratio) on the supplier cost (HHR markup + HHR tax excluded; supplier VAT kept). The legacy SELLING_PRICE / MEAN_MINUS_REDUCER scraper sources no longer apply.

    Shown only to the authenticated owner (it carries the admin's name only — never their id or email). It is null for self-serve bookings that no admin handled. On a guest read (email + phone, no login) the field is omitted entirely. The same block is present on the list endpoint and on the customer invoice.

The invoice block ​

The embedded invoice is the customer copy of the invoice row, and it is what the printed invoice sheet is rendered from. It appears on this endpoint, on GET /custom-booking/code/:bookingCode, and on each item of the list endpoint — with one difference on the list, which does not carry paymentInformation.

It is not on PATCH /custom-booking/:id/confirm-received. That response is built from the updated row, whose query does not load the invoice relation, so invoice comes back null for a customer, a guest and an impersonation token — and absent altogether for a real admin token, whose money strip removes the key.

It differs from the stored invoice in two ways.

Internal columns are absent. metadata, notes, mitraRegistrationId, supplierBaseFareSAR, supplierTaxAmountSAR and supplierTotalFareSAR do not appear at all — the keys are missing, rather than present with a null value.

Note metadata also held the effective SAR→IDR rate that was in force when the invoice was generated. That rate is still customer-reachable, on exchangeRate.rate of GET /api/v1/invoice/{id}.

A USD denomination is attached. The stored invoice holds SAR and the invoice currency (IDR on a custom booking) and has no USD column, so the USD figures are computed when the response is built:

FieldMeaning
usdSarRateSAR per 1 USD — the rate this booking was priced at, for the sheet's rate line. Rounded to 2 decimal places, because it is printed

usdSarRate is the rate line, not a conversion factor to re-apply. The per-line USD figures are scaled from the booking's own frozen SAR and USD totals, so that a line covering the whole booking reproduces the printed total exactly. Dividing a SAR figure by usdSarRate yourself can therefore land a cent away from what is printed beside it. The 2-dp rounding is a second reason not to: an IMPLIED rate is a quotient, so 132 ÷ 35.21 is 3.7489349… and prints as 3.75. The rounding touches this field only — the per-line figures are scaled from the unrounded totals.

Print the USD figures as given — never derive one from another. Each USD figure is rounded up on its own, so a column of them does not add up: 160 ÷ 3.75 gives 42.67 and 800 ÷ 3.75 gives 213.34, while 5 × 42.67 is 213.35. amountUSD is the figure that reconciles with the payment rail. Dividing to recover the rate is lossy for the same reason (800 ÷ 213.34 is 3.74988…, not 3.75), which is why usdSarRate is sent rather than left to be inferred.

Where the rate comes from, in this order:

usdSarRateSourceMeaning
BOOKINGThe rate frozen on the booking at create, which is what a booking created from this version onward carries
IMPLIEDtotalPriceSAR ÷ totalPriceUSD, both frozen on the booking. Used where no rate was frozen but both totals were
LIVEThe current rate. The last resort, for a booking carrying neither a frozen rate nor both totals

Why IMPLIED rather than the current rate. On a booking with no frozen rate, totalPriceUSD is still frozen — at a rate nothing recorded. Converting the lines at today's rate would print a breakdown that contradicts the total on the same page: a 1600 SAR booking frozen at 3.75 has a USD total of 426.67, and if the current rate moved to 3.60 its two lines would come to 444.46. The implied rate is a hair off the original — totalPriceUSD was rounded up — but it reconciles with the printed totals and cannot move afterwards. On a LIVE row the USD total is live-converted too, so the sheet and the payment screen still agree.

The USD total is totalPriceUSD, not the sum of the lines ​

The USD figures on the lines are a breakdown of the booking's totalPriceUSD, not addends. Each rounds up on its own, so they do not add up to it: two lines of 800 SAR at 3.75 come to 213.34 each, or 426.68, where the whole booking 1600 ÷ 3.75 rounds up to 426.67.

Put totalPriceUSD — which sits on the booking, beside totalPriceSAR and totalPriceIDR — in the sheet's TOTAL AMOUNT DUE box. It is the figure the payment rail bills. The SAR and IDR columns do not have this problem: their per-line values sum to their totals exactly.

For the PAYMENT INFORMATION block on the sheet — bank name, account name, account number — see Payment information.

Payment information (the destination bank) ​

invoice.paymentInformation is the PAYMENT INFORMATION block on the sheet: where to send the money, and exactly how much.

The key is absent until the customer has started a manual transfer — not null, it does not appear at all. This is deliberate: a destination account is only meaningful once it is tied to a payment. FieldMeaning

Transfer amountToTransfer exactly. It is the reconciliation figure. An IDR transfer sent without its suffix matches no proof, so the payment cannot be reconciled by amount. For SAR and USD the suffix is forced off, so it is 0 and the figure is the plain amount.

The block does not disappear once the invoice is paid. Nothing filters it on status: a settled or expired payment is still where this customer was told to send the money, and hiding it would leave a paid invoice with no record of where it was paid. So check paymentStatus, proofStatus and invoice.status before presenting the block as "transfer this now" — a sheet that prints transfer instructions on a settled invoice will ask a customer who has already paid to pay a second time.

Four more things worth stating plainly:

  • It survives the window. Once expiresAt has passed the customer can no longer upload a proof, but the block still prints — it is still the account they were last told to pay into.
  • It describes one payment, in one currency. paymentInformation.currency is the currency of the newest manual-transfer attempt — it is not re-derived per denomination. Compare it against the denomination being printed: on a USD sheet backed by a SAR payment, this block is the wrong instruction. The SAR, USD and IDR amounts themselves stay available on every sheet regardless.
  • Guests get it too. A guest reading with a booking code plus a matching email and phone receives the same block as the signed-in owner.
  • The list endpoint does not carry it. It is loaded on the two detail routes only, so printing a sheet from a list item needs a detail read first.

The same data is reachable directly, if you also need the retry counters or the rejection reason: GET /api/v1/invoice/{invoiceId}/payments lists the attempts (login required; note it carries no per-attempt currency — a pre-existing gap on that response), and GET /api/v1/payments/{paymentId}/manual-transfer returns the same frozen account with the full proof state. Both are documented as steps 6 and 3 of the Manual Transfer guide.

4. Update Passenger Manifest ​

PATCH /custom-booking/:id/passengers

Fills in the passenger list (Step 3 of the booking flow). The count and breakdown must match the booking's adultCount + childCount + infantCount.

Side effect — auto-transition, auto-confirm & payment link: When a booking in PENDING successfully accepts a passenger list, it is atomically transitioned to UPLOADED_MANIFEST, a WhatsApp notification is sent to the admin, and — with auto-confirm ON (the default) — the booking is immediately confirmed (→ CONFIRMED): an invoice is generated and a Xendit payment link is delivered to you via WhatsApp (falling back to email if you have no phone on record). All of this is fail-soft — a failure does not affect this response; the booking simply stays at UPLOADED_MANIFEST for an admin to confirm. Concurrent requests are race-safe — only one transition wins, losers are silent no-ops. Re-editing passengers on an already-transitioned booking does not re-trigger the notification or re-confirm. See the admin guide for details: Passenger Upload, Auto-Confirm & Admin WhatsApp Notification.

Access ​

⚠️ MITRA-4 — admin / act-as-customer only. This route now requires a JWT for a real admin or an admin acting as the customer (impersonation). A pure customer (including a legacy guest with email + phone) receives 403 — the manifest is filled on the customer's behalf. The status window below still governs when the edit is allowed.

Callers must be one of:

  • Admin — bearer token for an admin account. Allowed at any non-terminal status.
  • Admin acting as the customer — an impersonation token (principal = the customer, tagged with the acting admin). Allowed within the same status window as the owner below.

Editable status window: PENDING, UPLOADED_MANIFEST, CONFIRMED, WAITING_FOR_PAYMENT, WAITING_PAYMENT_REVIEW, or PAID. Edits are rejected with 400 once the admin downloads the manifest (WAITING_FOR_TICKET onward) or the booking is terminal.

Why edits stay open after confirmation. Editing the manifest only changes passenger identity fields — the passenger counts are fixed at booking creation, so a re-edit never changes the price, the invoice, or the payment link, and never re-fires the auto-confirm side effects (those run once, on the PENDING → UPLOADED_MANIFEST transition). The window closes at WAITING_FOR_TICKET because by then the admin has downloaded the manifest and the ticket is being issued — late name changes would desync the in-flight ticket.

Callers with no token receive 401; an authenticated pure customer (non-admin, not impersonated) receives 403.

Saving Passengers to the Roster (rememberPassenger) ​

Set rememberPassenger: true on any individual passenger row to also save that passenger to the booking owner's reusable roster, so it can be quick-selected on future bookings. It is a per-row flag — set it only on the rows you want remembered; the others are stored on the booking but not added to the roster. The flag is honored wherever a manifest is submitted: inline in passengers on POST /custom-booking, or on PATCH /custom-booking/:id/passengers.

  • Idempotent. Saving is keyed on the passenger's document number (idNumber) per owner — re-saving the same document updates the existing saved passenger instead of creating a duplicate.
  • Owner-scoped. The passenger is always attached to the booking owner (booking.userId), never to whoever sends the request. An admin or guest editing the manifest never writes into their own roster.
  • Guest bookings are skipped on update. A legacy booking with no owner (userId is null) has no roster to attach to, so on PATCH :id/passengers the flag is silently ignored. At creation an owner always exists — create requires an authenticated promo customer, and the booking (and any remembered passengers) is attached to that account.
  • Best-effort. Saving never blocks or fails the manifest update — a roster write error is logged and swallowed; your passengers are still saved on the booking and the response is unaffected.
  • Not persisted on the booking. rememberPassenger is a control flag and is stripped before the manifest is stored, so it never appears in the booking's passengers on read-back.

Validation Rules ​

  • Blank/skeleton rows are ignored. A passenger row that carries neither a firstName nor an idNumber (both absent or whitespace-only) is treated as an empty placeholder and silently dropped before validation and the count check. The FE always sends a default idType, so idType alone does not make a row count as real. This lets the FE submit trailing empty rows without failing the count check.
  • A partially-filled row is still validated. Any row with a firstNameor an idNumber is treated as a real passenger and must pass full validation — in particular firstName and idNumber are trimmed and rejected when blank or whitespace-only, so a half-filled row throws 400 rather than being dropped or saved with blank identity fields.
  • Same rule at creation. POST /custom-booking with an inline passengers manifest applies the identical junk-row drop + blank-identity rejection before its count check.
  • After blank rows are dropped, total passenger count must equal adultCount + childCount + infantCount.
  • The number of ADT entries must equal adultCount exactly (same for CHD/INF).
  • A BadRequestException with a specific mismatch message is returned otherwise.
  • Replace semantics. The submitted passengers array fully replaces the stored manifest — it is not merged or appended. Always send the complete list; any field omitted from a row is lost.

The file is served from TICKET_UPLOADED_FULL, TICKET_UPLOADED_PARTIAL, SHORTFALL_REFUNDED, TICKET_RECEIVED and COMPLETED — and, on top of the status check, only once the ticket has been released by a second admin. A freshly uploaded file sits held until that review; see below.

TICKET_UPLOADED_PARTIAL is included. When the ticket source under-delivers, the passengers who were ticketed get their tickets straight away; the money owed for the ones who were not is refunded separately, on its own timetable. The shortfall blocks the booking from closing, not the download.

This is the same list the admin resend-ticket-email route uses, TICKET_UPLOADED_ PARTIAL included: on a short delivery the email states only that the ticket is issued and downloadable, naming no passenger count, so there is nothing left for it to overstate.

The customer is emailed automatically when the ticket is released — not when it is first uploaded, which sends nothing and leaves the ticket hidden from you — so from your side the file and the notification still become available together. A client should still surface the ticket object on the booking detail response rather than treating the email as the signal: a booking's ticket is released only once, so a corrected file or the tickets that resolve a shortfall appear here with no message accompanying them. Note that object is populated whenever a ticket file exists and has been released, so it stays absent on a held upload; it is also not filtered by status otherwise, so it is non-null on a cancelled booking too, where this endpoint answers 400. Gate on the booking status as well as on ticket.

A held ticket looks exactly like no ticket at all. While an uploaded file is awaiting a second admin's review, this route answers the same 400 as a booking that has never had one uploaded — the one naming WAITING_FOR_TICKET, which is the status you are shown for it. Same code, same message: you cannot tell the two apart from here. hasTicket is false on this endpoint, on GET /custom-booking/code/:bookingCode, and on your booking list. ticket reports null on this endpoint and on the by-booking-code one (same as when nothing has ever been uploaded); the list omits the ticket key entirely regardless. The reported status is masked to WAITING_FOR_TICKET too, but only when the stored status is TICKET_UPLOADED_FULL or TICKET_UPLOADED_PARTIAL — SHORTFALL_REFUNDED is never masked, since it records that the money already came back to you. ticketedPaxCount is withheld (null) alongside the status, on the same bookings and for the same reason: it moves from null to the ticketed figure the moment an admin uploads.

8. List My Custom Bookings ​

GET /custom-booking

Returns a paginated list of the authenticated user's custom bookings. This endpoint requires a valid bearer token — it has no guest fallback (a guest booking is retrieved by bookingCode + email/phone, not listed). Results are always scoped to the caller: user A cannot see user B's bookings.

Authentication ​

bash
curl -X GET "/api/v1/custom-booking?page=1&limit=10&sortBy=createdAt&sortOrder=desc" \
  -H "Authorization: Bearer <token>"

Query Parameters ​

ParamTypeDefaultNotes
pageint (≥1)1
limitint (1–100)20
statusenum—Filter by CustomBookingStatus (e.g., PENDING, COMPLETED)
bookingCodestring (≤64)—Case-insensitive substring match
departureDateFromISO date/datetime—Inclusive lower bound; date-only resolves to start-of-day UTC
departureDateToISO date/datetime—Inclusive upper bound; date-only extended to end-of-day UTC. Must be ≥ departureDateFrom
sortByenumcreatedAtOne of createdAt, updatedAt, departureDate, status
sortOrderasc | descdesc

status on each item is masked the same way as the detail response (see Download Ticket above): a booking whose ticket is uploaded but not yet released reports WAITING_FOR_TICKET here too, for TICKET_UPLOADED_FULL / TICKET_UPLOADED_PARTIAL only — SHORTFALL_REFUNDED is never masked, and ticketedPaxCount is withheld (null) alongside the status for the same bookings. The status query filter above matches the status this list REPORTS, so it agrees with what you see: ?status=WAITING_FOR_TICKET includes bookings whose ticket is uploaded but still held, and ?status=TICKET_UPLOADED_FULL / TICKET_UPLOADED_PARTIAL return only released ones. A tab built on either value shows exactly what it asked for.

Abbreviated example. The item above is trimmed for readability — only the headline fields are shown. totalPriceSAR is a whole riyal (e.g. 159) under the integer-floor model, not a fractional value. handledByAdmin is the name-only attribution of the admin who created the booking on your behalf ({ "name": "…" }), or null for a self-serve booking — the same block returned on the detail endpoint.

Each item uses the same shape as the GET /custom-booking/:id response (minus manifests, which is only populated on the detail endpoint). The item above shows "invoice": null because the booking is still PENDING; once the booking is confirmed the item embeds the same customer copy of the invoice — narrowed, with USD attached — that the detail endpoint returns. 9. Open a minted shortfall-attachment link ​

http
GET /api/v1/custom-booking/shortfall-attachment/:token

No authentication. The token in the path is the whole capability. This route is not part of the customer journey — it exists so an admin screen can show the shortfall attachment in an <img src> or a plain browser tab, which an Authorization-guarded route cannot do. Tokens are minted by the admin route.

What it sends back ​

The Content-Type is derived from the file's bytes, never from the type recorded when the file was uploaded — that recorded type is a string the uploader's browser chose and is wrong on real rows.

The bytes are…Content-TypeContent-Disposition
PNG, JPEG or WebPthat typeinline — renders
PDFapplication/pdfattachment — downloads
SVG, CSV, or anything unrecognisableapplication/octet-streamattachment — downloads

An SVG is never rendered here, whatever it is stored as: an SVG rendered from this origin would execute its script on it. X-Content-Type-Options: nosniff is sent on every response so the browser cannot second-guess the type, and it is sent by the application rather than the edge, so staging and preprod behave like production.

The link works on every render until it expires, which is what an <img> needs — it re-requests each time it is drawn.

Errors ​

StatusWhen
400The link has expired (24 hours after it was minted)
404Unknown token, a token belonging to a different rail, or the file is no longer stored. One answer for all three, so a holder cannot tell which

A token minted through POST /api/v1/storage/{fileId}/token is not accepted here, and a token minted here is not accepted at GET /api/v1/storage/ticket/{token}/download. The two have different permission gates and different rules about what may render, so their tokens are not interchangeable.

10. Open a minted shortfall-proof link ​

http
GET /api/v1/custom-booking/shortfall-proof/:token

No authentication. The token in the path is the whole capability. Like §9 this is not part of the customer journey: it exists so a finance screen can show the bank receipt for a shortfall settlement — the proof that money owed for unticketed passengers was sent back — in an <img src> or a plain browser tab, which an Authorization-guarded route cannot do. Tokens are minted by the admin route.

What it sends back ​

The Content-Type is derived from the file's bytes, never from the type recorded when the file was uploaded — that recorded type is a string the uploader's client chose.

Only bytes that prove to be a PNG, JPEG or WebP are served inline. Everything else — including application/pdf and anything unrecognisable — is served as an attachment download. An SVG is never rendered here under any stored label, because an SVG rendered from this origin would execute script on it. X-Content-Type-Options: nosniff is sent so a browser cannot second-guess the type.

Cache-Control: private, no-store is sent as well. The capability lives in the URL, so anything that caches on the URL would go on serving a bank receipt after the link has been revoked and after it has expired — revoking stops the origin, not a copy someone else already stored.

⚠️ A PDF proof downloads rather than previewing. Uploads accept PDF alongside the raster types, so a scanned receipt and a photographed one behave differently through the same link. A preview pane has to handle both.

The link is re-usable until it expires 24 hours after minting, which is what an <img> re-request on every render needs.

The two shapes this route answers with — a photographed proof and a scanned one:

http
HTTP/2 200
cache-control: private, no-store
content-disposition: inline; filename="proof.png"; filename*=UTF-8''proof.png
content-type: image/png
x-content-type-options: nosniff
content-length: 74
http
HTTP/2 200
cache-control: private, no-store
content-disposition: attachment; filename="berita-acara.pdf"; filename*=UTF-8''berita-acara.pdf
content-type: application/pdf
x-content-type-options: nosniff
content-length: 69

Errors ​

StatusWhen
400The link has expired.
404Unknown token, a token belonging to a different rail, a file that is no longer stored, or a token whose settlement no longer points at it. One answer for all of them, so a holder cannot tell which.

A token minted through POST /api/v1/storage/{fileId}/token is refused here, and a token minted here is refused by GET /api/v1/storage/ticket/{token}/download and by the shortfall-attachment route in §9. The rails have different mint gates and different serving rules, so their tokens are not interchangeable.
