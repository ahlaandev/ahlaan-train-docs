Manual Bank Transfer Payment (B2C / Guest) ​

This guide explains how to implement the manual bank transfer payment method on the front-end. It is an alternative to Xendit-hosted gateways for customers who prefer to transfer manually to one of Ahlaan's beneficiary bank accounts and upload a receipt for admin verification.

When to use this gateway: Invoice is for a Custom Booking paid in IDR and the customer wants to transfer from a bank or wallet not covered by Xendit, or explicitly prefers manual payment. Admin review introduces a delay (target: under 4 business hours) — if the customer needs instant settlement, use Xendit instead.

Scope restriction: MANUAL_TRANSFER is available only for invoices linked to a Custom Booking (Invoice.customBooking). Regular OTA bookings, wallet top-ups, and ad-hoc invoices must settle through Xendit so the OTA ticketing pipeline runs without admin intervention. The gateway is hidden from GET /invoices/:id/available-gateways for non-custom-booking invoices, and POST /invoices/:id/generate-payment with paymentGatewayCode=MANUAL_TRANSFER returns 400 Bad Request ("Manual transfer is only available for custom booking payments.").

Audience & Authentication ​

  • Authenticated users (JWT Bearer token) — the invoice owner reads and uploads without extra verification.
  • Guests (no JWT) — every request must include the guestEmail or guestPhone used on the original booking so the server can verify ownership.

All manual-transfer endpoints are rate-limited. Expect 429 Too Many Requests if you exceed ~10 uploads/min or ~30 reads/min per IP.

MANUAL_TRANSFER appears only when all of the following are true: (1) the invoice is linked to a Custom Booking (Invoice.customBooking), (2) the invoice currency is IDR, and (3) the admin has at least one active ManualTransferBankAccount for IDR. Step 2 — Generate Payment ​

bash
POST /api/v1/invoices/:invoiceId/generate-payment
Content-Type: application/json
json
{
  "paymentGatewayCode": "MANUAL_TRANSFER",
  "bankAccountId": "01925a4b-..."
}
  • bankAccountId is optional. If omitted, the server picks the active bank account with the highest priority.
  • For guest flows, also send guestEmail or guestPhone in the body.

Critical UX rule: Show uniqueAmount prominently — the customer MUST transfer exactly this value. When the unique-suffix feature is enabled, uniqueAmount contains a 3-digit suffix (e.g. 1,250,037) and a transfer for 1,250,000 will be rejected because reconciliation cannot match it. When the feature is disabled, uniqueAmount equals baseAmount and amountSuffix=0.

Example — unique-suffix feature disabled (default) ​

json
{
  "paymentId": "01925a50-...",
  "currency": "IDR",
  "baseAmount": 1250000,
  "uniqueAmount": 1250000,
  "amountSuffix": 0,
  "status": "AWAITING_UPLOAD",
  "paymentStatus": "PENDING"
}

In this mode the customer transfers the exact baseAmount. Admins must reconcile by cross-checking sender name, timestamp, and amount rather than the last three digits.

Step 5 — Poll for Status ​

Poll the Step 3 endpoint every ~15 seconds after SUBMITTED. Stop polling once status is APPROVED or REJECTED, or paymentStatus becomes EXPIRED / FAILED.

Side Effects on Approval ​

When the admin approves a proof, the customer will observe:

  1. Invoice.status → PAID (or OVERPAID for duplicates).
  2. Payment.status → PAID, paidAt populated.
  3. Booking.status → CONFIRMED (with BookingStatusHistory row).
  4. Booking confirmation email + WhatsApp dispatched.
  5. OTA ticketing job triggered → booking eventually TICKETED.
  6. Any pending booking-expiration queue jobs are cancelled.

Side Effects on Rejection ​

  1. Payment.status stays PENDING until retryCount > maxRetryCount (i.e. the next rejection after the user has exhausted their re-uploads), then transitions to FAILED.
  2. Rejection email sent with admin's reason (visible in rejectionReason).
  3. If payment still PENDING, re-upload is permitted until expiresAt.

Business Rules ​

  • Custom Booking invoices only. Regular OTA bookings, wallet top-ups, and ad-hoc invoices do not show MANUAL_TRANSFER and cannot use it via direct API call (server returns 400).
  • IDR only. Non-IDR invoices will not show MANUAL_TRANSFER.
  • Transfer the exact uniqueAmount. Rounding down or up by even 1 rupiah will cause rejection.
  • One active proof per payment. A rejected proof can be replaced.
  • Re-upload limit. Default 3 attempts (maxRetryCount). Server-authoritative — never bypass client-side.
  • Payment expiry still applies. If admin doesn't act before expiresAt, payment transitions to EXPIRED regardless of proof status.
  • Unique suffix (optional). When MANUAL_TRANSFER_ENABLE_UNIQUE_SUFFIX is enabled, the server generates a 3-digit suffix (0–999) that does not collide with other in-flight proofs for the same bank account. On rare collisions (>10 retries) the API returns 409 — ask the customer to pick a different bank account. When the flag is disabled (default), uniqueAmount always equals the rounded base amount and amountSuffix=0, and multiple in-flight proofs may legitimately share the same amount on the same bank account.

Polling ​

ts
async function pollUntilResolved(paymentId: string) {
  for (let i = 0; i < 120; i++) {
    const res = await fetch(`/api/v1/payments/${paymentId}/manual-transfer`);
    const data = await res.json();
    if (['APPROVED', 'REJECTED'].includes(data.status)) return data;
    if (['EXPIRED', 'FAILED'].includes(data.paymentStatus)) return data;
    await new Promise((r) => setTimeout(r, 15_000));
  }
}

UAT Scenarios ​

  1. Happy path. Generate payment → read instruction → upload valid receipt → admin approves → booking confirmed.
  2. Wrong amount rejection → retry. Upload receipt with mismatched amount → admin rejects with reason → re-upload corrected receipt → admin approves.
  3. File too large. Upload 6 MB file → receive 400 FILE_TOO_LARGE → no side effects.
  4. Guest flow. Book + pay as guest (no JWT), with guestEmail in every request → full happy path.
  5. Expiry during review. Upload → let expiresAt pass while status is SUBMITTED → admin approve attempt returns 409; customer sees EXPIRED.
  6. Retry exhaustion. Upload → rejected 4 times (initial + 3 re-uploads at default MAX_RETRIES=3) → Payment.status = FAILED, upload endpoint returns 409.
