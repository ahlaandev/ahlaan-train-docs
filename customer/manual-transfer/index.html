Manual Bank Transfer Payment (B2C / Guest) ​

This guide explains how to implement the manual bank transfer payment method on the front-end. It is an alternative to Xendit-hosted gateways for customers who prefer to transfer manually to one of Ahlaan's beneficiary bank accounts and upload a receipt for admin verification.

When to use this gateway: Invoice is for a Custom Booking and the customer wants to transfer manually rather than pay online — in SAR, USD, or now IDR. Each currency routes to its own destination bank account (e.g. SAR → Mandiri, USD → CIMB, IDR → Mandiri) with the exact amount to send in that currency. Admin review introduces a delay (target: under 4 business hours), so a customer who wants instant settlement in IDR should still use Xendit.

Currency selection: send currency: "SAR", "USD" or "IDR" in the POST /invoice/:id/generate-payment body. It is required for MANUAL_TRANSFER. The two failure modes return different messages, so match on the status code rather than the text: omitting it returns 400 — "Manual transfer requires a 'currency' of SAR, USD or IDR." — while sending an unsupported value fails DTO validation first and returns 400 with an array — ["currency must be one of the following values: SAR, USD, IDR"]. The SAR amount is the booking's authoritative SAR total; the USD amount is the frozen USD snapshot (or a live SAR→USD conversion for older bookings); the IDR amount is the invoice total. SAR/USD are display-only converted, never re-charged — the SAR figure remains the source of truth for accounting.

IDR now has two rails. idr in payment-options is Xendit (instant, settles by webhook); an IDR entry under manualTransfer.currencyOptions is this offline rail (waits on an admin reviewing the proof). They are kept apart in the response on purpose. The manual IDR rail is billed the full invoice total, so it is offered and accepted only on an invoice that has received nothing yet — see Paying IDR by transfer.

SAR can also be paid in person (MITRA-10): a SAR invoice may be settled either by uploading a transfer proof here or by paying in cash at the Ahlaan office, where an admin records the settlement for you. USD and IDR are manual transfer or Xendit only. The manual-transfer SAR/USD flow below is unchanged.

Scope restriction: MANUAL_TRANSFER is available only for invoices linked to a Custom Booking (Invoice.customBooking). Regular OTA bookings, wallet top-ups, and ad-hoc invoices must settle through Xendit so the OTA ticketing pipeline runs without admin intervention. POST /invoice/:id/generate-payment with paymentGatewayCode=MANUAL_TRANSFER on a non-custom-booking invoice returns 400 Bad Request ("Manual transfer is only available for custom booking payments.").

Discovering options: Call GET /invoice/:id/payment-options (see Step 1b) to render the FE note — it returns the IDR/Xendit amount plus per-currency manual-transfer options (amount + destination bank accounts). A currency with no active bank account is omitted.

Audience & Authentication ​

  • Authenticated users (JWT Bearer token) — the invoice owner reads and uploads without extra verification.
  • Guests (no JWT) — every request must include the guestEmail or guestPhone used on the original booking so the server can verify ownership.

All manual-transfer endpoints are rate-limited. Expect 429 Too Many Requests if you exceed ~10 uploads/min or ~30 reads/min per IP.

Paying IDR by bank transfer ​

IDR appears in manualTransfer.currencyOptions like any other currency, with one rule that has no SAR/USD equivalent:

It is offered only while the invoice has received nothing. The IDR manual transfer is billed the full invoice total, not the remaining balance. On an invoice that already took a partial payment, the two would disagree — and because an IDR transfer is the same currency as the invoice, settling it would push the paid total past the invoice total and mark it PAID with no overpayment flagged anywhere. So the option is withheld from currencyOptions in that state, and POST generate-payment refuses it with 400:

This invoice has already received 40.000 IDR. An IDR bank transfer would be billed for the full invoice total and overpay it. Please contact support to settle the remaining balance.

There is no self-service way to pay a remaining balance. payment-options.idr.amount shows the remainder, but that figure is for display only: generate-payment has no way to charge it. For Xendit it reuses an existing payment link if the invoice has one, and otherwise bills the full invoice.totalAmount; the request body has no amount field to override that. SAR and USD are not exempt either — they are billed the full booking total and are not refused in this state, which is the gap tracked as #593. A partly-paid invoice needs a manual resolution, not another payment on any rail.

Render only what currencyOptions returns and this never surfaces.

Of the gateways that are active at all, MANUAL_TRANSFER is listed only while these five hold: (1) the invoice currency is IDR, (2) the manual-transfer rail is switched on, (3) the invoice is linked to a Custom Booking (Invoice.customBooking), (4) the invoice is not yet settled — a PAID or OVERPAID invoice takes no further payment on any rail, and (5) an admin has selected a ManualTransferBankAccount for that currency and it is still active. Fail any of them and the gateway is hidden automatically; fail (1) to (4) and no destinationBankAccounts lookup is performed at all.

Condition (1) looks redundant — a custom booking creates an IDR invoice — but it is not. Custom-booking invoices were created as SAR until 2026-04-16, so a legacy row can still pair a Custom Booking with a SAR invoice, and this endpoint withholds the rail on one.

⚠️ That guard is on available-gateways alone. Step 1b and generate-payment do not apply it, so on a legacy SAR invoice they still offer and accept a manual transfer — and its IDR amount is read from invoice.totalAmount, a SAR-magnitude number quoted as rupiah. Tracked as #594. Do not treat this condition as protecting the payment flow.

A partly paid invoice still shows the rail. That is a known gap rather than a feature — see limit 2 below.

destinationBankAccounts therefore always holds exactly one entry — the selected destination for that currency, not a menu. Use Step 1b for the SAR/USD rails: that endpoint is the one with a currency dimension.

This endpoint has no currency dimension — prefer Step 1b ​

Two limits make available-gateways the wrong endpoint to drive a currency picker from. The first is visible in the response above; the second is set out in the table below it.

1. destinationBankAccounts is always the IDR account, whatever currency the customer intends. It is looked up by invoice currency, and condition (1) above means the rail is only ever listed on an IDR invoice. Render it for a customer who then chooses SAR and you will show them the rupiah account. payment-options is the endpoint that knows about currencies.

2. It answers "is this rail open at all", not "how much is left to pay". The two endpoints track the balance to different depths, and that is deliberate:

Invoice stateavailable-gatewayspayment-options
Nothing paidMANUAL_TRANSFER listedSAR, USD and IDR offered — minus any currency with no selected account
Partly paidMANUAL_TRANSFER still listedIDR entry withheld; SAR and USD still offered
Settled (PAID / OVERPAID)MANUAL_TRANSFER not listedmanualTransfer.enabled: false

The partly-paid row is a known gap, not a design you should build on

Every manual-transfer amount is the full booking total — no currency is billed for the remaining balance. Only IDR is refused once totalPaid > 0 (generate-payment answers 400); a SAR or USD transfer on the same invoice is accepted and billed in full, so the customer pays the earlier amount again on top. Tracked as #593.

Until that is resolved, do not move the customer to a second rail on an invoice that has already received a payment. No rail bills a remainder. For XENDIT, generate-payment never charges the outstanding balance: on a custom-booking invoice it hands back the most recent payment row that already has a paymentUrl — whatever that payment's status — and otherwise creates one for the full invoice.totalAmount. The request body has no amount field to change that. For manual transfer, every currency is billed the full booking total.

So the hazard is not a customer resuming the rail they already started; each rail reuses its own open payment rather than minting a duplicate. The hazard is offering a different rail alongside it. Detect that with:

  1. totalPaid > 0 on this response — money already settled.

  2. For a logged-in customer, a PENDING entry on a different gateway from GET /invoice/:id/payments. A PENDING row on the rail already in use is the normal resume case and is safe.

    ⚠️ GET /invoice/:id/payments requires a logged-in owner — it takes no guestEmail / guestPhone, unlike available-gateways and payment-options, so a guest-checkout client cannot make check 2. And totalPaid alone will not reveal a SAR/USD proof that is uploaded but not yet approved, because it moves only at settlement. On the guest flow, send a partly-paid invoice to support rather than to another rail.

If either holds, route the customer to support rather than to another rail.

available-gateways has no currency dimension, so it cannot express "the rail is listed but one of its currencies is refused" — which is why the payment screen belongs on Step 1b.

Drive the payment UI from Step 1b. Use available-gateways only to answer "is this rail configured at all".

Step 2 — Generate Payment ​

bash
POST /api/v1/invoice/:invoiceId/generate-payment
Content-Type: application/json
json
{
  "paymentGatewayCode": "MANUAL_TRANSFER",
  "paymentMethod": "BANK_TRANSFER",
  "currency": "SAR"
}

  • paymentMethod is optional — omit it. BANK_TRANSFER is the only method MANUAL_TRANSFER accepts and the server resolves it either way; four live 201s on preprod 2026-08-10 sent no paymentMethod at all and came back with "paymentMethod": "BANK_TRANSFER".

    ⚠️ When you do send it, it is validated on the mint path only. Minting with "paymentMethod": "CREDIT_CARD" returns 400 Bad Request — "Payment method 'CREDIT_CARD' is not supported by this gateway" — and mints nothing. The reuse path returns the open payment before the method is read, so the same wrong value answers 201 with "paymentMethod": "BANK_TRANSFER" and no complaint. Both measured on the same invoice in the same minute. This is the structural gap that was closed for bankAccountId below and is still open here, which is another reason to omit the field rather than echo one back.

  • currency is required for MANUAL_TRANSFER: "SAR", "USD" or "IDR". It selects both the destination bank account and the amount to transfer.

  • IDR bank transfer is a second IDR rail, alongside Xendit. It is billed the full invoice total, never the remaining balance, so it is refused with 400 once the invoice has received any payment: "This invoice has already received … An IDR bank transfer would be billed for the full invoice total and overpay it." There is no rail to send the customer to for the balance — Xendit is billed the full totalAmount as well, and a SAR/USD manual transfer is billed the full booking total and is not refused in this state (#593). payment-options withholds the IDR manual-transfer entry in exactly that state, so a client rendering only what that endpoint returns never hits this.

  • Pressing generate-payment twice returns the same payment. An open, unexpired manual-transfer payment in the same currency, still quoting the same amount, is handed back rather than a second one being created — one intended transfer produces one instruction and one proof. Switching currency, letting the window lapse, or a price change in the meantime each mint a fresh instruction instead.

  • A fresh instruction supersedes the older ones it replaces. When the call mints rather than reuses, older PENDING manual-transfer payments on the invoice whose proof is still AWAITING_UPLOAD move to EXPIRED — whatever their currency, and whether or not their own window had lapsed. An instruction the customer walked away from therefore stops being payable as soon as they ask for a new one. Untouched: a proof already SUBMITTED, FUNDS_VERIFIED or REJECTED (money may be in flight, or a re-upload is still owed), and payments on every other gateway — switching rails is unchanged.

    This is not a guarantee of one payable instruction per invoice. The sweep's where takes only MANUAL_TRANSFER payments whose proof is exactly AWAITING_UPLOAD, so anything outside that survives: a REJECTED proof is still uploadable and its payment stays PENDING; a SUBMITTED proof is skipped, and a later instruction sits beside it; and another rail is never swept at all. The two skips I measured — SUBMITTED and a Xendit payment — left the capture below ending with three PENDING rows on one invoice. Render only what the latest generate-payment returned rather than inferring that everything else is dead.

    If the customer already transferred against the old instruction, uploading their receipt now returns 409 and they need an admin to reopen that payment. Render only the instruction the latest generate-payment returned, and tell the customer the earlier one is void.

    Measured end to end on preprod 2026-08-10, invoice INV-202608-0021-9DV, reading GET /invoice/:id/payments after every call:

    #CallResultInvoice payments afterwards
    1generate IDRmint …abb2, PENDING1 row, 1 PENDING
    2generate SARmint …df94, PENDING2 rows, 1 PENDING — the IDR row moved to EXPIRED
    3generate SAR againreuse …df94, still PENDING2 rows, 1 PENDING — the reused row did not expire itself
    4generate USDmint …6c02, PENDING3 rows, 1 PENDING — the SAR row moved to EXPIRED
    5generate XENDITmint …4fc4de, PENDINGthe live manual-transfer row stayed PENDING — 2 PENDING, one per rail
    6upload a receipt on the live manual-transfer rowits proof → SUBMITTEDunchanged
    7generate SARmint …41ef2c, PENDINGthe SUBMITTED row is still PENDING, with submittedAt and expiresAt both unchanged

    Three of these are the ones worth reading:

    • #3 — the sweep takes only rows created strictly before the row it just minted or reused, so a repeat press cannot void the instruction it is handing back.
    • #5 — the sweep's where names paymentGateway.code = MANUAL_TRANSFER, so opening a Xendit payment leaves a live transfer instruction alone and is itself never swept. Switching rails is not a supersede.
    • #7 — this is the money-safety case. Once a receipt is up the proof is SUBMITTED, not AWAITING_UPLOAD, and a later instruction does not reach it. A customer who has already sent the money keeps the instruction they sent it against.

  • bankAccountId is deprecated — omit it. The destination is no longer a choice: each currency has exactly one admin-selected account and the server resolves it. If you do send a wrong value it is validated rather than ignored, and returns 400 naming the account that is correct:

    json
    {
  "statusCode": 400,
  "message": "Bank account '019dae1c-3871-77a9-be5f-548dee427a49' is not the destination for USD. Transfers in USD go to '019ea6a0-7f68-718c-86dc-f603082fae9b' (Bank CIMB Niaga 800123456). Re-read GET /invoice/:id/payment-options and send that account, or omit bankAccountId."
}

    The reuse path answers identically. Whether or not an open payment already exists for the requested currency, the same wrong id gets the same 400 — the check runs ahead of the reuse branches. It used to sit only in the destination resolver, which the reuse branches return before reaching, so the first press was refused and the second one silently accepted the bad value. That gap is closed.

    Validation targets the currently selected account, not the account a reused payment carries. Those can differ: a selection change applies to future payments only, so an instruction issued before the switch keeps pointing at the previous account while payment-options already quotes the new one. Echoing back what payment-options most recently returned is therefore always accepted, and is the only value worth sending — which is another way of saying: omit the field.

  • A 400 reading "No destination bank account is selected for SAR. Ask an admin to select one." means the rail is unarmed for that currency — an admin has not selected an account, or the selected one was deactivated. It is not a client error and retrying will not help.

  • For guest flows, also send guestEmail or guestPhone in the body.

paymentUrl and qrString are empty strings on this rail, not URLs — manual transfer has no hosted gateway page. Render your own instruction screen from Step 3; do not gate on paymentUrl being truthy.

The amount/currency reflect the chosen currency. A USD payment returns the decimal USD amount (e.g. 213.34); an IDR one returns the whole-rupiah invoice total. For a SAR/USD payment the invoice reconciles in SAR (totalPaidSAR) and the IDR totalPaid is left untouched. An IDR payment is same-currency, so it credits totalPaid directly — measured on preprod, a settled IDR transfer of 3816000 produced totalPaid: 3816000 against totalAmount: 3816000, plus totalPaidSAR: 800 from the SAR anchor.

This holds for a cross-currency settlement too: a SAR/USD manual transfer marks the invoice PAID while leaving the IDR totalPaid at 0, and the endpoint guards on the invoice status, not just that numeric figure. Re-render payment options only while the invoice is unpaid.

Display paymentUrl if you want a pre-built landing page; otherwise call Step 3 and render your own UI.

  • partnerRegistrationNumber / partnerName are the mitra partner snapshot (MS.XXX / MG.XXX / MR.XXX), and are null on a non-mitra invoice. These two are the only placeholder values in the block above — the capture carried a real partner, and its name and number are stood in for here.
  • A SAR payment on the same invoice returns the SAR figures against the SAR account — measured: currency: "SAR", baseAmount: 800, uniqueAmount: 800, amountSuffix: 0, bankAccount.accountNumber: "900654321".

Critical UX rule: Show uniqueAmount prominently — the customer MUST transfer exactly this value. Today it equals baseAmount on every currency, because the 3-digit reconciliation suffix is disabled (MANUAL_TRANSFER_ENABLE_UNIQUE_SUFFIX=false on every environment). Admins reconcile by sender name, timestamp and the uploaded receipt. Read uniqueAmount rather than baseAmount regardless — it is the field that would change if the suffix were ever switched on, and quoting the base would then understate the bill.

Download your proof file ​

fileId is the stored proof image. The proof is always a PRIVATE file, and it belongs to the invoice owner — no matter who uploaded it. Logged in, as a guest, or by an admin on your behalf: the owner is the account the invoice was issued to.

So GET /api/v1/storage/{fileId}/download with that account's bearer token returns the receipt.

Proofs uploaded before this rule shipped are the exception. A guest upload used to store the file with no owner at all, which left it readable only by an admin. If an older receipt returns 403, ask an admin — they can download it directly or mint a shareable token (POST /api/v1/storage/{fileId}/token → GET /api/v1/storage/ticket/{token}/download).

You cannot delete a proof file. DELETE /api/v1/storage/{fileId} returns 403 for a manual_transfer_proof, for everyone including admins — it is the evidence that a payment was made. To correct a wrong receipt, upload a replacement: the proof record points at the newest one, and that is the fileId this endpoint returns. The file it replaces stays in storage, unreferenced.

Step 5 — Poll for Status ​

Poll the Step 3 endpoint every ~15 seconds after SUBMITTED. Stop polling once status is APPROVED or REJECTED, or paymentStatus becomes FAILED. FUNDS_VERIFIED is not a stop condition - it is the second of two review states, so keep polling through it. Expiry is not a poll state — this endpoint reports the stored paymentStatus (PENDING until approval/failure), and a lapsed window surfaces only as a 409 when the customer tries to upload past expiresAt.

Recommended UI branches ​

Reopened by support. For a FAILED payment — or one whose window already lapsed (PENDING with expiresAt in the past) — an admin may reopen the same payment after the customer contacts support (no automatic notification is sent). The window then becomes uploadable again — the payment stays/returns to PENDING and expiresAt is refreshed — so keep the Step 3 / Step 4 endpoints reachable from the support flow rather than forcing a brand-new payment. (As noted above, a custom-booking manual-transfer paymentStatus is never stored EXPIRED; a lapsed window surfaces as PENDING past expiresAt.)

Polling does not survive a closed tab. Every step above is keyed on paymentId, which the frontend learns only from the Step 2 response. A customer who closes the tab loses it. Step 6 is how they get it back.

The Step 3 instruction endpoint returns the stored paymentStatus, which for custom-booking manual transfer is never EXPIRED (no webhook and no scheduled expiration job write it). A SUBMITTED proof therefore stays PENDING past expiresAt and remains approvable by an admin. Expiry is enforced at upload only (409). A separate gateway status mapping may derive EXPIRED for an AWAITING_UPLOAD / REJECTED proof once the window lapses, but a proof in either review state (SUBMITTED or FUNDS_VERIFIED) is never mapped to EXPIRED.

Side Effects on Approval ​

When the admin approves a proof, the customer will observe:

  1. Invoice.status → PAID (or OVERPAID for duplicates).
  2. Payment.status → PAID, paidAt populated.
  3. Booking.status → CONFIRMED (with BookingStatusHistory row).
  4. Booking confirmation email + WhatsApp dispatched.
  5. OTA ticketing job triggered → booking eventually TICKETED.
  6. Any pending booking-expiration queue jobs are cancelled.

Side Effects on Rejection ​

  1. Payment.status stays PENDING until retryCount > maxRetryCount (i.e. the next rejection after the user has exhausted their re-uploads), then transitions to FAILED.
  2. Rejection email sent with admin's reason (visible in rejectionReason).
  3. If payment still PENDING, re-upload is permitted until expiresAt.

Business Rules ​

  • Custom Booking invoices only. Regular OTA bookings, wallet top-ups, and ad-hoc invoices do not show MANUAL_TRANSFER and cannot use it via direct API call (server returns 400).

  • IDR invoices only — which is not the same as paying in IDR. available-gateways lists the gateway only when the invoice currency is IDR, which a custom booking created since 2026-04-16 is, and resolves destinationBankAccounts from that same currency. The check is on that endpoint only: Step 1b and generate-payment do not apply it, so a legacy SAR custom-booking invoice is still offered and still accepted there (#594). What the customer then transfers may be SAR, USD or IDR — Step 1b is the endpoint that says which. Do not read this rule as "manual transfer is an IDR-only rail".

  • Transfer the exact uniqueAmount. Rounding down or up by even 1 rupiah will cause rejection.

  • One active proof per payment. A rejected proof can be replaced.

  • Re-upload limit. Default 3 attempts (maxRetryCount). Server-authoritative — never bypass client-side.

  • Payment expiry is enforced at upload time. Manual transfer has no payment-gateway webhook and (for custom bookings) no scheduled expiration job, so a lapsed window does not auto-cancel the booking. Expiry is enforced when you upload: once expiresAt passes, a new upload or re-upload is rejected (409, Payment has expired; please start a new payment.). A proof you submitted before the window closed stays valid for admin review — approval has no expiresAt guard, so a real transfer that arrived in time still settles to PAID even if review runs slightly past expiresAt. The window is a fixed 30 minutes by default (configurable per environment via CUSTOM_BOOKING_MANUAL_TRANSFER_EXPIRY_MINUTES), measured from payment creation — so transfer and upload the proof promptly. Re-uploads after rejection must also land before expiresAt.

  • Unique suffix — off, and staying off. uniqueAmount always equals the rounded base amount and amountSuffix is always 0, so multiple in-flight proofs may legitimately share the same amount on the same bank account; admins separate them by the uploaded receipt and the payer's account name.

    MANUAL_TRANSFER_ENABLE_UNIQUE_SUFFIX would make the server append a 3-digit suffix (0–999) that does not collide with other in-flight proofs for the same account. It must not be enabled. Settlement credits payment.amount — the base — while the customer is instructed to transfer uniqueAmount. Turning the flag on would therefore have the bank receive up to Rp 999 more per transfer than the system ever records, silently and on every payment. Closing that means crediting uniqueAmount at settlement, which is a change to the shared path used by every rail. Until that happens the flag stays false on all environments.

Polling ​

ts
async function pollUntilResolved(paymentId: string) {
  for (let i = 0; i < 120; i++) {
    const res = await fetch(`/api/v1/payments/${paymentId}/manual-transfer`);
    const data = await res.json();
    if (['APPROVED', 'REJECTED'].includes(data.status)) return data;
    if (data.paymentStatus === 'FAILED') return data;
    await new Promise((r) => setTimeout(r, 15_000));
  }
}

UAT Scenarios ​

  1. Happy path. Generate payment → read instruction → upload valid receipt → admin approves → booking confirmed.
  2. Wrong amount rejection → retry. Upload receipt with mismatched amount → admin rejects with reason → re-upload corrected receipt → admin approves.
  3. File too large. Upload 6 MB file → receive 400 FILE_TOO_LARGE → no side effects.
  4. Guest flow. Book + pay as guest (no JWT), with guestEmail in every request → full happy path.
  5. Approval after window lapse. Upload before expiresAt → let expiresAt pass while status is SUBMITTED → admin approve still succeeds (approval has no expiresAt guard) → Payment.status = PAID, booking confirmed. The window only blocks new/re-uploads (Step 4 returns 409), not approval of an already-submitted proof.
  6. Retry exhaustion. Upload → rejected 4 times (initial + 3 re-uploads at default MAX_RETRIES=3) → Payment.status = FAILED, upload endpoint returns 409.
