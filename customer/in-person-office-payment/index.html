In-Person Office Payment (SAR cash) ​

A SAR custom-booking invoice can be settled by paying cash at an Ahlaan office. The customer is shown an office name and address instead of bank details, walks in, pays, and an admin marks the payment settled.

This is the third custom-booking rail, alongside Xendit (IDR) and manual bank transfer (SAR/USD).

Availability. This rail is deliberately narrow. It is offered only on the mitra host, only while the office-settlement feature flag is on, and only to an admin or an admin acting as the customer. An ordinary logged-in mitra customer and a guest both see nothing. See Gating below.

Flow ​

Settlement runs through the same shared routine as a Xendit webhook or a manual-transfer approval, so one call marks the payment and invoice PAID, advances the booking, and fires ticketing and confirmation notifications.

The admin settles the customer's own row. The admin works from the invoice screen and has no payment id in hand. An empty-body settlement now auto-reuses the customer's open PENDING IN_PERSON payment — the exact row this rail created and the customer polls on GET /payments/:paymentId/in-person — rather than minting a twin and leaving the customer's row stranded PENDING. Passing an explicit { paymentId } still works and targets that specific row; a fresh payment is minted only for a genuine walk-in with no open row. See admin guide → office-settlement.

Gating ​

Three independent server-side gates, all required:

GateCheckOn failure
G1 feature flagOFFICE_SETTLEMENT_ENABLEDRail hidden; write returns 400
G2 mitra hostRequest arrived on the mitra hostRail hidden; write returns 400
G3 principalA real ADMIN, or an admin impersonating the customerRail hidden; write returns 403

Plus: the invoice must be a custom booking and must not already be settled.

G2 reports the same wording as G1 on purpose, so an off-host caller cannot tell "this feature does not exist" from "you are on the wrong host".

G3 is the boundary. It is the only thing between an ordinary mitra customer and this rail, so it is enforced on all three surfaces (payment-options, available-gateways, generate-payment), not only on the write.

The one deliberate exception ​

GET /payments/:paymentId/in-person applies G1 + G2 + owner scope only, not G3.

The customer walks to the office after the admin has ended the impersonation session. Enforcing G3 on that read would hide the office address at exactly the moment the customer needs it. Creating a payment still requires G3; reading back an already-created, owner-scoped one does not.

This does not widen who can use the rail: a customer with no in-person payment has nothing to read, and owner-scoping means they only ever see their own.

Which office the customer is sent to ​

There is one office at launch and no customer picker. The server always auto-picks the highest-priority active SAR office (priority descending, then createdAt ascending).

  • The API accepts no office id from the client, anywhere. Not on generate-payment, not in metadata.
  • The chosen office is frozen onto the payment. If an admin later reprioritises or deactivates offices, a customer already en route still sees the office they were actually sent to.

Offices are managed at Admin > Office Locations.

Endpoints ​

Every example below is a real request/response pair captured end to end against one booking: 92TDZMV, invoice INV-202607-0030-RFB, 5 adult passengers Madinah -> Makkah, 930 SAR (186 SAR per passenger). The ids line up across all five calls, so they can be read as a single walkthrough.

2. Create the payment ​

bash
POST /api/v1/invoice/:id/generate-payment
json
{
  "paymentGatewayCode": "IN_PERSON",
  "paymentMethod": "CASH",
  "currency": "SAR"
}

All three fields are required:

FieldValueNotes
paymentGatewayCode"IN_PERSON"
paymentMethod"CASH"the only method this rail accepts
currency"SAR"required, and must be sent explicitly - see below

currency is not optional here, and it does not default. Unlike XENDIT (where currency is ignored and the payment is always IDR), this rail rejects a request that omits it:

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "In-person office settlement requires a 'currency' of SAR.",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

Note this check runs after the three gates, so receiving this error rather than a 403 or "Office settlement is currently disabled." confirms the feature flag, host and principal were all accepted. metadata is ignored on this rail - there is no e-wallet or hosted checkout to parameterise.

4. Repeat calls to generate-payment ​

Calling generate-payment again for the same invoice reuses the open PENDING in-person payment rather than minting a second one. Without this, each FE re-render would create another row and fill the admin worklist with duplicates for a single office visit.

Payment window ​

CUSTOM_BOOKING_IN_PERSON_EXPIRY_MINUTES, default 60 minutes. Longer than the two 30-minute siblings because the customer has to physically travel.

The window is enforced actively by the custom-booking payment-expiration job: at expiresAt the payment moves to EXPIRED, the booking to EXPIRED, and the invoice ISSUED -> OVERDUE.

The job is off by default. It is gated on CUSTOM_BOOKING_PAYMENT_EXPIRY_JOB_ENABLED (default false) because it gives custom bookings a write-side expiry for the first time, which changes behaviour on two rails that are already live. While it is off, the 60-minute window is advisory and nothing auto-expires.

Late arrival is expected, not exceptional. An admin reopens the payment and then settles it:

bash
POST /api/v1/admin/manual-transfer/payments/:paymentId/reopen
POST /api/v1/admin/invoice/:id/office-settlement   { "paymentId": "..." }

Reopen accepts an in-person payment even though it has no transfer proof row. It also sends the invoice back OVERDUE -> ISSUED when it revives an expired booking, so the booking and its invoice never disagree.

Currency ​

SAR only. A non-SAR request is rejected. The amount is billed off the same SAR anchor the manual-transfer rail uses, so the figure the customer is told to bring matches the SAR amount everywhere else in the system.
