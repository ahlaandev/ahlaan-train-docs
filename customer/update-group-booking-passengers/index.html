Update GROUP Booking Passengers ​

This guide explains how to update passenger data for GROUP bookings using the dedicated passengers endpoint.

Overview ​

The PATCH /ota/bookings/:id/passengers endpoint provides a simplified way to update passenger information for GROUP bookings without requiring ticketing.

When to Use This Endpoint ​

Use CaseEndpointNotes
Update passengers before ticketing (GROUP bookings)PATCH /ota/bookings/:id/passengers✅ Recommended - no passenger count restrictions
Add passenger names to GROUP bookingPATCH /ota/bookings/:id/modify (Type 4)Requires ALL passengers at once
Update passenger info for TICKETED bookingsPATCH /ota/bookings/:id/modify (Type 40)Limited to document fields only
Correct names on a TICKETED GROUP bookingPATCH /ota/bookings/:id/modify (Type 4)Allowed: the tickets were issued against placeholder travelers

Key Differences: /passengers vs /modify ​

Feature/passengers/modify (Type 4)
OTA Communication❌ No - updates local database only✅ Yes - sends OTA_AirModifyRQ
Passenger CountPartial updates allowedMust provide ALL passengers
Booking TypeGROUP onlyGROUP only
StatusCONFIRMED, TICKETEDCONFIRMED, TICKETED
Partial Updates✅ Yes❌ No
Document Updates (TICKETED)✅ Yes✅ Yes
Name Updates (TICKETED)❌ No✅ Yes (GROUP tickets carry placeholder names until pushed)

Endpoint ​

http
PATCH /ota/bookings/:id/passengers
Authorization: Bearer <access_token>
Content-Type: application/json

Request Format ​

Headers ​

Content-Type: application/json
Authorization: Bearer {token}

Request Body ​

json
{
  "passengers": [
    {
      "rph": 1,
      "passengerTypeCode": "ADT",
      "title": "MR",
      "firstName": "Ahmad",
      "lastName": "Al-Saud",
      "gender": "Male",
      "idType": "PASSPORT",
      "idNumber": "A12345678",
      "idExpirationDate": "2030-12-31",
      "nationality": "SA",
      "dateOfBirth": "1990-01-15"
    }
  ],
  "rememberPassengers": false
}

Request Fields ​

FieldTypeRequiredDescription
passengersarrayYesArray of passenger objects
passengers[].rphnumberYesPassenger reference number (1, 2, 3...)
passengers[].passengerTypeCodestringYesPassenger type: ADT, CHD, or INF
passengers[].titlestringYesTitle: MR, MISS, MRS, etc.
passengers[].firstNamestringYesFirst name
passengers[].lastNamestringYesLast name
passengers[].genderstringYesGender: "Male" or "Female"
passengers[].idTypestringYesDocument type: PASSPORT, NATIONAL_ID
passengers[].idNumberstringYesDocument number
passengers[].idExpirationDatestringYesDocument expiry (YYYY-MM-DD)
passengers[].nationalitystringYesCountry code (e.g., "SA", "ID")
passengers[].dateOfBirthstringYesDate of birth (YYYY-MM-DD)
passengers[].emailstring | nullNoPassenger email. Omit or send a blank string to leave it unchanged; send null to clear the stored value.
passengers[].phonestring | nullNoPhone in international format. Omit or send a blank/digit-less string (e.g. "+") to leave it unchanged; send null to clear the stored value.
rememberPassengersbooleanNoSave passengers for future bookings

Optional contact fields — blank vs null: email and phone are optional. An empty/blank string ("", " ") or a digit-less phone is treated as "not provided" and is ignored (no validation error, field left unchanged). Sending an explicit null clears the stored value.

Behavior by Booking Status ​

CONFIRMED Status ​

When booking is in CONFIRMED status:

  • All fields can be updated: rph, passengerTypeCode, title, firstName, lastName, gender, idType, idNumber, idExpirationDate, nationality, dateOfBirth
  • Passengers are updated by matching rph (same rph = replace)

TICKETED Status ​

When booking is in TICKETED status:

  • Only document fields can be updated: idType, idNumber, idExpirationDate, nationality, dateOfBirth
  • Name fields (firstName, lastName, gender, title, passengerTypeCode) cannot be changed

Getting the Updated Passengers List ​

After updating passengers, you can retrieve the latest passenger list using the booking detail endpoint:

bash
GET /ota/bookings/:id

The response will include the updated passengers in the passengers.names array. names is the resolved list for the booking: when passengers were supplied through another channel, they appear here too.

json
{
  "passengers": {
    "type": "GROUP",
    "quantities": {
      "adults": 11,
      "children": 0,
      "infants": 0
    },
    "names": [
      {
        "rph": 56,
        "title": "MR",
        "firstName": "NAMEE1",
        "middleName": "",
        "lastName": "FAMILYE1",
        "passengerTypeCode": "ADT",
        "gender": "Male",
        "idType": "PASSPORT",
        "idNumber": "P1",
        "idExpirationDate": "2030-01-01",
        "dateOfBirth": "1990-01-01",
        "nationality": "ID",
        "countryOfResidence": "ID",
        "email": null,
        "phone": null
      }
    ],
    "contactPerson": {
      "title": "MR",
      "firstName": "Triawan",
      "middleName": "",
      "lastName": "Nugroho",
      "email": "contact@example.com",
      "phone": "+6281234567890",
      "countryCode": "+62"
    },
    "progress": {
      "total": 11,
      "completed": 11,
      "remaining": 0,
      "percentage": 100,
      "isComplete": true
    }
  }
}

rph is taken from the supplier's traveller list, so it is not a 1-based index into names. progress is always present for GROUP; completed counts the passengers whose first name is filled in and is not a supplier UNKNOWN placeholder, so a booking whose list is still all placeholders reads completed: 0 and keeps ADD_PASSENGERS in actions.availableActions.

Alternatively, use the booking code lookup:

bash
GET /ota/bookings/code/:bookingCode

Use Cases ​

1. Update Passengers by RPH (CONFIRMED) ​

Update specific passengers by providing their rph:

bash
curl -X PATCH "/api/v1/ota/bookings/019bfef1-61fd-731c-9a77-2da9417f6da8/passengers" \
  -H "Authorization: Bearer eyJhbGc..." \
  -H "Content-Type: application/json" \
  -d '{
    "passengers": [
      {
        "rph": 1,
        "passengerTypeCode": "ADT",
        "title": "MR",
        "firstName": "Ahmad",
        "lastName": "Al-Saud",
        "gender": "Male",
        "idType": "PASSPORT",
        "idNumber": "A12345678",
        "idExpirationDate": "2030-12-31",
        "nationality": "SA",
        "dateOfBirth": "1990-01-15"
      }
    ]
  }'

    "passengers": [
      {
        "rph": 1,

Error Responses ​

All 400 responses now use the unified OTA error envelope ({ statusCode, error, message, code, category, retryable, cause?, context? }). The endpoints below all throw legacy bare-string BadRequestException, so they currently surface with code: UNCODED, category: VALIDATION, retryable: false via the global normalizer. Stable codes will be added in a follow-up. Branch on code === 'UNCODED' && category === 'VALIDATION' as a generic non-retryable validation failure, or fall back to displaying message.

400 — Booking Not GROUP Type ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Passengers can only be updated for GROUP bookings",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

400 — Invalid Status ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Booking must be in CONFIRMED or TICKETED status to update passengers. Current status: PENDING",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

400 — Missing RPH ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Passenger at index 0 is missing required rph",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

400 — Passenger Not Found ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Passenger with rph 99 not found in booking",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

400 — TICKETED — Non-Document Fields ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Passenger at index 0 cannot update non-document fields for TICKETED bookings. Only document fields (idType, idNumber, idExpirationDate, nationality, dateOfBirth) are allowed.",
  "code": "UNCODED",
  "category": "VALIDATION",
  "retryable": false
}

400 — DTO Validation (e.g., invalid date format) ​

json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": ["dateOfBirth must be a valid ISO 8601 date string"],
  "code": "INPUT_VALIDATION",
  "category": "VALIDATION",
  "retryable": false,
  "context": {
    "fields": [
      { "path": "passengers.0.dateOfBirth", "constraint": "isDateString", "message": "dateOfBirth must be a valid ISO 8601 date string" }
    ]
  }
}

Migration note: for INPUT_VALIDATION, message remains string[] (the flattened class-validator constraint messages) — backwards-compatible with the legacy ValidationPipe shape. New consumers should read context.fields[] for structured per-field detail.
