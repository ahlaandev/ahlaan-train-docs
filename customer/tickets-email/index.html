Tickets & Email ​

This guide explains how to download tickets and resend confirmation/cancellation emails for B2C bookings.

Quick Overview ​

FeatureDescription
Download TicketsGET /api/v1/ota/bookings/:id/tickets - owner/same-org via token, or guest with email + phone
Download Single TicketGET /api/v1/ota/bookings/:id/ticket - same access rules
Download by OTA RefGET /api/v1/ota/tickets/:otaRef/download - same access rules
Resend Cancellation EmailPOST /api/v1/ota/bookings/:id/resend-cancellation-email
Resend Confirmation EmailPOST /api/v1/ota/bookings/:id/resend-confirmation-email

Base URL ​

/api/v1

Host & route are per-frontend

The ticket-download URLs returned in booking responses and confirmation emails are absolute and point at the host AND route of the frontend the booking originated from. Regular (main-OTA) bookings use the main API host on the ota/bookings route (e.g. https://tiket.ahlaan.co.id/api/v1/ota/bookings/:id/tickets); BlockSeat bookings (bookingVariant=BLOCKSEAT) use the BlockSeat host on the blockseat-bookings route (e.g. https://blockseat.ahlaan.co.id/api/v1/blockseat-bookings/:id/tickets). The route segment differs because each variant's ticket endpoints are variant-isolated — a BlockSeat booking requested on the ota/bookings route returns 404 Booking not found. When the BlockSeat host is not configured the host falls back to the main host, but the blockseat-bookings route segment is always used for BlockSeat bookings (it has no fallback — the ota/bookings route would reject the booking).

Ticket-download access control ​

Tickets expose passenger PII, so all three download endpoints below are access-controlled:

  • Authenticated user — send Authorization: Bearer <token>. The user must own the booking (or belong to the same organization). No contact parameters needed.
  • Guest (no token) — supply the email and phone used at booking creation as query parameters. Both must match the booking contact. These are the same values embedded in the confirmation-email ticket links, so links from the email work without logging in.

Errors: 401 (guest missing email/phone), 403 (authenticated non-owner), 404 (booking not found or guest contact mismatch).

Download Tickets ​

Download all tickets for a booking as a single ZIP archive (one PDF per passenger).

http
GET /ota/bookings/:id/tickets

Request Parameters ​

ParameterTypeRequiredDescription
idstringYesInternal booking ID (UUID)
emailstringGuests onlyEmail used at booking creation
phonestringGuests onlyPhone used at booking creation

Response ​

Content-Type: application/zip

Content-Disposition: attachment; filename={bookingCode}.zip

The response is a ZIP archive containing one PDF per passenger (each with the passenger's QR code).

Requirements ​

  • Booking must be in TICKETED status

Download Specific Ticket ​

Download a specific ticket PDF by ticket number and coupon number.

http
GET /ota/bookings/:id/ticket?ticketNumber={ticketNumber}&couponNumber={couponNumber}

Request Parameters ​

ParameterTypeRequiredDescription
idstringYesInternal booking ID (UUID)
ticketNumberstringYesTicket number from OTA response
couponNumberstringYesCoupon number (usually "1")
emailstringGuests onlyEmail used at booking creation
phonestringGuests onlyPhone used at booking creation

Response ​

Content-Type: application/pdf

Content-Disposition: attachment; filename=ticket-{ticketNumber}.pdf

Use Case ​

Designed for confirmation-email links. The emailed link already carries the booking email + phone, so a guest recipient downloads without logging in; a logged-in user is authorized by their bearer token.

Request Example ​

bash
# Guest (email link): contact carried in the query string
GET /api/v1/ota/bookings/019bfef1-61fd-731c-9a77-2da9417f6da8/ticket?ticketNumber=4471110041159&couponNumber=1&email=ahmad@example.com&phone=+966501234567

Download Tickets by OTA Reference ​

Download all tickets for a booking using the OTA booking reference. The reference is short and guessable, so the same access check applies.

http
GET /api/v1/ota/tickets/:otaRef/download

Request Parameters ​

ParameterTypeRequiredDescription
otaRefstringYesOTA booking reference (5-6 characters)
emailstringGuests onlyEmail used at booking creation
phonestringGuests onlyPhone used at booking creation

Response ​

Content-Type: application/zip

Content-Disposition: attachment; filename=tickets-{otaRef}.zip

OTA Booking Reference Format ​

  • 5-6 alphanumeric characters (e.g., JVSJC3, XVW3NR, ABC12)
  • Provided in booking confirmation and emails
  • Different from the 7-character bookingCode (e.g. UW4V4KK, SREDF8U)

Use Case ​

This endpoint is ideal for:

  • Email links that don't require user login
  • Sharing tickets with third parties
  • Customer support scenarios

Request Example ​

bash
GET /api/v1/ota/tickets/XVW3NR/download

Resend Cancellation Email ​

Resend cancellation email to specified recipients for a cancelled booking.

http
POST /ota/bookings/:id/resend-cancellation-email
Authorization: Bearer <access_token>
Content-Type: application/json

Request Format ​

Headers

Content-Type: application/json
Authorization: Bearer {token}

Request Parameters ​

ParameterTypeRequiredDescription
idstringYesInternal booking ID (UUID)

Request Body ​

json
{
  "emails": ["passenger@example.com", "admin@company.com"],
  "ccEmails": ["finance@company.com"],
  "bccEmails": ["records@company.com"],
  "segments": [
    {
      "flightDesignator": "HHR0080",
      "departure": "MKX",
      "arrival": "DMX",

Request Body Parameters ​

FieldTypeRequiredDescription
emailsarrayYesPrimary email recipients
ccEmailsarrayNoCC recipients
bccEmailsarrayNoBCC recipients
segmentsarrayNoSpecific cancelled segments to include (all if omitted)

Segment Object ​

FieldTypeRequiredDescription

departurestringYesDeparture station code
arrivalstringYesArrival station code
departureDatestringYesDeparture date (YYYY-MM-DD)

Response Format ​

json

}

Requirements ​

  • Booking must be in CANCELLED status
  • User must own the booking
  • All email addresses must be valid

Code Examples ​

JavaScript/TypeScript (fetch) ​

typescript
// Download tickets for a booking. Authenticated callers pass their bearer
// token; guests pass the booking email + phone. Returns a ZIP archive.
async function downloadTickets(
  bookingId: string,
  auth: { token?: string; guest?: { email: string; phone: string } },
): Promise<Blob> {
  const query = auth.guest
    ? `?email=${encodeURIComponent(auth.guest.email)}&phone=${encodeURIComponent(auth.guest.phone)}`
    : '';
  const response = await fetch(
    `/api/v1/ota/bookings/${bookingId}/tickets${query}`,
    {
      method: 'GET',
      headers: auth.token ? { Authorization: `Bearer ${auth.token}` } : {},
    },
  );

  if (!response.ok) {
    throw new Error(`Failed to download tickets: ${response.statusText}`);
  }

  return await response.blob();
}

// Download specific ticket. Same access rules (token or guest email + phone).
async function downloadSpecificTicket(
  bookingId: string,
  ticketNumber: string,
  couponNumber: string,
  auth: { token?: string; guest?: { email: string; phone: string } },
): Promise<Blob> {
  const params = new URLSearchParams({ ticketNumber, couponNumber });
  if (auth.guest) {
    params.set('email', auth.guest.email);
    params.set('phone', auth.guest.phone);
  }

  const response = await fetch(
    `/api/v1/ota/bookings/${bookingId}/ticket?${params}`,
    {
      method: 'GET',
      headers: auth.token ? { Authorization: `Bearer ${auth.token}` } : {},
    },
  );

  if (!response.ok) {
    throw new Error(`Failed to download ticket: ${response.statusText}`);
  }

  return await response.blob();
}

// Download tickets by OTA reference. Same access rules. Returns a ZIP archive.
async function downloadTicketsByOtaRef(
  otaRef: string,
  auth: { token?: string; guest?: { email: string; phone: string } },
): Promise<Blob> {
  const query = auth.guest
    ? `?email=${encodeURIComponent(auth.guest.email)}&phone=${encodeURIComponent(auth.guest.phone)}`
    : '';
  const response = await fetch(`/api/v1/ota/tickets/${otaRef}/download${query}`, {
    method: 'GET',
    headers: auth.token ? { Authorization: `Bearer ${auth.token}` } : {},
  });

  if (!response.ok) {
    throw new Error(`Failed to download tickets: ${response.statusText}`);
  }

  return await response.blob();
}

// Save blob to file
function saveBlob(blob: Blob, filename: string) {
  const url = window.URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = filename;
  document.body.appendChild(a);
  a.click();
  window.URL.revokeObjectURL(url);
  document.body.removeChild(a);
}

// Example: Download and save tickets (ZIP archive of per-passenger PDFs)
async function downloadAndSaveTickets(bookingId: string) {
  try {
    const zipBlob = await downloadTickets(bookingId);
    saveBlob(zipBlob, `tickets-${bookingId}.zip`);
  } catch (error) {
    console.error('Download failed:', error);
    alert('Failed to download tickets. Please try again.');
  }
}

// Resend cancellation email
async function resendCancellationEmail(
  bookingId: string,
  emails: string[],
  options?: {
    ccEmails?: string[];
    bccEmails?: string[];
    segments?: Array<{
      flightDesignator: string;
      departure: string;
      arrival: string;
      departureDate: string;
    }>;
  },
) {
  const response = await fetch(
    `/api/v1/ota/bookings/${bookingId}/resend-cancellation-email`,
    {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${getAccessToken()}`,
      },
      body: JSON.stringify({
        emails,
        ccEmails: options?.ccEmails || [],
        bccEmails: options?.bccEmails || [],
        segments: options?.segments || [],
      }),
    },
  );

  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.message || 'Failed to resend email');
  }

  return await response.json();
}

json

json
{

json

Email Integration Tips ​

Email Template Variables ​

When integrating email links, use these patterns:

The confirmation-email ticket links are generated server-side with the booking email + phone already appended, so a guest recipient downloads without logging in. Build email links the same way:

Email link (All Tickets by Booking ID):

https://yourdomain.com/api/v1/ota/bookings/{bookingId}/tickets?email={email}&phone={phone}

Returns a ZIP archive of per-passenger PDFs.

Email link (Specific Ticket):

https://yourdomain.com/api/v1/ota/bookings/{bookingId}/ticket?ticketNumber={ticketNumber}&couponNumber={couponNumber}&email={email}&phone={phone}

Email link (By OTA Ref):

https://yourdomain.com/api/v1/ota/tickets/{otaRef}/download?email={email}&phone={phone}

Simplest for email links — the reference is short, so the email + phone are required.

CC/BCC Best Practices ​

javascript
// Good: Separate business logic from email routing
const emailData = {
  emails: ['passenger@example.com'], // Primary recipient

// Avoid: Sending customer emails to BCC

javascript
// For multiple bookings, send emails in parallel
async function resendEmailsForBookings(bookingIds: string[]) {
  await Promise.all(
    bookingIds.map(id =>
      resendConfirmationEmail(id, ['admin@company.com'])

}

Custom Booking Ticket Email ​

For custom bookings (separate from the OTA flow above), an admin uploading a ticket via POST /admin/custom-booking/:id/ticket sends nothing — it records the file and stops, and the customer has no sign it exists. The customer receives a one-off email once a second admin releases that upload via POST /admin/custom-booking/:id/ticket/verify. Closing the booking afterwards (PATCH /admin/custom-booking/:id/status with status: COMPLETED) sends nothing either. See Release or Reject a Ticket for the full release/reject contract.

PropertyValue
SubjectKonfirmasi Tiket Kereta Anda - {bookingCode}
TriggerThe ticket release: POST .../ticket/verify, called from any status the ticket is delivered from — TICKET_UPLOADED_FULL, TICKET_UPLOADED_PARTIAL, SHORTFALL_REFUNDED, TICKET_RECEIVED or COMPLETED. COMPLETED is not theoretical: uploading onto an already-closed booking is supported and keeps the status, so such a ticket is held and still needs releasing. Requires custom-bookings:verify-ticket — a code custom-bookings:upload-ticket does not confer.
RecipientcontactPerson.email on the custom booking, falling back to the account email
AttachmentThe released ticket file (presigned R2 URL)
Body contentBooking code, route, departure date, the invoice total under Total Pembayaran, and the passenger count on a full delivery only. The total is rendered in the invoice's own currency — not SAR. The custom-booking invoice generator sets that currency to IDR.
RetriesNone — the queue job is submitted with attempts: 1, so a failed send is never retried.
Not triggered byAn upload, whether the first on a booking or a later one. A rejection — it sends nothing to anybody. Any status change, COMPLETED included — which is why the legacy confirm-received endpoint and the hourly auto-complete cron stay silent without needing to be special-cased. A second release attempt on an already-released booking, which answers 409 instead.

On a partial delivery the email says less, not more. It states that the ticket is issued and can be downloaded. It gives no passenger count, does not claim the passenger data is complete, and says nothing about the refund owed for the passengers who could not be ticketed — the team handles that separately. Everything it does say is true of the file attached.

It is sent once. If the missing tickets arrive later, or a corrected file is uploaded, no further email goes out automatically. The booking page always carries the current file; support can re-send on request via POST /admin/custom-booking/:id/resend-ticket-email, which re-queues the newest ticket file without changing the booking status.

If the email does not arrive within a few minutes, check spam first, then contact support with your booking code.

Sending is best-effort and runs after the release is committed: if the queue or the email provider fails, the booking is still released and downloadable and only a warning is logged. The release still returns 201 — that does not guarantee the mail went out. Use the resend endpoint to recover — there is no automatic retry.
