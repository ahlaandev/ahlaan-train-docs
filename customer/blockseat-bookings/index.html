BlockSeat Bookings Guide (Wholesale) ​

BlockSeat bookings are the wholesale flow for groups of ≥11 seated passengers (adults + children; infants are lap, configurable via BLOCKSEAT_MIN_PASSENGERS). They ride the standard ota/* booking flow — a real supplier GROUP reservation, payment → CONFIRMED → async ticketing → TICKETED, with passenger names added later (supplier-native). There is no manifest step and no auto-confirm — BlockSeat does not use the custom-booking lifecycle.

They differ from a regular ota/* booking only in:

  • Pricing. Priced supplier price − BlockSeat route reducer (ECONOMY), STANDARD fare (no strikethrough). The booked price equals the BlockSeat OTA quote exactly.
  • ECONOMY-only. BlockSeat sells ECONOMY only. A booking whose leg is BUSINESS is rejected with 400 — both at the book/calculate quote and again at booking creation. The rule is forward-only: existing BlockSeat BUSINESS bookings remain readable and operable.
  • Variant scope. BlockSeat rows are the same Booking table with bookingVariant = BLOCKSEAT. BlockSeat endpoints only ever see BlockSeat bookings; ota/* endpoints only see standard bookings (a cross-variant id/code returns 404).

Everything else — request bodies, GROUP reservation, status machine, payment (Xendit / wallet), cancellation + refund, ticket download — is identical to OTA Bookings.

Host. Served on blockseat.ahlaan.co.id.

Flow ​

  1. Quote via POST /api/v1/blockseat-ota/book/calculate (≥11 enforced).
  2. Book via POST /api/v1/blockseat-bookings/book with passengerQuantities (GROUP — names not required yet). A real supplier reservation is held; status PENDING.
  3. Pay (Xendit link or wallet) → webhook → CONFIRMED.
  4. Add passenger names via PATCH /:id/modify (Type 4) within the supplier's update-travellers deadline.
  5. Ticketing runs (async / admin retry) → TICKETED; download tickets.

No manifest upload, no admin manifest review, no auto-confirm-on-manifest.

Host-aware redirects & links

BlockSeat is served on its own host (e.g. blockseat.ahlaan.co.id). Three things are host-aware so BlockSeat users stay on the BlockSeat frontend rather than the main OTA:

  • OAuth login (Google / Apple) initiated from the BlockSeat host returns to the BlockSeat frontend — see Register & Login (multi-frontend callback resolution).
  • Xendit payment success redirects to the BlockSeat success page via the XENDIT_REDIRECT_URL_BLOCKSEAT config (source BLOCKSEAT) — see System Configuration.
  • Ticket-download URLs in booking responses and confirmation emails are built on the BlockSeat host (derived from BLOCKSEAT_DOMAIN_NAME) and the variant-isolated blockseat-bookings route — e.g. …/api/v1/blockseat-bookings/:id/tickets — instead of the main-OTA ota/bookings route — see Tickets & Email. Generated server-side at ticketing time, so both host and route follow bookingVariant=BLOCKSEAT, not the request host. The route is mandatory: the ota/bookings endpoints reject a BlockSeat booking with 404 Booking not found.

The OAuth/Xendit redirects require the corresponding env / OAuth-provider registration for the BlockSeat host; when the BlockSeat host is unset the OAuth/Xendit/ticket host falls back to the main OTA (but the BlockSeat ticket route does not — it has no main-OTA equivalent that would resolve the booking).

Status lifecycle ​

Status lifecycle, payment, and refunds follow the standard OTA booking model (PENDING → CONFIRMED → TICKETING_IN_PROGRESS → TICKETED; CANCELLED / EXPIRED / FAILED terminal).
