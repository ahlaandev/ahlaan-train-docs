Search & Booking Limits (Front-End Reference) ​

The back-end owns the group-size and advance-booking limits for all three products. Fetch them once from a single endpoint and drive your own validation from the returned numbers — do not hardcode min-passenger or advance-day values.

GET /api/v1/search-booking-limits ​

Optional authentication. Host-aware. Returns the effective limits for the caller in one call so you can cache once.

  • Send the bearer token when the user is logged in — custom then reflects their pricing tier (a GOLD partner gets the reduced floor).
  • Guests may call it without a token; they resolve to the base tier.

Response ​

jsonc
{
  "tier": "GOLD",                     // caller's resolved tier (informational)
  "limits": {
    "ota":       { "minSeatedPax": 1,  "minAdvanceDays": 0 },
    "blockseat": { "minSeatedPax": 11, "minAdvanceDays": 3 },
    "custom":    { "minSeatedPax": 5,  "minAdvanceDays": 0 }
  }
}
FieldMeaning
minSeatedPaxMinimum adults + children (infants are lap, not counted). null = no floor.
minAdvanceDaysDeparture must be at least n × 24 hours ahead. null / 0 = no rule. 3 = 72 hours.

custom reflects the caller tier (5 for GOLD, 10 otherwise). ota and blockseat are tier-flat.

How the limits are enforced ​

  • Search endpoints (ota/search, blockseat-ota/search, custom-ota/search) return an empty result (no error) when the request is below a limit — the same shape as a search with no matching flights. Use the numbers from this endpoint to explain why to the user (e.g. "wholesale needs 11+ passengers" or "book at least 3 days ahead") instead of relying on an error message.
  • Booking creation and price-calculation (.../book/calculate, booking create) return 400 Bad Request when below a limit.

Note for wholesale (blockseat): a search with fewer than 11 passengers, or a departure less than 72 hours out, now returns empty results rather than an error. Read this endpoint and validate client-side before searching so the user sees a clear reason.
