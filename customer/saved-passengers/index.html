Saved Passengers Guide ​

This guide explains how to manage saved passengers — a reusable address book of traveller profiles that an authenticated user can quickly select when creating bookings.

Overview ​

The Saved Passengers endpoints let an authenticated user store, list, update, and delete passenger profiles (name, document, nationality, contact, and optional airline reservation details). These are distinct from:

  • User Details (/user-details) — a single profile record for the account holder.
  • Group Booking Passengers (/bookings/.../passengers) — passenger edits scoped to one booking.

Saved passengers are a standalone, multi-record collection owned by the user.

Populated automatically from custom bookings. Besides the explicit POST /passengers endpoint below, the roster can also be filled as a side-effect of submitting a custom-booking manifest: set rememberPassenger: true on a passenger row — inline at POST /custom-booking or via PATCH /custom-booking/:id/passengers — and that passenger is upserted into the booking owner's roster (idempotent on idNumber). See Custom Booking → Saving Passengers to the Roster.

Base URL: /api/v1

Authentication: Required (JWT Bearer token) on every endpoint.

Swagger tag: 2. Passengers

Endpoints ​

Create Passenger ​

Create a new saved passenger for the authenticated user.

http
POST /passengers
Authorization: Bearer <access_token>
Content-Type: application/json

{

  "countryOfResidence": "SA",

List Passengers ​

Retrieve all saved passengers for the authenticated user. Favorites are returned first, then most recently created. Supports search and a favorites-only filter, with pagination.

http
GET /passengers?page=1&limit=20&search=john&favoritesOnly=true
Authorization: Bearer <access_token>

Update Passenger ​

Update fields on a saved passenger. This is a partial update — only the keys you send are changed; omitted keys are left untouched.

http
PATCH /passengers/0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "nickname": "Father",
  "isFavorite": false,
  "airlineFlightPNR": "XY9",
  "airline": "Flynas"
}

Request Fields: all fields from Create Passenger are accepted and optional here.

Clearing nullable fields: for airlineFlightPNR and airline, send an explicit null to clear the stored value. Sending an empty string ("") is rejected with 400.

http
PATCH /passengers/0190f2a1-8b3c-7d4e-9f50-6a1b2c3d4e5f
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "airlineFlightPNR": null,
  "airline": null
}
Body for a fieldEffect
key omittedleaves the current value unchanged
"airline": "Saudia"sets the value
"airline": nullclears the value to null
"airline": ""rejected — 400 (isNotEmpty)

Response: 200 OK — returns the updated Passenger Object.

Error Responses:

CodeDescription
400Validation failed (bad enum, empty airlineFlightPNR/airline, over max length, etc.)
401Missing or invalid access token
404Passenger not found (or not owned by this user)

Code Examples ​

JavaScript/TypeScript ​

typescript
const BASE = '/api/v1/passengers';

// Create a passenger
async function createPassenger(accessToken: string, data: CreatePassengerDto) {
  const response = await fetch(BASE, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${accessToken}`,
    },
    body: JSON.stringify(data),
  });

  if (response.status === 409) {
    throw new Error('A passenger with this document number already exists');
  }
  return await response.json();
}

// List passengers (with search + pagination)
async function listPassengers(
  accessToken: string,
  opts: { page?: number; limit?: number; search?: string; favoritesOnly?: boolean } = {},
) {
  const qs = new URLSearchParams();
  if (opts.page) qs.set('page', String(opts.page));
  if (opts.limit) qs.set('limit', String(opts.limit));
  if (opts.search) qs.set('search', opts.search);
  if (opts.favoritesOnly) qs.set('favoritesOnly', 'true');

  const response = await fetch(`${BASE}?${qs.toString()}`, {
    headers: { Authorization: `Bearer ${accessToken}` },
  });
  return await response.json(); // { data: [...], meta: {...} }
}

// Get one passenger
async function getPassenger(accessToken: string, id: string) {
  const response = await fetch(`${BASE}/${id}`, {
    headers: { Authorization: `Bearer ${accessToken}` },
  });
  if (response.status === 404) return null;
  return await response.json();
}

// Update a passenger (partial; send null to clear airline fields)
async function updatePassenger(accessToken: string, id: string, data: UpdatePassengerDto) {
  const response = await fetch(`${BASE}/${id}`, {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${accessToken}`,
    },
    body: JSON.stringify(data),
  });
  return await response.json();
}

// Delete a passenger
async function deletePassenger(accessToken: string, id: string) {
  const response = await fetch(`${BASE}/${id}`, {
    method: 'DELETE',
    headers: { Authorization: `Bearer ${accessToken}` },
  });
  return await response.json(); // { success: true }
}

Notes ​

  • Ownership scoping: every endpoint is scoped to the authenticated user. A passenger that exists but belongs to another user returns 404, not 403.
  • Unique document number: idNumber must be unique per user. Re-using one on create returns 409.
  • Document type mapping: send idType as PASSPORT or NATIONAL_ID. Input is upper-cased before validation; the database stores 2 (passport) / 5 (national ID), but the API always exchanges the string enum.
  • Sort order: GET /passengers returns favorites first (isFavorite: true), then newest first by createdAt.
  • Phone format: phone is stored in international format without a leading + (e.g. 966501234567). See User Details Guide for the shared phone-normalisation behaviour.
  • Airline fields: airlineFlightPNR and airline are optional and capture the operating airline's reservation (record locator + carrier name), not the HHR booking code. airlineFlightPNR is stored uppercased. Both accept null on update to clear. These mirror the per-passenger fields captured in the custom-booking manifest.
  • Auto-save from a custom booking: a custom-booking manifest row sent with rememberPassenger: true (inline at create or on the manifest PATCH) upserts into this roster, keyed to the booking owner (booking.userId) — never the acting admin or a guest. On the manifest PATCH, bookings with no owner are skipped; at create an owner is always resolved (guests get a found-or-created account). The save is best-effort: a failure is logged per row and never blocks the booking flow.
