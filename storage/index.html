Storage — Download a File by its ID ​

Every file uploaded through the API (SPK, KTP, NIB, partnership document, payment proof, generated ticket, manual-transfer proof, …) is stored once and identified by a single File.id. Wherever a response gives you a document id (spkDocumentId, ktpDocumentId, nibDocument.id, manualTransfer.fileId, ticket fileId, …), that id is the handle you use to download the file here.

All storage routes live under the versioned prefix /api/v1/storage.

Access model (who can download what) ​

A file has one visibility: PUBLIC, ORGANIZATION, or PRIVATE. Access is decided by validateFileAccess in storage.service.ts:

CallerPUBLIC fileORGANIZATION filePRIVATE file
Admin✅✅✅ (any file)
File owner (file.userId === your id)✅✅✅ (your own)
Same-organization member✅✅ (same organizationId)❌
Other authenticated user✅❌❌
Anonymous (no token)✅❌❌

Most sensitive documents (SPK, KTP, NIB, payment/transfer proofs) are PRIVATE, so only the file's owner or an admin can download them — not any logged-in user.

Owner is not always the uploader. A manual-transfer proof belongs to the invoice owner even when an admin submitted it for them, so the customer can always read their own receipt back. See Manual transfer — download your proof file.

Uploads are checked against their bytes, not their label ​

The Content-Type of a multipart part is a string the client chooses, so the MIME allowlist on its own only ever proved "the client claimed an allowed type". Every upload now also has its leading bytes read, and a part whose content contradicts its declared type is rejected with 400:

json
{
  "message": "File content does not match its declared type 'image/jpeg' — the bytes are image/png.",
  "error": "Bad Request",
  "statusCode": 400
}

The separator before "the bytes are" is an em dash, not a hyphen. Do not match on this string — it is prose and can change; match on the 400.

When the leading bytes match no signature the check knows, the sentence stops at the declared type instead of naming a detected one. Both forms were captured on preprod 2026-08-11 by posting to POST /api/v1/admin/custom-booking/:id/ticket:

PNG bytes declared as application/pdf
→ "File content does not match its declared type 'application/pdf' — the bytes are image/png."

plain text declared as application/pdf
→ "File content does not match its declared type 'application/pdf'."

What this changes for a client:

  • Renaming a file is no longer enough. A PNG saved as .jpg is sent by the browser as image/jpeg and is now refused. Re-save it in the format you declare. The message names the type the bytes really are.
  • application/zip, .xlsx and .docx share one signature. All three are ZIP archives, so the check proves "a real ZIP archive" and cannot tell them apart. A plain ZIP declared as xlsx is accepted.
  • text/csv and image/svg+xml have no signature at all and are accepted with no content check. Nothing can verify them, which is why neither is ever rendered in a browser — see the clamp on routes 2 and 3 below.
  • A declared type with no signature case is refused even when it is on the allowlist (File type 'x' cannot be content-verified). Adding a MIME to ALLOWED_MIME_TYPES therefore cannot silently restore the old behaviour.
  • A PDF must begin with %PDF- at byte 0. The format requires it, and the mitra and B2B document endpoints have always enforced it; the check now applies to every upload route. A PDF carrying a byte-order mark or leading whitespace before its header — some print-to-PDF and scanner pipelines emit these — is rejected where it previously would have been stored. Re-export it if you hit this. The same test decides the served type, so a PDF of that shape already stored is served as application/octet-stream rather than application/pdf wherever the type is re-derived. It still downloads; it just no longer names itself a PDF.

Entity types a generic upload may not claim ​

POST /api/v1/storage/upload takes a free-text entityType, so a handful of values are reserved for the routes that own them — including manual_transfer_proof, which is undeletable once stored. Without the reservation any signed-in caller could mint a permanent file.

Captured on preprod 2026-08-09, as a * super admin:

json
{
  "message": "entityType \"manual_transfer_proof\" is written by its own endpoint and cannot be set on a generic upload.",
  "error": "Forbidden",
  "statusCode": 403
}

The four download routes ​

1. Direct download — GET /api/v1/storage/{fileId}/download ​

Returns the raw bytes with Content-Disposition: attachment.

  • Auth: optional bearer token (OptionalAuthGuard). The same validateFileAccess check above applies: admin → any file; owner → own PRIVATE; org member → ORGANIZATION file of their org; anonymous → PUBLIC only.
  • Use when: you have the fileId and the caller is the owner or an admin.
GET /api/v1/storage/019f6427-1733-72dd-b0b8-04dfc67450f2/download
Authorization: Bearer <token>

2. Presigned URL — GET /api/v1/storage/{fileId}/url?expiresIn=3600 ​

Returns a time-limited direct link instead of the bytes:

json
{ "url": "https://…", "expiresIn": 3600 }
  • Auth: bearer token required, and the same owner-or-admin validateFileAccess check — this is not "any JWT holder". A user who does not own the file (and is not admin) gets 403.
  • expiresIn: seconds, default 3600 (1 hour).
  • Use when: the frontend needs a link the browser can open/preview directly.

⚠️ The link now forces its own type and disposition. Previously the presigned URL carried neither, so the object store replayed the content type the file was uploaded with and the browser decided what to do with it. The link now states both:

Stored typeWhat the link does
image/png, image/jpeg, image/webp, application/pdfinline under that type - previews in a tab, as before
anything else, including image/svg+xml and text/csvdownloads as application/octet-stream

The behaviour change to plan for is an SVG: it used to render, and now downloads. That is deliberate - an SVG rendered from the storage host executes its own script there. Everything a proof-preview screen actually shows (JPEG, PNG, WebP, PDF) still previews exactly as it did.

3. Shareable token — POST /api/v1/storage/{fileId}/token → GET /api/v1/storage/ticket/{token}/download ​

A two-step flow for links that must work without the recipient logging in (email links, previews):

  1. Mint the token — bearer token required, and the same owner-or-admin validateFileAccess check to prove you may share this file:

    POST /api/v1/storage/{fileId}/token
Authorization: Bearer <token>
{ "expiresIn": 86400, "maxDownloads": 1 }

    expiresIn defaults to 86400 (24 h); maxDownloads defaults to 1.

  2. Redeem the token — no auth; the token itself is the capability:

    GET /api/v1/storage/ticket/{token}/download

    The token is rejected once it is expired or its download count reaches maxDownloads.

  • Use when: a guest / email recipient must download a PRIVATE file they do not own.

⛔ Tokens from other rails are not accepted here, and vice versa. Some features mint their own no-login links against the same table but behind their own permission and with their own serving rules — the shortfall-attachment preview link is one. Each redeem route accepts only the tokens minted for it; presenting the wrong one answers 404, identically to an unknown token. Do not try to redeem a token on whichever route seems convenient.

The token itself is now a 24-character lowercase hex string drawn from a cryptographic random source. Treat it as opaque: do not parse it, do not assume a length, and do not log it — it is a bearer capability for the file.

4. Public file — GET /api/v1/storage/public/{fileId} ​

No authentication, but serves PUBLIC-visibility files only. It will not return PRIVATE documents (SPK/KTP/NIB/proofs) even with a valid id — use route 1 (as owner/admin) or route 3 (a minted token) for those.

Choosing a route ​

You need…Use
Owner/admin downloads their own documentRoute 1 (/download)
A browser-openable link, still access-checkedRoute 2 (/url)
A link that works for a not-logged-in recipientRoute 3 (/token → /ticket)
